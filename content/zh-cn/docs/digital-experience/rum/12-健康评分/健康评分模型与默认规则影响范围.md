# RUM 健康评分模型与默认规则影响范围

> 本文档梳理 RUM 健康评分的完整计算链路、线性评分模型、规则优先级体系、指标缺失兜底机制，并记录两个关键设计问题：崩溃率 100% 但健康评分仍高达 97.42 的根因，以及默认规则编辑对已有/新建应用的影响范围。

---

## 一、健康评分概述

RUM 健康评分用于量化评估「应用 / 页面 / 视图 / 网络请求 / 操作」等多个对象维度的质量状况。评分结果以 0~100 分呈现，并配套环比变化（ringRate）。

评分入口：`HealthScoreServer.getHealthScore(...)`（单对象评分）与 `getHealthScoreForApi(...)`（OpenAPI 批量应用评分）、`getPageHealthScoreForApi(...)`（OpenAPI 批量页面评分）。

核心源码位置（newonexm 仓库）：

| 文件 | 职责 |
|------|------|
| `framework/plugins/rum/rum-core/src/main/java/com/bonree/rum/core/common/util/HealthScoreServer.java` | 评分编排：取规则、匹配规则、组装指标查询、汇总得分 |
| `framework/plugins/rum/rum-core/src/main/java/com/bonree/rum/core/common/util/HealthScoreUtils.java` | 线性评分模型：根据 T0/T1 计算 k、b，按 metricDirection 计算单项得分 |
| `framework/plugins/rum/rum-common/src/main/java/com/bonree/rum/common/bean/enums/health/HealthScoreEnum.java` | 评分对象类型枚举（classType） |
| `framework/plugins/rum/rum-common/src/main/java/com/bonree/rum/common/bean/enums/health/HealthPlatformMapping.java` | 应用平台类型 → 评分类型映射 |
| `framework/plugins/rum/rum-common/src/main/java/com/bonree/rum/common/constant/Constants.java` | `healthScoreMetricMap`：指标缺失时的兜底默认值表 |
| `framework/plugins/rum/rum-database/src/main/resources/com/bonree/rum/mysql/common/HealthScoreMapper.xml` | `selectRuleList`：按 classType/userId/envId/appId 查询规则 |
| `framework/plugins/rum/rum-database/src/main/resources/com/bonree/rum/mysql/setting/RumSettingHealthScoreMapper.xml` | `selectAppCreateSourceRule`：新建应用时克隆规则的来源查询 |
| `framework/plugins/rum/rum-core/src/main/java/com/bonree/rum/core/common/config/InitAppScoreRuleSync.java` | 启动时补齐应用缺失的自定义规则（克隆预置/默认规则） |

## 三、评分规则体系

### 3.1 规则存储表

评分规则存储在 `t_rum_config_app_score_rule` 表（v4.0.0.0 起从旧表迁移而来，按 appId 直接匹配，一行一条规则）。规则关联三张子表：
- 评分指标模型表（`ScoreMetricsModel`，存 T0/T1/weight/metricDirection/zero 等）
- 评分条件表（`ScoreRuleConditionEntity`，用于网络请求 URL/别名匹配）
- 规则关联关系

### 3.2 规则类型 type

| type | 含义 | 说明 |
|------|------|------|
| 1 | 自定义规则 | 用户为特定应用/对象配置的规则，优先级最高 |
| 2 | 预置规则 | 历史账号级预置规则；在 `distributeRule` 中由「userId=-1 且 appId=-1 的全局默认」重分类而来 |
| 3 | 默认规则 | 账号级默认规则（userId=accountId） |

> **关键点**：`distributeRule()` 方法会把 `userId=-1 && appId=-1` 的全局默认规则**重分类为 type=2（预置）**，而不是保持 type=3。这影响后续优先级判定。

### 3.3 规则优先级

`getScoreMetirsModelByType()` 取规则时的优先级顺序：

```
1. 自定义规则(type=1)  → 按 appId 精确匹配，命中即用
2. 默认规则(type=3)    → 自定义未生效时回退
3. 预置规则(type=2)    → 自定义与默认都未生效时最终回退
```

`selectRuleList` SQL 只查 `type=1 OR type=3`，并按 `type ASC, order_index DESC` 排序。type=2（预置）是通过 `distributeRule` 在内存中从全局默认（userId=-1, appId=-1）重分类得到的。

```sql
-- HealthScoreMapper.xml: selectRuleList（简化）
SELECT id, user_id, class_type, app_id, type, note, relation, env_id, order_index
FROM t_rum_config_app_score_rule
WHERE class_type = #{classType}
  AND ((user_id = #{userId} AND env_id = #{envId}) OR user_id = -1)
  AND (type = 1 OR type = 3)
  AND flag != 1
  AND status = 1
  AND (app_id = #{appId} OR app_id = -1)   -- 当 appId 传入时
ORDER BY type ASC, order_index DESC
```

### 3.4 单规则应用类型去重

`InitAppScoreRuleSync.deduplicateSingleRuleTypes()` 对「单规则应用类型」做去重，每个应用只保留一条规则（按 `order_index` 最大者优先）：

```java
private static final Set<String> SINGLE_RULE_APP_TYPES = Stream.of(
        ScoreTypeEnum.ANDROID, ScoreTypeEnum.IOS, ScoreTypeEnum.HONGMENG,
        ScoreTypeEnum.WINDOWS, ScoreTypeEnum.WEB, ScoreTypeEnum.MP)
    .map(e -> String.valueOf(e.getType()))
    .collect(Collectors.toSet());
```

即 classType ∈ {10, 11, 12, 13, 14, 15} 的应用类型，每个 appId 只保留一条规则；其他类型（VIEW/PAGE/NET/ACTION）不去重。

## 四、线性评分模型

`HealthScoreUtils` 实现了基于两点的线性评分函数 `y = kx + b`。

### 4.1 计算 k、b

`getScoreMetricsModel()` 根据两个阈值点 T0、T1 计算 k、b：

```java
// 越低越好（如崩溃数、错误率）
if ("low".equals(metricDirection)) {
    k = 100.0 / (t0Val - t1Val);
    b = 100.0 - t0Val * k;
}
// 越高越好（如满意度、吞吐）
if ("high".equals(metricDirection)) {
    k = -100.0 / (t0Val - t1Val);
    b = 100.0 - t1Val * k;
}
```

### 4.2 单项得分计算

`calculateModelScore()` / `linearModelScore()` 的核心逻辑：

- **metricDirection = "low"（越低越好）**：
  - `metricValue <= T0` → 满分 100
  - `metricValue >= T1` → 0 分
  - T0 < metricValue < T1 → `y = kx + b` 线性插值
- **metricDirection = "high"（越高越好）**：
  - `metricValue <= T0` → 0 分
  - `metricValue >= T1` → 满分 100
  - T0 < metricValue < T1 → `y = kx + b` 线性插值

### 4.3 一票零分（zero 字段）

```java
// 指标评分为0时健康评分置零
if (scoreMetricsModel.getZero() == 1 && healthScore == 0.0) {
    return -1D;   // 返回 -1 作为"置零"标记
}
```

当某指标的 `zero=1` 且该指标得分为 0 时，返回 `-1` 作为标记。在 `HealthScoreServer.getScore()` 中检测到 `-1` 会把整体 `isZEROScore=true`，最终整体健康评分置为 0：

```java
if (metricHealthScore.compareTo(new BigDecimal("-1")) == 0) {
    isZEROScore = true;
    scoreMap.put(key, BigDecimal.ZERO.doubleValue());
}
// ...
if (isZEROScore) {
    healthScore = BigDecimal.ZERO;
}
```

### 4.4 权重分摊

`scoreMetricsModelMap()` 计算每个指标的权重占比 `weightRate`（百分比，合计 100）。为避免除不尽，前 n-1 个指标用 `weight/weightSum` 计算，最后一个用 `100 - weightRateSum` 兜底。最终总分：

```
总分 = Σ (单项得分 × weightRate / 100)
```

## 五、评分计算流程

`getHealthScore()` 的完整链路：

```
getHealthScore(classType, userId, condition, url, urlAlias, appId, envId, language)
    │
    ├─ getScoreMetirsModelByType()
    │     ├─ configScoreMapper.selectRuleList(classType, accountId, envId, appId)  // 取规则
    │     ├─ distributeRule(ruleList)                                              // 按 type 分组，全局默认重分类为 type=2
    │     ├─ 优先匹配 type=1（自定义，按 appId 精确匹配）
    │     ├─ 回退 type=3（默认）
    │     └─ 最终回退 type=2（预置）
    │     → 返回 List<ScoreMetricsModel>
    │
    ├─ scoreMetricsModelMap(scoreMetricList)
    │     ├─ HealthScoreUtils.getScoreMetricsModel(model)  // 算 k、b
    │     └─ 计算 weightRate（权重分摊）
    │     → 返回 Map<metricId, ScoreMetricsModel>
    │
    ├─ cacleScore()
    │     ├─ getMetricMap()                  // 组装 ClickHouse 指标查询
    │     ├─ 按 classType 追加基础统计门槛指标
    │     │     - NET: one.rum.net.businessRequest.Count
    │     │     - VIEW: one.rum.page.view.count
    │     │     - PAGE: one.rum.page.h5.pv
    │     │     - ACTION: one.rum.action.throughput.count
    │     │     - 应用类(10-15): one.rum.app.session.sessionCount
    │     ├─ rumSqlFilterFactory.getSqlFilter(...)  // 拼接过滤条件
    │     └─ metricParallelQueryService.queryMetricParallel(...)  // 查 ClickHouse
    │
    └─ getScore(data, scoreMetricMapList)
          ├─ 遍历每个指标
          ├─ 取指标值；若缺失走 Constants.healthScoreMetricMap 兜底
          ├─ HealthScoreUtils.calculateModelScore(value, model)  // 算单项分
          ├─ zero=1 且单项 0 分 → 标记整体置零
          └─ Σ (单项分 × weightRate / 100) → 总分
```

## 六、指标缺失兜底（Constants.healthScoreMetricMap）

`HealthScoreServer.getScore()` 中，当 ClickHouse 查询结果里某指标值为 `null` 时，走兜底逻辑：

```java
Object data = dataMap.get(key);
if (null == data) {
    if (Constants.healthScoreMetricMap.containsKey(key)) {
        // 命中兜底表：用兜底默认值计算
        Double value = Double.parseDouble(Constants.healthScoreMetricMap.get(key).toString());
        metricHealthScore = HealthScoreUtils.calculateModelScore(value, metricsModel);
    } else {
        // 不在兜底表：直接按满分 100 计入（不参与实际评分计算）
        metricHealthScore = new BigDecimal("100");
    }
}
```

### 6.1 兜底表内容

`Constants.healthScoreMetricMap` 是一个静态 Map，绝大多数指标的兜底值为 `0`，例如：

- `one.rum.app.crash.count` → 0
- `one.rum.app.crash.crashRatio` → 0
- `one.rum.app.anr.count` → 0
- `one.rum.app.JSerror.count` → 0
- `one.rum.app.session.sessionCount` → 0
- `one.rum.net.businessRequest.Count` → 0
- …（共约 100+ 个指标，绝大多数兜底为 0）

**例外（兜底值为 100 的指标）**：

| 指标 | 兜底值 |
|------|--------|
| `one.rum.page.h5.satisfyingLoadRatio` | 100 |
| `one.rum.page.view.satisfyingLaunchRatio` | 100 |
| `one.rum.net.request.satisfyingRatio` | 100 |
| `one.rum.net.businessRequest.satisfyingRatio` | 100 |
| `one.rum.action.performance.Ratio` | 100 |

### 6.2 关键行为差异

- 命中兜底表的指标缺失：用兜底值（多为 0）参与评分计算 → 对"越低越好"的指标得满分，对"越高越好"的指标得 0 分
- **未命中兜底表的指标缺失**：直接按 `100` 分计入总分 → 该指标按满分贡献权重分

> 这意味着：**未在 `healthScoreMetricMap` 中登记的指标，一旦查询缺失，会按满分贡献其权重到总分**。这是一个容易被忽略的"隐形满分"行为。

## 七、关键设计问题一：崩溃率 100% 但健康评分 97.42 的根因

### 7.1 现象

某应用截图显示崩溃率 100%，但健康评分高达 97.42。

### 7.2 根因

**健康评分的"崩溃"指标使用的是 `one.rum.app.crash.count`（崩溃次数，绝对计数），不是 `one.rum.app.crash.crashRatio`（崩溃率）。**

证据链：

1. `HealthScoreServer.cacleScore()` 在应用类评分时，追加的基础统计指标是会话数，不是崩溃率：
   ```java
   } else if (null != HealthPlatformMapping.getPlatformByHealth(Integer.valueOf(classType))) {
       metricMap.put("uniqTheta(metric['one.rum.app.session.sessionCount'])", "one_rum_app_session_sessionCount");
   }
   ```

2. 默认规则里崩溃维度配置的指标是 `one.rum.app.crash.count`（崩溃次数），阈值 T1 通常为 500。当崩溃次数为 43（远小于 500）时，按线性模型得分很高。

3. 而前端"崩溃率"卡片展示的是另一个指标 `one.rum.app.crash.crashRatio`：
   - `MetricCardEnum.CRASH_RATE` → `one.rum.app.crash.crashRatio`
   - `AppMetricChart` → `frm(metric['one.rum.app.crash.crashRatio'])`

4. 二者口径完全不同：
   - **崩溃率 100%** = 崩溃影响会话数 / 总会话数（比率）
   - **崩溃次数 43** = 绝对计数，阈值 T1=500，43/500 远未触底

### 7.3 其他指标贡献

除崩溃指标外，其他指标（如 apdex、满意度等）在该场景下要么本身为 100%，要么因查询缺失且**未在 `healthScoreMetricMap` 兜底表中**而按满分 100 计入。例如 `one.rum.net.businessRequest.apdex` 不在兜底表中，缺失时按 100 分贡献权重。

最终：崩溃指标按 43/500 的线性得分贡献其权重 + 其他指标按满分贡献权重 → 总分 97.42。

### 7.4 结论与设计问题

这是一个**口径错位的设计问题**：
- 用户视角：崩溃率 100% = 所有会话都崩溃 = 应该是极差体验
- 评分视角：崩溃次数 43 < 阈值 500 = 崩溃不严重 = 高分

**潜在风险**：当应用会话量很小时（如测试环境），崩溃率可能 100% 但崩溃绝对次数很少，健康评分仍显示高分，与用户感知严重背离。

> 该问题在当前版本（截至 2026-07）依然存在，源码确认未修复。如需修正，应将崩溃维度指标从 `one.rum.app.crash.count` 改为 `one.rum.app.crash.crashRatio`，或引入会话量门槛对低会话量应用做特殊处理。

## 八、关键设计问题二：默认规则编辑的影响范围

### 8.1 问题

调整默认健康评分规则，是只对新创建的应用生效，还是对已有应用也生效？

### 8.2 两条路径的行为差异

#### 路径 A：通过 UI 编辑默认规则（推荐路径，copy-on-write）

`HealthScoreServiceImpl.editDefaultRules()` → `editRules()`：

```java
public Long editRules(ReqEditScoreRule req, List<ReqRuleCondition> cond) {
    int count = healthScoreMapper.validRule(userProvider.getAccountId(), req.getRuleId(), ...);
    if (count <= 0) {
        HealthRuleInfo ruleInfo = healthScoreMapper.queryRuleInfoByRuleId(req.getRuleId(), null, ...);
        if ("-1".equals(ruleInfo.getUserId())) {
            // -1 代表全局默认配置，不能编辑，需要进行 add 操作（copy-on-write）
            req.setRuleId(null);
        } else {
            throw new RestException(RumExceptionCodeEnum.AUTH_500_ERROR);
        }
    }
    // ... 后续 add/update 逻辑
}
```

**copy-on-write 机制**：当用户尝试编辑 `userId=-1` 的全局默认规则时，系统不会修改全局默认规则，而是把 `ruleId` 置空，走 add 逻辑，创建一条**账号级默认规则（type=3, userId=accountId）**。

→ **结论：UI 编辑默认规则只影响"该账号的未来评分计算"，不修改全局默认规则本身。**

#### 路径 B：新建应用时克隆规则

`RumSettingHealthScoreMapper.selectAppCreateSourceRule` 决定新建应用时克隆哪条规则作为该应用的自定义规则：

```sql
-- 简化：优先 type=2 的账号级预置规则，回退 type=3 的全局默认(userId=-1)
where class_type = #{classType}
  and (
    (type = 2 and user_id = #{userId} and env_id = #{envId} and app_id in (#{appId}, -1))
    or
    (type = 3 and user_id = -1 ...)
  )
```

新建应用时，`initAppCustomScoreRule` 会把源规则克隆为该应用的自定义规则（type=1, appId=新应用ID）。

#### 路径 C：启动时补齐缺失规则

`InitAppScoreRuleSync.completeMissingCustomRules()` 在服务启动时扫描所有终端应用，为缺失自定义规则的应用克隆预置/默认规则：

```java
private void completeMissingCustomRules() {
    List<AppEntity> terminalApps = ...selectAllTerminalAppsForScoreRuleCompletion()...;
    Map<String, Long> existingCustomRuleMap = ...selectExistingEnabledCustomRules()...;
    List<AppScoreRuleNewTableRow> sourceRules = migrationMapper.selectCompletionSourceRules();
    // 对每个缺失自定义规则的应用，克隆一条
}
```

### 8.3 综合结论

| 场景 | 是否影响已有应用 | 是否影响新建应用 | 说明 |
|------|----------------|----------------|------|
| UI 编辑默认规则 | **否**（评分时仍用应用自己的自定义规则 type=1） | **间接影响**（新建时克隆的源规则可能变化） | copy-on-write 只创建账号级默认，不改全局；但新建应用克隆时优先取 type=2 预置，再回退 type=3 |
| 直接改 DB 全局默认（userId=-1） | **否**（已有应用有自己的 type=1 克隆规则） | **是**（新建应用克隆时会取到改后的全局默认） | 仅当账号没有 type=2 预置规则时才回退到全局默认 |
| 重启服务触发补齐 | **是**（对缺失自定义规则的应用会补克隆） | — | `completeMissingCustomRules` 为缺失规则的应用补克隆 |

**核心结论**：在常见场景下，**UI 编辑默认规则对已有应用基本无影响**（因为已有应用在创建/启动时已被克隆了 type=1 自定义规则，评分时优先用 type=1）。只有"直接改 DB 全局默认 + 账号无预置规则 + 新建应用"的组合才会让新应用受影响。

### 8.4 设计怪点

这是一种"**写时复制 + 克隆隔离**"的设计：
- 优点：每个应用的评分规则独立，互不干扰，全局默认不会被误改
- 缺点：用户以为"改默认规则能全局生效"，实际上几乎不会生效；想统一调整所有应用评分口径，需要逐应用修改或重置，运维成本高

> 该行为在当前版本（截至 2026-07）依然如此。如需"统一调整所有应用评分口径"，应提供"批量重置应用规则为默认"的功能，而非依赖编辑默认规则。

## 九、评分计算的关键细节补充

### 9.1 会话时长指标的特殊处理

`one.rum.app.session.sessionTime` 指标已废弃。在 `getScore()` 中遇到该指标直接给满分：

```java
if (METRIC_ID_SESSION_TIME.equals(key)) {
    // 会话时长指标已删除,如果有配置直接将该项设置为满分
    healthScore = healthScore.add(BigDecimal.valueOf(metricsModel.getWeightRate()));
    scoreMap.put(key, metricsModel.getWeightRate());
    continue;
}
```

### 9.2 旧网络指标向后兼容

`convertToBusinessRequestMetric()` 把旧的 `one.rum.net.request.*` 指标自动转换为 `one.rum.net.businessRequest.*`，保持与旧 DB 配置的兼容性：

```java
if (metricId != null && metricId.startsWith(OLD_REQUEST_METRIC_PREFIX)) {
    String suffix = metricId.substring(OLD_REQUEST_METRIC_PREFIX.length());
    return BUSINESS_REQUEST_METRIC_PREFIX + suffix;
}
```

### 9.3 环比计算（ringRate）

`getHealthScore(RumBaseCondition, ...)` 在算完当前时段分数后，会用对称时间窗口算上一时段分数，再调用 `MathUtils.formatRingDecimal(healthScore, lastHealthScore)` 计算环比。

### 9.4 OpenAPI 评分入口

- `getHealthScoreForApi()`：批量应用评分，按 appId 或 appVersion 分组，支持 `filters` 按 entity.app 属性过滤
- `getPageHealthScoreForApi()`：批量页面/视图评分，按 appId + scoreEnum(page/view) 分组，WHERE pageId IN (...)，GROUP BY pageId

两个入口都通过 `isFromOpenApi` 标记区分 OpenAPI 与内部调用，影响指标查询的过滤策略。
