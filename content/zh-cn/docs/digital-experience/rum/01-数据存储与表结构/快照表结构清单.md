## 2. 十三张 RUM 快照分表（`CkSnapshot`，每表 36 列）

以下 **13 张物理表** 共用 `CkSnapshot.java`，**列名、顺序、`CkColumnType` 完全一致**；**Java 组装类**均为 `SnapshotResultZeus`。为便于逐表查阅，**每张表下均重复列出完整 36 行列表明细**（基础 32 列内容相同，差异仅体现在第 33 列 `other_index` 的业务键部分）。

**`other_index` / `other_json`（第 33～34 列）说明**：`other_index` 在第 33 行 **说明** 列中为 **`键`：说明** 逐行罗列，先 **dealCommonOtherIndex 合并键**，再 **本表业务键**（各表不同）。**`other_json`（第 34 列）已废弃**，各表说明列仅标注状态；背景与历史 `dealOtherJson` 见 §2.0。

### 2.0 共用说明：`other_json`（十三张 CkSnapshot 分表，**已废弃**）

> **`other_json` 列状态**：**已废弃**。表结构仍保留该列；rum-controller **不写入**，请使用 **`other_index`** 承载扩展键值。

**为何 `t_rum_net_snapshot` 等与 `t_rum_common_snapshot` 文档里对 `other_json` 的说明一致？**
不是复制粘贴应付，而是 **rum-controller 源码事实**：十三张表共用 `CkSnapshot` 列定义与 `SnapshotResultZeus`，组装入口 **仅有** `BusinessCommonBiz.getCommonSnapshotTable` / `dealCommonEventSnapshot`。工程内 **不存在**「网络快照写一套 JSON、崩溃快照写另一套」的分支；扩展指标在 **`other_index`（Map）** 上按业务不同，**`other_json`（string）未被当前链路赋值**。

**rum-controller 运行时**

- `getCommonSnapshotTable` / `dealCommonEventSnapshot` **未调用** `SnapshotResultZeus.setOtherJson`。
- 全工程 `*.java` 检索 **`setOtherJson` 无业务调用点**；私有方法 **`dealOtherJson` 无引用**（死代码）。
- 结论：**十三张 CkSnapshot 物理表在 rum-controller 落库路径上，对 `other_json` 的行为完全一致**——通常为类型默认值/空，**不随 `EtlBizTypeEnum` 变化**。

**历史设计（列已废弃，下列仅供对照遗留代码 `dealOtherJson`）**：若曾计划调用 `dealOtherJson` 再 `setOtherJson`，则 JSON 由 `JsonUtil.mapToJsonStr` 序列化 **下列键**（同一套逻辑适用于任意 CkSnapshot 分表；**当前不应再启用该列**）：

| （`otherInfo` 入参中的全部键） | `otherInfo != null` 且非空 | 调用方 Map 原样并入后再序列化；**当前无调用方，故无实例** |

## 9. other_index / other_json 与扩展 Map 字段说明

> **与正文关系**：`other_index` 已内联于 **§2 主表第 33 行**、§3 第 25～26 行、§4 第 12 行。**`other_json`（已废弃）** 的背景与历史逐键说明在 **§2.0**；§2 各表第 34 行统一标注废弃状态。本节为汇总索引。

本节依据 **rum-controller** 内对 `SnapshotResultZeus`、`BatterySnapshotResultZeus`、`TraceSnapshotResultZeus` 的赋值逻辑整理。**Map 的 key 均为字符串**；值为字符串（`other_index` 全为 `Map<String,String>`）。部分键仅在分支条件满足时出现。

### 9.1 通用 `other_index` 合并键（`dealCommonOtherIndex`）

凡通过 `BusinessCommonBiz.getCommonSnapshotTable` 或 `dealCommonEventSnapshot` 构建的 **CkSnapshot 族**快照，在业务传入的 `otherIndexMap` 之上会 **merge** 下列键（后者可覆盖前者同名键）：

| 键 | 出现条件 | 含义 / 来源 |
|----|----------|-------------|
| （业务传入的全部键） | 各 `*EventService` 构建 | 先拷贝进 Map |
| `trackId` | `commonModel.getTrackId()` 非空 | 追踪 ID |
| `userInfo` | `uiModel.getExtraInfo()` 非空 | 用户扩展信息原文 |
| `viewTitle` | `eventViewInfoEntity.getViewTitle()` 非空 | 当前视图标题 |
| `isException` | 由 `ExceptionStateUtil.getEventIsExceptionValue(type, exceptionValue)` 计算 | 是否异常态（会写入并覆盖业务侧同名键） |
| `snapshotVersion` | 固定 | 字面量 `"1"` |
| `osType` | 设备信息 | 操作系统类型（字符串形式） |
| `mergeNetserviceId` | `nsiModel != null` | `BaseService.getNetServiceId` 合并后的运营商 ID |

> **与 §2 各子表对应关系**：§2.1～§2.13 每张表在「详细表结构」之下的业务键，均需 **再并上本表** 所列通用键（除非某键在业务侧未出现且条件不满足，则不存在）。

### 9.2 `other_json` 列说明（CkSnapshot 第 34 列对应入库字段，**已废弃**）

- **状态**：**已废弃**；保留列仅兼容 DDL/存量数据，**勿用于新扩展**（用 `other_index`）。
