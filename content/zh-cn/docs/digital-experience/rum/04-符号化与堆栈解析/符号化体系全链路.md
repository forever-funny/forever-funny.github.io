## 1. 符号类型矩阵（Symbol / SourceMap / Native）

RUM 的符号化体系按 **平台 × 符号类型** 双维度划分。平台维度由 `PlatformEnum` 描述，符号类型维度由 `t_rum_config_file.type` 字段与 `isNativeSymbolFile` 标志共同决定。

### 1.1 PlatformEnum 全量类型

| 类型值 | 枚举 | 中文名 | symbolAnalysis | getAppSymbolPath 是否处理 |
|--------|------|--------|----------------|---------------------------|
| 1 | ANDROID | Android | true | ✅ |
| 2 | IOS | iOS | true | ✅ |
| 3 | WEB | Web | false | ❌ 返回 null |
| 4 | WINDOWS | Windows | false | ❌ 返回 null |
| 5 | WECHAT_MINI_PROGRAM | 微信小程序 | false | ❌ 返回 null |
| 6 | HARMONY | HarmonyOS | true | ✅ |

- `symbolAnalysis = true` 的三种平台（Android / iOS / HarmonyOS）才参与本地符号文件同步与解析。
- Web / Windows / 微信小程序的崩溃/错误栈在前端侧或其他链路处理，不进入 `getAppSymbolPath` 的本地符号文件路径。

### 1.2 符号类型维度

| `t_rum_config_file.type` | 含义 | 对应 `isNativeSymbolFile` | 典型文件 |
|--------------------------|------|--------------------------|----------|
| 0 | 符号文件（Symbol File） | Android/Harmony 看 crash 类型：Java 走 `false`、Native 走 `true`；iOS 固定走 `false`（dSYM 落在 mapping 目录） | dSYM、ProGuard mapping.txt、so.zip、sourceMap.zip |
| 1 | SourceMap 文件 | `false` | `*.map`（JS SourceMap） |

> 注：`type=1` 的 SourceMap 主要服务于 JS 错误（Web/H5/小程序）的堆栈还原，存储在 BRFS（`T_RUM_SOURCE_MAP`）或 NFS，不参与 `getAppSymbolPath` 的本地路径拼接。`type=0` 的符号文件才由 `LocalSymbolFileJob` 同步到本地磁盘。

### 1.3 平台 × 符号类型支持矩阵

| 平台 | Java/ArkTS 层符号（`isNative=false`） | Native 层符号（`isNative=true`） |
|------|---------------------------------------|----------------------------------|
| Android | ProGuard/R8 `mapping.txt` | Native so 调试符号（`so.zip` 解压到各 ABI 子目录） |
| iOS | dSYM（统一落在 `mapping/` 目录，方法内部固定 `isNative=false`） | —（iOS 不区分 native/non-native 目录） |
| HarmonyOS | ArkTS `sourceMap.zip` 解压到 `sourceMap/` | Native so（`so.zip` 解压到 `so/`，不按 ABI 分子目录） |
| Web | JS SourceMap（`type=1`，走 BRFS，不经 `getAppSymbolPath`） | — |
| Windows / 微信小程序 | 不支持 | 不支持 |

## 2. 路径拼接与兼容路径

### 2.1 统一入口：MappingPathUtils.getAppSymbolPath

**源码位置**：`framework/plugins/rum/symbol-analysis/src/main/java/com/bonree/rum/analysis/utils/MappingPathUtils.java`

`getAppSymbolPath` 是按应用维度定位本地符号化文件的统一入口。解析服务（`AnalysisApi.doRetrace`、各平台 `*Retrace` 实现）在反混淆/反符号化堆栈前，通过该方法得到实际可读符号文件或目录的绝对路径。

**设计要点**：

- 路径由 **应用 ID + 应用版本 ID + 符号类型（Native / 非 Native）+ 平台** 共同决定。
- 仅 iOS、Android、HarmonyOS 三种平台返回有效路径；其余平台直接返回 `null`。
- 返回前做存在性校验：文件需 `fileIsExist`，目录需 `dirNotEmpty`；不满足则返回 `null`。
- iOS 存在多条历史兼容路径，按优先级依次尝试。

**方法签名与分发逻辑**：

```java
public static String getAppSymbolPath(PlatformEnum type, Long appId, Long appVersionId,
                                      String appName, boolean isNativeSymbolFile,
                                      String abi, boolean isWidgetCrash) {
    if (PlatformEnum.IOS.equals(type)) {
        return getIOSAppSymbolPath(appId, appVersionId, appName, isWidgetCrash);
    } else if (PlatformEnum.ANDROID.equals(type)) {
        return isNativeSymbolFile
            ? getAndroidNativeSymbolPath(appId, appVersionId, abi)
            : getAndroidSymbolPath(appId, appVersionId);
    } else if (PlatformEnum.HARMONY.equals(type)) {
        return isNativeSymbolFile
            ? getHarmonyOSNativeSymbolPath(appId, appVersionId)
            : getHarmonyOSSymbolPath(appId, appVersionId);
    }
    return null;
}
```

**参数说明**：

| 参数 | 含义 | 使用平台 |
|------|------|----------|
| `type` | 平台枚举 `PlatformEnum` | 全部分支 |
| `appId` | 应用 ID（Long） | 全部分支 |
| `appVersionId` | 应用版本 ID（Long） | 全部分支 |
| `appName` | 应用名称（Bundle 名 / 模块名） | **仅 iOS** |
| `isNativeSymbolFile` | 是否为 Native 符号文件 | Android、HarmonyOS |
| `abi` | 崩溃日志中的 ABI 字符串（如 `arm64`、`arm`） | **仅 Android Native** |
| `isWidgetCrash` | 是否为 Widget 扩展崩溃 | **仅 iOS**（决定 `.app.dSYM` / `.appex.dSYM`） |

### 2.2 基础路径：getBaseSymbolFilePath

所有应用符号化文件的根目录由 `getBaseSymbolFilePath` 生成：

```
{BASE_SYMBOL_FILE_PATH}/{appId}/{appVersionId}/{native|mapping}/
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `BaseConstants.BASE_SYMBOL_FILE_PATH` | `/data/br/data/rum/analysis/` | 可通过配置覆盖 |

| isNativeSymbolFile | 子目录常量 | 目录含义 |
|--------------------|------------|----------|
| `true` | `SymbolAnalysisConstants.NATIVE_SYMBOL_FILE_DIR` → `"native"` | Native 崩溃符号（so、dSYM 解压后的 DWARF 等） |
| `false` | `SymbolAnalysisConstants.SOURCEMAP_SYMBOL_FILE_DIR` → `"mapping"` | 应用层符号（ProGuard mapping、Harmony sourceMap 等） |

**示例**：

```
/data/br/data/rum/analysis/10001/20001/mapping/
/data/br/data/rum/analysis/10001/20001/native/
```

> iOS 特例：`getIOSAppSymbolPath` 方法内部固定使用 `isNativeSymbolFile = false` 调用 `getBaseSymbolFilePath`，即 iOS dSYM 实际基础路径为 `mapping/` 目录（与 Android/Harmony 的 native 目录命名策略不同）。

### 2.3 iOS 路径拼接（getIOSAppSymbolPath）

**输入**：`appId`、`appVersionId`、`appName`（来自崩溃堆栈中的 Binary/Image 名）。

#### 2.3.1 主路径（当前标准）

**普通 App 崩溃**：

```
{basePath}dSYMs/{appName}.app.dSYM/Contents/Resources/DWARF/{appName}
```

**Widget 扩展崩溃**（堆栈行含 `widgetCrash` 标记时，`appName` 追加 `.appex` 后缀）：

```
{basePath}dSYMs/{appName}.appex.dSYM/Contents/Resources/DWARF/{appName}
```

其中：

- `dSYMs` = `BaseConstants.ios_unzip_fileName`
- `{basePath}` = `/data/br/data/rum/analysis/{appId}/{appVersionId}/mapping/`

**完整示例**：

```
/data/br/data/rum/analysis/10001/20001/mapping/dSYMs/MyApp.app.dSYM/Contents/Resources/DWARF/MyApp
```

#### 2.3.2 历史兼容路径（依次 fallback）

若主路径文件不存在，按顺序尝试（源码常量 `IOS_dSYMs_PATH` = `dSYMs/Resources/DWARF/`）：

| 优先级 | 路径模式 | 说明 |
|--------|----------|------|
| 1 | 主路径（见 §2.3.1） | 标准 dSYM 完整目录结构 |
| 2 | `{basePath}dSYMs/Resources/DWARF/{appName}` | 老数据：扁平化 DWARF 路径，无 `.app.dSYM/Contents` 层级 |
| 3 | `{basePath}{appId}/dSYMs/Resources/DWARF/{appName}` | 更老数据：在 mapping 下按 appId 再套一层目录 |

> 注：路径 2、3 在拼接时会在 `basePath` 后额外追加一个文件分隔符，实际磁盘路径可能出现双斜杠 `//`，一般不影响 Linux 文件系统访问。

**校验规则**：返回的路径必须是存在的文件（`FileUtil.fileIsExist`），否则继续下一条；三条均失败返回 `null`。

#### 2.3.3 iOS 三方与系统符号路径（不在 getAppSymbolPath 内）

iOS 堆栈解析（`IOSRetrace`）在应用符号路径未命中时，还会尝试：

| 方法 | 用途 | 路径模式 |
|------|------|----------|
| `getIOSThirdSymbolPath` | 第三方 Framework | `{basePath}dSYMs/{lineName}.framework.dSYM/Contents/Resources/DWARF/{lineName}` |
| `getSystemSymbolicPathMap` | iOS 系统库 | 按系统版本查找，非 `getAppSymbolPath` 范畴 |

### 2.4 Android 路径拼接

#### 2.4.1 非 Native（Java/Kotlin 混淆）

**方法**：`getAndroidSymbolPath(appId, appVersionId)`

**符号类型**：ProGuard/R8 `mapping.txt`（`isNativeSymbolFile = false`）

**基础路径**：`/data/br/data/rum/analysis/{appId}/{appVersionId}/mapping/`

**文件候选（按顺序，任一存在即返回）**：

| 优先级 | 相对路径 | 说明 |
|--------|----------|------|
| 1 | `mapping.txt` | 标准命名 |
| 2 | `{appId}.txt` | 兼容老命名（以 appId 为文件名） |

**PlatformEnum 本地上传文件名**：`mapping.txt`（`PlatformEnum.ANDROID.getLocalFileName(false)`）

#### 2.4.2 Native（so 符号）

**方法**：`getAndroidNativeSymbolPath(appId, appVersionId, abiType)`

**符号类型**：Native 崩溃 so 调试符号（`isNativeSymbolFile = true`）

**基础路径**：`/data/br/data/rum/analysis/{appId}/{appVersionId}/native/`

**ABI 目录映射**（`AbiTypeEnum.fromAbi(abi)`，按崩溃日志 ABI 字符串匹配，忽略大小写）：

| 崩溃日志 abi | 枚举 | 符号目录 symbolDirectory |
|--------------|------|--------------------------|
| `arm64` | ARM64 | `arm64-v8a` |
| `arm` | ARM | `armeabi-v7a` |
| `x86_64` | X86_64 | `x86_64` |
| `x86` | X86 | `x86` |
| 未匹配 / 空 | — | 返回 `null` |

**完整路径**：`{basePath}so/{abi目录}/`

**示例**：`/data/br/data/rum/analysis/10001/20001/native/so/arm64-v8a/`

**说明**：

- 返回的是目录路径（以 `/` 结尾），校验使用 `FileUtil.dirNotEmpty`。
- `so` = `BaseConstants.NATIVE_UNZIP_FILENAME`。
- **PlatformEnum 本地上传文件名**：`so.zip`（解压到 `native/so/` 下各 ABI 子目录）。

### 2.5 HarmonyOS 路径拼接

#### 2.5.1 非 Native（ArkTS / JS）

**方法**：`getHarmonyOSSymbolPath(appId, appVersionId)`

**符号类型**：ArkTS SourceMap（`isNativeSymbolFile = false`）

**基础路径**：`/data/br/data/rum/analysis/{appId}/{appVersionId}/mapping/`

**返回路径**：`{basePath}sourceMap/`

**说明**：

- `sourceMap` = `BaseConstants.HARMONY_ARKTS_UNZIP_FILENAME`。
- 上传时为 zip，同步任务 `LocalSymbolFileJob` 解压到该目录。
- 返回目录，校验 `dirNotEmpty`。
- **PlatformEnum 本地上传文件名**：`sourceMap.zip`。

#### 2.5.2 Native（so 符号）

**方法**：`getHarmonyOSNativeSymbolPath(appId, appVersionId)`

**符号类型**：Native 崩溃 so（`isNativeSymbolFile = true`）

**基础路径**：`/data/br/data/rum/analysis/{appId}/{appVersionId}/native/`

**返回路径**：`{basePath}so/`

**说明**：与 Android Native 类似，但 **Harmony 不按 ABI 分子目录**，统一在 `so/` 下。校验 `dirNotEmpty`。**PlatformEnum 本地上传文件名**：`so.zip`。

## 3. iOS 包结构与 Info.plist 要求

### 3.1 Info.plist 在不同环节的必需性

对于 iOS 符号化文件：

- **定时任务（LocalSymbolFileJob）**：Info.plist **不是必需的**（定时任务不验证）。
- **符号化使用时（IOSRetrace）**：Info.plist **是必需的**（UUID 验证需要）。

缺少 Info.plist 会导致严重的符号化失败问题，且问题在定时任务阶段不会暴露，只在用户实际使用符号化功能时才显现。

### 3.2 定时任务处理逻辑（不验证 Info.plist）

**代码位置**：`LocalSymbolFileJob.processSymbolFile()` / `handleSymbolFileUnzip()`

```java
private void processSymbolFile(RumAnalysisAppSymbolEntity item, final Set<String> oldKeys) {
    try {
        // ... 其他逻辑 ...
        if (PlatformEnum.IOS.equals(platform)) {
            handleSymbolFileUnzip(localFile, basePath, BaseConstants.ios_unzip_fileName, platform);
        }
        putUpdateTime(item.getAppId(), item.getAppVersionId(), isNativeSymbolFile, item.getUpdateTime());
    } catch (Exception e) {
        log.error("{}Error processing symbol file: {}", LOG_TAG, e.getMessage(), e);
    }
}

private void handleSymbolFileUnzip(String localFile, String basePath, String unzipFileName, PlatformEnum platform) {
    File targetDir = new File(basePath, unzipFileName);
    try {
        FileUtil.delete(targetDir);
        if (PlatformEnum.IOS.equals(platform)) {
            ZipFileUtil.unZipFilesAndMove(new File(localFile), basePath, unzipFileName);
        }
    } catch (Exception e) {
        log.error("{}Failed to unzip {} symbol file: {}", LOG_TAG, platform.getName(), localFile, e);
        throw new RuntimeException("Symbol file unzip failed", e);
    }
}
```

**关键点**：

- 定时任务只负责解压 zip 文件。
- **不验证解压后的文件完整性**。
- **不检查 Info.plist 是否存在**。
- 只要解压成功，就会更新缓存时间戳。

### 3.3 实际使用时的 UUID 验证（需要 Info.plist）

**代码位置**：`IOSRetrace.getIOSRetraceResult()`

```java
public static RetraceResponse getIOSRetraceResult(...) {
    // ... 解析 binaryInfo 获取 UUID ...
    String uuid = tmpBiArr[1];
    String cpu = tmpBiArr[0];

    boolean checkAppUuid = checkUuid(appSymbolPath, cpu, uuid);
    if (!checkAppUuid) {
        AnalysisLogUtils.printLog("[symbol analysis] 符号化文件查找uuid失败:appSymbolPath={}, cpu={}, uuid={}",
            appSymbolPath, cpu, uuid);
        return new RetraceResponse(ResponseCodeEnum.APP_CHECK_UUID_FAILED);
    }
    // ... 继续符号化处理 ...
}
```

**UUID 验证逻辑**：

```java
private static boolean checkUuid(String dSYMFilePath, String architecture, String uuid) {
    String result = getUUID(dSYMFilePath, architecture);
    if (StringUtils.isNotEmpty(result)) {
        result = result.toLowerCase().replaceAll("-", "").replaceAll("\n", "").trim();
        uuid = uuid.toLowerCase().replaceAll("-", "").replaceAll("\n", "").trim();
        if (result.contains(uuid)) {
            return true;
        } else {
            return false;
        }
    } else {
        // 关键：如果 getUUID 返回 null 或空，直接返回 false
        return false;
    }
}

public static String getUUID(String filePath, String arch) {
    try {
        String result;
        if (BaseConstants.initSo) {
            result = Bratos4j.bratosGetUUID(filePath, arch);
        } else {
            result = getBratosGetUUID(filePath, arch);
        }
        return result;
    } catch (Exception e) {
        log.error("bratos getUUID:[bratos -o {} -A {} -u]", filePath, arch);
        log.error(e.getMessage(), e);
        return null;
    }
}
```

### 3.4 bratos 工具对 Info.plist 的依赖

`bratos` 工具（或 `Bratos4j` JNI 库）在获取 UUID 时：

1. 读取 dSYM 文件结构。
2. 查找 Info.plist 文件（位于 `Contents/Info.plist`）。
3. 从 Info.plist 中提取 UUID 信息。
4. 返回 UUID 字符串。

如果缺少 Info.plist：

- `bratos -o dSYMFilePath -A arch -u` 命令会失败或返回空。
- `Bratos4j.bratosGetUUID()` JNI 调用会返回 `null`。
- 无法验证 dSYM 文件与崩溃日志的 UUID 是否匹配。

### 3.5 缺少 Info.plist 的严重问题

#### 问题 1：UUID 验证失败 ⭐⭐⭐

**问题流程**：

1. 用户上传缺少 Info.plist 的 iOS zip 符号化文件。
2. 定时任务解压成功（不验证完整性）。
3. 缓存时间戳更新，文件被认为"正常"。
4. 用户尝试符号化崩溃堆栈。
5. 系统调用 `bratos -o dSYMFilePath -A arch -u` 获取 UUID。
6. bratos 工具无法从缺少 Info.plist 的 dSYM 中提取 UUID。
7. `getUUID()` 返回 `null` 或空字符串。
8. `checkUuid()` 返回 `false`。
9. 整个符号化过程立即失败。

**错误代码**：`ResponseCodeEnum.APP_CHECK_UUID_FAILED(407, "符号化文件查找uuid失败")`

#### 问题 2：所有崩溃堆栈无法解析 ⭐⭐⭐

- 所有使用该符号化文件的崩溃堆栈都无法解析。
- 用户看到的错误信息：`"符号化文件查找uuid失败"`。
- 无法进行任何堆栈符号化操作。

#### 问题 3：文件不会被自动删除但无法使用 ⭐⭐

- 定时任务不会删除缺少 Info.plist 的文件（因为不验证）。
- 文件会一直占用存储空间，但完全无法使用。
- 用户需要手动删除并重新上传正确的文件。

#### 问题 4：系统符号化文件也会受影响 ⭐⭐

**代码位置**：`IOSRetrace.getSystemSymbolicPathMap()`

```java
public static String getSystemSymbolicPathMap(BratosEntity bratosEntity, String systemVersion) {
    // ... 查找系统符号化文件 ...
    boolean result = checkUuid(symbolicPath, bratosEntity.getArchitecture(), bratosEntity.getUuid());
    if (result) {
        return symbolicPath;
    }
    return null;
}
```

如果系统符号化文件也缺少 Info.plist，系统堆栈也无法解析。

### 3.6 实际影响场景

| 场景 | 流程 | 结果 |
|------|------|------|
| 用户上传不完整的 dSYM | 上传 → 解压成功 → 缓存更新 → 使用时 UUID 验证失败 | `APP_CHECK_UUID_FAILED`，需重新上传 |
| 解压过程中 Info.plist 丢失 | 上传完整 zip → 解压异常 → Info.plist 丢失 → 定时任务认为成功 → 使用时失败 | 所有符号化操作失败 |
| 手动删除或损坏 Info.plist | 文件原本完整 → 磁盘错误/手动删除 → 定时任务不发现 → 使用时才发现 | 直到用户尝试使用时才暴露 |

### 3.7 修复建议

### 4.6 定时清理任务：deleteUnusedSymbolFiles

**触发条件**：

- 每天执行一次（`needDailyCleanup()` 返回 true）。
- 判断依据：距离上次删除时间超过 24 小时。

**删除逻辑**：

```java
private void deleteUnusedSymbolFiles() {
    File baseDir = new File(BaseConstants.BASE_SYMBOL_FILE_PATH);
    File[] appDirs = baseDir.listFiles((dir, name) -> StringUtils.isNumeric(name));

    for (File appDir : appDirs) {
        File[] versions = appDir.listFiles(File::isDirectory);
        for (File version : versions) {
            // 关键问题：同时检查 native 和 mapping 目录
            boolean nativeUnused = isSymbolUnused(appDir, version, true);
            boolean mappingUnused = isSymbolUnused(appDir, version, false);

            if (mappingUnused) {
                // iOS 文件存储在 mapping 目录下
                deleteFile(Path.of(version.getAbsolutePath(),
                    SymbolAnalysisConstants.SOURCEMAP_SYMBOL_FILE_DIR).toFile(),
                    "Unused mapping symbol directory");
            }

            // 如果两个目录都未使用，删除整个版本目录
            if (nativeUnused && mappingUnused) {
                deleteFile(version, "Unused version directory");
            }
        }
    }
}

private boolean isSymbolUnused(File appDir, File version, boolean isNative) {
    // 关键：从内存缓存中获取更新时间
    return getUpdateTime(appDir.getName(), version.getName(), isNative) == null;
}

public static Long getUpdateTime(String appId, String appVersionId, boolean isNative) {
    // 从内存缓存 symbolVersionTime 中获取
    return symbolVersionTime.get(getKey(appId, appVersionId, isNative));
}
```

### 4.7 误删根因分析

#### 根因 1：缓存依赖问题 ⭐⭐⭐

**问题根源**：

1. **缓存依赖问题**：判断文件是否未使用完全依赖于内存缓存 `symbolVersionTime`。
2. **iOS 文件的 key**：对于 iOS，`isNativeSymbolFile()` 总是返回 `false`，所以 key 是 `appId_appVersionId_0`。
3. **缓存未更新**：如果同步过程中出现问题，缓存中没有对应的 key，`getUpdateTime()` 返回 `null`。
4. **误判为未使用**：返回 `null` 会被判定为"未使用"，导致文件被删除。

#### 根因 2：定时清理任务判断逻辑缺陷 ⭐⭐⭐

**核心问题**：

1. **只依赖内存缓存**：判断是否未使用完全依赖于内存缓存，没有检查磁盘上的实际文件。
2. **没有检查时间戳文件**：虽然代码中有 `_updateTime` 文件，但 `deleteUnusedSymbolFiles()` 没有读取这个文件。
3. **缓存可能丢失**：如果服务重启，内存缓存会清空，所有文件都会被判定为未使用。

#### 根因 3：同步失败导致缓存未更新（最可能）⭐⭐⭐

**问题流程**：

1. 用户上传 iOS zip 文件。
2. 文件保存到数据库和存储系统。
3. `LocalSymbolFileJob` 定时同步任务执行。
4. 同步过程中出现异常（解压失败、文件读取失败等）。
5. 异常被 catch，但 `putUpdateTime()` 没有被调用。
6. 内存缓存 `symbolVersionTime` 中没有对应的 key。
7. 24 小时后，定时清理任务执行。
8. `getUpdateTime(appId, appVersionId, false)` 返回 `null`。
9. 文件被判定为"未使用"，被删除。

#### 根因 4：服务重启导致缓存丢失（可能）⭐⭐

**问题流程**：

1. 用户上传 iOS zip 文件。
2. 同步成功，缓存中有对应的 key。
3. 服务重启（或缓存被清空）。
4. 内存缓存 `symbolVersionTime` 被清空。
5. 定时清理任务执行。
6. `getUpdateTime()` 返回 `null`。
7. 文件被误删。

#### 根因 5：数据库查询问题（可能）⭐

**问题流程**：

1. 用户上传 iOS zip 文件。
2. 数据库记录保存成功。
3. 但查询时由于 JOIN 条件或过滤条件，iOS 文件记录没有被查询到。
4. `syncSymbolFiles()` 中没有对应的记录。
5. `processSymbolFile()` 不会被调用。
6. 缓存中没有对应的 key。
7. 定时清理时文件被误删。

| 删除位置 | 触发条件 | 说明 |
|----------|----------|------|

#### 修复方案 2：改进删除判断逻辑（推荐）

**问题**：只依赖内存缓存判断，没有检查磁盘文件。

```java
private boolean isSymbolUnused(File appDir, File version, boolean isNative) {
    // 先检查内存缓存
    Long updateTime = getUpdateTime(appDir.getName(), version.getName(), isNative);
    if (updateTime != null) {
        return false;  // 缓存中有记录，说明在使用
    }

    // 缓存中没有，检查磁盘上的时间戳文件
    String symbolDir = isNative ?
        SymbolAnalysisConstants.NATIVE_SYMBOL_FILE_DIR :
        SymbolAnalysisConstants.SOURCEMAP_SYMBOL_FILE_DIR;
    File symbolDirFile = Path.of(version.getAbsolutePath(), symbolDir).toFile();

    if (!symbolDirFile.exists()) {
        return true;  // 目录不存在，确实未使用
    }

    // 检查是否有时间戳文件
    PlatformEnum platform = getPlatformByAppId(appDir.getName());
    if (platform == null) {
        return true;
    }

    String localFileName = platform.getLocalFileName(isNative);
    if (localFileName == null || localFileName.isBlank()) {
        return true;
    }

    File localFile = new File(symbolDirFile, localFileName);
    File updateTimeFile = new File(localFile.getAbsolutePath() + "_updateTime");

    if (updateTimeFile.exists()) {
        // 有时间戳文件，说明文件曾经成功同步过，不应该删除
        try {
            String updateTimeStr = FileUtil.readFile(updateTimeFile.getAbsolutePath());
            Long diskUpdateTime = Long.parseLong(updateTimeStr);
            // 更新缓存，避免下次再误判
            putUpdateTime(appDir.getName(), version.getName(), isNative, diskUpdateTime);
            return false;
        } catch (Exception e) {
            log.warn("{}Failed to read updateTime file: {}", LOG_TAG, updateTimeFile, e);
        }
    }

    // 没有时间戳文件，但目录存在，可能是正在同步中，保守处理：不删除
    return false;
}
```

private void restoreCacheFromDisk() {
    File baseDir = new File(BaseConstants.BASE_SYMBOL_FILE_PATH);
    if (!baseDir.isDirectory()) {
        return;
    }
    File[] appDirs = baseDir.listFiles((dir, name) -> StringUtils.isNumeric(name));
    if (appDirs == null) {
        return;
    }
    for (File appDir : appDirs) {
        File[] versions = appDir.listFiles(File::isDirectory);
        if (versions == null) {
            continue;
        }
        for (File version : versions) {
            // 检查 mapping 目录（iOS 文件存储在这里）
            File mappingDir = Path.of(version.getAbsolutePath(),
                SymbolAnalysisConstants.SOURCEMAP_SYMBOL_FILE_DIR).toFile();
            if (mappingDir.exists()) {
                restoreCacheFromDir(appDir.getName(), version.getName(), mappingDir, false);
            }
            // 检查 native 目录
            File nativeDir = Path.of(version.getAbsolutePath(),
                SymbolAnalysisConstants.NATIVE_SYMBOL_FILE_DIR).toFile();
            if (nativeDir.exists()) {
                restoreCacheFromDir(appDir.getName(), version.getName(), nativeDir, true);
            }
        }
    }
}

private void restoreCacheFromDir(String appId, String versionId, File symbolDir, boolean isNative) {
    File[] files = symbolDir.listFiles((dir, name) -> name.endsWith("_updateTime"));
    if (files != null && files.length > 0) {
        try {
            String updateTimeStr = FileUtil.readFile(files[0].getAbsolutePath());
            Long updateTime = Long.parseLong(updateTimeStr);
            putUpdateTime(appId, versionId, isNative, updateTime);
            log.debug("{}Restored cache from disk: {}_{}_{}", LOG_TAG, appId, versionId, isNative);
        } catch (Exception e) {
            log.warn("{}Failed to restore cache from disk: {}", LOG_TAG, files[0], e);
        }
    }
}

## 5. 配置表删除与 TYPE 安全（MySQL 删除 SQL 修复方案）

### 5.1 问题描述

在 RUM 模块中，删除 SourceMap 文件时存在**会误删同名其他类型文件**的安全隐患。

**问题位置**：
- 文件：`framework/plugins/rum/rum-database/src/main/resources/com/bonree/rum/mysql/setting/RumSettingAggMapper.xml`
- 方法：`delete`（第 155-164 行）

**问题 SQL**：

```xml
<delete id="delete">
    delete from
        t_rum_config_file
    where
            flag = 0
        and
            app_id = #{param.keyId}
        and
            alias_name = #{param.fileName}
</delete>
```

**问题说明**：

1. 数据库表 `t_rum_config_file` 中的 `TYPE` 字段用于区分文件类型：
   - `TYPE = 0`：符号文件（Symbol File）
   - `TYPE = 1`：SourceMap 文件

2. 当前删除 SQL **缺少 `TYPE = 1` 的过滤条件**，导致删除 SourceMap 文件时，如果同一应用下存在同名但类型不同的文件（TYPE=0），会被误删。

3. 对比参考：删除符号文件的 SQL（`deleteSymbolFile` 方法）正确包含了 `TYPE = 0` 的条件：

```xml
<delete id="deleteSymbolFile">
    delete from
        t_rum_config_file
    where
            flag = 0
          and
            `TYPE` = 0
          and
            id = #{id}
          and
            user_id = #{userId}
</delete>
```

### 5.2 风险场景示例

- 场景：同一个 app 下存在两个文件
  - 文件 A：TYPE=1（SourceMap），alias_name='bundle.js.map'
  - 文件 B：TYPE=0（符号文件），alias_name='bundle.js.map'
- 操作：删除 SourceMap 文件 'bundle.js.map'
- 结果：**文件 A 和文件 B 都会被删除**（错误！）

### 5.3 修复方案

在删除 SourceMap 文件的 SQL 中添加 `TYPE = 1` 的过滤条件。

**修改后代码**：

```xml
<delete id="delete">
    delete from
        t_rum_config_file
    where
            flag = 0
        and
            `TYPE` = 1
        and
            app_id = #{param.keyId}
        and
            alias_name = #{param.fileName}
</delete>
```

**关键改动**：

- 添加条件：`and TYPE = 1`，确保只删除 SourceMap 文件（TYPE=1）。
- 使用反引号包裹 `TYPE` 关键字，避免与数据库关键字冲突（兼容 MySQL）。

### 5.4 达梦数据库兼容性

- 经过代码审查，`deleteSymbolFile` 方法也没有 `databaseId="dm"` 版本。
- 达梦数据库也支持 `TYPE` 字段和条件过滤。
- **建议**：如果后续发现达梦数据库有兼容性问题，再添加 `databaseId="dm"` 版本。

**如果将来需要添加达梦版本**（示例代码，当前不需要）：

```xml
<delete id="delete" databaseId="dm">
    delete from
        t_rum_config_file
    where
            flag = 0
        and
            "TYPE" = 1
        and
            app_id = #{param.keyId}
        and
            alias_name = #{param.fileName}
</delete>
```

### 5.5 SQL 执行效果对比

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| **场景 1**：只存在 SourceMap 文件（TYPE=1，alias_name='test.js.map'） | ✅ 正确删除 | ✅ 正确删除 |
| **场景 2**：只存在符号文件（TYPE=0，alias_name='test.js.map'） | ❌ **错误删除** | ✅ 不删除（正确） |
| **场景 3**：同时存在两种类型文件（TYPE=1 和 TYPE=0，alias_name='test.js.map'） | ❌ **两种文件都被删除** | ✅ 只删除 TYPE=1 的文件（正确） |

## 7. 与解析引擎的衔接

符号化文件的本地路径拼接（§2）与定时同步（§4）共同保证了磁盘上存在可读的符号文件。解析引擎在拿到崩溃/错误堆栈后，按平台路由到对应的 `*Retrace` 实现，再通过 `MappingPathUtils.getAppSymbolPath` 定位本地符号文件完成反混淆/反符号化。

### 7.1 衔接点

| 衔接点 | 说明 |
|--------|------|
| `AnalysisApi.doRetrace` → `MappingPathUtils.getAppSymbolPath` | 解析引擎通过路径拼接入口定位本地符号文件 |
| `LocalSymbolFileJob` 写入路径 ↔ `MappingPathUtils` 读取路径 | 必须保持一致（见 §4.2 同步与路径关系表） |
| `IOSRetrace.checkUuid` | 使用 bratos 工具读取 dSYM 的 Info.plist 验证 UUID（见 §3） |
| `t_rum_config_file.type` | 区分符号文件（0）与 SourceMap（1），决定走符号化引擎还是 JS SourceMap 解析（见 §1.2） |

### 7.2 各平台解析引擎路由

- **JS 错误（moduleType=3）**：Node.js 子进程 + `source-map` 库，读取 BRFS 中的 `.map` 文件（`type=1`），不经过 `getAppSymbolPath`。
- **Android Java 崩溃**：`RumR8Retrace`，通过 `getAndroidSymbolPath` 读取 `mapping.txt`。
- **Android Native 崩溃**：`AndroidNativeRetrace`，通过 `getAndroidNativeSymbolPath` 读取 `so/{abi}/`。
- **iOS 崩溃**：`IOSRetrace`，通过 `getIOSAppSymbolPath` 读取 dSYM，并校验 Info.plist 中的 UUID。
- **HarmonyOS Native 崩溃**：`hstack` 命令行工具，通过 `getHarmonyOSNativeSymbolPath` 读取 `so/`。
- **HarmonyOS ArkTS 崩溃**：HarmonyOS ArkTS SourceMap 解析，通过 `getHarmonyOSSymbolPath` 读取 `sourceMap/`。

解析引擎的完整链路、前端过滤校验、问题 ID 归并逻辑详见同目录《堆栈解析与展示.md》。

### 7.3 排查建议

1. **`getAppSymbolPath` 返回 null**：按平台检查对应目录/文件是否存在；Android Native 重点核对崩溃日志中的 `abi` 字符串能否被 `AbiTypeEnum.fromAbi` 识别。
2. **iOS 有包但解析失败**：确认 `appName` 与 dSYM 内 DWARF 文件名一致；老版本数据尝试 §2.3.2 的 fallback 路径；检查 Info.plist 是否存在（§3）。
3. **Harmony ArkTS**：确认 zip 已解压到 `mapping/sourceMap/` 且目录非空。
4. **路径前缀不一致**：确认 `BASE_SYMBOL_FILE_PATH` 配置与 `LocalSymbolFileJob` 写入路径一致。
5. **Web/Windows/小程序**：不应调用 `getAppSymbolPath` 期望有结果，属预期行为。
6. **文件莫名被删**：按 §4.7 误删根因排查，重点检查缓存是否未更新或服务重启后缓存丢失。
7. **SourceMap 误删同名符号文件**：按 §5 检查 `RumSettingAggMapper.xml` 的 `delete` 方法是否包含 `TYPE = 1` 条件。
