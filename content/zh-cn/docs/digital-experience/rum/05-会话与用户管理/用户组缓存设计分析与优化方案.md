# Ingester RUM 用户组缓存：设计分析与优化方案

> 文档范围：`controller/ingester` 中 RUM 模块针对 **用户ID、用户组、用户组关联应用** 的缓存实现、设计逻辑、优缺点，以及「删除立即生效且不显著增加性能/内存压力」的改造建议；并包含 **客户数据量级不确定时** 原方案与推荐方案的分级权衡。
> 核心类：`UserGroupCache`
> 路径：`controller/ingester/ingester-business/ingester-rum/.../cache/UserGroupCache.java`
> 整理日期：2026-07-09

---

## 1. 背景与目标

### 1.1 业务诉求

RUM Upload / 会话回放入库时，需要把探针上报的用户ID（`ui.ui` / `memberId`）解析为用户组ID（`user_group_id`），并写入 ClickHouse 相关快照/会话视图，供：

- 会话列表按用户组筛选、展示
- 会话回放用户范围白名单（依赖解析出的 `groupId`）
- 其他事件/指标维度中的 `userGroupId`

配置侧关系来自 MariaDB：

| 关系 | 表 |
|------|-----|
| 用户（用户ID） | `t_rum_user_member` |
| 用户 ↔ 用户组 | `t_rum_member_group_relation` |
| 用户组 ↔ 应用 | `t_rum_app_group` |
| 用户组实体 | CMDB `usergroup`（instanceId 作为 groupId） |

### 1.2 工程约束

- Upload **QPS 高**，热路径不能每条数据查 MariaDB
- 关系是三元组：`memberId × groupId × appId`（另含 `accountId`）
- 用户量可能很大，精确全量集合有内存压力顾虑
- 配置变更频率远低于数据写入频率 → 可接受最终一致（但删除时效有产品诉求）

### 1.3 本文结论预览

| 项 | 结论 |
|----|------|
| 当前方案 | 本地两级缓存：应用→组集合 + 组内 BloomFilter；5 分钟增量 / 每天 1 点全量 |
| 主要问题 | Bloom **不可删**、假阳性约 3%、删除/换组最长约 1 天才纠正、多组命中不确定 |
| 推荐改造 | **精确 `member→group` Map + 变更推送（增删改）**；定时拉取仅作兜底对账 |
| 推荐方案取舍 | 正确性/删除时效/热路径更优；代价是推送依赖、版本协议、改造面与超大规模堆占用（见 §6.8） |
| 量级不确定时 | **不要静态二选一**：默认精确 Map + 推送；按账号关系数/内存水位分级，超限再降级到 Bloom/混合（见 §7） |
| 过渡方案 | 保留 Bloom + **tombstone 删除旁路**（可立即盖住删除，但仍有假阳性；亦可作超大户降级手段） |

## 2. 当前实现全景

### 2.1 端到端数据流

```text
【配置】rum-core / 控制台
  用户组 ↔ 应用 → t_rum_app_group
  用户 ↔ 用户组 → t_rum_user_member + t_rum_member_group_relation
        │
        ▼  HTTP 分页拉取（5min 增量 / 日全量）
【Manager】POST /ingester/rum/userGroupList
  SQL: UserGroupMapper.selectMemberGroupAppList
        │
        ▼
【UserGroupCache】（ingester-rum 进程内）
  app_group_map:     appId_accountId → Set<appId_groupId>
  group_member_map:  appId_groupId   → BloomFilter(appId_memberId)
        │
        ▼  Upload / Replay 解析
【DataFactory】
  getGroupId(appId, memberId, accountId) → userInfo.groupId
        │
        ▼
【写 CK】user_group_id / member_id
  （历史会话不回写；只影响之后入库的数据）
```

### 2.2 数据源 SQL（扁平三元组）

```sql
-- UserGroupMapper.selectMemberGroupAppList（示意）
SELECT m.member_id AS memberId,
       r.group_id  AS groupId,
       trag.app_id AS appId,
       m.account_id AS accountId
FROM t_rum_member_group_relation r
LEFT JOIN t_rum_user_member m ON r.user_member_id = m.ID
LEFT JOIN t_rum_app_group trag ON trag.group_id = r.group_id
WHERE r.update_time >= #{time}
LIMIT #{from}, #{to}
```

一行 =「某账号下，某用户在某应用上属于某用户组」。

ingester-rum **不直连** MariaDB，经 Manager HTTP 分页拉取（每页 10000，最多约 10000 页）。

### 2.3 缓存结构

```text
app_group_map
  key   = appId + "_" + accountId
  value = Set<"appId_groupId">          // 该应用下有哪些用户组

group_member_map
  key   = appId + "_" + groupId
  value = UserGroupBloomEntity {
            groupId,
            BloomFilter(元素 = "appId_memberId")
          }
```

设计意图：

1. 先按 **应用 + 账号** 收窄候选用户组，避免全库扫组
2. 组内用户用 **BloomFilter** 做成员近似判断，控制内存
3. **关联应用**编码进 key：同一用户组绑多个应用 → 多份 `appId_groupId` 过滤器

### 2.4 Bloom 参数

| 参数 | 代码值 | 注释声称 | 说明 |
|------|--------|----------|------|
| 预期元素数 `n` | 2_000_000 | 同左 | **每个组**一个过滤器的预期容量 |
| 假阳性率 `p` | **0.03** | ≈0.001 | **以代码为准**；注释与实现不一致 |
| 元素 | `appId_memberId` | — | 字符串 funnel |

### 2.5 刷新策略

调度：`RumInitializationManager` → `CacheServer.initAllCache(FIVE_MINUTE)`
`UserGroupCache.refreshInterval() = 5` → 挂在 **每 5 分钟** 链路上。

| 条件 | 行为 |
|------|------|
| 缓存为空（首次） | 全量：`initAllUserGroup(0, true)`，新建 Map 后整体替换 |
| 距上次全量 ≥1 天 **且** 当前小时 == 1 | 全量重建（双检锁） |
| 其他 5 分钟周期 | 增量：`initAllUserGroup(当天0点 - 10分钟, false)`，往现有 Bloom **只 put 不删** |

说明：

- 增量时间窗是「**当天 0 点往前 10 分钟**」，不是「当前时间 − 10 分钟」
- 当天内变更一般能被后续刷新扫到；**删除/移出组**无法从 Bloom 抹掉，依赖日全量
- 全量失败或错过 1 点窗口，脏数据可能拖到下一个 1 点

### 2.6 热路径查询

`DataFactory.buildCommonModel`（及回放相关路径）：

```java
groupId = userGroupCache.getGroupId(appId, memberId, accountId);
userInfoEntity.setGroupId(groupId);
```

`getGroupId` 算法：

```text
1. mapKey = appId_accountId
2. 取该应用下所有 groupKey
3. 依次 Bloom.mightContain(appId_memberId)
4. 第一个命中 → 返回该 groupId；全未命中 → null
```

另有 `checkMemberExist(appId, accountId, groupId, memberId)`：已知组时做存在性校验；生产主路径主要用 `getGroupId`。

### 2.7 相关但不相同的缓存

会话回放「哪些用户组可回放」使用 `TerminalUserGroupSetting`：

- 精确 `Set<Long> groupId`
- 配置 **推送** 增量更新

与「用户属于哪组」的 Bloom **拉取**模式并存 → 同一业务域两套一致性模型。

## 3. 设计优点

### 3.1 热路径性能好

`getGroupId` 全程进程内内存：无 DB、无 Redis。适合 Flink/ingester 高吞吐 Upload。

### 3.2 空间相对可控（相对朴素 HashSet）

相对「每个组一个 `HashSet<memberId>` 全量精确集合」，Bloom 可按容量预估内存，大用户量场景下有空间优势（但见下文「按 200 万预分配」的浪费问题）。

### 3.3 分层索引贴合业务语义

「用户组关联应用」体现在 key 中：未绑定当前应用的组不参与匹配，避免跨应用误绑。

### 3.4 配置与计算解耦

Manager 负责查库与分页；ingester 只做本地缓存与匹配。多实例部署时计算节点不被业务库拖垮。

### 3.5 全量替换有基本安全意识

全量时新建 Map，加载完成再整体赋值，读侧不易看到半加载状态；双检锁避免并发全量。

### 3.6 与现有 Cache 框架一致

挂在 `AbstractCache` + 固定刷新间隔上，运维心智统一。

## 4. 设计缺点与风险

### 4.1 Bloom 假阳性（正确性近似）— 中高

- 代码 `p=0.03`，约 3% 误判「可能在组内」
- 应用下组越多，遍历时假阳性叠加概率越高
- 可能错绑用户组，影响会话筛选、回放白名单等
- 注释写 0.001、代码 0.03，**实现比文档暗示更差**

### 4.2 增量只增不删（删除/换组延迟）— 高

Bloom 不支持删除。用户从组移除、换组、解绑应用后：

- 增量只会 `put` 新关系
- 旧成员仍可能 `mightContain=true`
- 通常要等到 **凌晨 1 点全量** 才纠正
- 错绑会持续写入 CK；**历史数据不回写**

这是「删除立即生效」诉求下的核心障碍。

### 4.3 多组命中结果不确定 — 中

同一 `appId + accountId` 下，用户落在多个组（配置疏漏或假阳性）时：

- `HashSet` 遍历顺序不稳定
- 「第一个命中」→ 不同实例/重启后可能绑不同 `groupId`

若产品约束「同应用下用户唯一属于一组」，应在配置侧强约束，或匹配侧做确定性策略（如取最小 groupId）。

### 4.4 增量时间窗语义别扭 — 中

`currDayTime - 10 * 60 * 1000`：

- 当天内近似「反复扫当天变更」→ Manager/DB 压力随当天变更量累积
- 跨天到全量前，删除仍依赖全量
- 不如滑动窗口 `now - N` 直观

### 4.5 全量触发脆弱 — 中

条件：`距上次全量 ≥1 天` **且** `hour == 1`。

- 1 点那一轮失败/进程错过 → 再等下一个 1 点
- 类内缺少显式「全量失败重试 / 手动强制全量」路径
- `lastInitTme` 为 static，多实例各自独立，运维难统一观察

### 4.6 内存模型隐藏成本 — 中

- `snapshotBlMaxSize=200万` 是 **每个组** 的预期容量，不是全局共享
- 组数多时：内存 ≈ `组数 × 单过滤器大小` 线性增长
- 小组成员也按 200 万建过滤器 → 小租户浪费明显
- Guava Bloom 不可扩容：单组超预期后假阳性恶化，代码无告警

### 4.7 并发与可观测性 — 低～中

- 增量直接改现有 Map；`app_group_map` 的 value 为普通 `HashSet`，若刷新非严格单线程存在并发风险
- 缺少：组数、put 数、全量/增量耗时、拉取失败率、对账差异等指标，排障困难

### 4.8 与回放配置缓存风格不统一 — 低

回放白名单已是精确集合 + 推送；用户组成员却是 Bloom + 拉取，增加理解与排障成本。

## 5. 问题本质（针对「删除立即生效」）

| 诉求 | 当前能力 |
|------|----------|
| 删除后本进程立即不再命中 | ❌ Bloom 无法 remove |
| 全集群秒级一致 | ❌ 仅定时拉，且增量不删 |
| 热路径无 DB | ✅ |
| 内存可控 | ⚠️ 有优势也有按组满配浪费 |

**结论**：要在不大压性能/内存的前提下做到删除立即生效，必须让缓存结构支持 **真删**，并用 **推送（或等价变更流）** 驱动各实例本地 `remove`；定时拉取降级为兜底对账，而不是删除生效的主路径。

继续缩短增量窗口、或提高全量频率，**无法从根上解决 Bloom 不可删**；热路径回源 DB/Redis 则会把延迟和依赖打回 Upload。

## 6. 推荐方案：精确 Map + 变更推送

### 6.1 目标

- 删除 / 换组 / 解绑应用：**秒级**在各 ingester 实例生效
- Upload 热路径：仍为 **纯内存 O(1)**，不查库
- 内存：按 **真实关系数** 存储，避免按 200 万/组预分配 Bloom
- 正确性：无假阳性；一用户一应用一条映射，结果确定

### 6.2 建议数据结构

```text
// 主索引（必需）
member_group_map: ConcurrentHashMap<String, Long>
  key   = appId + "_" + accountId + "_" + memberId
  value = groupId

// 可选：若仍需「应用下有哪些组」
app_group_map: appId_accountId → Set<groupId>

// 可选：加速「整组解绑应用」时的批量删除
group_member_index: appId_groupId → Set<memberKey>
  （仅维护反向索引；删除组/解绑时遍历 remove 主索引）
```

热路径：

```text
getGroupId(appId, memberId, accountId)
  → member_group_map.get(key)   // 命中返回 groupId，否则 null
```

删除：

```text
member_group_map.remove(key)    // 立即对该进程生效
```

换组：

```text
member_group_map.put(key, newGroupId)  // 覆盖即可
```

### 6.3 变更推送（全集群立即生效）

沿用已有配置推送通道（参考 `TerminalUserGroupSetting` / RuleSetting），增加用户组成员变更事件：

| 事件 | 载荷（建议） | 本地动作 |
|------|--------------|----------|
| ADD / UPDATE | appId, accountId, memberId, groupId, version/updateTime | `put(key, groupId)` |
| DELETE | appId, accountId, memberId[, groupId] | `remove(key)` |
| UNBIND_APP | appId, groupId | 借助反向索引批量 `remove` 相关 key |
| GROUP_DELETE | groupId | 批量清理该组在所有应用下的映射 |

要求：

- 消息带 **版本号或 update_time**，避免乱序覆盖新数据
- 各 ingester 实例独立消费，本地改 Map
- **推送是删除生效的主路径**

### 6.4 定时拉取的新定位

| 场景 | 行为 |
|------|------|
| 进程启动 | 全量拉取构建精确 Map |
| 推送丢失 / 对账 | 低频全量或按时间窗增量拉取，与本地 Map diff |
| 每天 1 点 | 可选全量对账，修漂移；**不再是删除生效的唯一手段** |

原「5 分钟只 put 的 Bloom 增量」可下线或改为「对账增量」。

### 6.5 内存与性能为何可控

| 点 | 说明 |
|----|------|
| 内存 | 只存真实三元组；不再按 200 万/组预分配 |
| CPU | 单次 Hash 查找，通常优于「遍历应用下所有组做 mightContain」 |
| 删除 | `remove` 真删，无需等日全量 |
| 多组 | 一用户一应用一条记录，天然唯一 |

粗算：百万级关系时，精确 Map 通常为几十～一百多 MB 量级（视 memberId 长度），多数场景可接受；且常小于「大量组 × 满配 Bloom」。

若个别超大客户仍紧张，可再优化：

- key 编码压缩（数值型 appId/accountId 拼接，memberId 单独）
- 按 account 分片 Map
- 一般不必上「冷用户不进本地」这类复杂策略

### 6.6 落地顺序建议

1. **Manager / 配置侧**：成员增删改、组解绑应用时发变更消息（带版本）
2. **ingester**：本地改为 `ConcurrentHashMap` 精确缓存；消费推送做 put/remove
3. **保留低频全量拉取**做启动加载与对账
4. **灰度**：双写一段时间（Bloom 与 Map 对比命中差异），再下线 Bloom
5. **监控**：Map size、推送延迟、对账差异数、全量耗时、拉取失败率

### 6.7 与现有组件对齐

会话回放用户组白名单已是「精确 Set + 推送」。用户组成员改为同一范式后：

- 一致性模型统一
- 排障路径统一
- 减少「一种能删、一种不能删」的认知负担

### 6.8 推荐方案优缺点深度分析

本节专门评估 **「精确 `member→group` Map + 变更推送」** 相对当前 Bloom 方案，以及落地时自身引入的收益与代价。

#### 6.8.1 优点

**1. 删除 / 换组可真删、可立即生效（核心收益）**

- `ConcurrentHashMap.remove(key)` / `put` 覆盖即可，不依赖 Bloom 重建
- 配合推送，各 ingester 实例可在秒级（消息到达延迟）内与配置侧对齐
- 不再把「删除正确性」绑在凌晨 1 点全量上，产品预期与实现一致

**2. 正确性从近似变为精确**

- 无假阳性、无假阴性（在缓存已同步的前提下）
- 消除「错绑用户组 → 会话筛选/回放白名单误伤」类问题
- 一用户一应用一条映射时，结果确定，不再受 `HashSet` 遍历顺序影响

**3. 热路径性能通常更好、更稳**

| 对比项 | 当前 Bloom | 精确 Map |
|--------|------------|----------|
| 查询复杂度 | O(该应用下组数) × Bloom 探测 | O(1) 一次 get |
| 组很多时 | CPU 随组数线性涨 | 与组数无关 |
| 锁/网络 | 无 | 无 |

Upload 主路径仍纯内存，不引入 DB/Redis，满足原性能约束。

**4. 内存按真实关系伸缩，避免「小组也按 200 万预分配」**

- Bloom：成本近似 `组数 × 满配过滤器`
- 精确 Map：成本近似 `关系条数 × (key + value)`
- 大量「小组 / 多组」场景下，精确 Map **往往更省**；只有「极少组、每组近千万成员且可接受误判」时 Bloom 才更占优

**5. 与现有 Setting 推送范式统一**

- 可复用 `AbstractSetting` / `RuleSetting` 一类通道（参考 `TerminalUserGroupSetting`）
- 运维、排障、灰度经验可迁移，降低「两套缓存哲学」的长期成本

**6. 运维语义更清晰**

- 缓存内容可枚举、可对账（Map 可遍历 diff；Bloom 难以列出成员）
- 监控指标直观：size、put/remove QPS、推送延迟、对账差异条数
- 出问题时可回答「这个用户现在绑的是哪组」，Bloom 做不到精确回答

**7. 全量拉取降级为兜底，日常压力更小**

- 日常增删改走推送，不必每 5 分钟用「日切大窗口」反复扫库
- 日全量从「正确性救命绳」变为「对账保险」，失败影响面更小（短暂漂移而非整天错绑）

**8. 扩展批量变更更自然**

- 换组、解绑应用、删组：可用明确事件 +（可选）反向索引批量 `remove`
- 不必发明 tombstone / Counting Bloom 等补丁结构

#### 6.8.2 缺点与风险

**1. 内存随关系数线性增长（上限风险）**

- 超大租户、千万级 `member×app` 关系时，精确 Map 的对象头、字符串 key 会明显占堆
- 相对「高度压缩的 Bloom 位图」，在 **单组极大且可接受误判** 的极端场景，Bloom 仍可能更省
- **缓解**：key 编码压缩、按 account 分片、堆监控告警、超大户专项评估；一般不必一上来上多级缓存

**2. 强依赖推送通道的可用性与时效**

| 风险 | 影响 |
|------|------|
| 消息丢失 | 局部缓存与 DB 不一致，直到对账修复 |
| 推送延迟 / 积压 | 「立即生效」退化成秒～分钟级 |
| Broker / 配置中心故障 | 变更暂时推不出去（查询仍可用旧缓存） |
| 消费端 bug | 单实例落后于集群 |

- **缓解**：消息幂等 + 版本号；ACK/重试；定期对账；推送失败告警；启动全量兜底
- 本质是用「推送复杂度」换「删除时效」，运维面比纯定时拉更大

**3. 乱序与并发变更需要版本协议**

- 先发的 DELETE 晚到、后发的 ADD 先到 → 可能误删新关系
- 必须在载荷中带 `version` / `update_time`，本地仅接受「更新」的变更
- 增加配置侧发数与 ingester 消费的协议设计成本（Bloom 拉取模型几乎无此问题）

**4. 整组 / 解绑应用删除需要反向索引或扫全表**

- 仅有 `member→group` 正向 Map 时，`UNBIND_APP(appId, groupId)` 要扫全 Map 才能清干净 → 大缓存下昂贵
- 若维护 `group→members` 反向索引：删除快，但 **双写内存约再增一截**，且要保证与主索引一致
- 这是精确方案相对 Bloom「按组一把过滤器扔掉」的额外设计点

**5. 改造面跨模块，一次性成本高于调参**

涉及大致：

- 配置写入路径（rum-core / 控制台保存用户、用户组、应用绑定时发事件）
- Manager 或 Setting 下发通道（新 SettingEnum / 消息体）
- ingester 缓存重写（Map 替换 Bloom、消费 put/remove）
- 启动全量与对账任务、监控、灰度双读

比「只改 Bloom 参数 / 加 tombstone」工作量大，需要排期与回归（Upload、回放过滤、会话列表用户组）。

**6. 启动与全量对账仍有尖峰**

- 进程冷启动仍需拉取全量关系构建 Map，耗时与瞬时内存与关系规模正相关
- 对账全量若用「整表替换」，需注意替换瞬间的内存双份（可分片替换或先 diff 再改）
- 推送不能替代「首次加载」

**7. 批量导入场景可能打爆推送**

- 一次导入数万成员若逐条推送，易造成消息风暴与消费滞后
- **缓解**：批量事件（一条消息带成员列表）、导入完成后发「组级失效 + 触发增量/全量拉取」、限流

**8. 产品若允许「同应用多组」，单值 Map 表达力不足**

- 当前推荐结构假设：同一 `appId + accountId + memberId` **至多一个 groupId**
- 若业务允许一人多组：需改为 `Map<key, Set<groupId>>` 或主组 + 次组策略，内存与查询语义都更复杂
- 落地前需与产品确认唯一性约束（配置侧最好强校验）

**9. 一致性模型从「定时拉」变为「推送 + 对账」双路径**

- 好处：日常更快；坏处：两套机制都要正确，对账逻辑写不好会引入「推送已删、对账又加回」等 bug
- 需要明确优先级：例如「对账以 DB 为准覆盖本地」或「仅修复推送空洞」，并做好审计日志

**10. 多实例之间仍是最终一致（秒级），不是强一致事务**

- 推送到达各实例时间可能差几百毫秒～数秒
- 极端情况下，极短窗口内不同 ingester 写入的 `user_group_id` 可能不同
- 相对「天级错误」已可接受；若业务要求跨实例强一致，需外部协调（成本高，通常不必要）

#### 6.8.3 优缺点对照小结

| 维度 | 相对当前 Bloom | 说明 |
|------|----------------|------|
| 删除时效 | **明显更好** | 真删 + 推送，秒级 |
| 正确性 | **明显更好** | 无假阳性 |
| Upload 性能 | **持平或更好** | O(1)，组多时更优 |
| 内存（常见：多组/中小规模） | **往往更好** | 按真实关系，无满配浪费 |
| 内存（极端：单组近千万+） | 可能更差 | 需专项评估 / 压缩 key |
| 工程复杂度 | **更高** | 推送协议、版本、对账、跨模块改造 |
| 运维依赖 | **更高** | 依赖消息通道；需监控推送与对账 |
| 可观测 / 可对账 | **更好** | Map 可 diff、可排查单用户 |
| 与现有 Setting 体系 | **更一致** | 对齐回放用户组配置模式 |

#### 6.8.4 适用结论

| 判断 | 建议 |
|------|------|
| 删除/换组要准、要快；关系规模在百万～千万以内可接受堆占用 | **优先采用精确 Map + 推送** |
| 短期只能小改、且可暂时容忍假阳性 | 先上 Tombstone 过渡，再迁 Map |
| 已确认存在单租户远超堆预算的关系量，且可接受误判 | 评估「热点精确 + 长尾 Bloom」混合，或压缩 key / 分片；不宜简单退回纯日全量 Bloom |
| **事前无法确定各客户量级（常见）** | **不要全站锁死单一方案**；采用「默认精确 + 账号级降级」，详见 **§7** |

**一句话**：推荐方案用「可枚举的精确状态 + 事件驱动更新」换掉「不可删的近似过滤器 + 日历式全量」，在多数 RUM 用户组规模下能同时拿到正确性、删除时效和热路径性能；主要代价是 **推送与对账的工程/运维复杂度**，以及超大规模下的 **堆内存线性增长** 需要提前度量。量级未知时的完整权衡见 **§7**。

## 7. 客户数据量级不确定时的权衡策略

### 7.1 为什么不能「二选一拍脑袋」

真实交付里，**事前往往无法确定**各客户的用户组关系规模：

| 客户类型 | 典型特征 | 对方案的压力点 |
|----------|----------|----------------|
| 小客户 / 试用 | 组少、成员少（千～万级关系） | 满配 Bloom **浪费内存**；精确 Map 更合适 |
| 中型客户 | 十万～百万级关系 | 两种都能扛；差异主要在正确性与删除时效 |
| 超大客户 | 单账号千万级 `member×app` 关系 | 精确 Map **堆线性涨**可能触顶；Bloom 省内存但删不掉、有误判 |

若全站只选一种：

- **全站 Bloom**：小客户吃亏（内存浪费 + 删除慢 + 假阳性），大客户「能跑」但产品体验差
- **全站精确 Map**：小/中客户体验最好；遇上超大户可能把 ingester 堆打满、启动全量拖死

因此权衡目标不是「永远选推荐方案」或「永远保留原方案」，而是：

> **在默认保证正确性与删除时效的前提下，用可观测的规模信号做分级/降级，避免未知大户把集群拖垮。**

### 7.2 先对齐不可妥协项与可妥协项

在量级未知时，先把需求拆成「必须」和「可降级」：

| 诉求 | 建议态度 | 说明 |
|------|----------|------|
| Upload 热路径不查库 | **必须** | 原方案与推荐方案都能满足 |
| 删除/换组尽快生效 | **默认必须**；超大户可降级 | 产品强诉求；仅极端规模才允许拉长窗口 |
| 无假阳性（绑组正确） | **默认必须**；超大户可降级 | 影响筛选/回放；降级需产品知情 |
| 单实例内存上限 | **必须有预算** | 例如每 ingester 用户组缓存 ≤ X GB |
| 实现简单、零推送 | 可妥协 | 量级未知时，纯简单方案往往用正确性/时效换运维省心 |

**原则**：不要用「客户可能很大」作为理由，长期停留在「全站不可删 Bloom」；应默认走精确路径，并为超大户准备 **显式降级**，而不是让所有客户陪跑最差体验。

### 7.3 用「关系条数」而不是「用户数」做度量

决策指标建议统一为：

```text
relation_count ≈ COUNT(用户组关系扁平行)
              = 有应用绑定的 (accountId, appId, memberId, groupId) 条数
```

不要只看「用户数」或「组数」：

- 1 个用户 × 10 个应用绑定 ≈ 10 条关系（精确 Map 按条计费）
- 100 个组 × 每组按 200 万预分配 Bloom ≈ 与真实成员数无关的内存（原方案按组计费）

**建议在 Manager 侧提供可查询指标**（控制台或运维接口）：

- 全局 / 按 `accountId`：`relation_count`、`group_count`、`app_bind_count`
- 单组最大成员数、单账号最大关系数
- ingester 上报：本地 Map size、估算堆占用、是否已降级

没有度量，就无法在原方案与推荐方案之间做动态权衡。

### 7.4 三级策略（推荐作为默认架构）

在量级不确定时，**不要静态二选一**，采用「默认精确 + 超阈降级」：

```text
                    ┌─────────────────────────────┐
                    │  变更推送（所有规模共用）      │
                    │  ADD/UPDATE/DELETE 事件     │
                    └─────────────┬───────────────┘
                                  │
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        【L1 精确层】        【L2 精确层】        【L3 降级层】
        小/中账号            大账号但仍低于预算    超预算账号
        全量进 Map           全量进 Map            见下方降级选项
        删除秒级             删除秒级              正确性/时效降级
```

| 层级 | 触发条件（示例，需按堆预算标定） | 存储 | 删除生效 | 正确性 |
|------|----------------------------------|------|----------|--------|
| **L1 默认** | 单账号关系数 < T1（如 200 万） | 精确 Map | 推送秒级 | 精确 |
| **L2 观察** | T1 ≤ 关系数 < T2（如 800 万） | 精确 Map + 压缩 key / 分片；加强监控 | 推送秒级 | 精确 |
| **L3 降级** | 关系数 ≥ T2，或进程用户组缓存超堆预算 | 见 §7.5 降级菜单 | 按所选方案 | 可能近似 |

说明：

- **T1/T2 必须用压测与线上采样标定**，上表数字仅为量级示意，不能直接当生产阈值
- 分级建议按 **`accountId`（主账号）** 隔离：一个超大户降级，不影响其他客户仍走精确 Map
- **推送通道建议始终建设**：即便 L3 降级到 Bloom，DELETE 也可先走 tombstone，避免再退回「只能等凌晨全量」

### 7.5 超大户降级菜单（L3 选项权衡）

当某账号突破预算时，在「原方案能力」与「推荐方案能力」之间按产品容忍度选择：

| 降级选项 | 做法摘要 | 内存 | 删除时效 | 正确性 | 适用 |
|----------|----------|------|----------|--------|------|
| **A. 精确 Map + 强压缩** | 短 key、原始类型、必要时 off-heap/分片 | 中 | 秒级 | 精确 | 刚超阈值、仍想保正确性 |
| **B. 精确 Map + Tombstone 优先** | 仍以 Map 为主；内存告警时限制新 put，删除仍 remove | 中 | 秒级 | 精确（可能拒收新增） | 保删除，暂缓扩张 |
| **C. 混合：热点精确 + 长尾 Bloom** | 最近活跃 member 进 Map；冷数据进 Bloom | 中低 | 热点秒级；冷数据弱 | 热点精确；冷近似 | 活跃集远小于全量 |
| **D. 账号级 Bloom + Tombstone** | 接近原方案，但删除靠 tombstone 推送 | 低 | 秒级（盖住） | 近似 | 内存最紧、可接受误判 |
| **E. 回退纯 Bloom + 日全量** | 等同当前原方案 | 低（相对满配仍看组数） | 差（天级） | 近似 | **不推荐**；仅作应急 |

**量级未知时的推荐排序**：默认 L1/L2（精确）→ 超限优先 **A/B** → 仍不够再 **C** → 最后 **D**；尽量避免 **E**。

混合方案（C）示意：

```text
getGroupId:
  1. exactMap.get(key) 命中 → 返回（含显式 null 标记可选）
  2. 若账号处于 L3-Bloom 模式 → bloom.mightContain 路径
  3. 都未命中 → null

DELETE 推送:
  exactMap.remove(key)
  deletedTombstone.add(key)   // 盖住 Bloom 假阳性/旧成员
```

代价：实现与排障复杂度高于「单一 Map」；应用前需确认「冷用户绑错组」的业务可接受度。

### 7.6 原方案 vs 推荐方案：在不确定量级下的决策矩阵

| 问题 | 偏原方案（Bloom 拉） | 偏推荐方案（Map + 推送） | 不确定时的折中 |
|------|----------------------|---------------------------|----------------|
| 会不会有超大户？ | 「有」就不敢上 Map | 「有」也先上 Map，超限再降级 | **默认 Map + 账号级降级** |
| 删除是否强诉求？ | 弱才可留 Bloom | 强则必须 Map/Tombstone | 推送必须建；存储可降级 |
| 能否接受假阳性？ | 可接受才用纯 Bloom | 不可接受则禁止纯 Bloom | 大户降级需产品签字 |
| 堆预算是否清晰？ | 无预算时容易盲目选 Bloom | 无预算时 Map 有爆堆风险 | **先定每进程预算，再定 T1/T2** |
| 工程能否做推送？ | 不做推送则删不掉 | 推送是推荐方案前提 | 推送优先落地；存储形态可分档 |
| 多租户是否隔离？ | 全局一种结构 | 可按账号分结构 | **按 accountId 分级（强烈建议）** |

### 7.7 「先度量、再切换」的落地节奏（适合量级未知）

避免一上来全量替换或长期不动：

```text
阶段 0  度量
        - Manager 统计各账号 relation_count 分位数（P50/P95/P99/Max）
        - 抽样估算：精确 Map 每条关系字节数 × P99 → 是否撑得住

阶段 1  基建
        - 上线变更推送（ADD/UPDATE/DELETE）+ 版本号
        - 即便暂时仍写 Bloom，DELETE 也可先打 tombstone（改善删除）

阶段 2  默认精确
        - 新缓存以 Map 为主；全量启动加载
        - 对 P95 以下账号关闭 Bloom 路径

阶段 3  护栏
        - 配置 T1/T2、进程级内存水位
        - 超限账号自动进入 L3（A→D 按策略）并告警

阶段 4  收敛
        - 观察超限账号占比；若长期为 0，删除 Bloom 分支降复杂度
        - 若总有超大户，保留「账号级降级」作为正式能力
```

这样即使 **事前不知道** 客户有多大，也能用 P99 与水位做权衡，而不是赌「都不大」或「都很大」。

### 7.8 内存粗算方法（用于标定阈值）

精确 Map（量级估算，非精确 JVM 值）：

```text
map_bytes ≈ relation_count × (key_bytes + 16~24 的 value/入口开销)
key_bytes ≈ 字符串 "appId_accountId_memberId" 长度 × 2（UTF-16）+ 对象头
```

示例（仅示意）：

| 关系数 | 假设每条 80～150B | 单进程粗算 |
|--------|-------------------|------------|
| 100 万 | ~80～150 MB | 通常可接受 |
| 500 万 | ~400～750 MB | 需看堆与其他缓存 |
| 2000 万 | ~1.6～3 GB | 多数进程需降级或压缩/分片 |

原方案 Bloom：

```text
bloom_bytes ≈ group_count × size_of(Bloom(n=200万, p=0.03))
```

与 `relation_count` 弱相关、与 **组数** 强相关 → 组多的中小客户可能 **Bloom 更亏**，单组极大客户可能 **Bloom 更省**。

**权衡动作**：用现网 `group_count` 与 `relation_count` 分位数各算一遍，看「若全站 Map」与「若全站 Bloom」谁在 P99 账号上更危险，再定默认路径与降级阈值。

### 7.9 产品与交付话术（避免期望错位）

量级不确定时，建议对内对外统一表述：

1. **默认能力**：用户组绑定精确匹配，删除/换组近实时生效（精确 Map + 推送）
2. **容量护栏**：单账号关系数或缓存内存超过阈值时，系统可降级该账号的存储策略，并告警
3. **降级后果**（若走到 Bloom/混合）：可能出现极低比例误绑；冷数据删除时效依赖 tombstone/对账——需在合同/产品说明中可选披露
4. **不承诺**：在未计量的前提下，不承诺「任意客户任意规模均为精确 + 秒级且内存无上限」

### 7.10 本节结论

| 错误做法 | 正确做法 |
|----------|----------|
| 因「可能有大客户」而全站锁死原 Bloom 方案 | 默认推荐方案；大户账号级降级 |
| 因「推荐方案更好」而全站无护栏上 Map | 先度量分位数 + 进程内存水位 |
| 静态二选一、永不调整 | 推送统一建设；存储按规模 L1/L2/L3 |
| 无指标凭感觉调 T1/T2 | 用 relation_count / 堆占用标定 |

**一句话**：量级不确定时，权衡的不是「原方案 or 推荐方案」的口号，而是 **「推荐方案做默认，原方案能力（Bloom/近似）做超限降级」**；用账号级规模信号与内存护栏，在正确性、删除时效与爆堆风险之间取得可运营的平衡。

## 8. 过渡方案：Bloom + Tombstone（短期）

若短期不能替换 Bloom，可用删除旁路盖住旧命中：

```text
查询 getGroupId：
  1. 若 (appId, accountId, memberId) 在 deletedSet → 直接视为无组（或跳过旧 group）
  2. 再走现有 Bloom 逻辑

删除推送 / 感知到删除：
  deletedSet.add(key)
  （Bloom 内旧元素暂留，靠 tombstone 盖住）

换组：
  deletedSet 处理旧关系 + 新关系 put 进 Bloom（或旁路精确 put）

全量重建成功后：
  清空 deletedSet（或按版本裁剪）
```

| 优点 | 缺点 |
|------|------|
| 改动相对小 | 仍依赖推送维护 tombstone |
| 删除可立即「对外生效」 | 假阳性仍在 |
| | 换组逻辑更绕 |
| | 长期仍建议迁精确 Map |

Counting Bloom / Cuckoo Filter 等可删结构：实现重、仍是近似，**一般不如精确 Map + 推送干净**。

## 9. 不建议的做法

| 做法 | 原因 |
|------|------|
| 删除后热路径回源 DB/Redis | Upload QPS 下延迟与依赖风险大 |
| 仅缩短增量窗口，仍用不可删 Bloom | 删不掉，无法真正「立即生效」 |
| 全量改为每 5 分钟 | 能近似纠正，但 Manager/DB 与刷新线程压力大，且仍有分钟级窗口 |
| 继续调低 p 但不解决删除 | 只改善误绑，不解决删除时效 |
| 因「可能有大客户」全站锁死 Bloom，或因「推荐更好」无护栏全站 Map | 量级未知时应 **默认精确 + 账号级降级**（见 **§7**），避免静态二选一 |

---

## 10. 方案对比总表

| 方案 | 删除时效 | 正确性 | 热路径性能 | 内存 | 改造成本 | 量级未知时的角色 |
|------|----------|--------|------------|------|----------|------------------|
| 当前 Bloom + 日全量 | 最长约 1 天 | 近似（假阳性） | 优 | 大组有优势，小组/多组易浪费 | — | 仅作应急，不作默认 |
| Bloom + Tombstone + 推送 | 秒级（盖住） | 仍近似 | 优 | 同 Bloom + tombstone 开销 | 中 | 超大户 L3 降级选项之一 |
| **精确 Map + 推送（推荐）** | **秒级（真删）** | **精确** | **优（O(1)）** | **按真实关系，通常更可控** | 中～高 | **默认路径（L1/L2）** |
| 精确 + 账号级 Bloom/混合降级 | 默认秒级；降级账号见策略 | 默认精确；降级可近似 | 优 | 有护栏，防爆堆 | 高 | **量级不确定时的推荐架构** |
| 热路径查 DB/Redis | 即时 | 精确 | 差/依赖中间件 | 本地小 | 低～中（但违背约束） | 不采用 |

---

## 11. 综合结论

1. **当前设计**面向高 QPS 入库，用「应用维度索引 + 组内 Bloom」换取零查库，方向合理，但正确性与删除时效偏弱。
2. **删除不能立即生效**的根因是 Bloom 不可删 + 增量只增不删 + 全量依赖凌晨 1 点。
3. **推荐**：改为 **精确 `member→group` 映射 + 配置变更推送**；定时拉取仅作启动与对账。这通常能同时满足「删除立即生效」和「不大压性能/内存」，并消除假阳性。
4. **推荐方案代价**：推送通道依赖、版本乱序处理、整组删除的反向索引、跨模块改造与超大规模下的堆线性增长（详见 **§6.8**）。
5. **量级不确定时的权衡**（详见 **§7**）：不要静态二选一；**默认精确 Map + 推送**，按账号 `relation_count` 与进程内存水位做 L1/L2/L3；超限再降级到压缩 Map / 混合 / Bloom+Tombstone，避免小客户陪跑 Bloom、大客户打爆堆。
6. **过渡**：Bloom + tombstone 可快速改善删除观感，也可作为 L3 降级手段，但全站纯 Bloom + 日全量不应作为终态。
7. **配套**：产品侧确认「同应用用户唯一组」、推送幂等与对账策略、关系数分位数度量、T1/T2 与堆预算标定、监控（Map size / 推送延迟 / 对账差异 / 降级账号数）。
