## 1. 概述

本文档梳理 RUM 模块中「有效会话数」和「活跃设备数」两个核心指标的概念定义、入库规则、预聚合公式及查询层映射，并说明两者之间的区别与联系。同时补充「无效会话」在各层次的判断逻辑，以及会话满意度分类（异常/可容忍/满意）的完整规则。

### 1.1 给产品评审会直接使用的 5 句摘要

1. 探针会先通过 `config` 接口拿到会话 ID，并在后续每次 `upload` 时持续携带这个 session。
2. 但平台**不会**因为"这次 upload 带了 session"就直接把它算成一个有效会话。
3. 只有当这个 session 下出现了被平台认定为"有效事件"的数据，如启动、操作、崩溃、ANR、卡顿、JS 错误，或满足会话接入条件的页面/H5/路由等事件时，这个 session 才会被激活为有效会话。
4. 纯网络汇总、上传动作本身、以及未满足会话接入条件的部分页面/链路事件，虽然可能带有 session，但不会贡献有效会话数。
5. 因此，**有效会话数的本质不是 session 总数，而是"被有效事件激活过的 session 去重数"**；同一台设备在一天内可以产生多个有效会话，所以活跃设备数通常小于或等于有效会话数。

## 3. 有效会话数

### 3.1 概念定义

「有效会话」是指在 RUM 数据采集链路中，被明确标记为**对会话统计有效**的终端事件所关联的会话。其核心判定标准是：终端聚合行的 `effective_session_num_uniq12` 字段是否被写入了合法的 `sessionId`。

- 有效会话数 = 在给定时间范围和过滤条件下，`effective_session_num_uniq12` 字段非空的终端行中，对 `sessionId` **去重**后的数量。
- 与「总会话数」（`sessionCount`，依赖 `session_id_uniq12`）的区别在于：总会话数覆盖所有携带 `session_id` 的终端行，不区分该事件是否属于有效会话语境；有效会话数仅统计经过有效性判定的会话。

### 3.1.1 数据入库前的判断链路

文档前文主要描述了 `TerminalResultBuild` 对 `effectiveSessionNumUniq12` 的直接赋值规则，但从代码实现看，「某条数据是否有资格在 terminal 行中贡献有效会话」的判断其实在更上游就已经开始了，整体链路如下：

```
事件进入策略类
    ↓
dataClean / modelConvert 过滤非法事件
    ↓
flatten 阶段构造子级 ServiceModel，透传 parentHasSession / pEventType / viewSkipToSession
    ↓
各事件策略计算 hasSession / sessionFlag / route status / span socket 条件
    ↓
TerminalResultBuild 决定是否写入 effectiveSessionNumUniq12
    ↓
CkResultModelWrapper 根据 uniq12 双写配置决定是否保留该字段
```

各关键环节如下：

| 环节 | 关键代码 | 对有效会话的影响 |
|------|----------|------------------|
| 事件清洗 | 各策略类 `dataClean()` | 若事件在清洗阶段被过滤，则后续不会生成 terminal 行，自然不可能贡献有效会话 |
| 父子会话透传 | `ServiceModel.getSubBaseServiceModel(...)` | 把父事件的 `hasSession` 结果写入子节点的 `parentHasSession`，作为后续判断输入 |
| Launch / Action 子树特殊处理 | `LaunchEventStrategy.flatten()`、`ActionExitEventStrategy.flatten()` | 两者都会把子级 `ServiceModel.viewSkipToSession` 置为 `true`，影响下游 View/MpView 的 `hasSession` 判定 |
| View / MpView 会话门控 | `HasSessionWrapper` | 按 `!viewSkipToSession && parentHasSession && 父事件类型 != LAUNCH_EVENT` 计算 `hasSession`，并进一步导出 `subHasSession`、`usedParentPId` |
| View terminal 前置标记 | `ViewResultZeusConvert.setSessionFlag()` | 先把 `hasSession` 转成 `sessionFlag`，随后 `buildViewResult()` 只认 `sessionFlag == 1` |
| H5 / Route / Span 事件 | 对应策略类各自计算 `hasSession` | H5 直接取 `parentHasSession`；Route 取 `event.status == 0`；Span 除了要求 `parentHasSession` 之外，还会对 websocket/socket 与 `pid` 做额外判断 |
| Terminal 最终赋值 | `TerminalResultBuild.build*()` | 这里才真正决定是否调用 `setEffectiveSessionNumUniq12(...)` |
| 入库前技术性处理 | `CkResultModelWrapper.dealUniq12()` | 若系统处于 `uniq12Type=1` 或双写时间窗外，`effectiveSessionNumUniq12` 可能会被置空；这是存储兼容逻辑，不属于业务层"无效会话" |

### 3.1.2 文档容易遗漏的前置门槛

以下判断发生在 `TerminalResultBuild` 之前，建议与"入库规则"区分理解：

1. `ViewEventEnterStrategy.buildGranResult()` 中，**自定义视图**和 **H5 类型视图**会直接 `return Collections.emptyList()`，不生成 VIEW/TERMINAL 行；因此它们不是"terminal 行生成后未写有效会话"，而是**根本不进入该条入库链路**。H5 的有效会话统计来自独立的 H5 策略链，而不是 View enter 链路。
2. `UploadEventStrategy.buildGranResult()` 当前直接返回空列表，虽然 `TerminalResultBuild` 中保留了 `buildUploadCommonResult()` 方法，但**当前代码路径并不会生成上传类 terminal 行**。
3. 代码中并未看到一层统一的 `sessionId isNotBlank` 强校验后才允许写 `effectiveSessionNumUniq12`；多数场景是先通过事件类型、父子关系和 `hasSession` 规则判定，再直接写入上游携带的 `sessionId`。

### 3.1.3 面向产品经理的完整逻辑说明

这一节不从代码类名出发，而是从"探针怎么拿到 session、怎么上传、平台最后怎么算有效会话"三个问题来解释。

#### 一句话结论

**有效会话数不是"上传过 session 就算 1"，而是"上传过 session 且该 session 下至少出现过一类被平台认定为有效的事件，才算 1"。**

换句话说：

```
先有 session
    ↓
session 内上报一批事件
    ↓
平台判断这些事件里，是否至少有一条属于"可计入有效会话"的事件
    ↓
如果有，则该 session 计入有效会话数
如果没有，则该 session 只是"存在过"，但不算有效会话
```

#### 1. 探针先通过 config 拿到会话，再带着会话去 upload

根据《客户端探针 config&upload 完整协议》：

- 探针请求 `config` 后，服务端会在 `ConfigResponse.s` 中下发当前会话 ID；
- 同一次 config 响应里，还会下发 `sc` 会话配置：
  - `it`：无操作多久切换新会话；
  - `mst`：单个会话最长可持续多久；
- 后续探针发 `upload` 时，URL 参数和请求体里都要求带 `s`（session）；
- 若发生"**崩溃先于 config 响应**"这种极端场景，协议允许探针自己先构造一个 `br:uuid` 格式的 session 继续上报。

这说明从协议层看，**session 是 upload 的基础字段**，绝大多数事件在进入平台时，天然都挂在某个 session 下面。

#### 2. 一个 upload 中的事件，默认都属于同一个 session

在 upload 协议里：

- `UploadRequest.s` 表示这次上传所属的会话；
- `UploadRequest.e[]` 是这次上传携带的事件集合；
- 每条事件有自己的类型（如 `view`、`launch`、`action`、`h5`、`routechange`、`jserror`、`crash`、`anr`、`lag`、`span` 等），但**不再单独重新定义一个新的 session**。

从产品视角可以把它理解成：

> 一次会话期间，探针会持续采集很多事件，分多次 upload 上传；这些 upload 只要带的是同一个 `s`，平台就认为它们属于同一场会话。

因此，**有效会话数的核心不是"有没有 upload"**，而是"这个 session 上传进来的事件里，有没有命中有效事件口径"。

#### 3. 平台不会把所有带 session 的数据都算成有效会话

这是最容易和产品口径混淆的地方。

协议层只解决了"**这批数据属于哪个 session**"的问题；但业务指标层还要进一步解决"**这个 session 值不值得计入有效会话**"的问题。

代码里的实际处理逻辑可以概括为两类：

| 事件类型 | 产品理解 | 是否容易计入有效会话 |
|----------|----------|----------------------|
| 启动、操作、崩溃、ANR、卡顿、JS 错误、自定义有效事件 | 这些事件本身就代表用户真实使用、真实故障或关键行为 | **基本直接计入** |
| 视图、H5、路由、小程序视图、Span | 这些事件是否计入，要看它是否处在"允许挂会话"的上下文里 | **需要额外判断** |
| 纯网络汇总、网络资源汇总 | 更像性能统计明细，不直接代表一次有效会话行为 | **不计入** |
| upload 事件本身 | 只是"上传动作"，不是用户行为 | **当前代码不计入** |

所以，**"会话存在"不等于"有效会话成立"**。

#### 4. 为什么有些视图/页面事件不算有效会话

对页面类、路由类、H5 类、Span 类事件，平台不是一律计入，而是会先判断"这个事件是否应该接入会话"。

产品上可以理解为平台在过滤两类噪声：

1. **不是用户真实会话上下文中的页面/请求**
   - 比如父级链路本身就没有会话语义；
   - 比如某些事件只是附属技术事件，不适合代表一次真实会话。

2. **虽然有 session，但不应该拿来代表有效会话的技术明细**
   - 比如纯网络汇总；
   - 比如 websocket/socket 类型 span；
   - 比如 upload 自己这类后台传输动作。

对应到代码里，页面类事件要经过 `hasSession` / `sessionFlag` 判断后，才会把 `sessionId` 写入 `effective_session_num_uniq12`。如果没通过，就算该数据带着 session 上传进来了，也**不会**给有效会话数加 1。

#### 5. 从产品口径看，真正计数的瞬间发生在"terminal 行写入有效会话字段"

后端收到 upload 后，不是直接拿 upload 请求里的 `s` 去统计，而是会把每种事件拆解成内部的统计行。

只有当某条 terminal 聚合行满足条件，并把：

```text
effective_session_num_uniq12 = sessionId
```

写进去时，这个 session 才算获得了"参与有效会话数去重统计"的资格。

后续查询的有效会话数，本质上就是：

> 在统计周期内，把所有写进 `effective_session_num_uniq12` 的 sessionId 去重后的结果。

因此从产品语言说：

- `config/upload` 协议负责**把 session 带到平台**；
- ingester 规则负责**判断哪些事件有资格代表一次有效会话**；
- 指标聚合负责**把这些 session 做去重计数**。

#### 6. 为什么一个设备会产生多个有效会话

协议中 `ConfigResponse.sc` 明确支持会话切换控制：

- `it`：长时间无操作后切换新会话；
- `mst`：超过最大时长后切换新会话。

所以对同一台设备来说：

- 设备 ID 可能始终不变，因此活跃设备数通常只算 1；
- 但只要会话超时、自动切换，或者用户再次进入形成新 session，就可能产生多个 session；
- 这些 session 中，只要分别都出现过有效事件，就会分别计入有效会话数。

这也是为什么通常会出现：

```text
活跃设备数 <= 有效会话数
```

因为同一设备在一天内完全可能产生多个有效 session。

#### 7. 适合产品经理记忆的最终口径

可以把"有效会话数"记成下面这句话：

> **探针先通过 config 获取会话，并在 upload 中持续携带该会话；平台收到这些事件后，不是见到 session 就计数，而是只有当这个 session 下出现了被认定为"有效事件"的数据时，才把该 session 计入有效会话数。**

再进一步压缩成三个关键词：

```text
有 session
不等于
有效会话
```

真正的业务口径是：

```text
有效会话数 = 被有效事件"激活"的 session 去重数
```

### 3.2 `hasSession` 与 `sessionFlag` 的含义

在 ingester-rum 的入库链路中，有效会话的写入依赖两个关键标志：

#### 3.2.1 `hasSession`（是否接入会话）

由 `HasSessionWrapper` 类统一计算：

```java
// HasSessionWrapper.java
hasSession = !skipSession && parentHasSession
             && !(serviceModel != null && EventTypeEnum.LAUNCH_EVENT.equals(serviceModel.getPEventType()));
```

三个条件同时满足时，`hasSession = true`：

| 条件 | 含义 |
|------|------|
| `!skipSession` | 当前视图未配置「跳过会话」（`serviceModel.isViewSkipToSession() == false`） |
| `parentHasSession` | 父级服务/应用已开启会话接入（`serviceModel.isParentHasSession() == true`，或无 `serviceModel` 时默认为 `true`） |
| 父事件类型不是 `LAUNCH_EVENT` | 启动事件本身不触发子视图的会话计入 |

#### 3.2.2 `sessionFlag`（视图会话标志）

`sessionFlag` 是视图类数据（`ViewResultZeus`）中携带的字段，赋值逻辑为：

```java
// ViewResultZeusConvert.java
result.setSessionFlag(hasSession ? 1 : 0);
```

即 `sessionFlag = 1` 代表该视图处于会话接入语义下，`sessionFlag = 0` 表示未接入会话。

#### 3.2.3 `hasSession` / `sessionFlag` 与探针 upload 协议的对应关系

这是一个非常容易误解的点：

- 探针 **upload 协议里没有 `hasSession` 字段**；
- 探针 **upload 协议里也没有 `sessionFlag` 字段**；
- 探针真正上传的是 **原始会话 ID**，也就是 `UploadRequest.s`；
- `hasSession` 和 `sessionFlag` 都是 **ingester 在服务端解析 upload 后推导出来的内部语义字段**。

可以用下面这张表理解三者关系：

| 层次 | 字段 | 来源 | 含义 |
|------|------|------|------|
| 协议层 | `ConfigResponse.s` | config 响应 | 服务端下发给探针的当前会话 ID |
| 协议层 | `UploadRequest.s` | upload 请求 | 这次 upload 属于哪个 session；是所有后续判断的原始输入 |
| 协议层 | `ConfigResponse.sc.it/mst` | config 响应 | 控制探针何时切换新 session，决定 session 的边界，但**不直接等于** `hasSession` |
| 服务端语义层 | `hasSession` | ingester 计算 | 当前某条事件在平台内部是否"允许接入会话统计语义" |
| 存储层 | `sessionFlag` | `hasSession ? 1 : 0` 或直接赋值 | 入库时落在 Zeus/Snapshot/部分统计模型上的会话标志位 |

##### 1. 协议里的 `s` 是"原始 session"，不是 `hasSession`

在 upload 协议中：

- URL 参数有 `s`
- `UploadRequest` 请求体也有 `s`

它表示的是：**这批事件属于哪个会话**。

服务端收到 upload 后，会先做两步基础映射：

1. `UploadRequestConvert` 把协议里的 `s` 解析成 `UploadRequestEntity.session`
2. `DataFactory.buildCommonModel()` 再把这个值放到 `CommonModel.session`

从这一刻开始，后续所有事件若需要写 session，拿到的都是这份**原始 sessionId**。

但要注意：

> **有 `UploadRequest.s`，只说明"这个事件挂在哪个 session 下面"；并不说明"这个事件一定能参与有效会话统计"。**

##### 2. `hasSession` 是平台基于 upload 内容"二次判断"出来的结果

`hasSession` 不是探针上传的，而是平台根据 upload 中的这些信息推导出来的：

- `UploadRequest.s`：这批数据的原始 sessionId
- `Event.k`：事件类型（view、mpview、launch、action、h5、routechange、span 等）
- `Event.revts` / `revtt`：事件的父子/关联结构
- 当前事件上游链路是否已经具备会话语义（`parentHasSession`）
- 某些事件自身的业务状态，如：
  - route 的 `status == 0`
  - span 是否为 websocket/socket
  - span 是否存在 `pid`
  - view 链路是否被标记为 `viewSkipToSession`

所以从协议到服务端语义的关系是：

```text
UploadRequest.s
    ↓
说明"属于哪个 session"
    ↓
结合事件类型、父子关系、上游链路状态
    ↓
服务端推导出 hasSession=true/false
```

也就是说：

- `UploadRequest.s` 回答的是"**是谁**"
- `hasSession` 回答的是"**这个事件能不能按会话事件来算**"

##### 3. `sessionFlag` 是把 `hasSession` 落成可入库的标记

对视图类和部分快照类数据，平台不会把布尔值 `hasSession` 直接原样传下去，而是会转成整型标志位 `sessionFlag`：

```java
result.setSessionFlag(hasSession ? 1 : 0);
```

因此两者关系可以理解为：

```text
hasSession = 业务判断结果
sessionFlag = 入库表达形式
```

最典型的是：

- `ViewResultZeusConvert`：`sessionFlag = hasSession ? 1 : 0`
- `ViewSnapshotResultZeusConvert`：`sessionFlag = hasSession ? 1 : 0`
- `H5SnapshotResultZeusConvert`：`sessionFlag = hasSession ? 1 : 0`
- `RouteChangeEventStrategy` 构建快照时：`sessionFlag = model.isHasSession() ? 1 : 0`
- `SpanSnapshotResultZeusConvert`：`sessionFlag = hasSession ? 1 : 0`

随后 terminal 统计层再继续使用这个标记。例如页面视图 `buildViewResult()` 就不是重新算一次，而是直接看：

```text
sessionFlag == 1
```

决定是否写入 `effectiveSessionNumUniq12`。

##### 4. 为什么有些事件 `sessionFlag = 1`，但并不是来自协议字段

像启动、操作、崩溃、ANR、卡顿、JS 错误、状态变更、自定义有效事件这类数据，在快照侧通常会直接：

```text
sessionFlag = 1
```

原因不是探针协议里专门传了一个"该事件有效"的标志，而是平台在业务上默认把这些事件视为天然具备会话语义的关键事件。

因此要区分清楚：

- 协议上传的是 `sessionId`
- 平台判断的是 `hasSession`
- 入库存储的是 `sessionFlag`

三者不是同一个字段，只是前后衔接的三个层次。

##### 5. 最终可给产品和研发统一使用的口径

可以统一记成下面这句话：

> **探针 upload 协议只负责上传原始 session（`s`）；`hasSession` 是服务端根据事件类型和上下文推导出的"是否接入会话"的判断；`sessionFlag` 是这个判断在入库模型中的落地表达。**

再压缩成一条公式：

```text
UploadRequest.s（原始会话）
    + 事件类型/父子关系/链路上下文
    -> hasSession（服务端判断）
    -> sessionFlag（入库标志）
```

#### 3.2.4 `hasSession` 的完整判断逻辑

如果只看代码实现，`hasSession` 不是一个全局统一字段，而是一套**按事件类型分支执行**的判断规则。完整逻辑可以拆成四层：

##### 第一层：默认前提

平台先假设 upload 已经带来了原始 session（`UploadRequest.s`），然后再判断"当前事件是否允许按会话事件处理"。

在多数实现里，第一步都会先取：

```text
parentHasSession = (serviceModel == null) ? true : serviceModel.isParentHasSession()
```

含义是：

- 如果当前事件没有父级上下文（顶层事件），默认认为父级允许接入会话；
- 如果当前事件是某个父事件展开出来的子事件，则先继承父事件传下来的 `parentHasSession`。

所以，**`hasSession` 的判断起点不是固定 true/false，而是先看上游链路有没有把"会话资格"传下来。**

##### 第二层：父子事件如何传播 `hasSession`

父子传播由 `ServiceModel.getSubBaseServiceModel(...)` 完成：

- 父事件在创建子事件执行上下文时，会把自己当前的 `hasSession` 结果写到子级 `ServiceModel.parentHasSession`；
- 后续子事件在计算自己的 `hasSession` 时，再以这个 `parentHasSession` 为输入。

这意味着：

```text
父事件 hasSession = false
    ↓
子事件默认也很难再变成 true
```

除非该子事件走的是完全独立、不依赖父链路的业务分支。

##### 第三层：View / MpView 特有规则

页面视图和小程序视图不是直接看 `parentHasSession`，而是统一走 `HasSessionWrapper`：

```text
hasSession = !skipSession
          && parentHasSession
          && (父事件类型 != LAUNCH_EVENT)
```

这里三个条件缺一不可：

| 条件 | 含义 | 不满足时的结果 |
|------|------|----------------|
| `!skipSession` | 当前视图链路没有被标记为"跳过会话" | `hasSession = false` |
| `parentHasSession` | 父级链路本身允许接入会话 | `hasSession = false` |
| 父事件类型不是 `LAUNCH_EVENT` | 启动事件的直接子视图不按普通会话页面处理 | `hasSession = false` |

另外 `HasSessionWrapper` 还会给出两个衍生结果：

| 字段 | 逻辑 | 作用 |
|------|------|------|
| `subHasSession` | `skipSession ? parentHasSession : hasSession` | 决定子节点继续继承什么会话资格 |
| `usedParentPId` | `skipSession && parentHasSession` | 决定子节点是否沿用父 `pId` |

这也是为什么 `view/mpview` 的 `hasSession` 是整套逻辑里最复杂的一类。

##### 第四层：按事件类型分别判断

下面是当前代码里真正参与 `hasSession` 计算的完整分支：

| 事件类型 | `hasSession` 逻辑 | 说明 |
|----------|------------------|------|
| `view` | `!viewSkipToSession && parentHasSession && 父事件类型 != LAUNCH_EVENT` | 通过 `HasSessionWrapper` 统一计算 |
| `mpview` | 同 `view` | 也是 `HasSessionWrapper` |
| `h5` | `parentHasSession` | `H5EventDefaultStrategy` / `H5EventErrorStrategy` 中直接判断 |
| `webview error` | `parentHasSession` | 本质按 H5 语义处理 |
| `routechange` | `event.status == 0` | 正常路由切换才入会话；异常路由切换不入 |
| `span` | `parentHasSession && !(websocket/socket 且 pid == null)` | 父链路无会话则直接 false；socket/websocket 且无 `pid` 也 false |
| `network` 普通/错误快照 | `parentHasSession` | 只影响网络快照是否带会话标志 |
| `network resource` / `resource error` 快照 | 恒为 `false` | 资源类快照明确"不入会话" |

##### 各分支展开说明

1. `view` / `mpview`

这是最标准的 `hasSession` 判断场景：

```text
hasSession = !skipSession
          && parentHasSession
          && 父事件类型不是 LAUNCH_EVENT
```

补充说明：

- `LaunchEventStrategy` 会给子级 `ServiceModel` 设 `viewSkipToSession = true`；
- `ActionExitEventStrategy` 也会给子级 `ServiceModel` 设 `viewSkipToSession = true`；
- 所以 launch/action 子树下的 view/mpview，常常不会按普通页面事件那样直接拿到 `hasSession=true`。

2. `h5`

H5 的判断比 view 简单很多，代码等价于：

```text
hasSession = parentHasSession
```

即：

- 父级允许会话，则 H5 允许；
- 父级不允许，则 H5 也不允许。

它不再额外检查 `viewSkipToSession`，也不检查父事件是不是 `LAUNCH_EVENT`。

3. `routechange`

路由切换不看父级链路，而是直接看路由事件本身状态：

```text
hasSession = (status == 0)
```

即：

- 正常路由切换：`hasSession = true`
- 异常路由切换：`hasSession = false`

同时，这个结果也会继续作为子事件的 `parentHasSession` 往下传。

4. `span`

span 的完整逻辑可以写成：

```text
if (!parentHasSession) {
    hasSession = false
} else if (websocket/socket && pid == null) {
    hasSession = false
} else {
    hasSession = true
}
```

因此 span 失去会话资格的两种典型场景是：

- 它挂在一个已经没有会话资格的父链路下面；
- 它本身是 websocket/socket 类型，且没有 `pid`。

并且即便 `span.hasSession = true`，terminal 侧还要再过一层：

```text
!websocketOrSocket && hasSession
```

才会真正写入有效会话字段。也就是说，**socket/websocket span 在 terminal 侧本就不会贡献有效会话**。

5. `network` / `network error`

普通网络快照和错误网络快照中的 `hasSession` 判断都很简单：

```text
hasSession = parentHasSession
```

这类判断主要影响快照侧 `sessionFlag`，而不是有效会话指标本身；因为 terminal 的 `buildNetResult()` 本来就不写 `effectiveSessionNumUniq12`。

6. `network resource` / `resource error`

资源类快照明确写死为：

```text
hasSession = false
```

所以它们无论挂在哪条父链路下，都不会以会话事件的方式存储。

##### 哪些事件根本不走 `hasSession`

下面这些事件虽然会影响有效会话指标，但并不是通过 `hasSession` 判定的：

- `launch`
- `action`
- `crash`
- `selfCrash`
- `anr`
- `lag`
- `jsError`
- `buildEffectiveCommonResult`
- `buildStateEffectiveCommonResult`

这类事件的特点是：

- 要么 terminal 侧直接写 `effectiveSessionNumUniq12`
- 要么 snapshot 侧直接 `sessionFlag = 1`

因此它们属于"**天然具备会话语义的关键事件**"，而不是"先算 `hasSession`，再决定是否入会话"的场景。

##### 最终可落地成一句总公式

如果把所有分支抽象成统一表达，可以写成：

```text
hasSession
= 父链路是否允许会话
  × 当前事件类型自己的准入规则
```

其中"当前事件类型自己的准入规则"分别是：

- `view/mpview`：不跳过会话、父事件不是 launch
- `h5`：无额外规则
- `route`：必须 `status == 0`
- `span`：若是 websocket/socket，则必须有 `pid`
- `resource`：固定不入会话

所以，`hasSession` 的本质可以总结为：

> **它不是在判断"有没有 sessionId"，而是在判断"当前这条事件，是否有资格代表这个 session 参与会话语义和后续统计"。**

### 3.3 各事件类型入库规则

下表列出 `TerminalResultBuild` 中所有 `build*` 方法对 `effectiveSessionNumUniq12` 的写入规则：

| 事件类型 / 方法 | `effectiveSessionNumUniq12` 写入条件 | 备注 |
|---------------|--------------------------------------|------|
| 页面视图 `buildViewResult` | `sessionFlag == 1` 时写入 | 依赖 `ViewResultZeus.sessionFlag` |
| 小程序视图 `buildMpViewResult` | `hasSession == true` 时写入 | |
| Span（网络请求等）`buildSpanResult` | `!websocketOrSocket && hasSession` 时写入 | WebSocket/Socket 类型不写入 |
| 路由变更 `buildRouteResult` | `hasSession == true` 时写入 | |
| H5 `buildH5Result` | `hasSession == true` 时写入 | |
| 操作 `buildActionResult` | **始终写入** | 无条件关联会话 |
| JS 错误 `buildJsErrorResult` | **始终写入** | |
| ANR `buildAnrResult` | **始终写入** | |
| 卡顿 `buildLagResult` | **始终写入** | |
| 启动 `buildLaunchResult` | **始终写入** | |
| 原生崩溃 `buildCrashResult` | **始终写入** | |
| 自采集崩溃 `buildSelfCrashResult` | **始终写入** | |
| 有效事件 `buildEffectiveCommonResult` | **始终写入**，且 `eventNum = 1` | 专用于「有效事件」快照 |
| 状态有效事件 `buildStateEffectiveCommonResult` | **始终写入**，且 `eventNum = 1` | |
| 网络资源 `buildNetResourceResult` | **不写入** | 纯网络汇总行不贡献有效会话 |
| 网络汇总 `buildNetResult` | **不写入** | 纯网络汇总行不贡献有效会话 |
| 上传快照 `buildUploadCommonResult` | **当前代码路径不生成 terminal 行** | `UploadEventStrategy.buildGranResult()` 已直接返回空列表，方法保留但未被调用 |

**规律总结：**
- 崩溃、ANR、卡顿、启动、JS 错误、操作等**异常/质量类事件**无条件贡献有效会话，体现其业务重要性；
- 页面视图、小程序视图、Span、路由、H5 等**流量类事件**需要在会话接入语义下才贡献有效会话（`hasSession/sessionFlag` 判定）；
- 纯网络汇总行不贡献有效会话，但仍会写入 `device_id_uniq12`，影响活跃设备数；上传事件在当前代码下不生成 terminal 行，因此也不参与有效会话或活跃设备统计。

## 4. 活跃设备数

### 4.1 概念定义

「活跃设备」是指在给定时间范围和过滤条件下，上报了 RUM 事件数据的终端设备。活跃设备数 = 终端聚合行中 `device_id_uniq12` 字段的去重数量。

与有效会话数的关键区别：
- **无额外有效性限制**：不要求 `hasSession == true`，也不要求 `effectiveSessionNumUniq12` 有值；只要终端行携带了可聚合的 `device_id_uniq12`，就计入活跃设备。
- 即使是纯网络汇总行（`buildNetResult`/`buildNetResourceResult`）等不贡献有效会话的行，只要带有 `device_id_uniq12`，该设备仍会被计入活跃设备数。当前 `UploadEventStrategy` 不生成 terminal 行，因此上传事件不参与活跃设备统计。

## 5. 两个指标的对比

| 对比项 | 有效会话数 | 活跃设备数 |
|--------|-----------|-----------|
| **统计粒度** | 会话（`sessionId`）去重 | 设备（`deviceId`）去重 |
| **统计口径** | 被标记为「有效」的会话 | 上报任意事件的设备 |
| **入库条件** | 依赖事件类型和 `hasSession/sessionFlag` | 所有事件均写入，无额外条件 |
| **不计入场景** | 纯网络行、上传快照、未接入会话的视图类事件 | 无（所有事件均贡献活跃设备） |
| **典型用途** | 衡量真实用户会话规模，过滤无效/空会话 | 衡量使用产品的真实终端设备规模 |
| **数值关系** | 有效会话数 ≤ 总会话数（`sessionCount`） | 活跃设备数 ≤ 有效会话数的设备数（同一设备可产生多个会话） |

## 7. 无效会话的判断逻辑

RUM 代码中没有一个统一的 `isInvalidSession` 字段，「无效会话」的含义分布在**三个不同层次**，每个层次有各自独立的判定规则。

### 7.1 指标层：不贡献有效会话的会话

这是最接近「有效/无效」对立概念的层次。判定标准：入库时 `effective_session_num_uniq12` 字段是否被写入合法的 `sessionId`。

**未写入该字段（视为指标层无效）的场景：**

| 场景 | 原因 |
|------|------|
| 自定义视图 / H5 类型视图（`ViewEventEnterStrategy`） | 直接不生成 VIEW/TERMINAL 行，不进入该条有效会话入库链路 |
| 页面视图 `sessionFlag = 0` | `hasSession = false`，视图未处于会话接入语义下 |
| 小程序/Span/路由/H5 中 `hasSession = false` | 父级未开启会话接入，或当前视图配置了「跳过会话」 |
| Span 且 `websocketOrSocket = true` | WebSocket/Socket 类型网络请求不计入有效会话 |
| 纯网络汇总行（`buildNetResult`/`buildNetResourceResult`） | 纯网络数据聚合行，始终不写 |
| 上传事件（`UploadEventStrategy`） | 当前不生成 terminal 行，因此不会写入 `effective_session_num_uniq12` |

**`hasSession` 的判定公式（`HasSessionWrapper`）：**

```
hasSession = !skipSession
          && parentHasSession
          && (父事件类型 ≠ LAUNCH_EVENT)
```

| 变量 | 含义 |
|------|------|
| `skipSession` | `serviceModel.isViewSkipToSession()` 为 true，表示该视图配置了「跳过会话」 |
| `parentHasSession` | `serviceModel.isParentHasSession()`，父级服务/应用是否开启了会话接入 |
| 父事件类型不是启动事件 | 避免将启动事件的直接子视图错误计入会话 |

只要上述三个条件同时满足，`hasSession = true`，该事件对应的会话才进入有效会话统计。

---

### 7.2 会话列表层：`eventNum = 0` 的「空会话」被过滤

这是会话列表（`t_rum_session_view`）展示时的基础门槛，由 HAVING 条件实现，与指标层的有效性逻辑完全独立：

```sql
HAVING if(sum("eventNum") is null, 0, sum("eventNum")) > 0
```

**含义：** 即使 `t_rum_session_view` 中存在某个 `sessionId` 的记录，若该会话的所有终端行聚合后 `eventNum` 总和 ≤ 0，则不会出现在任何会话列表中。这类会话可理解为**「空会话」**——有会话 ID 但没有有效事件数据。

> 代码位置：`RumCkSessionService.ConcatQueryEntrySessionList()`，约 973–979 行

**注意事项：**
- 流量类事件（页面视图等）在 `sessionFlag = 0` 时既不写 `effectiveSessionNumUniq12`，**也不写 `eventNum`**（即不设 `eventNum = 1`）；
- 这意味着一个「仅有网络数据或上传快照」的会话，其 `eventNum` 可能为 0，会被该 HAVING 过滤，既不出现在列表，也不贡献有效会话指标。

---

### 7.3 满意度层：会话质量分类（非「无效」而是「异常/可容忍/满意」）

进入会话列表的每个会话，还会被进一步按**满意度规则**分类，计算 `sessionStatus`。这一层描述的是会话的「质量好坏」，而非「有效/无效」。

#### 7.3.1 硬规则（开关控制，优先级最高）

以下情况若对应开关已开启，**直接判定为异常会话**（`sessionStatus = -1`）：

| 开关配置项 | 触发条件 | 对应 flag |
|-----------|---------|-----------|
| `IS_EXIST_CRASH`（是否存在崩溃） | `crashFlag > 0` 或 `anrFlag > 0` | 原生崩溃或 ANR |
| `IS_EXIST_EXCEPTION`（是否存在异常） | `selfCrashFlag > 0` | 自采集崩溃/自定义异常 |
| `IS_EXIST_PAGE_LOAD_FAIL`（是否存在页面加载失败） | `h5ErrorFlag > 0` | H5/页面加载失败 |
| `IS_EXIST_OPERATION_FAIL`（是否存在操作失败） | `actionErrorFlag > 0` | 操作失败 |

#### 7.3.2 比例规则（阈值计算，次优先级）

在硬规则未命中时，根据事件比例与配置阈值计算：

```
异常事件占比 = exceptionEventNum / userEventNum × 100

if 异常事件占比 >= exceptionLimit  →  sessionStatus = -1（异常）
else if 满意事件占比 >= satisfiedLimit  →  sessionStatus = -3（满意）
else  →  sessionStatus = -2（可容忍）
```

| 阈值配置 | 配置项 code | 含义 |
|---------|------------|------|
| `exceptionLimit` | `EXCEPTION_LIMIT` | 异常事件占比达到该百分比时判为异常，默认由租户配置 |
| `satisfiedLimit` | `SATISFIED_LIMIT` | 满意事件占比达到该百分比时判为满意，默认由租户配置 |

> 代码位置：`SessionSatisfactionUtils.calculatedSessionSatisfaction()`

#### 7.3.3 `sessionStatus` 完整取值含义

| `sessionStatus` 值 | 含义 | 列表 Tab 筛选传值 |
|-------------------|------|-----------------|
| `-1` | **异常会话** | `otherFilters` 传 `value="2"` 或 `value="-1"` |
| `-2` | **可容忍会话** | `otherFilters` 传 `value="-2"` |
| `-3` | **满意会话** | `otherFilters` 传 `value="1"` 或 `value="-3"` |

#### 7.3.4 会话列表 API 返回的统计字段

| 字段名 | 含义 |
|--------|------|
| `sessionNum` | 全部会话数（满足 HAVING 的 sessionId 去重数） |
| `exceptionSession` | 其中异常会话数（`sessionStatus = -1`） |
| `acceptableSession` | 其中可容忍会话数（`sessionStatus = -2`） |

> 对应 `UserSessionModel.java` 中的字段定义

### 7.4 三层无效判断的关系与区别

```
所有 session（t_rum_session_view 中存在）
    │
    ├─ sum(eventNum) = 0  →  【空会话】不进入任何列表（列表层过滤）
    │
    └─ sum(eventNum) > 0  →  进入「全部会话」列表
           │
           ├─ 有 effective_session_num_uniq12  →  贡献【有效会话数】指标
           │
           └─ 无 effective_session_num_uniq12  →  不贡献有效会话指标（指标层无效）
                    但仍出现在「全部会话」列表中！
```

```
进入列表的会话 → 按满意度规则分类 →
    sessionStatus = -1  →  异常会话
    sessionStatus = -2  →  可容忍会话
    sessionStatus = -3  →  满意会话
```

**关键结论：**
- **指标层有效/无效**（是否贡献 `effectiveSessionCount`）与**列表层是否展示**（`eventNum > 0`）是两套独立规则，一个会话可以出现在「全部会话」列表但不贡献有效会话指标；
- **会话满意度分类**（异常/可容忍/满意）是对已进入列表的会话进行的质量评价，与有效/无效概念正交；
- 代码中不存在名为 `invalidSession`、`invalid_session`、`无效会话` 的统一字段或枚举，需按使用场景区分。

### 8.4 `sessionNum` 的具体作用

在 `AppService.appListQuery()` 的后处理阶段，`sessionNum`（有效会话数）被用作以下**比率计算的分母**：

| 计算目标 | 公式 | 代码字段 |
|---------|------|---------|
| ANR 率 | `anrImpactSessionNum / sessionNum` | `metric.setAnrRate(...)` |
| 崩溃率 | `crashImpactSessionNum / sessionNum` | `metric.setCrashRate(...)` |
| 业务请求错误影响会话占比 | `errorRequestImpactSessionNum / sessionNum` | `metric.setErrorRequestImpactSessionRatio(...)` |
| 慢请求影响会话占比 | `slowRequestImpactSessionNum / sessionNum` | `metric.setSlowRequestImpactSessionRatio(...)` |
| JS 错误影响会话占比 | `jsErrorImpactSessionNum / sessionNum` | `metric.setJsErrorImpactSessionRatio(...)` |

此外，当 `sessionNum > 0` 时，还会触发**零值补齐逻辑**：对崩溃次数、崩溃影响会话数/用户数、ANR 次数/影响数等字段，若未返回数据则统一置为 `"0"`，避免前端展示空值。

```java
// AppService.java, 约 495-516 行
if (StringUtils.isNotEmpty(sessionNum)) {
    Long sesionNumData = Long.valueOf(sessionNum);
    if (sesionNumData > 0) {
        if (StringUtils.isEmpty(metric.getCrashImpactSessionNum())) {
            metric.setCrashImpactSessionNum("0");
        }
        // ...其他字段零值补齐
    }
}
```

### 8.5 与 `AppMetricChart` 中 `sessionNum` 的对比

| 维度 | `query-field.xml` `queryType=200000` | `AppMetricChart.java` `metricName="sessionNum"` |
|------|---------------------------------------|------------------------------------------------|
| 使用场景 | **终端应用列表**（`/listQuery` 接口） | **应用详情图表**趋势线/柱状图 |
| 实际映射指标 | `effectiveSessionCount`（有效会话数） | `sessionCount`（总会话数） |
| 调用入口常量 | `RumQueryType.APP_LIST_TABLE = "200000"` | `AppMetricChart`（`metricName` 参数传入） |
| `isDefault` | `true`，始终查询 | 按需，由请求 `metricName` 决定 |
| 用途 | 列表列展示 + 各比率计算的分母 | 时序趋势图的指标值 |

**结论：** 在终端应用列表场景（`queryType=200000`）下，`sessionNum` 始终代表**有效会话数**（`effectiveSessionCount`），既用于列表中「会话数」列的直接展示，也作为 ANR 率、崩溃率、请求影响会话占比等多个衍生指标的**计算分母**；而应用详情图表中的 `sessionNum` 实际查询的是**总会话数**（`sessionCount`），两者含义不同，需注意区分。

## 9. 会话页「全部会话数」与列表条数不一致分析

本节针对 RUM 会话查询页（检索中心 → 用户会话）中「Tab 上的全部会话数」与「下方表格列表条数」不一致的现象，从前端取数、后端组装、SQL 聚合口径三个层面进行根因分析。

### 9.1 问题现象

从截图看，页面位于 RUM 的会话查询页，页面上方展示了 `全部会话(数字)`，下方表格展示会话列表。当前现象是：

- Tab 上的"全部会话数"和下方实际查询出来的列表条数不一致。
- 截图里网络面板可见核心请求为 `sessionList`，同时还有 `query` 等辅助请求。

需要回答两个问题：

1. 这个页面前后端到底怎么取数。
2. 为什么会出现"总数"和"列表条数"不一致。

### 9.2 页面和接口定位

#### 9.2.1 前端页面定位

#### 9.2.2 页面初始化请求

### 9.3 前端取数逻辑

#### 9.3.1 Tab 数字和列表不是两个接口

前端 `initTableList` 的逻辑说明得很清楚：

- `staticInfo.sessionNum` 取自 `res.data.sessionNum`

前端关键逻辑位于：
`view/rum/src/packages/retrieval/userSession/models/userSession/index.ts`

可概括为：

#### 9.3.2 当前页表格只显示当前分页

页面表格还做了一个前端截断：

  pagination={{ ...userPagination }}

```

因此：

- `Tab 数字` / `分页 total` 是总量概念
- 表格里看到的是当前页数据

如果只是"总数 100、当前页显示 10 条"，这是正常分页行为，不属于 bug。

但如果出现类似"全部会话数 1，列表却有 3 条"这种明显反常，就不是前端分页造成的，而要看后端返回的 `sessionNum` 和 `results` 是如何组装出来的。

1. 先查"候选会话集合"和统计数
2. 再按分页去查列表明细

#### 9.4.3 SQL Mapper

- `framework/plugins/rum/rum-database/src/main/resources/com/bonree/rum/mysql/rumqueryservice/session/queryservice/query/xml/RumSessionMapper.xml`

这里正是问题的根源。

### 9.5 不一致的根因

#### 9.5.1 根因一：总数和列表使用了不同的聚合粒度

后端统计 `sessionNum` 时，走的是：

- `querySessionIdList`

SQL 关键点：

```sql
SELECT "sessionId" sessionId
FROM one_rum_datasource_snapshot.t_rum_session_view
...
group by sessionId, deviceId
```

也就是说，统计总数时，后端按：

- `sessionId + deviceId`

这一粒度来算。

但是列表明细走的是：

- `querySessionList`

SQL 关键点：

```sql
select
  "sessionId" sessionId,
  "appId" appId,
  "appVersion" appVersion,
  "sdkVersion" sdkVersion,
  "clientDeviceName" fullBrandModel,
  "clientOsName" osName,
  "deviceId" deviceId,
  "channel" channel,
  "dataCenterId" dataCenterId
from one_rum_datasource_snapshot.t_rum_session_view
...
group by
  sessionId, appId, appVersion, fullBrandModel, clientOsName, deviceId, sdkVersion, channel, dataCenterId
```

也就是说，列表是按下面这组更细的字段聚合：

- `sessionId + appId + appVersion + fullBrandModel + clientOsName + deviceId + sdkVersion + channel + dataCenterId`

这会带来一个直接后果：

- 统计总数把它当成 `1` 个会话
- 列表明细可能因为 `appVersion`、`sdkVersion`、`channel`、`dataCenterId` 等字段变化，被拆成多行

所以从设计上看，`sessionNum` 和 `results.size()` 就不是严格一一对应关系。

这就是最核心的逻辑问题。

#### 9.5.2 根因二：分页查列表时，只按 `sessionId` 回查，丢失了 `deviceId`

后端先查出候选会话集合：

```java
List<SessionModel> allList = rumSessionMapper.querySessionIdList(queryCountList);
```

这个集合的统计粒度其实是：

- `sessionId + deviceId`

但是后续回查列表时，追加的过滤条件却只有：

```java
whereFilterListSessionList.add(
    RumSqlFilterUtil.putFilterOption("sessionId", FilterTypeEnum.in, sessionIds)
);
```

注意这里过滤的是：

- 只有 `sessionId`
- 没有再带 `deviceId`

这意味着如果存在以下情况，列表会被放大：

1. 不同设备上出现同名 `sessionId`
2. 同一个 `sessionId` 在底层视图里存在多条不同维度组合的数据
3. 总数阶段和列表阶段本来就不是同一个唯一键

这会导致：

- 统计数阶段算出来是若干个 `(sessionId, deviceId)`
- 列表阶段却只拿 `sessionId in (...)` 去查
- 最终列表可能查出比统计更多的记录行

如果截图里的真实现象是"全部会话数 1，但列表 3 条"，这一条是最值得优先怀疑的原因之一。

#### 9.5.3 根因三：列表查询和统计查询的时间窗不完全一致

`querySessionList` 里还有一个细节：

- 初次统计总数时，先按原始时间范围查 `querySessionIdList`
- 后续查异常会话、可容忍会话以及最终列表时，会对 `monitor_time` 做 `sessionQueryTimeExpansion` 的前后扩窗

代码里能看到对 `monitor_time` 的处理：

```java
filterOption.setValue(
  DateUtil.formatDateToString(
    DateUtil.getDateAddDate(new Date(condition.getStartTime()), DateUtil.MINUTE, -rumConfig.sessionQueryTimeExpansion),
    DateUtil.YYYY_MM_DDHHMMSS
  )
)
```

以及结束时间的正向扩展。

这说明：

- 统计集合使用的原始时间窗
- 列表明细使用的扩展时间窗

并不完全一致。

虽然列表最终还会再加 `sessionId in (...)`，但扩窗后参与聚合的底层记录变多，仍然可能进一步放大列表拆分行数。

#### 9.5.4 根因四：前端没有取消 `sessionList` 请求，快速切换时有旧请求覆盖风险

前端只对 `queryFilters` 做了取消请求：

```ts
request.cancelRequest(['/rest/rum/filter/query'])
```

但没有对 `sessionList` 做取消。

这意味着在以下情况下存在风险：

- 快速切换 Tab
- 快速改时间范围
- 快速连续筛选

可能出现旧请求后返回，把新页面状态覆盖掉的情况。

这个问题更像"偶发性展示错位风险"，不是当前截图里"稳定出现的总数/列表不一致"的第一根因，但它确实会放大问题排查难度。

### 9.6 结论：为什么会出现不一致

结论可以直接归纳为下面几点：

1. **前端不是两个接口口径不一致**
   前端 Tab 数字和列表都来自同一个 `sessionList` 响应。

2. **真正的问题在后端 `sessionList` 的内部组装逻辑**
   同一个响应里，`sessionNum` 和 `results` 来自两套不同粒度的查询。

3. **总数统计粒度更粗**
   `sessionNum` 基于 `group by sessionId, deviceId`。

4. **列表明细粒度更细**
   `results` 基于 `group by sessionId, appId, appVersion, fullBrandModel, clientOsName, deviceId, sdkVersion, channel, dataCenterId`。

5. **列表回查时又只按 `sessionId` 过滤，没有带 `deviceId`**
   这会进一步造成结果放大。

因此，"全部会话数"和"查出来的会话列表条数不一致"不是展示层偶然问题，而是当前后端接口实现本身就存在口径不统一。

### 9.7 对截图现象的最可能解释

如果截图中实际是类似：

- `全部会话(1)`
- 表格里却展示了 `3` 条会话记录

那么最可能的解释顺序是：

1. 后端统计阶段只认定了 `1` 个 `(sessionId, deviceId)` 会话单元。
2. 后端列表阶段按更细维度聚合，把同一会话拆成了多行，或者把同 `sessionId` 的其他维度数据也带出来了。
3. 前端只是原样展示后端返回的 `sessionNum` 和 `results`，所以看起来就变成"上面 1、下面 3"。

### 9.8 与 §6.2 / §8.5 的 `sessionNum` 双重映射的关系

需要特别区分的是，本节讨论的「全部会话数与列表条数不一致」与 §6.2、§8.5 中提到的「`sessionNum` 双重映射」是**两个不同层面的问题**：

| 问题 | 层面 | 根因 |
|------|------|------|
| `sessionNum` 双重映射（§6.2 / §8.5） | **指标映射层**：同一个字段名 `sessionNum` 在不同入口映射到不同指标（`effectiveSessionCount` vs `sessionCount`） | `query-field.xml` 与 `AppMetricChart` 对 `sessionNum` 的定义不同 |
| 全部会话数与列表条数不一致（本节） | **接口组装层**：同一个 `sessionList` 响应里，`sessionNum` 字段和 `results` 列表基于不同聚合粒度 | `querySessionIdList` 与 `querySessionList` 的 `group by` 粒度不同 + 列表回查丢失 `deviceId` |

二者可能同时存在，但排查时需分别定位：前者是"字段名相同但指标含义不同"，后者是"同一接口内总数与列表口径不统一"。

### 9.9 修复建议

#### 9.9.1 后端修复建议

优先级最高的修复方向：

1. **统一统计和列表的唯一粒度**
   `sessionNum` 与 `results` 应基于同一个唯一键集合。

2. **分页回查时不要只带 `sessionId`**
   至少应把统计阶段的唯一键一起带回去，例如：
   - `sessionId + deviceId`
   - 或直接使用真正全局唯一的 session 主键

3. **列表 SQL 的 group by 需要和"一个会话"的业务定义一致**
   否则一个会话会被拆成多行。

4. **统计和列表的时间窗保持一致**
   避免一边原始时间、一边扩展时间。

#### 9.9.2 前端兜底建议

前端虽然不是主因，但可以补两点兜底：

1. 给 `sessionList` 增加取消请求或响应序号校验，避免旧请求覆盖新状态。
2. 在出现 `total < 当前页列表条数` 这类明显异常时打监控日志，便于尽快定位后端口径问题。

## 11. 最终结论

1. **有效会话数的本质**：不是"上传过 session 就算 1"，而是"被有效事件激活过的 session 去重数"。启动、操作、崩溃、ANR、卡顿、JS 错误等异常/质量类事件无条件贡献有效会话；页面视图、Span、路由、H5 等流量类事件需通过 `hasSession`/`sessionFlag` 判定；纯网络汇总行与上传事件不贡献有效会话。

2. **活跃设备数的本质**：上报任意事件的设备去重数，无额外有效性限制，所有 terminal 行均写入 `device_id_uniq12`。因此 `活跃设备数 ≤ 有效会话数`（同一设备一天内可产生多个有效会话）。

3. **`sessionNum` 字段的双重映射**：终端应用列表（`queryType=200000`）中 `sessionNum` = 有效会话数（`effectiveSessionCount`）；应用详情图表中 `sessionNum` = 总会话数（`sessionCount`）。二者含义不同，对比数值时需确认入口。

4. **三层"无效会话"判断相互独立**：指标层（是否贡献 `effectiveSessionCount`）、列表层（`eventNum > 0` 才展示）、满意度层（异常/可容忍/满意）是三套独立规则，一个会话可以出现在「全部会话」列表但不贡献有效会话指标；满意度分类与有效/无效概念正交。

5. **会话页「全部会话数」与列表条数不一致的根因**：不是前端展示问题，而是后端 `sessionList` 接口内部口径不统一——`sessionNum` 基于 `group by sessionId, deviceId`，`results` 基于更细的 9 字段 `group by`，且列表回查时只按 `sessionId` 过滤丢失了 `deviceId`，叠加列表查询的时间窗扩展，导致列表条数可能大于总数。
