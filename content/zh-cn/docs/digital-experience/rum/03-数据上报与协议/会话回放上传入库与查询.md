# RUM 模块 —— 会话回放：上传接收、入库与查询

> 本文梳理会话回放从 **config 下发 → `/uploadReplay` 上报 → ingester 入库 → 查询播放** 的完整链路，并重点说明 **一个会话回放包含哪些文件与内容**。
>
> 代码根目录：`D:\Bonree\CodeProject\newone`  
> 关联字段级映射见同目录：`config-upload-grip-uploadReplay字段全链路.md`（§6 / §10.4）。

---

## 1. 一句话结论

**会话回放 = 多个时间片包。** 每包在 BRFS（`T_RUM_SESSION_REPLAY`）落 **1～2 个文件**（`*_event` 必选语义上承载可播内容，原生另有 `*_imgs`），并在 ClickHouse 公共快照表写一条 **`type=REPLAY` 索引**；查询先按会话拉时间轴 `fileId` 列表，再按 `fileId` 从 BRFS 取正文播放。

| 端 | 事件文件正文 | 图片文件 |
|----|--------------|----------|
| Web | rrweb 流 `wsd` | 通常无 / 弱依赖 |
| 原生 | 动作流 `msd` | `*_imgs`（截图 base64 等） |

---

## 2. 端到端链路

```text
config 下发 sessionreplay 模块（ua=/uploadReplay, fps/uc/脱敏等）
        ↓
SDK 按周期/触发策略 multipart 上报 /uploadReplay
        ↓
接入 → Kafka → ingester RumReplayFilterStrategy
        （解 multipart、应用校验、License）
        ↓
UploadReplayRequestConvert → RumReplayCommonTransform → ReplayEventStrategy
        ↓
┌─ BRFS：T_RUM_SESSION_REPLAY 存 event / image 二进制
└─ CK：t_rum_common_snapshot（type=REPLAY）存索引（eventFileId、duration、wev…）
        ↓
querySessionReplay（时间轴）→ querySessionReplayData（按 fileId 取内容）
        ↓
前端 rrWebPlay（Web）/ VFramePlay（原生）
```

| 阶段 | 关键代码 |
|------|----------|
| 配置下发 | config `ModelConfig` 中 `n=sessionreplay` → `SessionReplayConfiguration` |
| 接入过滤 | `ingester-rum/.../RumReplayFilterStrategy.java` |
| 协议解析 | `UploadReplayRequestConvert.java` → `ReplayUploadRequestEntity` |
| 入库策略 | `ReplayEventStrategy.java` |
| 文件写入 | `SnapshotFileService.saveReplaySnapshotFile` → `BrfsSaveSnapshotScheduling` |
| 查询 API | `RumSessionReplayController` |
| CK 查询 | `RumCkSessionReplayServiceImpl` + `RumSessionReplayMapper.xml` |
| 播放数据 | `RumSessionReplayDataService4Web` / `RumSessionReplayDataService4Native` |
| 前端 | `view/rum/src/packages/retrieval/sessionDetail/container/sessionReplay/` |

说明：最外层 HTTP Gateway → Kafka 首跳在部分仓库证据不完整，本文从 **ingester 输入侧** 闭环。

## 3. 配置侧（何时会采回放）

config 响应中 `sessionreplay` 模块常见字段（`SessionReplayConfiguration`）：

| 字段 | 含义 |
|------|------|
| `ua` | 回放上传地址，通常 `/uploadReplay` |
| `rq` | 录制/压缩质量 |
| `fps` | 截图最大采集频率 |
| `mci` | 最大采集间隔（秒） |
| `sl` | 脱敏等级 |
| `ac` | 是否允许蜂窝网上传 |
| `us` | 触发上传策略（crash/anr/lag/onlaunch 等） |
| `ims` | 单次请求图片最大大小（MB） |
| `uc` | 回传周期（秒）→ 决定「一个会话」被切成多少包 |
| `dt` | 截图类型（完整图 / 线框等） |

会话列表「是否有回放」来自会话聚合字段 **`replayFlag`**（与 BRFS 正文文件是不同查询链路）。

## 4. 上报协议（每包 `/uploadReplay`）

- 形态：`multipart/form-data`；`event` / `image` 可为 gzip（`BR-Content-Encoding:gzip`）
- 实体：`ReplayUploadRequestEntity`

| 协议字段 | 模型字段 | 作用 |
|----------|----------|------|
| `s` | `session` | 会话 ID |
| `v` | `version` | 探针版本 |
| `mt` / `cmt` | `monitorTimeUs` / `configMonitorTimeUs` | 监控时间 / config 时间基线 |
| `st` / `ud` | `startTimeUs` / `unitDurationUs` | 本包起始、本包时长（μs） |
| `wev` | `webEventVersion` | Web rrweb 协议版本 |
| `di` / `ai` / `ui` / `dfi` | 设备/应用/用户/打通 | 上下文维度 |
| **`event`** | `byte[] event` | 回放事件 JSON 字节 |
| **`image`** | `byte[] image` | 回放图片 JSON 字节（原生为主） |

### 4.1 `event` 内容结构

| 端 | 键 | 内容 |
|----|-----|------|
| Web | `wsd` | rrweb 事件流（DOM 全量/增量、鼠标等） |
| 原生 | `msd` | 动作数组：`to` 偏移、`t` 类型、`l` 触摸轨迹、`vf`、`md` 滑动时长等 |

原生 `t` 类型：`1` 触摸/鼠标，`2` 键盘弹出，`3` 键盘收起，`4` 屏幕方向变化。

### 4.2 `image` 内容结构（`SessionReplayImage`）

| 字段 | 含义 |
|------|------|
| `i` | 图片 base64 |
| `to` | 相对本包起始的时间偏移 |
| `ss` / `so` | 屏幕尺寸 / 方向 |
| `ka` | 键盘区域（部分事件） |

## 5. 入库逻辑

### 5.1 处理入口

`ReplayEventStrategy.buildSnapshotResult`：

1. 生成文件名：
   - `eventFileId = {session 去掉 "br:"}_{brKey}_event`
   - `imageFileId = {session 去掉 "br:"}_{brKey}_imgs`
2. 写 CK 公共快照：`EtlBizTypeEnum.RUM_COMMON_SNAPSHOT`，`DataTypeEnum.REPLAY`，`sessionFlag=1`
3. `otherIndex` 关键键：`sessionEventType`、`eventFileId`、`duration`、`displaySize`、可选 `wev`
4. 若 `event != null` → `saveReplaySnapshotFile(eventFileId, SESSION_REPLAY, ...)`
5. 若 `image != null` → `saveReplaySnapshotFile(imageFileId, SESSION_REPLAY, ...)`

### 5.2 文件存储

| 项 | 值 |
|----|-----|
| BRFS / 存储名 | `T_RUM_SESSION_REPLAY`（`EtlSnapshotTypeEnum.SESSION_REPLAY` / `BrfsStorageTypeEnum.SESSION_REPLAY_FILE`） |
| 压缩 | 写入前 Snappy（若上报已 gzip 则直接 Snappy；否则先 gzip 再 Snappy） |
| 调度 | `BrfsSaveSnapshotScheduling.addSnapshot` |

## 6. 一个会话回放包含哪些文件（重点）

### 6.1 结构示意

```text
会话 S
├── CK 索引（one_rum_datasource_snapshot.t_rum_common_snapshot_view，type=REPLAY）
│   ├── 包1: eventFileId=S_k1_event, duration, wev?, displaySize?
│   ├── 包2: eventFileId=S_k2_event, ...
│   └── ...
└── BRFS（T_RUM_SESSION_REPLAY）
    ├── S_k1_event   ← event 字节（Web: wsd / 原生: msd）
    ├── S_k1_imgs    ← image 字节（原生帧图；Web 常无）
    ├── S_k2_event
    ├── S_k2_imgs
    └── ...
```

**要点：**

- 「一个会话」= **N 个时间片包**（由 SDK `uc` / 触发策略决定），不是单文件。
- CK **只存索引与时间轴元数据**，不存回放正文。
- CK 索引稳定挂的是 **`eventFileId`（`*_event`）**；原生读图时用 `_event` → `_imgs` 推导图片文件名。
- 快照行上的 `snapshotFile` 元信息 JSON 可含 `eventFileId`，正文仍以 BRFS 文件为准。

### 6.2 Web vs 原生文件差异

| | Web | 原生 |
|--|-----|------|
| 必备文件 | `*_event`（含 `wsd`） | `*_event`（含 `msd`） |
| 图片文件 | 通常无 | `*_imgs`，按 `to` 与动作对齐 |
| 播放器 | `rrWebPlay` | `VFramePlay`（动作+截图合并） |

## 7. 查询逻辑

### 7.1 时间轴：`POST /rest/rum/session/replay/querySessionReplay`

- 入口：`RumSessionReplayController.sessionReplay` → `RumCkSessionReplayServiceImpl`
- 过滤：`sessionId` / `appId` / `deviceId` + `type=REPLAY`
- SQL（`RumSessionReplayMapper`）：
  - `querySessionReplayFileIdList`：按 `otherIndex['eventFileId']` 分组，得到 `{fileId, monitorTime, duration}`
  - `querySessionReplayOtherInfo`：起止时间、`wev`、`displaySize`
- 返回：`SessionReplayModel`（`fileIds`、`wev`、宽高、起止、总时长等）

### 7.2 播放数据：`POST /rest/rum/session/replay/querySessionReplayData`

- 按 `platform` 工厂选择服务：
  - **Web** `RumSessionReplayDataService4Web`：`FileUtils.getSessionReplayFile` 读 `*_event` → 取 JSON **`wsd`**
  - **原生** `RumSessionReplayDataService4Native`：读 `*_event` 的 **`msd`** + 同包 `*_imgs`，按时间偏移 `to` 合并动作与截图，排序后返回 `sessionReplayDataNatives`

## 8. 排查提示

1. **有会话无回放按钮**：先查会话聚合 `replayFlag`；再查 CK 是否存在 `type=REPLAY` 且同 `sessionId` 的索引。
2. **有时间轴无画面**：CK 有 `eventFileId` 但 BRFS 读空 → 查 `T_RUM_SESSION_REPLAY` 文件是否写入失败 / 时间路由 `monitorTime` 是否匹配。
3. **原生有动作无图**：确认同包是否存在 `*_imgs`，以及 `to` 是否能与 `msd` 对齐。
4. **Web 播放异常**：核对 `wev` 与前端 rrweb 兼容分支。
5. **包过多/过少**：对照 config 的 `uc`、`us`、`fps`、`ims` 与蜂窝限制 `ac`。
