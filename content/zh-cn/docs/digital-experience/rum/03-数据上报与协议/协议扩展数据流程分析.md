title: RUM 协议扩展数据流程与平均/P99 耗时差异分析
---

本文整合两类内容：协议扩展（Protocol Extend / Span）事件的端到端数据流程；以及协议扩展页面"平均耗时远小于 P99 耗时"现象的根因与统计口径分析。

## 一、概述

### 1.1 协议扩展定义

协议扩展（Protocol Extend）是 RUM 中用于采集 **socket / websocket / 自定义协议请求** 的事件类型。在系统内部以 `span` 命名，根据协议类型分为两种：

| 类型 | 事件码 | 说明 |
|------|--------|------|
| `SPAN_EVENT` / `PROTOCOL_EXTEND` | **30000** | 协议扩展（socket/websocket） |
| `SPAN_CUSTOM_EVENT` / `CUSTOM_PROTOCOL_EXTEND` | **30001** | 自定义协议扩展（非 socket/websocket） |

**状态枚举**（`SpanStatusEnum`）：

| Code | 含义 |
|------|------|
| 0 | Unknown |
| 1 | Success |
| 2 | Fail |

### 1.2 涉及代码范围

- Ingester 层：`controller/ingester/ingester-business/ingester-rum`
- Framework 查询层：`framework/plugins/rum`
- View 展示层：`view/rum`

## 二、数据上报（SDK → Ingester）

### 2.1 上报协议格式

SDK 客户端以 JSON 格式上报事件数据，事件类型标识为 `"k": "span"`。协议扩展事件的数据结构嵌套在事件的 `"v"` 字段中：

```json
{
  "ent": 1695000000000,  // 事件时间
  "k": "span",           // 事件类型标识
  "v": {
    "id": "uuid",         // 唯一ID（非必填，缺失时自动生成）
    "st": 100000,         // start time 开始时间 [单位：μs]
    "n": "192.168.1.1:8080", // name 名称 [必填]
    "t": "socket",        // type 类型 [必填] socket/websocket/其他自定义类型
    "du": 50000,          // duration 耗时 [必填] [单位：μs]
    "sta": 1,             // status 状态 0:unknown 1:success 2:fail [必填]
    "stac": "200",        // status code 状态码 [非必填]
    "ic": false,          // is custom 是否为自定义接口 [必填]
    "da": [               // data 数据 [非必填]
      {"k": "key1", "v": "value1"}
    ],
    "m": [                // metric 指标 [非必填]
      {"k": "dns", "v": 1000, "u": "us"}
    ],
    "tag": [              // tag 标签 [非必填]
      {"k": "process", "v": "connect"}
    ],
    "sub": [...]          // sub span 子协议节点 [非必填]，递归结构
  }
}
```

> **源码位置**: `ingester-rum/src/main/java/com/bonree/one/ingester/rum/model/entity/span/SpanEventEntity.java`

## 三、数据解析（Ingester — Protocol Convert）

### 3.1 事件类型识别

`EventConvert` 类是所有事件解析的入口，根据事件 JSON 中的 `"k"` 字段识别事件类型：

```java
// EventConvert.java
entity.setType(EventTypeEnum.getEnumByType(json.path("k").textValue()));
// EventTypeEnum: "span" → SPAN_EVENT
```

在 `convertEvent()` 方法中，`SPAN_EVENT` 类型路由到 `SpanEventConvert`：

```java
case SPAN_EVENT:
    eventEntity = SpanEventConvert.getInstance().convert(json);
    break;
```

> **源码位置**: `ingester-rum/.../convert/EventConvert.java` 第 191-193 行

### 3.2 协议扩展事件解析（SpanEventConvert）

`SpanEventConvert` 继承自 `AbstractProtocolConvert`，负责将 JSON 解析为 `SpanEventEntity`：

```java
// SpanEventConvert.resolve()
SpanEventEntity entity = new SpanEventEntity();
entity.setId(StringUtils.isEmpty(id) ? UUIDUtil.getUuid() : id);  // 自动补充ID
entity.setStartTime(getDataFromNode(json, "st", Long.class));      // 开始时间(μs)
entity.setName(getDataFromNode(json, "n", String.class));           // 名称
entity.setType(getDataFromNode(json, "t", String.class));           // 类型(socket/websocket/...)
entity.setDuration(getDataFromNode(json, "du", Long.class));        // 耗时(μs)
entity.setStatus(getDataFromNode(json, "sta", Integer.class));      // 状态
entity.setStatusCode(getDataFromNode(json, "stac", String.class));  // 状态码
entity.setIsCustom(getDataFromNode(json, "ic", Boolean.class));     // 是否自定义

entity.setData(dataConvert(json.get("da")));      // 数据列表 → List<SpanDataEntity>
entity.setMetric(metricConvert(json.get("m")));    // 指标列表 → List<SpanMetricEntity>
entity.setTag(tagConvert(json.get("tag")));        // 标签列表 → List<SpanTagEntity>
entity.setSubSpan(subConvert(json.get("sub")));    // 子span → 递归解析 List<SpanEventEntity>
```

**子结构解析**：

- `dataConvert()`: 解析 `da` 数组，每项包含 `k(key)` 和 `v(value)`
- `metricConvert()`: 解析 `m` 数组，每项包含 `k(key)`、`v(value)`、`u(unit)`
- `tagConvert()`: 解析 `tag` 数组，每项包含 `k(key)` 和 `v(value)`
- `subConvert()`: 递归调用 `resolve()` 解析子 span

> **源码位置**: `ingester-rum/.../convert/span/SpanEventConvert.java`

## 四、数据处理（Ingester — Strategy & Model Convert）

### 4.1 事件处理策略（SpanEventStrategy）

`SpanEventStrategy` 继承 `AbstractEventBaseStrategy<SpanModel>`，是协议扩展事件的核心处理策略，完整生命周期：

```
dataClean → modelConvert → flatten → buildGranResult + buildSnapshotResult + buildMetricResult + buildMySQLResult
```

#### 4.1.1 数据清洗（dataClean）

校验网络状态信息是否存在，为空则过滤：

```java
NetworkStateInfoModel nsiModel = SinStateInfoWrapper.getNsiModel(commonModel, event);
if (nsiModel == null) {
    return false;  // 过滤该事件
}
```

#### 4.1.2 模型转换（modelConvert → SpanEventModelConvert）

将 `SpanEventEntity` 转换为 `SpanModel`（含父子span）：

```java
SpanEventEntity spanEventEntity = (SpanEventEntity) event.getEvent();
return SpanEventModelConvert.getInstance()
    .convert(spanEventEntity, commonModel, eventTime, userInfoEntity, ...);
```

**核心转换逻辑**（`SpanEventModelConvert.buildSpanModel()`）：

1. **必填校验**: 通过 `ValidatorFactory` 校验 span 必填字段
2. **名称合并**: socket/websocket 类型需要进行域名/IP 合并（隐藏端口、IPv4 保留前三段、IPv6 保留前四段）
3. **类型判断**: 根据 `type` 字段判断是否为 socket/websocket
4. **loadTime 处理**: `spanModel.setLoadTimeUs(spanEventEntity.getDuration())` — 取 duration 作为耗时
5. **socket 特殊处理**:
   - 标记 `websocketOrSocket = true`
   - `tag.process=connect` 时，标记为建联阶段，从 metric 中提取 dns/tcp/ssl 耗时
   - **非 connect 阶段的 loadTime 置为 null**
6. **metric/data/tag 转换**: 转为 Map 结构，key 统一小写
7. **父子关系**: 子 span 继承父 span 的 `pName`、`pNameCode`、`dataType`

> **源码位置**: `ingester-rum/.../strategy/impl/span/SpanEventModelConvert.java`

### 4.2 SpanModel 数据模型

```java

```

## 五、数据入库（Ingester → ClickHouse / MySQL）

### 5.1 入库目标

`SpanEventStrategy` 在处理完成后，产出 **四类** 入库数据：

| 方法 | 入库目标 | 说明 |
|------|----------|------|
| `buildGranResult()` | ClickHouse 统计表 (`RUM_STAT_SPAN`) + Terminal 表 | 聚合统计数据 |
| `buildSnapshotResult()` | ClickHouse 快照表 (`RUM_SPAN_SNAPSHOT`) | 事件快照（会话详情查询用） |
| `buildMetricResult()` | OTLP Metric | 自定义 metric 指标数据 |
| `buildMySQLResult()` | MySQL | span 缓存数据 |

### 5.2 统计表入库（SpanResultZeusConvert）

构建 `SpanResultZeus` 写入统计表，核心字段映射：

```java
resultZeus.setUrl(model.getMergeName());                     // 合并后URL
resultZeus.setRequestId(model.getNameCode());                // 请求ID(哈希)
resultZeus.setParentUrl(model.getPName());                   // 父URL
resultZeus.setParentRequestId(model.getPNameCode());         // 父请求ID
resultZeus.setCustomRequestType(model.getDataType());        // 协议类型
resultZeus.setLoadTimeSum(model.getLoadTimeUs());            // 耗时(μs)
resultZeus.setCustomRequestStatusCode(model.getStatusCode()); // 状态码
```

**状态统计逻辑**:

- **socket/websocket 类型**:
  - connect 阶段: 记录 dns/tcp/ssl 耗时
  - 非 connect 阶段: `loadTimeSum = null`
  - fail → `errorNum=1, successNum=0` / success → `successNum=1, errorNum=0`

- **非 socket/websocket 类型**:
  - 无父名称（顶层span）: fail → `errorNum=1` / success → `successNum=1`
  - 有父名称（子span）: fail → `subErrorNum=1` / success → `subSuccessNum=1`

> **源码位置**: `ingester-rum/.../strategy/impl/span/SpanResultZeusConvert.java`

### 5.3 快照表入库（SpanSnapshotResultZeusConvert）

构建 `SnapshotResultZeus` 写入快照表（会话详情查询使用），核心字段映射：

```java
// 事件类型判断
ResultDataEventTypeEnum spanEventType = ResultDataEventTypeEnum.SPAN_CUSTOM_EVENT; // 30001
if (model.isWebsocketOrSocket()) {
    spanEventType = ResultDataEventTypeEnum.SPAN_EVENT; // 30000
}

// otherIndex JSON 字段
otherIndex.put("url", model.getMergeName());                        // 合并URL
otherIndex.put("requestId", model.getNameCode());                    // 请求ID
otherIndex.put("requestOriginUrl", model.getName());                 // 原始URL
otherIndex.put("sessionEventType", spanEventType.getType());         // 30000 或 30001
otherIndex.put("customRequestStatus", customRequestStatus);          // 状态
otherIndex.put("customRequestStatusCode", model.getStatusCode());    // 状态码
otherIndex.put("loadTime", model.getLoadTimeUs());                   // 耗时(μs)
otherIndex.put("parentUrl", model.getPName());                       // 父URL
otherIndex.put("parentRequestId", model.getPNameCode());             // 父请求ID
otherIndex.put("customRequestType", model.getDataType());            // 协议类型
otherIndex.put("metricMap", JacksonUtils.obj2JsonString(model.getMetricMap())); // 指标
otherIndex.put("dataMap", JacksonUtils.obj2JsonString(model.getData()));        // 数据
otherIndex.put("tagMap", JacksonUtils.obj2JsonString(model.getTag()));          // 标签
otherIndex.put("dnsTime", model.getDnsTimeUs());                     // DNS耗时
otherIndex.put("tcpTime", model.getTcpTimeUs());                     // TCP耗时
otherIndex.put("sslTime", model.getSslTimeUs());                     // SSL耗时
```

**会话关联判断**(`checkHasSession()`):

```java
// socket/websocket 类型且没有 pid → 不关联会话（sessionFlag=0）
if (spanEventType == SPAN_EVENT && model.getPid() == null) {
    return false;
}
```

> **源码位置**: `ingester-rum/.../strategy/impl/span/SpanSnapshotResultZeusConvert.java`

## 六、数据查询（Framework — REST API）

### 6.1 查询接口

协议扩展数据通过会话详情接口返回，在 `SessionSearchController` 中注册：

### 6.2 查询服务（RumCkSessionSearchService）

`querySessionEventDetailList()` 根据 `drawerType` 分流：

- **网络请求Tab**（drawerType=1/默认）→ `queryNetSessionEvent()` — 可查到协议扩展事件
- **用户交互Tab**（drawerType=2）→ `queryActionOrQuestionSessionEventList()`
- **问题Tab**（drawerType=3）→ `queryActionOrQuestionSessionEventList()`

协议扩展在会话事件列表中，与网络请求共同参与 **网络请求装饰**：

```java

        EventTypeEnum.NETWORK.getType().toString(),           // 10000
```

### 6.3 数据转换（SessionUtil）

#### 6.3.1 事件类型映射

快照表中 `sessionEventType` 为 `30000` 或 `30001`，在查询时通过 `EventTypeEnum` 匹配：

| 查询层枚举 | Code | 父级分类 |
|------------|------|----------|
| `EventTypeEnum.PROTOCOL_EXTEND` | 30000 | `"300"` (`PROTOCOL_EXTEND`) |
| `EventTypeEnum.CUSTOM_PROTOCOL_EXTEND` | 30001 | `"300"` (`PROTOCOL_EXTEND`) |

#### 6.3.2 事件状态映射

`EventStatusEnum` 定义了协议扩展的状态字段来源：

```java
protocolExtend(30000, "customRequestStatus"),       // 从 otherIndex.customRequestStatus 取状态
protocolExtendCustom(30001, "customRequestStatus"),  // 同上
```

#### 6.3.3 子类型映射

`EventSubTypeEnum` 定义了事件子类型（前端展示用）：

| 枚举 | eventType | eventStatus | 名称 |
|------|-----------|-------------|------|
| `PROTOCOL_EXTEND_NORMAL` | 30000 | 1 | 协议扩展-正常 |
| `PROTOCOL_EXTEND_FAIL` | 30000 | 3 | 协议扩展-失败 |
| `CUSTOM_PROTOCOL_EXTEND_NORMAL` | 30001 | 1 | 自定义协议扩展-正常 |
| `CUSTOM_PROTOCOL_EXTEND_FAIL` | 30001 | 3 | 自定义协议扩展-失败 |

#### 6.3.4 VO 构建（getInformationVO4NewData）

在 `SessionUtil.getInformationVO4NewData()` 的 `PROTOCOL_EXTEND` 分支中构建 `ProtocolExtendVO`：


#### 6.3.5 事件描述

`decorateDescription()` 中为协议扩展取 `otherIndex.url` 作为事件描述：


#### 6.3.6 loadTime 处理

与所有事件类型一致，`loadTime` 从 `otherIndex.loadTime`（μs）除以 1000 转为 ms：


### 7.2 列表展示

协议扩展事件在会话详情的事件列表中展示，使用与其他事件相同的列配置：

- **时间列**: `monitorTime` → 格式化为 `HH:mm:ss`
- **耗时列**: `loadTime` → 通过 `getLoadTime()` 渲染（ms→s转换后展示）
- **类型列**: `mergedEventTypeName` — 显示合并后的事件类型名称
- **事件描述列**: `eventSubTypeAndDescription` — 包含子类型名称 + 事件描述（合并URL）

# 十、协议扩展页面平均耗时与 P99 耗时差异分析

## 10.1 问题结论

截图中的"平均耗时"远远小于"P99耗时"，在当前代码实现下是**完全可能且符合统计口径**的，尤其在协议扩展（`socket` / `websocket` / 自定义 span）场景中更容易出现。

核心原因不是前端展示计算错误，而是：

1. 页面展示的 `平均耗时` 和 `P99耗时` 都是后端直接聚合返回，前端只负责展示。
2. 协议扩展首页列表查询的是聚合指标表，不是逐条快照。
3. `平均耗时` 使用 `avg(metric['one.rum.net.custom.time'])`。
4. `P99耗时` 使用 `quantile(metric['one.rum.net.custom.time'],0.99)`。
5. 对 `socket/websocket` 而言，**只有 connect 阶段才会写入耗时**，非 connect 阶段会保留次数/错误，但耗时会被置空。
6. 协议扩展名称在入库前存在**合并规则**，多个真实目标可能被归并到同一行，进一步放大长尾。

因此，一行数据里如果：

- 大多数请求很快；
- 少量请求特别慢；
- 或者这一行本身混入了多个被合并后的目标；

那么就会出现：

- 平均耗时看起来不高；
- P99 被极少数超慢请求抬得很高；
- 两者差距非常明显。

像截图里类似 `177ms` 对 `5320ms` 这种现象，从当前实现看是合理的。

## 10.2 页面展示口径

协议扩展页面前端通过 `view/rum/src/services/experience/request.ts` 调用：

- `/rest/rum/socket/list`：协议扩展首页列表
- `/rest/rum/socket/statisticalChart`：协议扩展卡片
- `/rest/rum/socket/trend`：趋势图
- `/rest/rum/socket/analysis`：分布

其中首页列表的表头定义在 `framework/plugins/rum/rum-core/src/main/resources/custom-header-cn.xml`，`businessType="21008"` 下默认就包含：

- `avgTotalTime` -> 平均耗时
- `p99TotalTime` -> P99耗时

也就是说，截图中的这两列并不是前端算出来的，而是后端聚合结果字段。

## 10.3 首页列表查询逻辑

### 10.3.1 查询入口

协议扩展首页列表后端入口是：

- `RumCustomSocketServiceImpl.socketList(...)`

其处理过程是：

1. 接收 `/rest/rum/socket/list` 请求。
2. 转成 `ReportCondition`。
3. 设置业务类型为 `RumBusinessType.CUSTOM_SOCKET_LIST`。
4. 进入 `CustomSocketList.assembleParam(...)` 组装指标查询。

### 10.3.2 实际聚合指标

`CustomSocketList` 对协议扩展首页列表的指标定义如下：

- `sum(metric['one.rum.net.custom.count'])` -> `totalAccessNum`
- `frm(metric['one.rum.net.custom.throughput'])` -> `throughputRate`
- `sum(metric['one.rum.net.custom.errorCount'])` -> `errorReqNum`
- `frm(metric['one.rum.net.custom.errorRatio'])` -> `errorReqRate`
- `avg(metric['one.rum.net.custom.time'])` -> `avgTotalTime`
- `quantile(metric['one.rum.net.custom.time'],0.5)` -> `p50TotalTime`
- `quantile(metric['one.rum.net.custom.time'],0.75)` -> `p75TotalTime`
- `quantile(metric['one.rum.net.custom.time'],0.9)` -> `p90TotalTime`
- `quantile(metric['one.rum.net.custom.time'],0.95)` -> `p95TotalTime`
- `quantile(metric['one.rum.net.custom.time'],0.99)` -> `p99TotalTime`
- `max(metric['one.rum.net.custom.time'])` -> `maxTotalTime`
- `min(metric['one.rum.net.custom.time'])` -> `minTotalTime`

### 10.3.3 分组维度

首页列表是按下面几个维度分组的：

- `dataType`
- `nameCode`
- `name`

即一行协议扩展数据，本质上是某个"协议扩展名称 + 数据类型"的聚合结果，而不是单次请求。

### 10.3.4 底层查询表

`queryCustomSocketMetricListData` 的 SQL 直接查的是：

- `"metric"."data"`

因此协议扩展首页列表是**指标聚合表查询**，不是快照明细表查询。

这意味着：

- `平均耗时` 是聚合后的均值；
- `P99耗时` 是聚合后的 99 分位；
- 它们天然就可能因为分布长尾而相差很大。

## 10.4 入库逻辑如何决定"耗时样本"范围

### 10.4.1 span 原始耗时来源

在 `ingester-rum` 中，协议扩展事件转换为 `SpanModel` 时：

- `loadTimeUs = spanEventEntity.getDuration()`

也就是说，协议扩展耗时原始值来自 span 的 `duration`。

### 10.4.2 socket / websocket 的特殊处理

但对 `socket` / `websocket`，代码又做了特殊分支：

- 如果 `type` 是 `socket` 或 `websocket`
- 并且 `tag.process == connect`
  - 保留 `loadTimeUs`
  - 同时拆出 `dnsTimeUs` / `tcpTimeUs` / `sslTimeUs`
- 如果不是 `connect`
  - 直接把 `loadTimeUs` 置为 `null`

这意味着：

**结论 A：协议扩展的耗时指标并不是所有 socket/websocket 事件都参与**

只有 connect 阶段进入耗时统计；非 connect 阶段虽然仍然是一条协议扩展记录，但不会给 `one.rum.net.custom.time` 提供样本。

**结论 B：次数/错误数 与 耗时样本 不是完全同一批数据**

在 `SpanResultZeusConvert` 中：

- `successNum` / `errorNum` 仍会正常写入；
- 但非 connect 阶段会把 `loadTimeSum` 置空。

因此可能出现：

- 次数很多；
- 错误数很多；
- 但耗时样本比次数少得多；
- 极端情况下甚至平均耗时和 P99 都为空。

这也解释了截图中某些行可能出现：

- 次数、错误率有值；
- 平均耗时 / P99耗时 却是 `--`。

## 10.5 为什么平均耗时会远远小于 P99

结合当前实现，主要有 5 类典型场景。

### 10.5.1 典型长尾分布

这是最常见的情况。

如果一组协议扩展中：

- 95%~99% 的 connect 很快；
- 只有极少数 connect 特别慢；

那么：

- `avg` 会被大量快请求拉低；
- `P99` 会非常接近最慢的 1%；

于是就可能出现：

- 平均耗时只有几百毫秒；
- P99 却达到几秒甚至十几秒。

这正是"长尾延迟"最标准的统计特征。

### 10.5.2 行级分组已经把多个真实目标合并了

`socket/websocket` 在入库前会对名称做合并：

- IP 可能按网段模糊化，例如 IPv4 只保留前三段并把最后一段替换为 `*`
- 端口可能被忽略

随后再基于合并后的名称生成 `nameCode` 并做列表聚合。

这会导致一个列表行可能并不只代表一个精确目标，而是多个相似目标的集合。只要这些目标的链路质量差异大，就会出现：

- 大部分样本很快；
- 少部分目标非常慢；
- P99 被慢目标抬高；
- 平均值仍然不高。

### 10.5.3 websocket/socket 的"次数口径"比"耗时口径"更宽

对 `socket/websocket`：

- 非 connect 阶段也会计入请求成功/失败等统计；
- 但这些阶段不会贡献耗时样本。

所以当某个协议扩展：

- 生命周期事件很多；
- 真正 connect 样本不多；
- connect 样本里又刚好存在少量极慢值；

就更容易看到：

- 整体看请求量很大；
- 但耗时指标实际上是基于较小样本集算出来的；
- P99 更容易被少数慢 connect 放大。

### 10.5.4 重连、超时、网络抖动会抬高尾部

协议扩展尤其是 `socket/websocket` 的 connect 阶段，天然容易受这些因素影响：

- DNS 偶发抖动
- TCP 重传
- SSL 握手慢
- 弱网下的重连/超时
- 局部区域网络异常

这些问题不一定频繁发生，但只要占比接近 1%，就足以显著推高 P99，而对平均值的影响有限。

### 10.5.5 样本量不大时，P99 会更接近最大值

当某一行聚合后的样本数不大时，P99 本身就会更接近极值。

比如只有几十次甚至十几次 connect：

- 一两个极慢值就会明显抬高 P99；
- 平均值仍可能被其他正常值压住。

所以小样本场景下，"平均值远小于 P99"会显得更夸张。

## 10.6 从当前实现推导出的几个重要现象

### 10.6.1 `平均耗时 << P99耗时` 本身不代表计算错

只要分布有长尾，这就是正常现象。

### 10.6.2 次数很大，不代表耗时样本也同样大

尤其对 `socket/websocket`，因为非 connect 阶段不参与耗时统计。

### 10.6.3 同一行可能已经混合了多个真实目标

因为名称存在合并规则，行级聚合粒度比"真实单连接目标"更粗。

### 10.6.4 有些行会出现"次数有值，但平均/P99为空"

原因不是前端显示问题，而是该组数据没有有效 `loadTime` 样本，或者有效耗时样本全部来自被过滤后的空值。

## 10.7 对截图现象的业务解释

如果截图中某一行表现为：

- 次数很多；
- 平均耗时只有 `177ms` 左右；
- P99 却达到 `5s+`；

那么按当前代码逻辑，更接近下面这种真实含义：

> 这组协议扩展请求的大多数 connect 很快，但至少约 1% 的 connect 非常慢；并且这一组数据还有可能已经混合了多个被名称合并后的目标，所以尾部延迟被进一步放大。

如果某一行表现为：

- 次数/错误数都有；
- 平均耗时和 P99 都是 `--`；

则更可能表示：

> 这一组协议扩展记录主要是 `socket/websocket` 的非 connect 阶段，记录了状态和次数，但没有有效 `loadTime` 进入耗时聚合。

## 10.8 最终结论

基于当前工作区代码，协议扩展页面出现"平均耗时远远小于 P99耗时"主要由以下几条共同决定：

1. **统计方式不同**
   平均耗时取均值，P99取 99 分位，本来就会对长尾更敏感。

2. **协议扩展首页走聚合指标表**
   查询的是 `"metric"."data"`，不是逐条快照直接展示。

3. **socket/websocket 的耗时只统计 connect 阶段**
   非 connect 阶段保留次数/错误，但耗时被置空。

4. **名称存在合并规则**
   多个真实地址/端口/IP 可能折叠到一行，导致分布更宽。

5. **少量超慢握手足以拉高 P99**
   DNS/TCP/SSL/弱网/重连等问题会优先反映在尾部指标上。

所以，**该现象从代码逻辑上看是合理的，不是前端口径问题，也不必然是后端查询 bug。**

如果后续要进一步判断是否"异常偏大"，建议重点排查：

- 该行是否为 `socket/websocket`
- 是否存在大量重连或 connect 超时
- 是否名称合并后混入了多个质量差异明显的目标
- 该时间窗口内 connect 有效样本数是否偏少
