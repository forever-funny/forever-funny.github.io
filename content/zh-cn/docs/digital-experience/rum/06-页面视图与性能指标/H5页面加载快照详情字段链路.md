# RUM H5 页面加载快照详情字段链路

## 1. 结论先行

本文梳理的字段，不是取自"应用分析"的聚合指标卡片，而是取自 **检索中心 -> 页面加载快照详情 -> 新版详情页**。

前端页面位置：

- `view/rum/src/packages/retrieval/application/view/detail/pageDetail/index.tsx`
- `view/rum/src/packages/retrieval/application/view/detail/pageDetail/page/newIndex/view/topCont/index.tsx`
- `view/rum/src/packages/retrieval/application/view/detail/pageDetail/page/newIndex/view/tabCont/resources/index.tsx`

接口入口：

- 前端调用：`POST /rest/rum/problem/h5/detail`
- 后端入口：`framework/plugins/rum/rum-core/.../RetrievalController.java`

### 1.1 页面完全加载耗时最终取值字段

"页面完全加载耗时"前端最终取值字段是：

- 前端展示字段：`info.loadTime`
- 接口响应来源：`otherIndex.loadTime`
- 前端格式化方式：`number.toUsTos(info.loadTime)`

也就是说，这个字段不是直接取 `snapshotFile.metricInfo`，而是取 **快照结果中的 `otherIndex.loadTime`**。

### 1.2 核心耗时字段最终取值字段

- `TTI 耗时`：前端取 `info.interactiveTime`，来源 `otherIndex.interactiveTime`
- `FCP 耗时`：前端取 `info.fcp`，来源 `otherIndex.fcp`
- `FP 耗时`：前端取 `info.fp`，来源 `otherIndex.fp`
- `LCP 耗时`：前端取 `info.largestContentfulPain`，来源 `snapshotFile.metricInfo.largestContentfulPain`

注意：LCP 虽然在快照 `otherIndex` 里也有一个 `lcp`，但当前这个页面顶部展示实际读的是 `largestContentfulPain`，不是 `lcp`。

## 2. 前端展示链路

### 2.1 页面入口与数据合并

文件：`view/rum/src/packages/retrieval/application/view/detail/pageDetail/index.tsx`

前端进入页面后，调用：

- `request.getH5Detail({ fileId, monitorTime })`
- 对应接口：`/rest/rum/problem/h5/detail`

接口返回成功后，新版快照数据会做一次合并：

1. `snapshotFile.baseInfo`
2. `snapshotFile.deviceInfo`
3. `snapshotFile.metricInfo`
4. `data`
5. `data.otherIndex`

合并顺序意味着：

- 如果 `otherIndex` 和 `metricInfo` 有同名字段，最终以前者为准
- `loadTime / interactiveTime / fcp / fp` 都会以 `otherIndex` 为准
- `largestContentfulPain` 因为 `otherIndex` 没有同名字段，所以最终来自 `metricInfo`

此外，页面还会做一个兼容转换：`baInfo.fcp / fp / largestContentfulPain` 会被除以 `1000` 填到 `baInfo.waterfall`，这是为了瀑布图区域沿用旧结构。

### 2.2 顶部基本信息区字段映射

文件：`view/rum/src/packages/retrieval/application/view/detail/pageDetail/page/newIndex/view/topCont/index.tsx`

顶部展示字段映射如下：

- `TTFB 耗时` -> `info.firstByteTime`
- `DOM interactive 耗时` -> `info.domInteractive`
- `OnDomContentLoaded 耗时` -> `info.domContentLoaded`
- `DOM complete 耗时` -> `info.domComplete`
- `Processing 耗时` -> `info.processing`
- `OnLoad 耗时` -> `info.loadEvent`
- `FP 耗时` -> `info.fp`
- `TTI 耗时` -> `info.interactiveTime`
- `FCP 耗时` -> `info.fcp`
- `LCP 耗时` -> `info.largestContentfulPain`

这些字段统一通过 `number.toUsTos()` 展示，也就是：

1. 接口返回值单位是 **微秒 us**
2. 前端先除以 `1000` 转成 **毫秒 ms**
3. 如果大于等于 `60000ms`，再转成 `s`

格式化函数位置：`view/rum/src/utils/number.ts`，`toUsTos(d)` 实现是 `Number(d) / 1000`。

### 2.3 "页面完全加载耗时"展示位置

文件：`view/rum/src/packages/retrieval/application/view/detail/pageDetail/page/newIndex/view/tabCont/resources/index.tsx`

该页面底部"瀑布图"区域展示的"页面完全加载耗时"逻辑为：

- 取值：`info.loadTime`
- 展示：`number.toUsTos(info.loadTime || 0)`

因此这个值本质上就是：`otherIndex.loadTime`，前端做 `us -> ms/s` 转换后的展示值。

## 4. 入库与存储链路

这里要区分两条并行存储链路：

1. **聚合指标链路**：给统计分析、趋势、聚合报表使用
2. **快照链路**：给当前这种单条快照详情页使用

本文对应的重点是 **快照链路**，但为了回答"完整链路"，下面两条都会说明。

### 4.1 原始上报字段

文件：`controller/ingester/ingester-business/ingester-rum/src/main/java/com/bonree/one/ingester/rum/convert/h5/H5EventConvert.java`

H5 性能指标来自上报体中的 `wpi` 节点，关键短字段如下：

- `fp` -> First Paint
- `fcp` -> First Contentful Paint
- `lcp` -> Largest Contentful Paint
- `tti` -> Time To Interactive
- `di` -> domInteractive
- `dc` -> domComplete
- `lee` -> loadEventEnd
- `les` -> loadEventStart

解析后落到 `WebviewPerformanceInfoEntity`：

- `fp` -> `firstPaintMs`
- `fcp` -> `firstContentfulPaintMs`
- `lcp` -> `largestContentfulPaintMs`
- `tti` -> `timeToInteractiveMs`
- `di` -> `domInteractiveMs`
- `dc` -> `domCompleteMs`
- `lee` -> `loadEventEndMs`

此时单位还是 **毫秒 ms**。

### 4.2 业务标准化转换

文件：`controller/ingester/ingester-business/ingester-rum/src/main/java/com/bonree/one/ingester/rum/convert/h5/H5EventModelConvert.java`

#### 4.2.1 页面完全加载耗时

内部并没有一个上报原始字段叫 `totalLoadTime` 或 `loadTime`。它是一个派生字段，逻辑为：

1. 如果 `loadEventEndMs == -1`，则取 `domCompleteMs`
2. 否则取 `loadEventEndMs`

这一步用于问题类型判断时的 `totalTimeMs`。

#### 4.2.2 FP

逻辑为：

1. 如果 `firstPaintMs > 0`，取 `firstPaintMs`
2. 否则退化为 `domLoadingMs`

因此前端看到的 `FP 耗时` 不一定直接等于原始上报 `fp`，有可能走了回退逻辑。

#### 4.2.3 FCP

逻辑为：只有 `firstContentfulPaintMs > 0` 时，才写入 `fcp`。

#### 4.2.4 TTI

逻辑为：

1. 优先取 `timeToInteractiveMs`
2. 否则如果 `domInteractiveMs > fp`，取 `domInteractiveMs`
3. 否则取 `fp`

因此页面里的 `TTI 耗时` 也不一定直接等于上报 `tti`，它是一个带回退的业务字段。

### 4.3 聚合指标入库链路

文件：`controller/ingester/ingester-business/ingester-rum/src/main/java/com/bonree/one/ingester/rum/convert/h5/H5ResultZeusConvert.java`

这里会把前面的业务字段写入 H5 聚合结果对象 `H5ResultZeus`，并统一转成 **微秒 us**：

- 页面完全加载耗时：`loadEventEndMs <= 0 ? domCompleteMs : loadEventEndMs`，再乘 `1000`，写入 `setTotalTime(totalTimeUs)`
- `FP`：`setFp(h5EventModel.getFp() * 1000)`
- `FCP`：`setFcp(h5EventModel.getFcp() * 1000)`
- `LCP`：`setLcp(largestContentfulPaintMs * 1000)`
- `TTI`：`setInteractiveTime(h5EventModel.getInteractiveTimeMs() * 1000)`

#### 4.3.1 聚合存储字段

文件：`controller/ingester/ingester-business/ingester-operator/src/main/java/com/bonree/one/ingester/operator/storage/model/enums/ck/CkH5.java`

对应关系如下：

- 页面完全加载耗时 -> 指标 ID `one.rum.page.h5.totalLoadTime` -> 列 `total_time`
- FP -> 指标 ID `one.rum.page.h5.fp` -> 列 `fp`
- FCP -> 指标 ID `one.rum.page.h5.fcp` -> 列 `fcp`
- LCP -> 指标 ID `one.rum.page.h5.lcp` -> 列 `lcp`
- TTI -> 指标 ID `one.rum.page.h5.timeToInteractive` -> 列 `interactive_time`

这条链路主要供聚合分析页、趋势图、指标卡等场景使用。

### 4.4 快照详情入库链路

文件：`controller/ingester/ingester-business/ingester-rum/src/main/java/com/bonree/one/ingester/rum/convert/h5/H5SnapshotResultZeusConvert.java`

这是和当前详情页最相关的链路。

#### 4.4.1 写入 otherIndex 的字段

`otherIndex` 中关键字段如下，单位全部为 **微秒 us**：

- `loadTime`
- `fcp`
- `fp`
- `lcp`
- `domInteractive`
- `interactiveTime`
- `firstByteTime`

其中：

- `otherIndex.loadTime = getTotalTimeUs(h5EventModel)`
- `otherIndex.fcp = h5EventModel.getFcp() * 1000`
- `otherIndex.fp = h5EventModel.getFp() * 1000`
- `otherIndex.lcp = largestContentfulPaintMs * 1000`
- `otherIndex.interactiveTime = h5EventModel.getInteractiveTimeMs() * 1000`

#### 4.4.2 写入 snapshotFile.metricInfo 的字段

同一个转换类还会构造 `metricInfo`，并最终写入 `snapshotFile`：

- `applicationCache`
- `domContentLoaded`
- `domComplete`
- `processing`
- `loadEvent`
- `largestContentfulPain`
- `blocking`
- `requestTime`
- `dnsTime`
- `tcpTime`
- `sslTime`
- `htmlDownloadTime`

这里特别注意：页面展示 `LCP 耗时` 用的是 `metricInfo.largestContentfulPain`，不是 `otherIndex.lcp`。

#### 4.4.3 snapshotFile 的组装

文件：`controller/ingester/ingester-business/ingester-rum/src/main/java/com/bonree/one/ingester/rum/biz/ThreadMethodBiz.java`

组装逻辑：

1. `baseInfo`
2. `deviceInfo`
3. `metricInfo`

最终通过 `buildBrfsFileJson()` 生成快照文件 JSON。

### 4.5 快照查询返回后与前端字段的最终对应

当前详情页所在页面，新版快照详情最终字段对应关系如下。

#### 页面完全加载耗时

1. 上报：`wpi.lee` / `wpi.dc`
2. 解析：`loadEventEndMs` / `domCompleteMs`
3. 派生：`loadEventEndMs <= 0 ? domCompleteMs : loadEventEndMs`
4. 快照入库：`otherIndex.loadTime`
5. 查询返回：`/rest/rum/problem/h5/detail` 的 `otherIndex.loadTime`
6. 前端展示：`info.loadTime` -> `number.toUsTos(info.loadTime)`

#### TTI 耗时

1. 上报：`wpi.tti`
2. 解析：`timeToInteractiveMs`
3. 业务回退：先取 `tti`，再退到 `domInteractive`，再退到 `fp`
4. 快照入库：`otherIndex.interactiveTime`
5. 查询返回：`otherIndex.interactiveTime`
6. 前端展示：`info.interactiveTime`

#### FCP 耗时

1. 上报：`wpi.fcp`
2. 解析：`firstContentfulPaintMs`
3. 入快照：`otherIndex.fcp`
4. 查询返回：`otherIndex.fcp`
5. 前端展示：`info.fcp`

#### FP 耗时

1. 上报：`wpi.fp`
2. 解析：`firstPaintMs`
3. 业务回退：先取 `firstPaintMs`，否则取 `domLoadingMs`
4. 入快照：`otherIndex.fp`
5. 查询返回：`otherIndex.fp`
6. 前端展示：`info.fp`

#### LCP 耗时

1. 上报：`wpi.lcp`
2. 解析：`largestContentfulPaintMs`
3. 入快照：`otherIndex.lcp` 和 `metricInfo.largestContentfulPain`
4. 查询返回：`snapshotFile.metricInfo.largestContentfulPain`
5. 前端展示：`info.largestContentfulPain`

## 5. 一个容易混淆但必须说明的点

`RetrievalService.decorateData4Alert()` 在处理 H5 快照时，还会额外往返回结果顶层的 `metricInfo` 里写：

- `interactiveTime = otherIndex.domInteractive / 1000`

但当前这个前端页面并 **没有** 使用返回结果顶层的 `metricInfo.interactiveTime` 作为最终展示值。

当前页面的数据合并逻辑是：

- 先拿 `snapshotFile.metricInfo`
- 再拿 `otherIndex`

因此页面上实际展示的 `TTI 耗时` 仍然是 `otherIndex.interactiveTime`，不是 `result.metricInfo.interactiveTime`。

这个差异在排查"为什么接口里看到两个 interactiveTime 概念"时要特别注意。

## 6. 这些指标在 RUM 前端监控中的含义

这一节从 **RUM 前端性能语义** 出发，解释这些指标各自代表什么、关注什么问题、以及它们之间通常有什么关系。

### 6.1 页面完全加载耗时

页面完全加载耗时，通常可以理解为：从本次页面导航开始，到页面主要加载流程结束，页面进入"基本加载完成"状态所消耗的总时间。

在浏览器标准语义里，这个概念通常更接近 `loadEventEnd`。而在当前系统实现里，页面完全加载耗时的取值逻辑是：

- 优先取 `loadEventEndMs`
- 如果 `loadEventEndMs <= 0`，则回退取 `domCompleteMs`

因此它反映的是 **整个页面加载流程的尾部耗时**，更偏向"页面什么时候整体收尾完成"。

它比较适合回答的问题是：

- 这个页面总体加载是不是慢
- 页面是否存在长尾资源、后置脚本、onload 之后才结束的工作
- 为什么用户觉得页面"整体结束得很晚"

### 6.2 FP 耗时

FP，`First Paint`，首帧绘制时间。它表示：浏览器第一次把任何像素真正绘制到屏幕上的时间。

它关注的是：

- 用户是不是很快看到"屏幕有变化了"
- 页面是否还处于完全空白状态

在 RUM 领域里，FP 常被拿来衡量：白屏时间、首次视觉反馈的早晚。

但要注意，当前系统中的 FP 不是完全等于浏览器原始 `fp`：

- 如果上报里的 `firstPaintMs > 0`，则取它
- 否则回退到 `domLoadingMs`

所以当前系统里的 `FP 耗时` 更准确地说，是一个 **"首个可见变化时间"的业务近似值**。

### 6.3 FCP 耗时

FCP，`First Contentful Paint`，首次内容绘制时间。它表示：页面首次把"有意义内容"绘制到屏幕上的时间。

这里的"内容"通常包括：文本、图片、`canvas`、SVG。

它比 FP 更贴近真实用户感知，因为：

- FP 只要求屏幕有像素变化
- FCP 则要求用户开始看到真正的内容

在体验分析里，FCP 常用于回答：

- 用户什么时候第一次看到页面内容
- 为什么页面不是白屏，但内容出现还是很晚

### 6.4 LCP 耗时

LCP，`Largest Contentful Paint`，最大内容绘制时间。它表示：视口内最大内容元素完成绘制的时间。

这个"最大内容元素"通常是：大图、大块文本、Banner、首屏主内容块。

LCP 在现代前端性能分析里非常重要，因为它比 FP/FCP 更贴近：用户认为"页面主内容是否已经出来了"。

也就是说：

- FP 解决"有没有亮"
- FCP 解决"有没有内容"
- LCP 解决"主要内容出来了没有"

所以从用户体感上讲，LCP 往往比 FP/FCP 更接近"首屏体验好不好"。

### 6.5 TTI 耗时

TTI，`Time To Interactive`，可交互时间。它表示：页面不仅已经显示出来了，而且用户开始可以稳定交互了。

所谓"可交互"，通常意味着：页面主线程不再长时间阻塞、点击/输入/滚动等交互能够及时响应。

它关注的不是"能不能看到"，而是：

- 能不能操作
- 操作后能不能比较快得到反馈

当前系统中，TTI 也不是绝对等于原始上报 `tti`，而是带回退逻辑：

1. 优先取 `timeToInteractiveMs`
2. 否则取 `domInteractiveMs`
3. 再不满足则回退为 `fp`

所以当前系统里的 `TTI 耗时` 更准确地说，是一个 **"页面可交互时刻的业务近似值"**。

### 6.6 这些指标通常存在什么关系

从标准语义和正常页面时序看，这几个指标通常代表的是页面体验逐步推进的几个阶段：

1. `FP`
2. `FCP`
3. `LCP`
4. `TTI`
5. `页面完全加载耗时`

可以粗略理解为：

- `FP`：屏幕第一次亮起来
- `FCP`：用户第一次看到真实内容
- `LCP`：用户看到首屏主要内容
- `TTI`：用户可以开始稳定操作
- `页面完全加载耗时`：页面整体加载流程基本收尾

如果用更口语化的话说：

- `FP` 解决"不是白屏了"
- `FCP` 解决"开始有内容了"
- `LCP` 解决"主要内容出来了"
- `TTI` 解决"终于能点了"
- `页面完全加载耗时` 解决"这次页面加载什么时候彻底结束了"

### 6.7 它们之间是否一定单调递增

理论上，很多页面会表现出类似这样的关系：

`FP <= FCP <= LCP <= TTI <= 页面完全加载耗时`

但这不是绝对数学定律，原因有两类。

#### 6.7.1 浏览器语义层面不一定绝对严格

例如：

- 某些页面首屏主内容很快出来，`LCP` 可能已经很早出现
- 但后面仍有大量脚本执行，导致 `TTI` 很晚
- 或者某些页面内容已经出来，但 `loadEventEnd` 还要等很多资源完成

所以：`LCP` 和 `TTI`、`TTI` 和 `页面完全加载耗时` 在业务上通常有先后倾向，但不能机械地理解成所有页面都严格固定。

#### 6.7.2 当前系统实现里存在回退逻辑

当前 RUM 系统对几个指标做了业务回退：

- `FP` 可能回退到 `domLoadingMs`
- `TTI` 可能回退到 `domInteractiveMs`，甚至回退到 `fp`
- `页面完全加载耗时` 可能回退到 `domCompleteMs`

因此在个别异常数据里，可能出现：`TTI` 看起来偏小、`FP` 和 `FCP` 非常接近、`页面完全加载耗时` 与 `DOM complete` 一样。这并不一定表示前端真实语义就是这样，也可能是 **采集缺失后的回退结果**。

#### 6.7.3 基于当前代码，什么情况下会出现"页面完全加载耗时 < FCP / LCP / TTI"

这一节只基于当前代码逻辑来分析，不讨论理想语义，只讨论 **当前系统最终会如何取值**。

先看几个关键取值逻辑：

- `页面完全加载耗时 = loadEventEndMs <= 0 ? domCompleteMs : loadEventEndMs`
- `FCP = firstContentfulPaintMs`，仅要求 `> 0`
- `LCP = largestContentfulPaintMs`，仅要求 `>= 0`
- `TTI = timeToInteractiveMs`，否则回退 `domInteractiveMs`，再否则回退 `fp`

并且当前校验逻辑只做了以下几类检查：

- 单字段范围是否合法
- `lee` 和 `dc` 不能同时 `<= 0`
- 少量固定前后顺序校验，例如 `responseEnd >= responseStart`

当前代码 **并没有** 校验：

- `FCP <= loadEventEnd/domComplete`
- `LCP <= loadEventEnd/domComplete`
- `TTI <= loadEventEnd/domComplete`

因此，只要这些字段自身数值合法，就可能被原样入库并在页面展示出来。

##### 情况一：页面完全加载耗时 < LCP

这是当前系统里 **最可能出现且相对合理** 的一种情况。

原因是：页面完全加载耗时取的是 `loadEventEnd`，缺失时取 `domComplete`；`LCP` 取的是 `largestContentfulPaint`；当前代码没有要求 `LCP` 必须早于 `loadEventEnd`。

在业务上，以下场景都可能出现：

- 页面主框架和大部分资源已经完成，`onload` 已经触发
- 但首屏最大元素是一个大图、Banner、懒加载主内容块
- 这个最大元素在 `onload` 之后才真正绘制完成

落到当前系统里，就会出现 `loadTime < LCP`。这类情况通常不一定是脏数据，也可能是页面加载策略本身导致的正常现象。

##### 情况二：页面完全加载耗时 < TTI

这也是当前系统里 **比较可能出现且通常合理** 的情况。

原因是：`页面完全加载耗时` 取 `loadEventEnd` 或 `domComplete`；`TTI` 优先取原始 `tti`，原始 `tti` 的语义是"页面真正稳定可交互"。

因此，如果页面出现下面这些情况：

- 首屏内容和资源已经基本加载完成
- 但 `onload` 之后还在执行大量 JS
- 主线程有长任务
- 事件绑定、数据计算、框架 hydration、异步渲染比较重

那么就可能出现：页面看起来"加载完了"，但交互仍然卡，真正稳定可交互的时间更晚。落到数值上就是 `loadTime < TTI`。

这个现象在前端性能分析里是成立的，而且往往正说明：页面"可见完成"早于"可交互完成"。

##### 情况三：页面完全加载耗时 < FCP

从浏览器正常页面加载语义看，这种情况 **通常不应该出现**。因为按常规理解：页面都已经到 `domComplete` 或 `loadEventEnd` 了，`FCP` 理应早就发生了。

但在当前系统代码里，这种情况并没有被强约束拦截，所以仍然可能出现。通常更偏向以下几类原因。

###### 3.1 `loadTime` 走了回退，而回退值偏小

当前 `loadTime` 的逻辑是：`loadEventEndMs <= 0` 时，直接回退到 `domCompleteMs`。

如果上报数据里：`loadEventEndMs` 缺失或异常、`domCompleteMs` 有值但偏小、同时 `firstContentfulPaintMs` 本身又被上报为更大的值，那最终就可能表现为 `loadTime < FCP`。

也就是说，这种场景下更像是：**页面完全加载耗时被回退到了一个较早的时间点**。

###### 3.2 上报数据本身存在时序不一致

当前校验逻辑会校验：范围是否越界、个别关键字段的先后顺序。但没有校验 `fcp <= dc`、`fcp <= lee`。

所以如果 SDK 上报、浏览器兼容、采集时钟、埋点实现出现偏差，像下面这种数据仍有可能通过：

- `domCompleteMs = 1200`
- `loadEventEndMs = -1`
- `firstContentfulPaintMs = 1800`

最终系统会得到：`loadTime = 1200`、`FCP = 1800`，于是页面上就会出现 `页面完全加载耗时 < FCP`。

这种情况从业务解释上通常更偏向：采集异常、浏览器实现差异、SDK 兼容问题、上报字段时序不一致，而不是正常用户体验链路。

###### 3.3 单条快照中不同字段来源于不同语义时间点

当前页面展示时，字段并不是全部来自同一个对象：

- `页面完全加载耗时` 取自 `otherIndex.loadTime`
- `FCP` 取自 `otherIndex.fcp`
- `LCP` 取自 `metricInfo.largestContentfulPain`
- `TTI` 取自 `otherIndex.interactiveTime`

虽然这些值本质都来自同一次上报，但经过了：解析、回退、快照组装、多字段落库。因此如果某个字段走了回退、另一个字段保留原值，就可能造成：语义上本该更晚的值看起来反而更早，或本该更早的值看起来反而更晚。这会放大 `loadTime < FCP/LCP/TTI` 这类现象。

##### 情况四：页面完全加载耗时 < TTI，但 TTI 不是原始 tti，而是回退值

如果原始 `tti` 没上来，TTI 会回退：先看 `domInteractiveMs`，再退到 `fp`。

其中：如果回退到 `domInteractiveMs`，而同时 `loadTime` 因为 `lee <= 0` 回退到了一个偏早的 `domCompleteMs`，那也可能出现 `loadTime < TTI`。

这时虽然结果表面上合理，但要注意：这里的 `TTI` 可能不是浏览器原生意义上的 `timeToInteractive`，而是系统回退后的"可交互近似值"。

##### 情况五：页面完全加载耗时 < LCP/FCP/TTI，且只在少量样本里零星出现

如果这类现象：不是普遍规律、只在少量样本里出现、尤其是 `loadTime < FCP`，那在当前系统下，更建议优先怀疑：

- 原始上报时序异常
- 浏览器兼容差异
- 采集字段缺失触发回退
- 极端边缘场景下的快照数据不一致

而不是先把它理解成页面正常性能表现。

#### 6.7.4 可以怎么判断这是"正常现象"还是"异常数据"

结合当前代码，可以按下面思路判断。

##### 更像正常现象

- `loadTime < LCP`
- `loadTime < TTI`
- 且差值不离谱
- 页面本身存在懒加载、大图、异步渲染、长任务、重 JS 执行

这时更像是：页面可见完成早于主内容完成、页面主内容完成早于可交互完成。

##### 更像异常或数据不一致

- `loadTime < FCP`
- `loadTime` 明显远小于 `FCP/LCP/TTI`
- 同时出现 `loadEventEnd <= 0` 的回退痕迹
- 或同类页面只有极少量样本出现

这时更像是：`loadTime` 回退过早、原始采集时序不一致、某些浏览器或 SDK 场景下字段语义不完全一致。

#### 6.7.5 针对本系统的最终判断建议

基于当前代码，可以给出比较稳妥的结论：

- `页面完全加载耗时 < LCP`：**可能正常，优先结合页面懒加载和首屏主内容渲染策略判断**
- `页面完全加载耗时 < TTI`：**可能正常，常见于 onload 后仍有重 JS 或长任务**
- `页面完全加载耗时 < FCP`：**通常不符合常规加载语义，在当前系统里更应优先怀疑回退逻辑或采集数据时序异常**

如果要把这部分用于交付或培训，建议统一表述为：

- `loadTime < LCP/TTI` 不一定是错，可能是页面加载与交互、主内容渲染脱钩
- `loadTime < FCP` 在当前实现下通常应视为重点排查样本

### 6.8 这些指标关注的是不同层次的问题

从排障视角看，这几个指标分别适合定位不同问题。

#### FP 偏大

更可能说明：页面白屏时间长、HTML 到首个像素渲染之间存在阻塞、CSS/同步脚本/首帧前执行逻辑过重。

#### FCP 偏大

更可能说明：页面虽然不完全白屏，但真实内容出来得慢、首屏关键文本/图片/首屏内容渲染慢。

#### LCP 偏大

更可能说明：首屏主内容资源慢、Banner/大图/大块内容渲染慢、首屏真正影响感知的核心区域出来得晚。

#### TTI 偏大

更可能说明：JS 执行过重、主线程长任务多、用户虽然看到了页面但点击无响应或响应迟缓。

#### 页面完全加载耗时偏大

更可能说明：页面尾部资源很多、onload 之后仍有较重工作、长尾请求/非关键资源/延后脚本让整体加载结束得很晚。

### 6.9 当前文档这几个指标之间的实现关系

结合本系统代码实现，可以把关系再总结成下面这样：

- `FP` 是最早的视觉反馈指标，但带回退逻辑
- `FCP` 是首次内容出现指标
- `LCP` 是首屏最大内容完成指标
- `TTI` 是可交互指标，但当前系统里是"原始 TTI + 回退逻辑"后的业务值
- `页面完全加载耗时` 是整体加载尾部指标，本系统取 `loadEventEnd`，缺失时回退 `domComplete`

所以在当前系统里，这五个指标不是互相替代关系，而是：

- **描述同一次页面加载过程的不同阶段**
- **从"能看到"到"主内容出现"再到"能操作"再到"整体结束"**
- **共同构成一条完整的用户加载体验链路**

## 7. 本次问题的最终答案

### 7.1 页面完全加载耗时从哪个字段取值

直接答案：

- 前端最终取值字段：`info.loadTime`
- 接口原始字段：`otherIndex.loadTime`
- 入库来源：H5 快照入库时写入的 `loadTime`
- 原始计算逻辑：`loadEventEndMs <= 0 ? domCompleteMs : loadEventEndMs`

### 7.2 TTI/FCP/LCP/FP 的完整链路

- `TTI 耗时`
  - 上报 `wpi.tti`
  - 解析为 `timeToInteractiveMs`
  - 业务回退得到 `interactiveTimeMs`
  - 写入 `otherIndex.interactiveTime`
  - 聚合链写入 `one.rum.page.h5.timeToInteractive / interactive_time`
  - 页面展示取 `info.interactiveTime`

- `FCP 耗时`
  - 上报 `wpi.fcp`
  - 解析为 `firstContentfulPaintMs`
  - 写入 `otherIndex.fcp`
  - 聚合链写入 `one.rum.page.h5.fcp / fcp`
  - 页面展示取 `info.fcp`

- `LCP 耗时`
  - 上报 `wpi.lcp`
  - 解析为 `largestContentfulPaintMs`
  - 写入 `otherIndex.lcp` 和 `metricInfo.largestContentfulPain`
  - 聚合链写入 `one.rum.page.h5.lcp / lcp`
  - 页面展示取 `info.largestContentfulPain`

- `FP 耗时`
  - 上报 `wpi.fp`
  - 解析为 `firstPaintMs`
  - 回退后得到 `fp`
  - 写入 `otherIndex.fp`
  - 聚合链写入 `one.rum.page.h5.fp / fp`
  - 页面展示取 `info.fp`
