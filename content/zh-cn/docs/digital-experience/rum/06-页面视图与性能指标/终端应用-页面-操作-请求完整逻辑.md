## 1. 文档目标

本文对 RUM 模块中与以下四类核心对象相关的完整链路进行梳理：

- 终端应用
- 页面
- 操作
- 请求

梳理范围覆盖两条主线：

1. **分析查询链路**：前端页面如何发起查询、如何跳转、调用哪些接口，最终查询哪一类 RUM 后端能力。
2. **原始采集入库链路**：终端 SDK / Web SDK 上报的原始数据，如何被接收、校验、过滤、判断、拆分、映射并最终写入下游存储。

## 2. 涉及的工程角色

### 2.1 `view/rum`

RUM 前端主工程，职责：

- 页面路由注册
- 页面分析、终端应用、网络请求、操作详情等页面展示
- 查询条件组装
- 调用 `/rest/rum/**` 接口
- 页面之间的跳转参数拼装

### 2.2 `framework/plugins/rum`

RUM Java 插件后端，职责偏向：

- 控制台查询接口
- 配置管理
- 检索中心
- 会话/回放/告警/设置
- 向 ingester / ETL 发配置或地址层面的衔接

**结论**：它主要是"查询/配置面"，不是原始 RUM 上报的主数据接收面。

### 2.3 `controller/controller`

控制层工程，当前可见代码中能确认：

- 存在通用上传入口，例如 `UploadController`
- 提供配置、上传、控制类能力

但对 **RUM 原始 JSON 上报 HTTP 路由**，当前可见代码里没有直接找到一个与 `RumControllerFilterStrategy` 一一对应的 `@RestController`。从可见代码可确认的是：**进入 ingester 时，原始请求已经被封装为 Kafka 输入消息，并保留了请求头和原始 query 信息**。

### 2.4 `controller/ingester/ingester-business/ingester-rum`

RUM 原始数据处理主工程，职责：

- 请求入站后的参数校验
- 应用合法性校验
- License 校验
- 解密、解压
- 原始协议 JSON 转 Java 对象
- 按事件类型拆分
- 页面/操作/请求等事件的清洗、判断、映射
- 生成统计表、快照表、DataSee 数据

### 2.5 `controller/ingester/ingester-business/ingester-operator`

通用 operator / 输出层，职责：

- 接收 `CkResultModel`
- 根据表名和数据模型做最终输出
- 调用 CK 客户端执行入库

## 3. 总体逻辑图

### 3.1 分析查询链路

```text
前端页面(view/rum)
  -> service 层调用 /rest/rum/** 接口
  -> framework/plugins/rum 的查询/配置能力
  -> 查询已处理、已入库的数据
  -> 返回终端应用 / 页面 / 操作 / 请求分析结果
```

### 3.2 原始采集入库链路

```text
SDK / Web SDK 原始上报
  -> 上游接入层/控制层
  -> Kafka 消息(保留 origin-url-query / brkey / x-real-ip 等头信息)
  -> RumControllerFilterStrategy
  -> RumInputTransform
  -> RumFlattenTransform
  -> EventProcessFactory 分发到 页面 / 操作 / 请求 等策略
  -> RumMappingTransform
  -> 生成 CkResultModel / SnapshotDataDTO / KafkaResultModel / MySQLTransferData
  -> ingester-operator 输出到 ClickHouse / 其他下游
```

## 4. 前端分析查询链路

### 4.1 路由入口

RUM 前端在 `view/rum/src/routes/route.ts` 中注册了以下关键页面：

- `/experience/application`：终端应用
- `/experience/page/analysis`：页面分析
- `/experience/page/analysis/detail/:appId/:pageId/:pageType/:pageName`：页面分析详情
- `/experience/application/detail/operate/:appId/:platform/:actionType/:viewCode/:actionCode/:actionName`：操作详情
- `/experience/request/**`：网络请求分析

因此，前端业务上"终端应用 -> 页面 -> 操作 -> 请求"的浏览路径是完整串联的。

### 4.2 页面分析列表：终端应用 -> 页面

#### 4.2.1 页面状态与请求入口

核心状态模型在 `view/rum/src/packages/experience/pageAnalysis/models/index.ts`，定义了页面分析列表的四个分页/Tab 维度：

- `1`：H5 页面
- `2`：单页面路由
- `3`：原生视图
- `4`：小程序视图

并维护了 `filterKeyObj`、`businessTypeObj`、`sortedInfoObj`、`filterValue`、`appIds`、`timeParams`。

#### 4.2.2 前端如何组装请求

列表拉取统一走 `initTableList()`：

- 先拼装 `filters`
- 拼装时间范围 `startTime/endTime`
- 拼装分页 `pageNo/pageSize`
- 拼装应用 `appIds`
- 拼装排序 `sortField/sortOrder`
- 拼装业务类型 `queryJson.businessType`

然后根据当前 `activeKey` 选择不同接口：

| 页面类型 | 前端方法 | 接口 |
| --- | --- | --- |
| H5 页面 | `request.getPageDomainList` | `/rest/rum/digit/appPage/pageDomainList` |
| 单页面路由 | `request.getPageRouteList` | `/rest/rum/digit/appPage/pageRouteList` |
| 原生视图 | `request.getViewTable` | `/rest/rum/digit/appView/getViewTableByApp` |
| 小程序视图 | `request.getMpViewTable` | `/rest/rum/mp/mpList` |

#### 4.2.3 页面分析列表中的过滤与表头

前端在列表拉取前，还会先拉两类配置：

1. **过滤器配置**：`commonServices.getFilter`，key 来自 `filterKeyObj`，例如 `page_analysis_app_h5_table`、`app_single_route_table`
2. **表头配置**：`commonServices.getHeader`，`businessType` 来自 `businessTypeObj`

这意味着前端的列表展示并不是写死字段，而是由后台配置驱动。

#### 4.2.4 前端对页面类型的统一枚举与分组

前端在 `pageAnalysis/common.tsx` 中维护了统一的页面类型枚举：

| pageType | 含义 |
| --- | --- |
| 1 | H5 |
| 2 | Activity |
| 3 | Fragment |
| 4 | Windows |
| 5 | Controller |
| 6 | Rn |
| 7 | Flutter |
| 8 | Ability |
| 9 | AbilitySlice |
| 10 | Mp |
| 11 | singlePage |

同时前端又把这些细粒度类型重新归并成"页面分析"所需的几类大类：

1. **详情页基础信息分组**：`getScoreEnumByPageType(pageType)`，`1/11 -> page`，其他 -> `view`
2. **页面饼图/趋势分析分组**：`getPieChartPageType(pageType)`，`1 -> 1`(H5)，`2-9 -> 2`(原生视图)，`10 -> 3`(小程序视图)，`11 -> 4`(单页面)
3. **列表 Tab 与应用类型匹配**：`appTypesEmus`，`1/2` 两个页面型 Tab 同时支持 H5 与单页面所在的应用类型，`3` 只承接原生视图型应用，`4` 只承接小程序应用

因此，前端虽然对用户展示为"页面分析"，但内部实际已经把页面类型拆成：H5 页面、单页面路由、原生视图、小程序视图，原生视图下再细分不同视图类型。

### 4.3 从页面列表进入页面详情

前端通过 `routeJump.pageAnalysisPageDetail()` 拼接页面详情路由。该函数会根据当前列表类型映射 `pageId`、`pageType`、`pageName`：

| activeKey | pageId 来源 | pageType | pageName 来源 |
| --- | --- | --- | --- |
| 1 | `nameCode` | `1` | `viewName` |
| 2 | `viewNameCode` | `11` | `pageUrl` |
| 3 | `viewNameCode` | 真实视图类型 | `viewName` |
| 4 | `viewCode` | `10` | `pageName` |

最终进入：`/experience/page/analysis/detail/:appId/:pageId/:pageType/:pageName`，其中 `pageName` 做了 Base64 编码。

### 4.4 页面详情：页面 -> 操作

页面详情状态模型在 `view/rum/src/packages/experience/pageAnalysis/pageDetails/models/index.ts`。

#### 4.4.1 页面详情初始化

进入详情页后，前端先做以下初始化：

1. 解析路由参数
2. 根据 `pageType` 判断 `pageEnum`：`page`（H5 / 路由页）、`view`（原生视图 / 小程序视图）
3. 拉取：smartalert 开关、健康分、基本信息、指标卡片、趋势/维度/饼图

#### 4.4.2 页面基本信息接口

- `pageEnum === 'page'`：`request.getH5BaseInfo` -> `/rest/rum/digit/appPage/basicInfo`
- `pageEnum === 'view'`：`request.getActivityBaseInfo` -> `/rest/rum/digit/appView/getViewDetailBasicInfo`

#### 4.4.3 页面级趋势/维度/饼图接口

在 `view/rum/src/services/experience/pageAnalysis.ts` 中定义：

- 趋势图：`/rest/rum/digit/appPage/trendAnalysisTop`
- 维度分析：`/rest/rum/digit/appPage/dimensionalAnalysis`
- 维度下拉：`rest/rum/metric/dimension/query`
- 代码异常饼图：`/rest/rum/digit/appPage/pieChart/codeException`
- 页面加载状态饼图：`/rest/rum/digit/appPage/pieChart/pageLoadingStatus`
- 单页面框架列表：`/rest/rum/digit/appPage/singlePageFrameworks`

关键差异：

- **H5 页面与单页面**：前端都走 `pageEnum = 'page'` 的查询面
- **原生视图与小程序视图**：前端都走 `pageEnum = 'view'` 的查询面
- **页面饼图/趋势类接口又会额外通过 `pageAnalysisType` 再细分**

所以前端对页面类型是"两层映射"：第一层决定调用 `appPage` 还是 `appView` 的基本信息能力，第二层决定趋势/维度/饼图接口里属于 H5、原生视图、小程序还是单页面。

#### 4.4.4 页面详情中的"操作"Tab

操作表格核心方法为 `getActionTableList()`，请求参数包括：`startTime`、`endTime`、`appId`、`filters`、`queryKey = 'app_action_table'`、`viewCode = routeParams.pageId`、`page/pageSize`、`keyEntityFlag`、`platform`、`sortField/sortOrder`。

对应接口：`/rest/rum/operation/operationListQuery`。

同时还会请求：

- 操作筛选配置：`commonService.getFilter({ key: 'app_action_table' })`
- 操作表头配置：`commonService.getHeader({ businessType: '44001' })`

### 4.5 从操作进入请求

页面详情中的操作表，行点击后通过 `routeJump.actionDetail()` 进入操作详情页：

`/experience/application/detail/operate/:appId/:platform/:actionType/:viewCode/:actionCode/:actionName`

随后在操作详情页内继续查看请求数据，主要接口包括：

- 操作趋势：`/rest/rum/operation/reqTrend`
- 操作维度分析：`/rest/rum/operation/reqAnalysis`
- 操作记录列表：`/rest/rum/retrieve-center/record-list`

因此从前端视角，完整链路是：

```text
终端应用
  -> 页面分析列表
  -> 页面详情
  -> 操作列表
  -> 操作详情
  -> 请求趋势 / 请求维度 / 请求记录
```

## 5. 原始采集接收与处理总链路

### 5.1 当前代码能确认的接收边界

当前可见代码中可以明确两件事：

1. **进入 RUM ingester 前，原始请求已经被包装成 Kafka 输入消息。**
2. Kafka 消息头里保留了这些原始入站信息：`origin-url-query`、`brkey`、`x-real-ip`、`content-encoding`。

这说明 RUM 原始上报的"HTTP 接入层"并不完全落在本次可见代码中，但从 `RumControllerFilterStrategy` 开始，后续处理链已经完整可见。

### 5.2 第一层：入站过滤与参数校验

核心类：`com.bonree.one.ingester.rum.filter.RumControllerFilterStrategy`

#### 5.2.1 处理步骤

`handleInput()` 的顺序非常清晰：

1. 从 `origin-url-query` 中解析 URL 参数
2. 解密 `decryptContent()`
3. 参数校验 `checkParam()`
4. 应用存在性校验 `filterApp()`
5. License 校验 `checkLicense()`
6. 校验 `brkey`
7. 如果 `content-encoding=gzip`，则解压
8. 对 Web 应用提取真实设备 IP
9. 将原始数据做转发埋点 `DataForwarder.inputDataForward()`
10. JSON 反序列化成 `UploadDataModel`

#### 5.2.2 参数校验逻辑

`checkParam()` 主要做了以下校验：

- `param` 不能为空
- 如果存在 `p`，先 Base64 解码再展开 query 参数
- 必填参数必须存在：`d`(deviceId)、`a`(appMd5)、`v`(协议版本)、`s`(session)、`mt`(monitorTime)
- `deviceId` 格式合法
- 请求体不能为空
- 请求体大小不能超过 `multipartMaxsize`
- 若为精简协议 `m=1` 且当前未开启 `agentMode`，则直接丢弃

#### 5.2.3 应用校验逻辑

`AbstractRumKafkaFilterStrategy.filterApp()` 通过 `AppCache` 做校验：

- 应用不存在 -> 丢弃
- 应用已归档 -> 丢弃
- 应用状态不是启用态 -> 丢弃

#### 5.2.4 License 校验逻辑

`AbstractRumKafkaFilterStrategy.checkLicense()` 做了四层判断：

1. `AppCache` 中能否取到应用
2. `RumLicenseCache` 中能否取到该用户 License
3. 是否能找到对应的 `LicenseCheckService`
4. 是否通过：web 配置校验、精简模式校验、uploadLicenseCheck

#### 5.2.5 大包处理与备份

若原始包过大：直接判定失败，把请求体写入本地目录 `multipartSavePath`，用于后续排障。

### 5.3 第二层：输入算子封装

核心类：`RumInputTransform`

职责：完成算子初始化、将 `UploadDataModel` 包装成 Flink 可处理结构、绑定 RUM 广播配置流。

处理逻辑：

1. 读取消息内容
2. 解析为 `UploadDataModel`
3. 提取时间戳
4. 写入 `UPLOAD_MODEL`
5. 进入下一算子

这一步还没有真正按事件拆解，只是把"一个上传包"变成标准流内对象。

### 5.4 第三层：上传协议解析

核心类：`UploadRequestConvert`

职责：把上传 JSON 解析成 `UploadRequestEntity`。

解析内容包括：session、version、monitorTime、configMonitorTime、firstUserInfoIndex、duration、trackId、processId、AppStateInfo、DeviceInfo、AppInfo、TrafficInfo、UserInfo 集合、DeviceStateInfo 集合、NetworkStateInfo 集合、Event 列表、DataFusionInfo、EventExtInfo、EventViewInfo、firstDay。

特别注意：`eventInfoConvert()` 在解析完真实业务事件后，还会额外补一个 `UPLOAD` 事件，用于统计上传本身。

### 5.5 第四层：构建公共上下文并做通用过滤

核心类：`RumFlattenTransform`

#### 5.5.1 核心职责

`RumFlattenTransform` 负责把"上传包"拆成"可独立处理的事件流"。它做了以下事情：

1. `DataFactory.dataConvert(uploadDataModel)` -> `UploadRequestEntity`
2. `DataFactory.buildCommonModel(...)` -> `CommonModel`
3. `DataCheckUtil.commonFilterIfNecessary(...)` -> 通用过滤
4. 从上传包中取出 `eventEntities`
5. 按 `EventTypeEnum` 分组
6. 进入递归平铺 `dfsEventFlatten()`

#### 5.5.2 预处理逻辑 `preProcessing()`

这一层是所有事件的通用"过滤、修正、排重"入口。主要逻辑包括：

**1. 崩溃事件去重**：使用 Redis key `one:brKeyCrash:{brKey}`，已处理过则直接丢弃。

**2. 事件级过滤**：调用 `DataCheckUtil.eventEntityFilter(commonModel, event, isPruneMode)`。

**3. 时间范围修正与过滤**：调用 `DataCheckUtil.checkTimeRange(...)`。返回逻辑：`0` 时间异常但可修正 -> 把事件时间改成当前时间；`1` 时间非法 -> 直接过滤；其他：保留。

**4. JS 错误附带时间修正**：如果是 `JS_ERROR_EVENT`，还会额外检查 `pageCreateTime` 的时间范围。

**5. Web 的默认网络状态兼容**：Web 没有完整网络状态上报时，会给事件补默认 `nsi` 索引。

**6. 精简模式事件白名单**：在 prune mode 下，仅保留 `CUSTOM_EVENT`、`UPLOAD`、`USER_CHANGE`，其他事件直接跳过。

**7. Nacos 动态事件过滤**：若配置了 `NACOS_FILTER_EVENT_TYPE`，则仅保留配置中的事件类型。

### 5.6 第五层：按事件类型分发

核心类：`EventProcessFactory`

它把上传事件按类型分发到不同策略，例如：

- `VIEW_EVENT` -> `ViewEventStrategy`
- `ACTION_EVENT` -> `ActionExitEventStrategy`
- `NET_WORK` -> `NetBaseStrategy`
- `ROUTE_CHANGE_EVENT` -> `RouteChangeEventStrategy`
- `UPLOAD` -> `UploadEventStrategy`

对本次关注的四个对象，最关键的是：

- 页面：`H5EventMainStrategy` / `ViewEventStrategy` / `RouteChangeEventStrategy` / `MpviewEventStrategy`
- 操作：`ActionExitEventStrategy`
- 请求：`NetBaseStrategy` + `NetPreEventStrategy` + `NetErrorEventStrategy` + `NetResourceEventStrategy`
- 终端应用：主要通过 `CommonModel`、终端统计表 `RUM_DRU_STAT_TERMINAL` 贯穿所有事件结果

## 6. 页面维度处理逻辑

页面在 RUM 中并不是只有一种数据来源，而是至少有四条：

1. H5 页面加载：`H5_EVENT`
2. 原生视图进入/退出：`VIEW_EVENT`
3. Web 单页面路由切换：`ROUTE_CHANGE_EVENT`
4. 小程序视图：`MPVIEW`

### 6.1 页面类型总分流规则

#### 6.1.1 前端查询侧的页面类型分流

前端页面详情中，`pageType` 并不是简单展示字段，而是决定整个详情页走向：

| pageType | 页面大类 | 基本信息接口分组 | 饼图/趋势分组 |
| --- | --- | --- | --- |
| 1 | H5 页面 | `page` | H5 |
| 11 | 单页面路由 | `page` | 单页面 |
| 2-9 | 原生视图 | `view` | 原生视图 |
| 10 | 小程序视图 | `view` | 小程序视图 |

这意味着：H5 与单页面共享 `appPage` 侧的详情接口；原生视图与小程序视图共享 `appView` 侧的详情接口；但在趋势、维度、饼图、框架类型等页面分析接口上仍会再次拆分。

#### 6.1.2 后端原始事件侧的页面类型分流

在 ingester 中，"页面"并不是只看一个 `pageType` 字段，而是按不同事件类型走不同策略：

| 页面大类 | 原始事件类型 | 主策略 |
| --- | --- | --- |
| H5 页面 | `H5_EVENT` | `H5EventMainStrategy` |
| 原生视图 | `VIEW_EVENT` | `ViewEventStrategy` |
| 单页面路由 | `ROUTE_CHANGE_EVENT` | `RouteChangeEventStrategy` |
| 小程序视图 | `MPVIEW` | `MpviewEventStrategy` |

因此，同样是"页面"，其后端处理入口、校验规则、入库表和快照策略都可能不同。

#### 6.1.3 原生视图细分类型

原生视图内部又继续细分为：

| 视图类型码 | 含义 |
| --- | --- |
| 2 | Activity |
| 3 | Fragment |
| 4 | Window |
| 5 | Controller |
| 6 | RN |
| 7 | Flutter |
| 8 | Ability |
| 9 | AbilitySlice |

并且 `CmdbPageTypeEnum` 会把这些类型直接映射为页面实体类型，用于页面实例识别和页面 ID 建模。

#### 6.1.4 原生视图类型与应用平台匹配关系

`ViewEventEntityValidator.filterViewType()` 明确了平台与视图类型的对应关系：

- Android：只接受 `Activity`、`Fragment`
- iOS：只接受 `Controller`
- Web / Windows：只接受 `Window`
- HarmonyOS：只接受 `Ability`、`AbilitySlice`
- 小程序平台：只接受 `MP`
- `RN`、`Flutter`：作为跨平台视图，不额外按 OS 强过滤
- `H5` 类型出现在 `VIEW_EVENT` 中时会被直接过滤

这说明后端不是只靠前端传过来的 `pageType` 做展示分类，而是会再次按平台与视图类型做强校验。

### 6.2 H5 页面：`H5EventMainStrategy`

H5 页面是页面类型里最容易和"单页面路由"混淆的一类，但在后端原始链路中，它们完全不是一套事件。

#### 6.2.1 分流规则

`H5EventMainStrategy` 会先判断当前 H5 页面是正常 H5 页面还是错误 H5 页面。若出现以下情况，会转入 `H5EventErrorStrategy`：

- HTTP 状态码 `>= 400`
- `domCompleteMs`、`domLoadingMs`、`domInteractiveMs` 缺失或不合法

否则进入 `H5EventDefaultStrategy`。

#### 6.2.2 H5 页面与单页子的根本差异

虽然前端页面详情里 `pageType = 1` 与 `pageType = 11` 都归类为 `page`，但后端原始入库逻辑中：

- `H5 页面` 来自 `H5_EVENT`
- `单页面路由` 来自 `ROUTE_CHANGE_EVENT`

二者的原始协议、校验逻辑、快照结构都不同。

#### 6.2.3 H5 页面入库结果

无论默认还是错误 H5 策略，最终都会生成：

- `RUM_DRU_STAT_H5`
- `RUM_DRU_STAT_TERMINAL`
- `RUM_H5_SNAPSHOT`

区别主要在于：默认策略按正常 H5 页面构建指标，错误策略按异常页面加载构建指标。

### 6.3 原生视图进入：`ViewEventEnterStrategy`

#### 6.3.1 数据清洗

先校验网络状态 `nsiModel` 是否存在：没有网络状态 -> 直接过滤。

#### 6.3.2 模型转换

构建 `ViewEventModel` 时会补全：`viewName`、`instanceId`、`parentViewName`、`parentInstanceId`、`preViewName`、`nsiModel`、`dsiModel`、`usiModel`、`eventExtInfoEntity`、`relatedEvents`。

同时通过 `CmdbFactory.dealCmdb(PageCmdbStrategy.class, ...)` 建立页面实体实例 ID。

#### 6.3.3 递归继续处理子事件

如果页面下挂了子事件，例如请求、操作、span，则会继续创建子 `ServiceModel`，递归进入下一层事件处理。

#### 6.3.4 页面入库结果

`buildGranResult()` 会产出：`RUM_DRU_STAT_VIEW`、`RUM_DRU_STAT_TERMINAL`。

`buildSnapshotResult()` 会产出：`RUM_VIEW_SNAPSHOT`。

#### 6.3.5 原生视图基础校验的特殊规则

在进入 `ViewEventEnterStrategy` 之前，`ViewEventStrategy` 和 `ViewEventEntityValidator` 会先做一轮更严格的页面类型过滤：

- `correlationId` 必须存在
- `loadTimeUs` 必须存在
- `model` 必须存在
- `type` 必须能映射为合法 `ViewTypeEnum`
- `name` 必须存在
- `custom` 必须存在
- 自定义视图 `custom=true` 直接过滤
- `H5` 类型的 `VIEW_EVENT` 直接过滤

同时对慢视图还有额外要求：`slow=true` 且为进入事件时，必须存在有效线程方法信息；Windows 慢视图允许无线程方法。

此外还会对异常值做过滤：

- 进入事件 `loadTimeUs` 超过 `viewFilterTime` 则过滤
- 退出事件 `stayTimeUs` 为空、<=0 或超过 `viewStayTimeThreshold` 则过滤

#### 6.3.6 不同原生视图类型的细节差异

`ViewEventEnterStrategy` 在建模时还会针对不同视图类型补父页面关系：

- `Fragment`：父级按 `Activity` 处理
- `AbilitySlice`：父级按 `Ability` 处理
- 其他类型：按当前视图自身建模

因此，原生页面里并不是所有视图都只有"自己一个页面 ID"，像 `Fragment`、`AbilitySlice` 会形成父子页面结构。

### 6.4 原生视图退出：`ViewEventExitStrategy`

退出事件不会继续递归，但会生成 DataSee 结果：

`DataEntrance.sendResultData(EtlBizTypeEnum.RUM_DRU_STAT_VIEW_EXIT, ...)`

这说明"页面退出"更偏向结果汇总与观测输出，而不是继续承接子链路。

### 6.5 单页面/路由页面：`RouteChangeEventStrategy`

#### 6.5.1 数据校验

通过 `RouteChangeEventEntityValidator` 做校验，主要包括：`isCustomer` 是否为空、`status` 是否为空、路由 URL 是否异常、`duration` 是否为空、`path/root/pageUrl/framework/clientType` 是否异常。

#### 6.5.2 数据校验的特殊点

`RouteChangeEventEntityValidator` 体现了单页面路由和其他页面类型完全不同的协议特征：

- `customer` 不能为空
- `status` 不能为空
- 自定义上报路由错误事件中，`customer=true` 且 `status != 0` 直接过滤
- `toUrl`、`fromUrl`、`root`、`pageUrl` 都必须合法
- `path`、`framework` 长度受限
- `clientType` 不能为空
- `duration` 必须存在，且成功路由切换时必须 `> 0`

这些校验项与原生视图、H5 页面都明显不同，说明单页面路由事件是独立协议。

#### 6.5.3 模型转换

组装 `RouteChangeEventModel` 时，补齐：`fromUrl`、`toUrl`、`duration`、`status`、`navigationStart`、`framework`、`pvid`、`root`、`relatedEvents`、`eventTime`、`eventViewInfo`、`networkStateInfo`、`userInfo`、`deviceStateInfo`、`pageUrl`。

#### 6.5.4 页面识别与归一

`flatten()` 中会对 `toUrl` 和 `root` 做：小写化、H5 URL 拆分、域名类型识别、URL merge、生成 `toUrlInstanceId`、生成 `rootUrlInstanceId`。

#### 6.5.5 页面入库结果

`buildGranResult()` 会产出：`RUM_DRU_STAT_ROUTE`、`RUM_DRU_STAT_TERMINAL`。

`buildSnapshotResult()` 会产出：`RUM_COMMON_SNAPSHOT`。快照中还会把 `webviewResourceInfoEntities` 整理为 `resource` 字段写入快照文件内容。

#### 6.5.6 单页面的额外前端差异

前端对单页面还有一层额外处理：`pageType = 11`、饼图分析类型映射为 `4`、详情页会额外调用 `/rest/rum/digit/appPage/singlePageFrameworks`。也就是说，单页面不仅与 H5 分开统计，在展示层还会额外展示"框架类型列表"。

### 6.6 小程序视图：`MpviewEventStrategy`

小程序视图与原生视图虽然前端都归到 `view` 类，但后端是独立事件体系。

#### 6.6.1 小程序视图校验逻辑

`MPViewEventEntityValidator` 会区分不同小程序视图模型：

- `enter`：必须校验 `readyLoadTime`、`loadTime`
- `showing` / `exit`：必须校验 `stayTime`

此外还要求：`pageViewId` 存在、`name` 存在、`model` 必须是合法 `MpModelEnum`、`custom` 非空、`slow` 非空。若存在 `setData`，还会进一步过滤其中不合法的数据项。

#### 6.6.2 小程序视图建模逻辑

`MpviewEventStrategy` 会复用 H5 URL merge 逻辑处理页面名称：

1. 先拆 URL 和参数
2. 再做 URL merge
3. 再生成 `pageName`
4. 最后通过 `CmdbPageTypeEnum.VIEW_MP` 建立页面实例

这意味着小程序页面在页面实体识别上更接近 H5 URL 页面，而不是原生 Activity/Fragment。

#### 6.6.3 小程序视图的统计差异

小程序事件中：

- 只有 `enter` 事件才记 `pv = 1`
- 非首次进入时 `pv = 0`
- `setData` 会额外计算聚合指标
- 只有 `enter` 事件才产出快照

#### 6.6.4 小程序视图入库结果

最终会生成：`RUM_DRU_STAT_MPVIEW`、`RUM_DRU_STAT_TERMINAL`、`RUM_MPVIEW_SNAPSHOT`。

## 7. 操作维度处理逻辑

核心类：`ActionExitEventStrategy`，这是"操作"最重要的业务判断类。

### 7.1 数据清洗

第一层通过 `ActionEventEntityValidator` 做校验，包括操作事件基础合法性、与超时阈值相关的判断。若校验失败，则整个操作直接丢弃。

### 7.2 模型转换

#### 7.2.1 基础加工

会先对操作字段做清洗，例如是否忽略控件文本中的数字，然后构建 `ActionEventModel`。

#### 7.2.2 必要过滤

若出现以下情况，则直接过滤：

- `nsiModel == null`
- `actionName` 为空
- `endTimeUs - startTimeUs < 0`
- 命中操作黑名单

#### 7.2.3 黑名单过滤

通过 `ActionBlacklistSettingAction` + `DataCheckUtil.filterBlackRule(...)` 实现。可根据以下字段命中黑名单：`actionName`、`subViewName`、`methodName`、`buttonText`、`controlId`。

### 7.3 操作健康状态判断

`getActionHealthyType()` 是操作判定的核心。判定顺序固定为：

1. 崩溃
2. 请求失败
3. 请求错误
4. JS 错误
5. 阻塞
6. 慢操作
7. 正常

#### 7.3.1 崩溃判定

只要存在 `crashIds`，直接视为崩溃操作。

#### 7.3.2 请求失败 / 请求错误判定

会读取用户和应用级配置：请求失败率阈值、黑白名单 URL 规则。并结合本次操作下的请求统计：`requestNum`、`requestErrorNum`、`netErrorRate`，做判断。

#### 7.3.3 阻塞判定

对非 Web / 非小程序，读取阻塞阈值配置 `mainThreadExecuteTime`，若主线程最大执行时间超过阈值，则标记为阻塞。

#### 7.3.4 慢操作判定

读取慢操作配置 `loadTime`，若操作总耗时超过阈值，则标记为慢操作。

### 7.4 操作与子事件关系

操作不是孤立事件，它会把自身挂接的子事件递归分析进去：网络请求、span、视图、小程序视图。具体由 `buildActionSubEvents()` 递归完成。

因此，操作是"页面与请求之间的业务桥梁"。

### 7.5 操作入库结果

`buildGranResult()` 会产出：`RUM_DRU_STAT_ACTION`、`RUM_DRU_STAT_TERMINAL`。此外还会对方法级数据生成多个 `ActionResultZeus` 聚合结果。

`buildSnapshotResult()` 会产出：`RUM_ACTION_SNAPSHOT`。

`modelConvertToDataSee()` 会产出：`ACTION_EVENT` 类型的 DataSee Kafka 数据。

## 8. 请求维度处理逻辑

核心类组合：`NetBaseStrategy`、`NetPreEventStrategy`、`NetErrorEventStrategy`、`NetResourceEventStrategy`、`NetResourceErrorEventStrategy`。

### 8.1 请求入口：`NetBaseStrategy`

#### 8.1.1 数据清洗

先通过 `NetEventBaseValidator` 做基础校验。

#### 8.1.2 模型转换

把事件统一转成 `NetworkEventModel`。

#### 8.1.3 请求分类判断

根据以下维度决定走哪条下游策略：是否错误请求 `errorNetReq`、是否资源请求 `resource`、协议类型 `protocolTypeEnum`、应用请求类型 `appRequestType`、错误码类型 `errorCodeTypeEnum`。

分发规则：

- 错误 + 资源 -> `NetResourceErrorEventStrategy`
- 错误 + WebView 文档类 -> `NetErrorEventStrategy` + `WebViewErrorStrategy`
- 错误 + 普通请求 -> `NetErrorEventStrategy`
- 非错误 + 资源 -> `NetResourceEventStrategy`
- 非错误 + 非资源 -> `NetPreEventStrategy`
- TCP/UDP Socket -> 不走这套普通网络统计

### 8.2 请求过滤逻辑

`modelFilter()` 中包含大量过滤规则：

1. `appRequestType` 不能为空
2. 域名不能为空
3. 非 HTTP 异常请求过滤
4. 非问题类请求的性能异常值过滤
5. 过滤平台自身请求
6. 黑白名单过滤
7. 异常 IP 过滤
8. 非法 URL 前缀过滤
9. 非法协议过滤
10. 自定义且错误类型异常的数据过滤
11. 命中网络错误过滤配置则过滤

这是请求维度最密集的一层"数据过滤"逻辑。

### 8.3 普通业务请求：`NetPreEventStrategy`

#### 8.3.1 模型补充

通过 `RequestCmdbStrategy` 生成请求实例 ID，并设置 `instanceId`、`detectedName`。

#### 8.3.2 入库结果

`buildGranResult()` 会产出：`RUM_DRU_STAT_NET`、`RUM_DRU_STAT_TERMINAL`。若开启调用链快照，还会产出 `APM_TRACE_DATA`。

#### 8.3.3 快照

`buildSnapshotResult()` 产出：`RUM_NETWORK_SNAPSHOT`。普通请求的 `saveFlag = 1`，即全量存快照。

### 8.4 错误请求：`NetErrorEventStrategy`

与普通请求类似，但在构建结果时会按"错误请求"逻辑生成：`RUM_DRU_STAT_NET`、`RUM_DRU_STAT_TERMINAL`、`RUM_NETWORK_SNAPSHOT`，并使用错误快照类型 `NET_ERROR_SNAPSHOT`。

### 8.5 资源请求：`NetResourceEventStrategy`

资源请求会写入：`RUM_DRU_STAT_NET_RESOURCE`、`RUM_DRU_STAT_TERMINAL`。

对于健康资源请求通常不存快照；只有慢资源请求才会采样存快照：`RUM_NETWORK_SNAPSHOT`，对应快照类型 `NET_SLOW_SNAPSHOT`。

### 8.6 操作与请求的关系

在操作维度中，请求还会被再次纳入操作健康度分析：

- 增加 `requestNum`
- 增加 `requestErrorNum`
- 计算 `requestErrorRate`
- 决定当前操作是否属于：请求失败、请求错误、慢操作

因此"请求"不仅单独入库，也会影响"操作"的最终状态。

## 9. 终端应用维度处理逻辑

终端应用并不是一条单独的事件策略，而是通过以下两种方式贯穿整个链路：

1. `CommonModel`：保存 appId、appType、envId、brUserId、session、设备状态、网络状态、用户信息等
2. 终端统计表：几乎所有核心事件都会额外生成一份 `RUM_DRU_STAT_TERMINAL`

也就是说：页面事件会生成 terminal 数据、操作事件会生成 terminal 数据、请求事件会生成 terminal 数据、路由事件会生成 terminal 数据。

所以"终端应用维度"本质上是所有事件的公共归属维度，而不是只对应一个独立事件类型。

## 11. 映射到最终输出层

`AbstractEventBaseStrategy.buildOutputData()` 会把一个事件最终转换成四类输出：

1. `granResultModels`：统计表数据，最终转成 `CkResultModel`
2. `snapshotResultModels`：快照数据，最终转成 `CkResultModel`
3. `dataSeeModels`：发送到 Kafka 的 DataSee 数据
4. `mySQLTransferData`：个别场景写 MySQL

随后在 `RumMappingTransform` 中统一封装为 `RumMappingData`，再传给下游输出算子。

### 11.1 ClickHouse 输出

`ingester-operator` 中的 `CkOutputTableAbstractStrategy` 负责真正执行入库：

1. 从 `ElementParseResult` 中取出 `List<CkResultModel>`
2. 校验表名是否存在于 `EtlBizTypeEnum`
3. 校验数据是否为空
4. 对 map 类型字段做空值过滤
5. 调用 `getCkDataClient().sendData(tableName, data)`

所以从代码事实看，RUM 的统计表与快照表最终都是经由 operator 输出到 CK。

## 12. 前端查询链路与入库链路的对应关系

前端页面分析查询的本质，是在读已经经过上述链路处理后形成的统计结果。对应关系可以概括为：

| 前端页面 | 前端接口 | 后端读取的数据类型 |
| --- | --- | --- |
| 页面分析-H5 页面 | `/rest/rum/digit/appPage/pageDomainList` | 页面统计结果 |
| 页面分析-单页面 | `/rest/rum/digit/appPage/pageRouteList` | 路由统计结果 |
| 页面分析-原生视图 | `/rest/rum/digit/appView/getViewTableByApp` | 视图统计结果 |
| 页面分析-小程序视图 | `/rest/rum/mp/mpList` | 小程序视图统计结果 |
| 页面详情-操作 | `/rest/rum/operation/operationListQuery` | 操作统计结果 |
| 操作详情-请求趋势 | `/rest/rum/operation/reqTrend` | 请求聚合结果 |
| 操作详情-请求分析 | `/rest/rum/operation/reqAnalysis` | 请求维度聚合结果 |

换句话说：

- **前端的"页面、操作、请求"分析页，并不是读取原始上报 JSON。**
- 它们读取的是 **ingester 已经加工、判断、过滤并入库后的统计结果**。

### 12.1 页面、操作、请求之间"关联成立"的代码机制

从当前代码看，这三类对象之间的"有关联"，并不是靠前端页面跳转建立的，而是靠后端在平铺阶段递归传递两类信息建立的：

1. `relatedEvents`：表示某个事件下面还挂着哪些子事件。`FlattenTargetData.buildMulEvent(...)` 会把这些子事件继续递归分发到对应策略。
2. `ServiceModel`：表示"当前子事件的父是谁"。里面保存了 `pId`、`pEventType`、`pInstanceId`、`pDetectedName`、`pActionId`、`actionInstanceId`、`pActionViewId` 等上下级信息。

因此，"页面和操作有关联 / 页面和网络请求有关联 / 操作和网络请求有关联"，本质上都是：

- 上级事件先把子事件放进 `relatedEvents`
- 再通过 `ServiceModel.getSubBaseServiceModel(...)` 把父级身份透传给子级
- 子级事件在自己转换结果和入库时，再把这层父子关系写回统计表或快照

### 12.2 什么情况下页面和操作有关联

#### 12.2.1 关联成立的核心条件

页面和操作有关联，核心要同时满足下面两个条件：

1. 页面类事件本身支持继续递归子事件
2. 该页面事件的 `relatedEvents` 中确实包含 `ACTION_EVENT`

当前代码中，能向下递归子事件的页面类策略主要有：`H5EventDefaultStrategy`、`H5EventErrorStrategy`、`RouteChangeEventStrategy`、`ViewEventEnterStrategy`、`MpviewEventStrategy`。

它们在 `flatten(...)` 里都会做同一件事：

- 如果 `relatedEvents` 为空，则只产出当前页面模型，不再往下递归
- 如果 `relatedEvents` 不为空，则构造页面作为父级的 `ServiceModel`，再把子事件继续分发

所以，**页面和操作有关联** 的直接判定标准就是：该条页面事件下面挂了操作子事件、页面事件和操作事件都没有在各自校验/过滤阶段被丢弃。

#### 12.2.2 哪些页面场景更容易形成"页面 -> 操作"关联

1. **H5 页面**：`H5_EVENT` 自身带 `relatedEvents`，当里面有 `ACTION_EVENT` 时，操作会作为 H5 页面的子事件被递归处理。
2. **单页面路由**：`ROUTE_CHANGE_EVENT` 的 `relatedEvents` 中有 `ACTION_EVENT`，则该操作归到这次路由页面之下。
3. **原生视图进入**：只有 `ViewEventEnterStrategy` 的进入态会继续递归子事件，如果进入视图事件下挂了 `ACTION_EVENT`，则页面和操作关联成立。
4. **小程序页面进入**：`MpviewEventStrategy` 只在 `model=enter` 且 `relatedEvents` 非空时继续递归，这时如果子事件里有 `ACTION_EVENT`，则页面和操作关联成立。

#### 12.2.3 什么情况下页面和操作不会形成有效关联

1. **页面没有子事件**：`relatedEvents` 为空，页面只会单独入自己的统计/快照，不会再带出操作。
2. **页面事件本身不是"可向下递归"的页面形态**：例如原生视图退出事件、小程序 `showing/exit`，代码里不会继续递归子事件。
3. **操作事件被校验过滤**：`ActionEventEntityValidator` 要求 `type=1`、`mode=2`、`id/name/info/viewName` 等字段完整。其中：
   - `type` 是操作类型，协议定义为 `0:其他、1:点击、2:手势、3:键盘、4:输入`
   - `mode` 是操作阶段，协议定义为 `1:开始、2:结束`
   - 当前代码只保留 `type=1`，含义是这里只统计"点击类操作"，手势、键盘、输入、其他动作即使上报到了 `ACTION_EVENT`，在当前这条操作分析链路里也会被过滤掉
   - 当前代码只保留 `mode=2`，含义是这里只处理"操作结束事件"，不处理"操作开始事件"，原因是后续 `ActionExitEventStrategy` 需要基于结束态数据做完整判定，例如：是否已经拿到本次操作的总耗时 `loadTime`、是否已经收齐该操作下挂的 `relatedEvents`、是否可以累计 `requestNum / requestErrorNum`、是否可以最终判定 `slow / blocked / request_error / request_failed / crash`
   - 换句话说，当前操作统计链路在语义上更接近：

```text
页面下挂了一个"已完成的点击操作"
  -> 才会继续建立 页面 -> 操作 关联
  -> 才会再往下分析该操作是否关联请求、视图、span 等子事件
```

   - 如果不是 `type=1` 或不是 `mode=2`，即使原始结构里挂在页面下，也不会形成最终可见的页面-操作关联，也不会进入当前这套点击操作健康度与请求关联分析逻辑。

4. **上游预处理已把该子事件过滤掉**：例如 `RumFlattenTransform.preProcessing(...)` 中的时间范围、事件白名单、动态过滤规则等。

### 12.3 什么情况下页面和网络请求有关联

#### 12.3.1 直接关联：请求是页面的直接子事件

页面和网络请求的最直接关联方式，是页面事件的 `relatedEvents` 中直接包含 `NET_WORK`。

代码路径是：

1. 页面策略在 `flatten(...)` 里创建以页面为父级的 `ServiceModel`
2. `NET_WORK` 子事件进入 `NetBaseStrategy`
3. `NetworkEventModelConvert` 继续把网络模型转换出来
4. `NetWorkResultBuild` 根据 `serviceModel.getPEventType()` 判断它的父级到底是页面还是操作

当父级是下面这些页面事件时，请求会直接写出页面关联信息：`H5_EVENT`、`ROUTE_CHANGE_EVENT`、`VIEW_EVENT`（且 `actionInstanceId == null`）、`MPVIEW`（且 `actionInstanceId == null`）。

也就是说，请求结果里会补上：`pageId`、`pageName`、`pageType`。这种情况就是"页面和网络请求直接有关联"。

#### 12.3.2 间接关联：请求在页面下面，但中间隔了一层操作

第二种常见情况：

```text
页面
  -> 操作
      -> 网络请求
```

这种情况下，请求逻辑上仍然发生在该页面上下文中，但代码在落请求结果时，会优先保留"操作关联"。原因是：

1. `ActionExitEventStrategy.flatten(...)` 会把 `pActionId`、`pActionViewId`、`pActionViewName`、`pActionViewType` 写进子级 `ServiceModel`
2. 如果操作下面再挂了 `VIEW_EVENT` / `MPVIEW`，则 `ViewEventEnterStrategy`、`MpviewEventStrategy` 会继续把 `actionInstanceId` 和操作识别名透传下去
3. `NetWorkResultBuild` 在发现父级为 `VIEW_EVENT` / `MPVIEW` 且 `actionInstanceId != null` 时，会优先把请求记到操作，而不是直接记到页面

所以这里要区分：

- **逻辑上下文上**：请求仍然属于这个页面会话里的行为链
- **最终请求结果的直接挂载上**：更可能优先挂到操作

#### 12.3.3 什么情况下页面和网络请求不会形成有效关联

1. 页面没有把 `NET_WORK` 作为直接或间接子事件带出来
2. 请求事件自身未通过 `NetEventBaseValidator` / `DataCheckUtil.networkEventEntityFilter(...)`
3. 页面已经在前面的清洗、时间校验、白名单/黑名单过滤中被丢弃
4. 请求虽然存在，但被识别为操作子孙链上的请求，最终结果优先记到了操作维度

### 12.4 什么情况下操作和网络请求有关联

#### 12.4.1 新协议 / 优化版操作：通过 `relatedEvents + ServiceModel` 建立关联

当 `commonModel.isActionOptimizeVersion()` 为真时，操作和请求的关联主要靠递归子事件建立。代码路径是：

1. `ActionExitEventStrategy.flatten(...)`：以当前操作为父级创建 `ServiceModel`，把 `pActionId` 设置为当前 `actionId`，把操作所在页面的 `pActionViewId/pActionViewName/pActionViewType` 一并带下去
2. 如果操作的 `relatedEvents` 中有 `NET_WORK`，则网络请求继续进入网络策略，`NetworkEventModelConvert` 会优先用 `ServiceModel.getPActionIdMethod(serviceModel)` 给请求补 `actionId`
3. 请求入统计/快照时，`NetWorkResultBuild` 会把操作实例、操作名称、操作健康状态、操作所在页面信息写到结果中

这说明优化版协议下，**操作和请求关联成立** 的主要条件是：该操作下面确实挂了网络请求子事件，这些子事件没有在后续校验中被过滤掉。

#### 12.4.2 老协议 / 非优化版操作：通过 `actionId` 和方法树建立关联

当 `commonModel.isActionOptimizeVersion()` 为假时，代码仍然保留老协议兼容逻辑：

1. `NetworkEventConvert` 直接从原始字段 `ai` 解析 `actionId`
2. `ActionEventConvert` 会把 `MethodEntity.networkEventEntity` 解析进操作的方法树
3. `ActionExitEventStrategy.buildActionMethodModel(...)` 会递归方法树，把网络请求计入：`requestNum`、`requestErrorNum`、后续的失败/异常判定

因此老协议下，操作和请求的关联更多体现为：请求本身带 `actionId`、操作内部方法树里嵌了请求信息。

#### 12.4.3 哪些情况下"有操作事件"但不会保留请求关联

`ActionExitEventStrategy.flatten(...)` 对优化版操作专门做了"是否保留操作父级关系"的判断：

1. **Web 操作**：如果 `relatedEvents` 里既没有 `NET_WORK`，也没有 `SPAN_EVENT`，会把 `pActionId` 和 `pId` 清空，结果是子事件即使继续处理，也不再作为该操作的有效挂载链。
2. **移动端操作**：如果 `relatedEvents` 里没有 `NET_WORK`、`SPAN_EVENT`、`VIEW_EVENT`、`MPVIEW`，同样会把 `pActionId` 和 `pId` 清空。

也就是说，**并不是所有操作都会天然保留到请求维度的关联**，而是要看操作下面是否真的带出了可识别、可入链的网络/Span/页面子事件。

#### 12.4.4 请求为什么会反向影响操作判定

这层关联不只是"挂载关系"，还会直接影响操作健康度。在 `ActionExitEventStrategy` 中：

- 优化版走 `buildActionSubEvents(...)`
- 老协议走 `buildActionMethodModel(...)`

两条路径最终都会累计：`requestNum`、`requestErrorNum`、`requestErrorRate`、`requestFailed`、`requestError`。最后再参与操作健康状态判定：`crash`、`request_failed`、`request_error`、`blocked`、`slow`、`normal`。

### 12.5 典型场景下是被过滤还是正常入库

下面 4 个场景，统一基于"在 a 页面点击了按钮 b"来分析。

为避免歧义，先说明两个前提：

1. 这里默认讨论的是已经通过 `ActionEventEntityValidator` 的操作事件，也就是 `type=1`、`mode=2`。若连这一步都不满足，则操作事件本身先被过滤，后面的关联分析不成立。
2. 当前代码里对这类场景的结论，强依赖两个分支：
   - **优化版操作链路**：`commonModel.isActionOptimizeVersion() == true`
   - **页面跳转形态**：Web/单页面更常见为 `ROUTE_CHANGE_EVENT`；原生 App / 小程序更常见为 `VIEW_EVENT` / `MPVIEW`

因此下面每个场景都按"当前主链路（优化版）"优先说明，同时补充 Web 与原生/小程序的差异。

#### 12.5.1 情况一：未触发任何网络请求，也没有跳转到新页面

```text
a页面
  -> 点击按钮b
  -> 没有 NET_WORK
  -> 没有 VIEW_EVENT / MPVIEW / ROUTE_CHANGE_EVENT
```

**结论**：

- **优化版操作链路下：操作事件通常会被过滤，不入操作统计/快照**
- a 页面本身如果之前已经正常上报，仍然按页面事件自己的链路正常入库
- 不会产生请求数据

**原因**：`ActionExitEventStrategy.flatten(...)` 在优化版下有两层过滤：

1. 如果 `relatedEvents` 为空，且当前操作不是崩溃操作，直接 `return FlattenTargetData.buildEmpty()`，这意味着该操作模型本身不会继续进入后续入库链路
2. 即使 `relatedEvents` 不为空，但里面既没有请求、也没有页面跳转、也没有 span，也会按"无有效子事件"处理

**对应结果**：页面 `a` 正常按自己的页面事件入库；操作 `b` 过滤；请求：无。

**补充**：如果走的是**老协议 / 非优化版操作链路**，则 `ActionExitEventStrategy` 不会在这里直接把操作清空，操作更可能仍然正常入库；但当前主线梳理的"页面/操作/请求递归关联"主要以优化版逻辑为主。

#### 12.5.2 情况二：触发了网络请求

```text
a页面
  -> 点击按钮b
      -> NET_WORK
```

**结论**：

- **操作通常正常入库**
- **请求通常正常入库**
- 请求会优先作为"操作关联请求"处理，而不是直接作为"页面直挂请求"
- a 页面本身也仍然按页面链路正常入库

**原因**：

1. `ActionExitEventStrategy.flatten(...)` 优化版下只要 `relatedEvents` 中包含 `NET_WORK`，该操作就不会被"无有效子事件"规则抛弃，会继续保留 `pActionId`
2. `NetworkEventModelConvert` 会优先从 `ServiceModel.getPActionIdMethod(serviceModel)` 中给请求补 `actionId`
3. `NetWorkResultBuild` 在父级是 `ACTION_EVENT`，或者父级虽是 `VIEW_EVENT/MPVIEW` 但带有 `actionInstanceId` 时，会把请求结果记到操作维度

**对应结果**：

- 页面 `a`：正常入库
- 操作 `b`：正常入库（统计表 `RUM_DRU_STAT_ACTION`，快照 `RUM_ACTION_SNAPSHOT`）
- 请求：正常入库（业务请求 `RUM_DRU_STAT_NET`，资源请求 `RUM_DRU_STAT_NET_RESOURCE`，快照 `RUM_NETWORK_SNAPSHOT`）

**额外影响**：该请求还会反向参与操作健康度判定，影响 `requestNum`、`requestErrorNum`、`requestErrorRate`、`request_error / request_failed`。

#### 12.5.3 情况三：跳转到了 c 页面，跳转到 c 页面后未触发网络请求

```text
a页面
  -> 点击按钮b
      -> 跳到 c页面
      -> c页面后没有 NET_WORK
```

这个场景要区分 Web/单页面 与 原生/小程序，两边代码行为不完全一样。

##### 场景 3A：Web / 单页面路由（`ROUTE_CHANGE_EVENT`）

**结论**：`c` 页面对应的路由事件通常正常入库；但点击操作 `b` 在优化版链路下，大概率会被过滤；不会产生请求数据。

**原因**：

1. Web 操作在优化版下，`ActionExitEventStrategy.flatten(...)` 明确要求：`relatedEvents` 中至少要有 `NET_WORK` 或 `SPAN_EVENT`。如果只有页面跳转，而没有请求或 span，会把 `pActionId` 和 `pId` 清空。
2. 代码注释也明确写了：`web 操作下 如果么有net和span,则抛弃, 但还要执行route`
3. `RouteChangeEventStrategy` 仍会继续处理 `ROUTE_CHANGE_EVENT`，因此 `c` 页面路由结果和快照仍会正常生成。

**对应结果**：页面 `a` 正常入库；操作 `b` 过滤；页面 `c`（路由事件）正常入库（统计表 `RUM_DRU_STAT_ROUTE`，快照 `RUM_COMMON_SNAPSHOT`）；请求：无。

##### 场景 3B：原生 App / 小程序页面跳转（`VIEW_EVENT` / `MPVIEW`）

**结论**：操作 `b` 通常正常入库；`c` 页面进入事件通常正常入库；不会产生请求数据。

**原因**：移动端优化版操作在 `ActionExitEventStrategy.flatten(...)` 中，保留操作的条件是：`NET_WORK`、`SPAN_EVENT`、`VIEW_EVENT`、`MPVIEW`。也就是说，只要点击后真的带出了"进入 c 页"的原生视图/小程序页面事件，操作不会被抛弃。

随后：`ViewEventEnterStrategy` / `MpviewEventStrategy` 会继续把 `c` 页面的页面事件正常展开，`c` 页面再单独生成页面统计与页面快照。

**对应结果**：

- 页面 `a`：正常入库
- 操作 `b`：正常入库
- 页面 `c`：正常入库（原生视图 `RUM_DRU_STAT_VIEW` + `RUM_VIEW_SNAPSHOT`，小程序页面 `RUM_DRU_STAT_MPVIEW` + `RUM_MPVIEW_SNAPSHOT`）
- 请求：无

#### 12.5.4 情况四：跳转到了 c 页面，跳转到 c 页面后触发了网络请求

```text
a页面
  -> 点击按钮b
      -> 跳到 c页面
          -> NET_WORK
```

这个场景仍要区分 Web/单页面 与 原生/小程序。

##### 场景 4A：Web / 单页面路由（`ROUTE_CHANGE_EVENT` 后再请求）

**结论**：`c` 页面路由事件通常正常入库；`c` 页面后的网络请求通常正常入库；但点击操作 `b` 是否保留，取决于这些请求是否被直接挂到了操作的 `relatedEvents` 下。

**为什么"操作 -> 单页面 -> 网络请求"更常见不保存操作 action 数据**：

在 Web 场景下，代码要求操作的**直接子事件**里至少出现以下之一：`NET_WORK`、`SPAN_EVENT`。如果没有，则即使后面还有路由事件，也会执行：清空 `pActionId`、清空 `pId`、然后走 `FlattenTargetData.buildNoModelMulEvent(...)`。代码注释写得很直接：`web 操作下 如果么有net和span,则抛弃, 但还要执行route`。

这意味着系统对 Web 点击操作的建模思路是：

1. **"点击"本身不一定值得单独保留成操作分析对象**：如果点击后没有直接请求、没有 span，代码认为它更像一次"仅触发前端路由切换"的导航动作，此时更希望把后续数据归到"页面变化"而不是"操作行为"。
2. **单页面路由被视为独立的页面对象**：`ROUTE_CHANGE_EVENT` 会继续正常入库，新页面 `c` 的加载、健康状态、后续请求，优先归属于 `c` 页面的页面链路，而不是继续强绑在上一个点击操作 `b` 上。
3. **避免把 c 页面的请求错误归因到前一个点击操作**：当前更常见的数据树是：

```text
ACTION_EVENT
  -> ROUTE_CHANGE_EVENT
      -> NET_WORK
```

   - 这里请求实际上是"c 页面建立后的页面请求"
   - 如果仍然强行保留 `b` 的 action，会把 `c` 页的后续请求错误率、慢请求、异常状态继续算进 `b`
   - 从代码设计上看，当前实现是在尽量避免这种"跨页面误归因"

4. **让 Web 的操作口径更偏向"有直接业务执行结果的点击"**：只有点击后直接发请求、或者有 span，操作才被保留，这样留下来的 action，更接近"可衡量执行结果的用户操作"，而不是所有路由跳转点击都进入操作统计，导致操作表噪声过大。

**更常见的代码结果**：

```text
ACTION_EVENT
  -> ROUTE_CHANGE_EVENT
      -> NET_WORK
```

在这种结构里：

1. Web 操作自身的直接子事件里如果没有 `NET_WORK` 或 `SPAN_EVENT`，操作仍会被按"无有效子事件"抛弃
2. `ROUTE_CHANGE_EVENT` 仍然正常入库为 `c` 页面
3. `NET_WORK` 作为 `ROUTE_CHANGE_EVENT` 的子事件正常入库，更偏向"页面 c 的请求"，而不是"操作 b 的请求"

**最终结果**：页面 `a` 正常入库；操作 `b` 可能被过滤；页面 `c`（路由事件）正常入库；请求正常入库，但更偏向挂在 `c` 页面上下文，而不是挂在 `b` 操作下。

**例外情况**：如果 SDK 上报结构是：

```text
ACTION_EVENT
  -> NET_WORK
  -> ROUTE_CHANGE_EVENT
```

那么因为操作的直接子事件里已经有 `NET_WORK`：操作 `b` 会被保留并正常入库，这条直接挂在操作下的请求会按"操作关联请求"处理，路由到 `c` 页的页面事件也仍会继续入库。

##### 场景 4B：原生 App / 小程序页面跳转后再请求

**结论**：操作 `b` 正常入库；页面 `c` 正常入库；`c` 页面下的请求正常入库；且这批请求通常仍会保留操作关联。

**原因**：

1. 点击后先进入 `VIEW_EVENT` / `MPVIEW`，移动端优化版操作因此被保留
2. `ViewEventEnterStrategy` / `MpviewEventStrategy` 如果它们的父级是 `ACTION_EVENT`，会把 `actionInstanceId`、`actionDetectedName`、`actionHealthyStatus` 继续透传给子级 `ServiceModel`
3. 当 `c` 页面下面再出现 `NET_WORK`，`NetWorkResultBuild` 在检测到父级为 `VIEW_EVENT/MPVIEW` 且 `actionInstanceId != null` 时，会优先把请求记到操作，同时补充 `actionPageId / actionPageName / actionPageType`

**对应结果**：

- 页面 `a`：正常入库
- 操作 `b`：正常入库
- 页面 `c`：正常入库
- 请求：正常入库，且通常同时保留"这是 c 页面上的请求"和"这是由 b 操作触发的请求"这两层上下文

#### 12.5.5 四个场景的简表结论

| 场景 | Web/单页面优化版 | 原生/小程序优化版 |
| --- | --- | --- |
| 情况一：点击后无请求、无跳页 | 操作通常过滤 | 操作通常过滤 |
| 情况二：点击后有请求 | 操作正常入库，请求正常入库 | 操作正常入库，请求正常入库 |
| 情况三：点击后跳到 c 页，c 页无请求 | 操作通常过滤，c 页正常入库 | 操作正常入库，c 页正常入库 |
| 情况四：点击后跳到 c 页，c 页再发请求 | 更常见为操作可能过滤，c 页和请求正常入库；若请求直接挂操作下则操作也保留 | 操作、c 页、请求通常都正常入库 |

## 13. 核心结论

### 13.1 页面、操作、请求三者不是孤立关系，而是递归父子关系

真实数据关系更接近：

```text
页面(视图/路由)
  -> 操作
      -> 请求 / Span / 子页面 / 小程序视图
```

也就是说，操作既属于页面，又会吸收请求结果来决定自己的健康状态。

### 13.2 请求是"单独入库 + 反向影响操作判定"的双重对象

请求不仅会生成：`RUM_DRU_STAT_NET`、`RUM_DRU_STAT_NET_RESOURCE`、`RUM_NETWORK_SNAPSHOT`，还会回流影响：`requestErrorNum`、`requestErrorRate`、操作是否失败/异常。

### 13.3 页面类型至少分四套逻辑

- H5 页面：`H5_EVENT`
- 单页面路由：`ROUTE_CHANGE_EVENT`
- 原生视图：`VIEW_EVENT`
- 小程序视图：`MPVIEW`

前端页面分析页虽然统一展示为"页面"，但后端处理策略并不相同。

### 13.4 `framework/plugins/rum` 更偏查询/控制面，不是原始接入面

前端查到的 `/rest/rum/**` 大部分接口落在 Java 插件查询能力；而原始数据的接收、校验、拆包、判断、入库主要发生在 `ingester-rum`。

## 14. 总体结论归纳

基于当前工作区代码，可以把 RUM 模块的完整逻辑归纳为：

1. **前端查询面**：`view/rum` 负责把终端应用、页面、操作、请求串联成完整分析路径。页面通过配置化过滤器、表头、业务类型参数去调用 `/rest/rum/**` 接口。
2. **原始接收面**：RUM 原始上报进入 ingester 前已被封装为 Kafka 输入。`RumControllerFilterStrategy` 是当前可见代码中最早、最完整的接收校验入口。
3. **核心处理面**：`UploadRequestConvert` 完成协议解析；`RumFlattenTransform` 完成公共过滤、时间修正、事件分组、递归平铺；`EventProcessFactory` 将事件分发到页面/操作/请求等具体策略。
4. **业务判断面**：页面负责页面实例识别、父子页面关系、页面快照；操作负责健康度、请求错误率、慢操作、阻塞、崩溃等综合判定；请求负责网络分类、错误识别、资源识别、异常过滤、快照采样。
5. **入库面**：`RumMappingTransform` 统一产出统计表、快照表、DataSee 数据；`ingester-operator` 通过 CK 输出策略把 `CkResultModel` 发送到 ClickHouse。

因此，"终端应用 -> 页面 -> 操作 -> 请求"的完整逻辑，并不是简单的页面跳转关系，而是：

**前端页面查询链路 + 后端原始事件递归建模链路 + 最终统计/快照入库链路** 的组合。
