# 第一部分：自定义视图取舍分析

## 1. 问题背景

本部分梳理 `rum` 模块中"自定义视图"相关逻辑，重点回答两个问题：

1. 为什么当前自定义视图会被过滤掉？
2. 如果重新打开自定义视图上报/处理逻辑，会带来哪些影响？

分析范围主要包括：

- `controller/ingester/ingester-business/ingester-rum`
- `framework/plugins/rum`

## 2. 结论摘要

当前 `rum` 模块中的**自定义视图**不是"未开发完成"或"遗漏处理"，而是被**明确设计为不进入性能视图主链路**。

从代码实现看，自定义视图被当成一种**行为类数据**，而不是标准的"页面性能视图"。因此系统当前的策略是：

- 在视图处理入口就直接过滤
- 在后续统计、快照、行为链路中继续防御性排除
- 不让它进入标准页面性能统计与展示体系

如果直接放开，不是简单删一行过滤代码就能安全生效，而是会影响：

- 页面性能统计口径
- CMDB 页面实体与关系
- 入库量与查询量
- 会话详情与前端展示逻辑
- 下游处理稳定性

## 3. 自定义视图在当前链路中的实际状态

### 3.1 协议层仍然支持"自定义视图字段"

视图事件实体 `ViewEventEntity` 中仍然保留了自定义视图字段：

- `custom`：是否为自定义视图
- `slow`：慢视图标记（但协议说明中已明确，自定义视图该字段可以为空）

这说明自定义视图在**协议上没有被删除**，SDK 仍可以上报这类数据。

#### 关键字段定义

- `custom`：`ic`
- `loadTimeUs`：`lt`
- `stayTimeUs`：`st`
- `model`：`m`（1 进入，2 退出）
- `type`：`t`
- `name`：`n`
- `title`：`vt`
- `slow`：仅非自定义数据要求有语义

#### 协议层体现的差异

协议里已经暗示：

- **普通视图**：是标准性能视图，具备"慢/不慢"的性能语义
- **自定义视图**：更像业务行为节点，`slow` 字段允许为空，不一定适合进入标准性能统计

## 4. 为什么自定义视图会被过滤掉

### 4.1 第一层：入口直接过滤

在 `ViewEventService.filterViewEntity(...)` 中有明确逻辑：

- 当 `viewEntity.getCustom() == true` 时，直接返回 `true`
- 表示该事件被过滤，不再进入后续处理

#### 关键注释

代码里有明确注释：`v3.0 版本删除自定义视图`。

#### 说明

这意味着：当前版本不是"没实现"，而是**主动关闭了自定义视图采集主链路**。

### 4.2 第二层：就算通过入口，也不进视图统计和快照

在 `ViewEventEnterService` 中，对视图统计和视图快照处理有额外限制：

- 只有 **非自定义视图**
- 且 **非 H5 类型**
- 才会进入：
  - `viewProcess(...)`
  - `viewSnapshotProcess(...)`

#### 设计含义

这说明即使去掉入口层的过滤，自定义视图也**不会自动进入标准视图统计表和快照链路**。

### 4.3 第三层：Action 子事件也排除自定义视图

在 `ActionExitEventService` 中，action 子事件里的 view 处理同样排除了自定义视图。

也就是说：

- 自定义视图不仅被排除在性能视图统计之外
- 当前也没有作为"标准 view 子事件"完整进入行为链路展示

这是一个多层防御，不是单点限制。

## 5. 代码中反映出的设计意图

### 5.1 自定义视图被视为"行为"，不是"性能页面"

在多个类中都出现了相同语义的注释：

- **自定义视图属于行为**
- **不应该在性能中展示**

这说明当前设计理念是：

- 普通 `activity / fragment / ability / controller / mpview` 等属于性能页面视图
- 自定义视图更像"业务行为切片"
- 因此不应该混入页面启动性能、慢视图、页面排行等能力中

### 5.2 自定义视图和普通视图的语义不同

从协议和后端逻辑看，两者并不是同一类数据对象。

#### 普通视图具备的语义

- 是否慢启动
- 是否有线程方法信息
- 启动耗时是否可用于性能统计
- 是否应该进入页面性能实体体系

#### 自定义视图不具备或不稳定的语义

- `slow` 可以为空
- 线程方法信息不一定存在
- `loadTime/stayTime` 的语义不一定等于"标准页面启动性能"
- 名称可能是业务层动态定义，不一定适合作为标准 PAGE 实体

## 6. 为什么产品/架构层面要把它关掉

### 6.1 避免污染页面性能统计口径

普通视图统计涉及的核心能力包括：

- 启动次数
- 慢启动次数
- 启动耗时
- 页面数量
- 页面排行
- 慢视图趋势
- 页面拓扑关系

这些指标默认统计对象应当是：真实页面、真实视图、稳定可识别的性能节点。

而自定义视图可能只是：弹窗、某个步骤页、某个业务层的自定义埋点视图、某个组件切换过程。

如果将这些对象混进标准页面视图统计，会导致：

- 页面数虚高
- 慢视图次数失真
- 页面性能排行被非真实页面污染
- 产品和运营误读页面性能结果

所以从统计口径治理角度，把它过滤掉是合理的。

### 6.2 避免 CMDB 页面实体与关系膨胀

视图处理过程中会调用 `dealCmdb(...)`：

- 注册 PAGE 实体
- 建立 APP -> PAGE 关系

如果自定义视图放开，会带来明显风险：

- 视图名可能动态变化
- 视图颗粒度很细
- 业务上可能存在大量短生命周期视图名
- 页面实体数量快速增加
- APP -> PAGE 关系数量膨胀

这会直接影响：

- 页面识别质量
- 页面配置治理
- 页面筛选体验
- 实体图谱质量

所以从 CMDB 实体治理角度，过滤掉自定义视图也有充分理由。

### 6.3 避免行为数据和性能数据混淆

当前系统已经形成默认边界：

- 普通视图 = 性能数据
- 自定义视图 = 行为数据

如果直接放开，就会引入一个根本问题：自定义视图到底应该算作页面性能，还是算作行为埋点？

如果这个边界不先定义清楚，直接让它进入现有 view 统计体系，只会让：

- 数据口径变乱
- 展示逻辑混乱
- 指标语义不一致

## 7. 历史上其实支持过自定义视图

虽然当前被过滤，但代码里保留了很多历史痕迹，说明自定义视图**并不是从系统中彻底删除**。

### 7.1 结果枚举仍保留自定义视图事件类型

在结果事件枚举中仍有：`CUSTOM_ACTIVITY(10202, "自定义视图")`。这说明下游仍然认识这种事件类型。

### 7.2 会话聚合枚举仍然认识 `10202`

在 session 聚合事件类型中：`CUSTOM_ACTIVITY` 仍被归到 `loadOperation`。

说明：自定义视图在历史上至少考虑过进入 session 展示语义。

### 7.3 快照构造逻辑中还保留了自定义视图分支

`ViewEventEnterService.viewSnapshotProcess(...)` 中仍然保留逻辑：

- 如果 `view.getCustom()` 为真
- 则设置 `sessionEventType = CUSTOM_ACTIVITY`

这说明历史上应该是支持过"自定义视图快照语义"的，只是后来入口和主链路被关闭了。

## 8. 如果重新打开自定义视图上报逻辑，会有什么影响

这里分两种情况分析。

### 8.1 情况一：只去掉第一层过滤

即仅去掉 `ViewEventService.filterViewEntity()` 中对 `custom == true` 的过滤。

#### 实际结果

这不会真正恢复功能，因为：

- `ViewEventEnterService` 仍然不让它进入统计和快照
- `ActionExitEventService` 仍然把它排除在标准 view 子事件之外

#### 实际影响

- 自定义视图只是通过了前置过滤
- 但不会真正进入完整视图主链路
- 代码行为会变得更难理解
- 对功能收益很小

#### 风险

- 容易让开发误判"功能已经放开"
- 实际数据仍不完整
- 链路呈现半开状态

### 8.2 情况二：完整放开自定义视图

如果真正要恢复支持，至少需要同步改动：

- `ViewEventService`
- `ViewEventEnterService`
- `ActionExitEventService`
- 相关 session 展示逻辑
- 查询与前端展示逻辑
- 指标说明与口径定义
- 可能还包括 CMDB 注册策略

这会带来一系列影响。

## 9. 放开的具体影响

### 9.1 页面性能统计口径变化

一旦放开并进入标准 view 统计：

- 页面启动次数会增加
- 慢视图次数会增加
- 页面数量会增加
- 页面启动耗时分布会变化
- 页面排行和趋势图会被重算

#### 风险

- 新老版本数据无法直接对比
- 页面性能结果中混入大量"业务行为视图"
- 影响运维、产品、测试对性能问题的判断

### 9.2 CMDB 页面实体与关系数量上升

因为自定义视图也会注册为 PAGE：

- 页面实体数量上涨
- 页面关系增加
- 动态视图名会产生碎片化实体
- 页面治理复杂度显著上升

#### 风险

- 实体识别变差
- 页面筛选噪音变多
- 页面拓扑图可信度下降

### 9.3 数据量上升

放开后，可能新增的数据会进入：

- 视图统计表
- 视图快照表
- terminal 统计
- session 明细
- 行为链路

#### 风险

- 写入量增加
- 存储量增加
- 查询压力上升
- 部分列表和详情性能下降

### 9.4 前端和查询层必须同步改造

如果只改后端而不改前端，会出现：

- 数据进来了，但没法正确展示
- 视图统计页混入自定义视图，语义混乱
- session 详情里出现无法解释的事件类型
- 缺乏"是否为自定义视图"的筛选与区分展示

至少要补齐：

- 自定义视图单独过滤条件
- 列表展示是否区分 `custom=true`
- 是否纳入页面性能主指标
- 是否提供独立列表或独立标签页
- 是否在 session 详情中单独展示 `10202`

### 9.5 可能触发运行时异常或统计异常

这是技术上最容易被低估的一点。

当前大量下游逻辑默认：自定义视图不会进入普通视图处理流程。

如果直接完整放开，可能遇到：

- `slow == null` 导致逻辑异常
- 线程方法信息缺失
- 快照状态不完整
- 启动状态统计不准确
- 某些字段语义与普通视图不一致

#### 本质

当前过滤逻辑不仅是业务限制，同时也在起到**技术保护作用**。

## 10. 为什么"恢复支持"不是删一行代码就行

原因在于系统已经形成了以下隐含前提：

1. 自定义视图不进入标准 view 统计
2. 自定义视图不进入标准 view 快照
3. 自定义视图不进入标准 action-view 子事件
4. 查询层默认只围绕普通页面视图设计
5. CMDB 页面模型默认服务于真实页面

因此如果要恢复，不是一个"开关"问题，而是一个完整的能力改造问题。

## 11. 如果未来要支持，建议的改造方向

如果确实有业务需求恢复自定义视图，建议不要简单混入现有 `VIEW` 主链路。更合理的做法是：

### 11.1 先明确产品口径

要先回答这几个问题：

1. 自定义视图是算"性能页面"还是"行为视图"？
2. 是否参与慢视图统计？
3. 是否注册为 PAGE 实体？
4. 是否进入视图统计排行？
5. 是否进入 session 明细？
6. 是否需要单独展示入口？

### 11.2 最好独立出数据链路

更理想的方式是：

- 将自定义视图视为一种单独的数据类型
- 不直接混入现有普通视图统计口径
- 单独设计统计、查询、展示能力

这样可以避免：

- 污染原有页面性能看板
- 对历史数据产生断层影响

### 11.3 同步补齐展示和查询

如果恢复支持，至少要补：

- 自定义视图列表
- 自定义视图详情
- `custom=true` 筛选
- 指标说明
- session 详情中的事件映射

### 11.4 加强兼容和校验

需要补充针对自定义视图的专用处理，例如：

- `slow == null` 的兼容逻辑
- 线程方法为空时如何处理
- 快照字段如何定义
- `loadTime / stayTime` 是否作为标准性能指标
- 是否允许注册 CMDB 实体

## 12. 自定义视图部分最终结论

### 12.1 为什么会被过滤

自定义视图被过滤，核心原因是：

1. `v3.0` 明确下线了自定义视图采集主链路
2. 设计上将其视为"行为类数据"，而不是"性能页面"
3. 为了避免污染页面性能统计和页面实体体系，产品上选择不展示
4. 下游统计、快照、行为链路也都按"不进入性能展示"这个前提编写

### 12.2 如果放开会有什么影响

如果完整放开，会带来：

1. 页面性能统计口径变化
2. CMDB 页面实体和关系膨胀
3. 数据量和查询压力上升
4. 前端展示和查询逻辑需要同步改造
5. 可能触发运行时异常和统计误差

### 12.3 结论性判断

当前自定义视图被过滤掉，是一个**明确的产品/架构决策**，不是代码遗漏。如果未来要恢复，应该把它当成一个**独立能力改造项目**来做，而不是简单删除过滤判断。

# 第二部分：端到端打通完整逻辑

## 13. `service_detected_name` 的真实来源

### 13.1 结论

`one_rum_datasource_gran.t_rum_net` 表中的 `service_detected_name`，并不是直接从 upload 协议中的同名字段入库，也不是来自网络请求自身的 `detectedName`。

它的真实来源是网络事件协议中的服务端透传信息：

1. 优先取 `resht`（响应头 trace 信息）里的 `x-br-response`
2. 如果 `resht` 中没有 `x-br-response`，则回退取网络事件协议字段 `xbr`
3. 将 `x-br-response/xbr` 按 `,` 或 `;` 切分成键值对
4. 对其中的 `sn` 做 Base64 解码
5. 解码后的 `sn` 赋值给 `NetworkEventModel.serverName`
6. 再赋值给 `NetResultZeus.serviceDetectedName`
7. 最终通过 `CkNet.serviceDetectedName -> service_detected_name` 映射写入 `one_rum_datasource_gran.t_rum_net`

换句话说：

- `service_detected_name = x-br-response/xbr 中 sn 解码后的值`
- 不是 `NetworkEventModel.detectedName`
- 也不是 `RequestCmdbStrategy` 里请求实体的 `detectedName(url)`

## 14. upload 协议入口

### 14.1 upload 整体协议解析入口

`UploadRequestConvert` 负责解析整包 upload 协议，其中事件数组在 `e` 字段中：

- `UploadRequestConvert.resolve(...)`
- `eventInfoConvert(uploadRequestEntity, json.path("e"))`
- 每个事件继续交给 `EventConvert.getInstance().convert(mark)`

这说明网络事件的 `service_detected_name` 链路，首先是从 upload 的 `e` 数组进入事件分发流程。

### 14.2 网络事件分发

`EventConvert.convertEvent(...)` 中，当事件类型是 `NET_WORK` 时，会走：

`NetworkEventConvert.getInstance().convert(json)`

也就是说，真正与网络请求相关的协议字段，都在网络事件 `e[].v` 这层被解析。

## 15. upload 协议里和该字段相关的原始取值

`NetworkEventConvert.resolve(...)` 中，和服务名有关的原始协议字段有两组：

### 15.1 原始兼容字段 `xbr`

```text
networkEventEntity.setXBrResponse(json.path("xbr").textValue());
```

这里的 `xbr` 对应协议中的网络事件字段，注释语义是 `X-BR-Response`。

### 15.2 响应头 trace 字典 `resht`

```text
networkEventEntity.setResponseHeaderTraceInfo(convertToMap(json.path("resht")));
```

`resht` 是响应头 trace 信息字典。如果里面包含 `x-br-response`，后续解析会优先使用它。

### 15.3 协议字段说明

`NetworkEventEntity` 对这些字段的说明非常明确：

- `xBrResponse`: `X-BR-Response` 端到端打通功能
- `responseHeaderTraceInfo`: `resht response header trace info`

因此，从协议层看，`service_detected_name` 的源头并不是单独的业务字段，而是网络事件里承载链路透传信息的 `xbr/resht`。

### 15.4 `resht` 和 `xbr` 的值格式分别是什么

这两个字段虽然都可能参与后续服务名提取，但协议形态并不一样。

#### 15.4.1 `resht` 的格式

`resht` 是一个 **JSON 对象 / 字典**，key 是响应头名，value 是响应头值。`NetworkEventConvert.resolve(...)` 里使用：

```text
convertToMap(json.path("resht"))
```

说明它在协议中不是普通字符串，而是对象结构。

单测中的真实协议样例就是：

```json
"resht": {
  "header2": "value2"
}
```

如果用于当前这条 `service_detected_name` 链路，那么更贴近实际的 `resht` 会长这样：

```json
"resht": {
  "x-br-response": "sn=U2VydmljZU5hbWU=;si=123456;auid=agent-001;dc=MQ=="
}
```

也就是说：

- `resht` 外层是 JSON 对象
- `x-br-response` 只是这个对象里的一个响应头 key
- 真正参与 `sn/si/dc` 解析的，是 `resht["x-br-response"]` 这个字符串值

#### 15.4.2 `xbr` 的格式

`xbr` 是一个 **普通字符串字段**，对应原始的 `X-BR-Response` 内容。`NetworkEventConvert.resolve(...)` 里使用：

```text
networkEventEntity.setXBrResponse(json.path("xbr").textValue());
```

说明它在协议中直接就是字符串，不是 JSON 对象。

单测里的最简样例是：

```json
"xbr": "xbr_response"
```

结合实际解析代码，标准格式通常类似：

```json
"xbr": "sn=U2VydmljZU5hbWU=;si=123456;auid=agent-001;dc=MQ=="
```

或者用逗号分隔也可以：

```json
"xbr": "sn=U2VydmljZU5hbWU=,si=123456,auid=agent-001,dc=MQ=="
```

原因是 `fmtXBr2Map(...)` 使用的是：

```text
xBrResponse.split("[,;]")
```

所以它同时兼容两种分隔符：

- 分号分隔：`sn=...;si=...;auid=...;dc=...`
- 逗号分隔：`sn=...,si=...,auid=...,dc=...`

#### 15.4.3 两者差异总结

可以把它们理解成：

- `resht`：**响应头字典**
- `xbr`：**字典里的某个关键响应头值被单独提出来后的原始字符串**

用一个完整的网络事件协议片段表示，大致会是这样：

```json
{
  "xbr": "sn=U2VydmljZU5hbWU=;si=123456;auid=agent-001;dc=MQ==",
  "resht": {
    "x-br-response": "sn=U2VydmljZU5hbWU=;si=123456;auid=agent-001;dc=MQ==",
    "content-type": "application/json"
  }
}
```

其中：

- `resht` 是对象
- `resht["x-br-response"]` 是字符串
- `xbr` 也是字符串
- 后续解析时优先取 `resht["x-br-response"]`，没有再回退到 `xbr`

### 15.5 `sn / si / auid / dc` 子字段含义

结合 `fmtXBr2Map(...)`、`getServerName(...)`、`getServerInstanceId(...)`、`getDataCenterId(...)` 这几段代码，可以把 `x-br-response/xbr` 中常见子字段理解为：

1. `sn`
   - 含义：服务名称（service name）
   - 编码：Base64 编码
   - 解析后用途：赋值给 `NetworkEventModel.serverName`
   - 最终用途：写入 `t_rum_net.service_detected_name`

2. `si`
   - 含义：服务实例 ID（service instance id）
   - 编码：原样字符串，不做 Base64 解码
   - 解析后用途：非镜像模式下，直接用于 `NetworkEventModel.serverId`
   - 最终用途：用于服务实例关联，不是 `service_detected_name`

3. `auid`
   - 含义：agent UID / 代理唯一标识
   - 编码：原样字符串，不做 Base64 解码
   - 解析后用途：镜像模式下，用它去 `ServiceCache` 查服务，再拿到服务实例 ID
   - 最终用途：间接参与 `serverId` 获取，不直接写 `service_detected_name`

4. `dc`
   - 含义：数据中心唯一标识（data center id）
   - 编码：Base64 编码
   - 解析后用途：赋值给 `NetworkEventModel.dataCenterId`
   - 最终用途：写入网络结果中的 `data_center_id`

可以简化记忆为：

```text
sn -> 服务名 -> service_detected_name
si -> 服务实例 ID -> serverId
auid -> 镜像模式下查服务实例 ID
dc -> 数据中心 ID -> data_center_id
```

## 16. 核心解析逻辑：从 `x-br-response/xbr` 提取服务名

真正把 upload 协议里的透传字段转成服务名的是：

- `DataFormatUtil.fmtXBr2Map(...)`
- `DataFormatUtil.getServerName(...)`

### 16.1 取值优先级

`fmtXBr2Map(...)` 的逻辑是：

1. 先取 `networkEventEntity.getResponseHeaderTraceInfo()`
2. 如果 `responseHeaderTraceInfo` 中包含 `x-br-response`，优先使用这个值
3. 否则回退到 `networkEventEntity.getXBrResponse()`
4. 如果最终为空，直接返回 `null`

也就是：

```text
优先级：resht["x-br-response"] > xbr
```

这个优先级很关键，因为网络请求在前面会做一次 trace 头过滤，`resht` 中只保留配置过的响应头。即使过滤后 `resht` 里没有 `x-br-response`，代码仍然会回退使用原始 `xbr`，所以不会因为 trace 头过滤而完全丢失服务名来源。

### 16.2 解析格式

`fmtXBr2Map(...)` 注释描述的格式为：

```text
sn=[serviceName];si=[serviceId];auid=[agentUID];xx=[其他待扩展]
```

而 `NetworkEventModel` 中对 `x-br-response` 的注释又补充了更完整的形态：

```text
sn=base64{serviceName},si={serviceId},auid={agentUID},dc=base64{数据中心唯一标识},xx={其他待扩展}
```

### 16.3 具体转换规则

`fmtXBr2Map(...)` 处理规则如下：

1. 用正则 `[,;]` 切分字符串
2. 每段按第一个 `=` 分成 `key/value`
3. 如果 key 包含 `sn` 或 `dc`，则对 value 做 Base64 解码
4. 其他字段原样放入 Map

所以：

- `sn` -> Base64 解码后得到服务名
- `si` -> 原样保留，供服务实例 ID 使用
- `auid` -> 原样保留，镜像模式下用于查缓存拿服务实例
- `dc` -> Base64 解码后得到数据中心 ID

### 16.4 服务名提取

`DataFormatUtil.getServerName(...)` 的逻辑非常直接：

- 从 `NetworkEventModel.xBrResponseMap` 中取 key=`sn`
- 存在则返回该值
- 不存在则返回 `null`

因此可以确定：

```text
NetworkEventModel.serverName = 解析后的 xBrResponseMap["sn"]
```

## 17. 模型转换链路

### 17.1 网络事件模型转换

`NetworkEventModelConvert.customConvert(...)` 中会执行：

1. `networkEventModel.setXBrResponseMap(DataFormatUtil.fmtXBr2Map(commonModel, networkEventEntity));`
2. `networkEventModel.setServerName(DataFormatUtil.getServerName(networkEventModel));`
3. `networkEventModel.setDataCenterId(DataFormatUtil.getDataCenterId(...));`
4. `networkEventModel.setServerId(DataFormatUtil.getServerInstanceId(...));`

这里可以看到：

- `serverName` 来源于 `sn`
- `dataCenterId` 来源于 `dc`
- `serverId` 来源于 `si` 或镜像模式下 `auid -> ServiceCache`

也就是说，`service_detected_name` 对应的是服务名 `sn`，而不是服务实例 ID。

### 17.2 网络事件策略继续处理

后续在 `NetPreEventStrategy.dealModelConvert(...)`、`NetErrorEventStrategy.dealModelConvert(...)` 里都会执行：

```text
model.setDetectedName(model.getUrl());
```

这一步很容易混淆，但它设置的是网络请求实体自身的 `detectedName`，值是请求 URL，用于请求 CMDB/实例注册链路，不是服务端服务名。

因此这里必须区分两套概念：

1. `model.detectedName = model.url`
   - 用于请求实体（request entity）的 detectedName
   - 本质上是"请求名称/请求实体识别名"
2. `model.serverName = x-br-response/xbr 中 sn 解码值`
   - 用于 `t_rum_net.service_detected_name`
   - 本质上是"服务端服务识别名"

## 18. 粗粒度结果集构造

网络性能数据落粗粒度表时，会走 `NetWorkResultBuild.buildPerformanceNetResult(...)`。

其中关键赋值是：

这一步已经把 `NetworkEventModel.serverName` 显式映射到了结果对象 `NetResultZeus.serviceDetectedName`。

```text
NetResultZeus.serviceDetectedName = NetworkEventModel.serverName
```


## 21. `service_detected_name` 容易混淆的点

### 21.1 `detectedName` 不是这里的来源

网络策略里虽然有 `model.setDetectedName(model.getUrl());`，但这个 `detectedName` 是请求实体自己的识别名，值是 URL，服务于 CMDB 请求实体注册，不会直接写入 `t_rum_net.service_detected_name`。

### 21.2 `service_detected_name` 取的是 `sn`，不是 `si`

- `sn`：服务名，Base64 解码后用于 `service_detected_name`
- `si`：服务实例 ID，用于 `serverId`
- `auid`：镜像模式下用于查 `ServiceCache` 进一步拿 `serverId`

### 21.3 `resht` 比 `xbr` 优先

若 `resht` 中存在 `x-br-response`，优先使用它；否则回退到 `xbr`。

### 21.4 缺失时可能为空

如果：

- `resht["x-br-response"]` 不存在
- 且 `xbr` 也为空
- 或解析失败后没有 `sn`

则 `serverName` 为 `null`，最终 `service_detected_name` 也会为空。

## 22. `service_detected_name` 一句话结论

`t_rum_net.service_detected_name` 的值，来自 upload 网络事件协议中的 `resht["x-br-response"]` 或回退字段 `xbr`，解析后取其中 `sn` 并做 Base64 解码，再经过 `NetworkEventModel.serverName -> NetResultZeus.serviceDetectedName -> CkNet.service_detected_name` 的映射链路落库。

## 23. RUM 何时写调用链数据到 `t_trace`

### 23.1 结论先说

RUM 模块写调用链数据到 `t_trace`，不是所有事件都会写，也不是所有带 `traceId` 的网络事件都会写。

当前代码里，**只有网络事件链路**会在满足条件时额外生成一份 `APM_TRACE_DATA` 数据，最终写入 `t_trace`。

直接触发条件是：

```text
RumBaseConfig.apmOpen == true
&& (networkEventModel.otherSnapshotFlag == true || networkEventModel.snapshotFlag == true)
```

满足这两个条件时，RUM 才会构造：

```text
GranDataDTO.build(EtlBizTypeEnum.APM_TRACE_DATA, ...)
```

而 `EtlBizTypeEnum.APM_TRACE_DATA` 对应的表名就是 `t_trace`。

### 23.2 最终写表入口

从枚举定义可以明确看到：

```text
APM_TRACE_DATA("t_trace", "one_apm_datasource_trace_snapshot", ...)
```

所以 RUM 这边只要产出了 `APM_TRACE_DATA`，最终目标表就是 `t_trace`。

### 23.3 哪些事件类型会走这条链路

当前 RUM 代码里，只有以下 4 个网络事件策略会判断是否写调用链：

1. `NetPreEventStrategy`
2. `NetErrorEventStrategy`
3. `NetResourceEventStrategy`
4. `NetResourceErrorEventStrategy`

它们在 `buildGranResult(...)` 里都有同样的判断：

```text
boolean saveCallChain = RumBaseConfig.getInstance().apmOpen
    && (model.isOtherSnapshotFlag() || model.isSnapshotFlag());
```

若 `saveCallChain == true`，就会执行：

```text
GranDataDTO.build(EtlBizTypeEnum.APM_TRACE_DATA,
    NetWorkResultBuild.buildTraceSnapshotResult(...))
```

这说明：

- 普通 RUM 页面、Action、Crash、H5 等事件本身**不会直接写** `t_trace`
- 是网络事件在特定条件下，**额外派生出一条调用链记录**写到 `t_trace`

### 23.4 识别依据一：总开关 `apmOpen`

第一层识别依据是 `RumBaseConfig.apmOpen`。只有在 APM 打通开关打开时，RUM 网络事件才允许写调用链到 `t_trace`。

如果这个开关是 `false`，即使网络事件里已经识别出了 trace 信息，也不会写 `t_trace`。

### 23.5 识别依据二：`snapshotFlag` 或 `otherSnapshotFlag`

第二层识别依据是两个布尔标识：

- `snapshotFlag`：Bonree 端到端打通场景下，强制存储快照/调用链标识
- `otherSnapshotFlag`：第三方协议（如 SkyWalking）存在端到端标识

只要其中一个为 `true`，并且 `apmOpen=true`，就会写 `t_trace`。

所以，RUM 是否写 `t_trace` 的直接判定，不是看 `service_detected_name`，也不是看 `xbr`，而是看：

```text
apmOpen + snapshotFlag/otherSnapshotFlag
```

### 23.6 这些标识是怎么识别出来的

`NetworkEventModelConvert.customConvert(...)` 中会调用：

```text
DataFormatUtil.getTraces(commonModel, networkEventEntity, networkEventModel)
```

这个方法就是 RUM 识别"当前网络事件是否具备调用链写入资格"的核心入口。

#### 23.6.1 配置规则先按域名筛选

`getTraces(...)` 会先读取 `RUM_TRACE` 配置，并根据域名规则筛选当前网络请求是否需要做 trace 头解析：

- 全部域名
- 白名单域名
- 黑名单域名

只有命中这些配置规则后，才会把对应的 trace header 规则放入待解析集合。

也就是说，**是否匹配 trace 配置域名规则**，是识别调用链的前置依据之一。

#### 23.6.2 优先识别第三方协议（SkyWalking）

如果配置中存在第三方 trace 协议（代码注释里写的是 SkyWalking，`protocolType = 1`），则优先解析。

当 `parseTraceId(...)` 解析成功后，会执行：

```text
networkEventModel.setTraceId(...)
networkEventModel.setTraceSpanId(...)
networkEventModel.setOtherSnapshotFlag(true)
return
```

这意味着：

- 一旦第三方 trace 头解析成功
- `otherSnapshotFlag` 会直接设为 `true`
- 后续满足 `apmOpen=true` 时，这条网络事件就会写 `t_trace`

这里可以理解为：

```text
第三方 trace 识别成功 => 直接允许写 t_trace
```

#### 23.6.3 再识别 Bonree 协议

如果第三方协议没有识别成功，则继续尝试 Bonree 协议（代码里标记为 `protocolType = 0`）。

Bonree 协议下分两种常见来源：

1. 响应头 `traceresponse`
2. 请求头 `traceparent`

##### 情况 A：存在 `traceresponse`

代码会解析：

```text
traceId = traceSplit[1]
traceSpanId = traceSplit[2]
snapshotFlag = "01".equals(traceSplit[3])
```

也就是说：

- 能识别出 `traceId`
- 只有当 `traceresponse` 第 4 段等于 `"01"` 时
- `snapshotFlag` 才为 `true`
- 之后这条网络事件才有资格写 `t_trace`

这说明在 Bonree 协议下：

```text
有 traceId 还不够
还必须有 "需要存储调用链/快照" 的标志位 == 01
```

##### 情况 B：只有 `traceparent`

如果没有 `traceresponse`，但有 `traceparent`，代码只会解析出：

- `traceId`
- `traceSpanId`

但不会把 `snapshotFlag` 置为 `true`，默认仍然是 `false`。

因此这种情况下：

- 虽然可能有 `traceId`
- 但 `snapshotFlag=false`
- 所以**不会写** `t_trace`

这个点非常关键，说明：

```text
仅有 traceId != 一定写 t_trace
```

### 23.7 老协议兼容逻辑

即使没有命中当前 trace 配置，代码最后还会兼容老探针字段：

1. `traceResponse`
2. `traceParent`

处理规则是：

#### 23.7.1 老字段 `traceResponse`

如果 `traceResponse` 存在，则：

```text
traceId = split[1]
snapshotFlag = "01".equals(split[3])
```

所以老协议下：`traceResponse` 中有 traceId，且第 4 段是 `"01"`，才会触发写 `t_trace`。

#### 23.7.2 老字段 `traceParent`

如果只有 `traceParent`，则：会解析 `traceId`，但 `snapshotFlag=false`。因此这种情况下同样**不会写** `t_trace`。

### 23.8 归纳成一张判断表

可以把 RUM 写 `t_trace` 的识别依据总结成下面这几种情况：

1. `apmOpen=false`：不写 `t_trace`
2. 第三方 trace 头识别成功：`otherSnapshotFlag=true`，写 `t_trace`
3. Bonree `traceresponse` 识别成功，且标记位为 `01`：`snapshotFlag=true`，写 `t_trace`
4. 只有 `traceparent`：有 `traceId`，但 `snapshotFlag=false`，不写 `t_trace`
5. 老协议 `traceResponse` 识别成功，且标记位为 `01`：`snapshotFlag=true`，写 `t_trace`
6. 老协议只有 `traceParent`：有 `traceId`，但 `snapshotFlag=false`，不写 `t_trace`

### 23.9 为什么说"识别依据"不是单纯的 `traceId`

从代码上看，`buildTraceSnapshotResult(...)` 会用到：

```text
String traceID = networkEventModel.getTraceId();
traceResult.setTraceId(traceID);
traceResult.setPartitionNum(MathUtils.getABSValue(traceID.hashCode() % 100));
```

这说明真正写 `t_trace` 时，确实依赖 `traceId`。

但是在调用之前，代码并不是仅仅判断 `traceId` 是否非空，而是判断：

```text
otherSnapshotFlag || snapshotFlag
```

因此更准确的说法是：

- `traceId` 是写 `t_trace` 的基础数据
- `snapshotFlag/otherSnapshotFlag` 才是"是否写"的直接识别依据

### 23.10 这条 `t_trace` 数据在 RUM 里是什么性质

RUM 写入 `t_trace` 时，构造的是 `TraceSnapshotResultZeus`，其中：

```text
traceResult.setDataType("2");
```

这说明这条数据在当前实现里是 RUM 侧派生出来的一条调用链/快照数据，不是 APM Agent 原生上报的 span 明文。

它主要承载的是：

- 当前网络请求的 `traceId`
- 请求 URL / Method / Code
- 总耗时
- `traceSpanId`
- session/user 等附加信息

### 23.11 `t_trace` 写入一句话总结

RUM 模块会写调用链数据到 `t_trace`，本质上发生在**网络事件**处理中；只有当 `apmOpen=true`，并且 `getTraces(...)` 识别出该请求属于可落调用链的 trace 场景（`otherSnapshotFlag=true` 或 `snapshotFlag=true`）时，才会额外生成 `APM_TRACE_DATA`，最终写入 `t_trace`。其中最关键的识别依据不是单纯"有 traceId"，而是"traceId 被识别出来后，同时命中了允许落调用链的标志位/协议规则"。

## 24. 有 `traceId` 但 `snapshotFlag=false` 时，网络快照表是否仍会存储 `traceId`

结论是：**会，仍然可能存储**。但这里要分清两个不同的落库目标：

1. `t_trace`：是否写入，取决于 `apmOpen && (otherSnapshotFlag || snapshotFlag)`
2. `t_rum_net_snapshot`：是否写入，以及里面是否带 `traceId`，是另一套网络快照逻辑

也就是说：

```text
不写 t_trace != 不写网络快照中的 traceId
```

### 24.1 为什么会存

在普通网络请求和网络错误请求里：

- `NetPreEventStrategy.buildSnapshotResult(...)`
- `NetErrorEventStrategy.buildSnapshotResult(...)`

都会无条件继续构建网络快照：

```text
SnapshotResultZeus snapshotResultZeus = NetWorkResultBuild
    .buildPerformanceNetSnapshotResult(...)
SnapshotDataDTO.build(EtlBizTypeEnum.RUM_NETWORK_SNAPSHOT, snapshotResultZeus)
```

这里并**没有**要求 `snapshotFlag=true` 才生成网络快照。

而且这两个策略里 `saveFlag` 直接写死为：

```text
int saveFlag = 1;
```

含义是"全存"。

所以只要这条网络事件本身走到了网络快照构建逻辑，`t_rum_net_snapshot` 就会照常生成，并不依赖 `snapshotFlag=true`。

### 24.2 `traceId` 写到网络快照表的哪里

`buildPerformanceNetSnapshotResult(...)` 在构造网络快照时，会把下面这些字段写进 `otherIndex`：

```text
otherIndex.put("traceFlag", networkEventModel.isSnapshotFlag() ? "1" : "0");
otherIndex.put("traceId", networkEventModel.getTraceId());
otherIndex.put("traceSpanId", networkEventModel.getTraceSpanId());
```

这说明：

- 即使 `snapshotFlag=false`
- 只要 `networkEventModel.traceId` 已经被识别出来
- 网络快照里的 `other_index` 仍然会写入 `traceId`
- 同时 `traceFlag` 会被写成 `"0"`

所以更准确地说：

```text
snapshotFlag=false 时：
  t_trace 通常不写
  t_rum_net_snapshot.other_index.traceId 仍可能有值
  t_rum_net_snapshot.other_index.traceFlag = "0"
```

### 24.3 为什么会出现"有 traceId 但 traceFlag=0"

典型场景就是前面提到的：

- 只有 `traceparent`
- 或老协议里只有 `traceParent`

这两种情况代码都可能识别出 `traceId`，但不会把 `snapshotFlag` 设为 `true`。

于是结果就是：

- `networkEventModel.traceId` 有值
- `networkEventModel.snapshotFlag = false`
- 不满足 `t_trace` 的写入条件
- 但网络快照 `other_index.traceId` 仍然会保留

### 24.4 是否还会写入 `other_index_json`

`BusinessCommonBiz` 在写快照时会：

```text
snapshotResult.setOtherIndex(otherIndex);
if (shouldSetOtherIndexJson(type)) {
  snapshotResult.setOtherIndexJson(JacksonUtils.rumObj2JsonString(otherIndex));
}
```

而 `RumBaseConfig` 对 `snapshotOtherIndexJsonTypes` 的默认说明是：默认仅 NET。

因此对于网络快照，默认情况下：

- `other_index` 里会有 `traceId`
- `other_index_json` 里通常也会序列化出同样的 `traceId`

### 24.5 最终结论

当 RUM 网络事件已经识别出 `traceId`，但 `snapshotFlag=false` 时：

1. 这条数据通常**不会写入** `t_trace`
2. 但普通网络快照表 `t_rum_net_snapshot` **仍然会照常生成**
3. 并且网络快照的 `other_index` / `other_index_json` 中**仍可能保留**：
   - `traceId`
   - `traceSpanId`
   - `traceFlag=0`

所以如果你在排查数据时发现：

```text
t_rum_net_snapshot 里有 traceId
但 t_trace 没有对应数据
```

这在当前代码逻辑下是**完全可能且合理**的，常见原因就是：

- 这条请求只识别出了 `traceId`
- 但没有命中允许写调用链的 `snapshotFlag/otherSnapshotFlag`
