# 工程化重构与性能调优方案

> 文档作用：整合 RUM 模块前后端插件代码实现质量分析、工程化重构实施方案、Controller 性能调优方案三部分内容，形成完整的工程化改进技术文档。
>
> 适用范围：后端 `framework/plugins/rum` + 前端 `view/rum`（Module Federation 插件 `one_rum`）+ 接入层 `controller/rum-controller`。

---

| 代码复用度 | ★★☆☆☆（按模块复制查询样板） | ★★☆☆☆（AppSelect/弹窗/列定义多份） |

| 技术债清理 | ★★☆☆☆（ES→CK 迁移残留、100+ 注释测试） | ★★☆☆☆（old/new 双轨 54+ 文件） |

> **共性根因**：前后端均处于「多年迭代 + 重大版本兼容（ES→ClickHouse、旧快照→新快照 snapshotVersion）」的形态。后端迁移策略为「按模块复制粘贴」而非「抽取公共框架」，前端则长期保留新旧双轨实现。功能完整但技术债集中。

### 1.2 后端插件（framework/plugins/rum）实现问题

#### 1.2.0 架构与 Maven 分层问题（最高优先）

- **依赖倒置**：`rum-common/pom.xml` 依赖 `symbol-analysis`（`BRFSUtil.java` 引用 `com.bonree.rum.analysis.service.*`），导致最底层的「公共层」反向依赖业务符号化模块，无法被其他插件独立复用。
- **隐式依赖**：`rum-core/pom.xml` 未直接声明 `rum-common`，仅通过 `rum-cache`/`rum-database` 传递依赖，分层意图不可见。
- **缓存层耦合 DB**：`rum-cache` 依赖 `rum-database`，`AppCache` 直接 `@Autowired RumQueryServiceAppMapper`，缓存层无法独立测试/复用。
- **目标分层建议**：`symbol-analysis → rum-common → rum-database → rum-cache → rum-core → rum-admin`，通过 Repository 接口隔离 cache 与 DB。

#### 1.2.1 代码复用不足

| 问题 | 证据 | 影响 |
|---|---|---|
| **Druid 查询样板大规模重复** | 60+ 个 `*/druid/*.java`（terminal 30、problem 12、network 8…）均自实现 `assembleParam(ReportCondition)`，手工 `Lists.newArrayList()` + `FilterOption` 拼装 | 新增指标查询需复制 80~200 行；改过滤规则要改几十处 |
| **filterComponent 解析散落** | 49 个文件各自 `JacksonUtil.json2list(condition.getFilterComponent(), FilterOption.class)`，解析失败统一 `throw new RuntimeException(e)`（70+ 处） | 错误信息不可区分，难定位 |
| **appId 过滤逻辑重复** | 70+ 文件手工拼 `dimension['appId']` 单值/列表两套逻辑 | 漏加即数据越权风险 |
| **工具类多份并存** | `DateUtil`（common 482 行 vs settings 329 行）、`ValueParseUtil`（common 323 vs settings 496）、`CollectionUtil`（common 53 vs settings 371）、`ZipFileUtil` 三份、`JacksonUtil`+`JacksonUtils` 双份 | 行为可能不一致，同名类冲突风险 |
| **分布占比/指标计算重复** | `NetworkMetricBuild.dealNumCondition`(163-189) 与 `AppViewPageTypeList`(175-208) 逐行相同 | 口径变更需多处同步 |
| **Service 薄包装模式重复** | `MiniProgramService`、`NetWorkService`、`AppDetailService` 均为 `ConditionConvertUtil.convert → rumMetricServiceFactory.query → Map→VO` | 缺少 `AbstractMetricQueryService<T>` 模板 |

**建议**：抽取统一 `MetricFilterAssembler`（filterComponent + appId + envId + 时间窗）、`FilterComponentParser`、`AbstractMetricQueryService<T>` 模板方法；合并重复工具类至 `rum-common` 单一入口。

#### 1.2.2 代码冗余重复

- **接口参数校验复制**：`NetWorkController` 11 个接口重复 `reqType == null` 校验（全文 22 处）；`CoulometryController` 6 个接口重复 `setEnvId/setAccountId` 注入。建议改 JSR-303 + `@ControllerAdvice` / AOP `RumContextInjector`。
- **重复类/常量**：`BizEventListVO` 在 `biz/entity` 与 `biz/entity/vo` 两套；`Constants.java`（481 行）与 `CommonConstant`（interface）双常量入口；`Md5Util`/`Md5Utils`、`EmptyUtils`、`FileUtils`/`FileUtil` 多份。
- **同构 Druid 类群**：`AppKinship*`（6 类）、`Problem*Chart`（12 类）、`PageAnalysis*Chart`（7 类）结构高度相似，可参数化为 `relationType/chartType` 配置驱动。
- **Redis Key 前缀不统一**：`:RUM:` 在多处硬编码，`RedisPermissionUtil` 又用 `CACHE_WEB_PREFIX + key`，同一 key 可能带/不带全局前缀。建议定义 `RumRedisKeys` 常量类。
- **巨型数据初始化**：`FilterFieldsCreator.java` 约 6000 行 static Map 初始化，建议外置 JSON/YAML 启动加载。
- **包名拼写错误**：`common/factroy/RumSqlFilterFactory`（`factroy` 拼错）被 15+ 处引用。

#### 1.2.3 实现不一致

- **时间处理混用**：`RumAlertController` 同时用 framework 的 `DateUtil.convertTimestamp` 与 rum 的 `DateUtil.YYYY_MM_DDHHMMSS`，时区行为不可预测。
- **分层边界模糊**：30+ 处 Service 直接返回 `RestResponse`（`AppDetailService` 21+ 处、`ProblemService` 17 处、`RumConfigWizardService` 49 处），Service 难单测、难复用。
- **分页模型分裂**：`BasePageRsp`（framework）、`com.bonree.rum.common.bean.BasePageRsp`、`RumPageRsp`（coulometry）三套并存。
- **错误码/I18n 不统一**：部分返回 `I18nUtil.INSTANCE.getMessage(...)`，部分直接返回裸 key 字符串。
- **异常策略三分**：`throw new RuntimeException(e)`（70+ 文件）/ `RestException` / `RestResponse.error` 混用，同一 JSON 解析失败有的 500 有的 400。
- **基础设施多套并存**：3 套本地缓存（Caffeine / Guava / ConcurrentHashMap）、3 套 Redis 分布式锁（`RedisLock` / `RedisUtils.getLock` ×2）、4 套调度（Quartz / `@Scheduled` / `@EventListener` / 已注释的 `RumScheduleConfig`）、6+ 个独立线程池（`ExecuteService` / `ExecutorFactory` 硬编码 4/8 / `AsyncThreadConfig` 按核数）。
- **路由前缀不统一**：仅 2 处使用 `/api/` 前缀，其余 45+ Controller 用 `/rest/`。
- **安全隐患**：`RumOpenApiUserFilter` 鉴权异常仅 `log.error` 不中断请求链，存在静默放行风险（建议 fail-fast 返回 401/403）。

#### 1.2.4 过时 / 废弃 / 无用代码

- **ES→CK 迁移残留**：`query/enums/QueryType.ES` 无实现 Bean；`RumEsToCkSessionSearchService` 命名暗示双实现实际仅 CK；`BaseEsService`、`CoulometryProcessEsTableEntity` 等含 Es 命名却走 CK；`RetrievalRepository` 仍 import `EsAliasConstant`/`EsUtils`。
- **v4 迁移代码待删**：`InitAppScoreRuleSync.java`（约 833 行，类注释自标 `v4.0.0.0-deprecate 下版本删除`）+ `migration/*` 实体，每次启动仍可能执行迁移逻辑。
- **`@Deprecated` 仍活跃**：`QueryFieldUtils.getQueryFields`、`AppDigitDownloadFilter.defaultBarCSVData`、`BaseCondition`/`BasePageCondition` 废弃基类仍在继承链、`RumTagsEntity`/`RumTagsRelationEntity`。
- **失效组件**：`MetricSwitchJob`（注释「one430 起弃用」仅打印配置）、`RumScheduleConfig`（`@Configuration` 被注释整类失效）。
- **测试虚胖**：rum-core 测试中 100+ 文件含大段 `//` 注释（如 `JsRuleCacheTest` 整文件注释、`RumThreadPoolSupportTest` 测试的类已不存在），覆盖率数字失真。
- **TODO 堆积**：terminal 包 57 文件、problem 包 15 文件含占位 `@说明：TODO`。

#### 1.2.5 可优化模块（超大类 / 性能）

| 文件 | 行数 | 问题 | 建议 |
|---|---|---|---|
| `common/util/SessionUtil.java` | ~4515 | 会话事件 VO 全量转换上帝类，新旧数据双路径并存 | **P0** 按 EventType 拆 Converter + 单测 |
| `problem/service/ProblemService.java` | ~4090 | 列表/统计/导出/OpenAPI 全堆一处 | 拆 List/Stat/Export 子服务 |
| `common/util/HealthScoreServer.java` | ~3901 | 规则+查询+计算耦合，与 settings `HealthScoreServiceImpl` 重叠 | 计算引擎与数据查询分离 |
| `common/service/AppDigitDownloadFilter.java` | ~3433 | 导出格式化上帝类 | 策略模式 + 按模块注册 |
| `terminal/service/AppDetailService.java` | ~2129 | Service 返回 RestResponse + 业务分支 | 拆领域服务，去 RestResponse |
| `RUMConfig.java` | ~684 / 100+ 配置 | 上帝配置对象 | 按域拆 Query/Wizard/Permission Config |

- **性能热点**：`RumCkSessionSearchService` 列表 enrich 多轮 for 遍历（O(n²) 排序拼装）；会话/CMDB 城市运营商补全无统一缓存（全库仅 1 处 Caffeine）。
- **弱模块**：`alert`（2 文件）、`filter`（1 文件）、`query`（7 文件）、`miniprogram`（6 文件）模块过薄，能力寄生在 terminal，建议合并或充实边界。

### 1.3 前端插件（view/rum）实现问题

#### 1.3.1 代码复用不足

| 问题 | 证据 | 影响 |
|---|---|---|
| **三域名请求页同构** | `experience/request/networkDomain`（~719 行）与 `resourceDomain`（~706 行）结构几乎一致，后者直接复用前者 less | 任一 Tab 改动需改 2~3 处 |
| **AppSelect 6+ 份** | request/user/pageAnalysis/breakdown/userSession 各一份 + `AppPicker` | 筛选/权限/缓存逻辑易漂移 |
| **自定义网络规则弹窗 4+ 套** | ConfigDistinguishRequest/Module、ConfigAiLag 下多份 `AddNetworkCustomRuleModal` | 校验逻辑重复维护 |
| **ConditionItem 条件行 40+ 文件** | configurationModule 内 SlowOperation/CodeException/FailedOperation/DataMasking… | 配置域最大重复源 |
| **表头列定义分散 15+ models** | `tableColmun.tsx`（拼写错误）+ `setTableColumnsFn` + 各 `common.tsx` | 列渲染/排序/下载重复 |
| **服务层 API 重复** | `getFilter→POST /rest/rum/filter/query` 6+ 处独立封装；`problem/*/detail` 3 处；`titles/label/alias` 2+ 处 | cancel 策略不一致，改接口漏改 |

**建议**：抽 `useRequestDomainPage`、统一 `packages/component/application/AppSelect`、`NetworkCustomRuleModal`、`useCustomTableHeader`；服务层建 `services/shared/`（filter / titles / problemDetail / recordList）。

#### 1.3.2 代码冗余重复

- **old/new 双轨完整目录（最严重）**：`pageDetail/page/{oldIndex,newIndex}`、`startDetail`、`netReqDetail`、`operateAnalysisDetail` 各对称 19+19 文件；`breakdown/Common/{old,new}` 14 个 hook。**合计约 54 个文件**服务于「快照版本双轨」，运行时靠 `info?.snapshotVersion ? <NewIndex/> : <OldIndex/>` 分支。
- **巨型 utils**：`utils/index.ts`（1106 行 / 60+ export），`secondTohhmmss` 与 `msVideo`、`FalseOrZero` 与 `FalseOrZeroSession` 近似重复，阻碍 tree-shaking。
- **APM 枚举重复继承**：`models/configurationModule/enum.ts`（1047 行）与 `utils/technologyType.ts` 中 `TechnologyType` 230+ 条目几乎完整重复，且多为 RUM 未使用的 APM 资产。
- **命名/拼写债**：`tableColmun`（应为 column）16 处引用、`modeles`（应为 models）目录、`inde.less`（缺 x）、`utils/operstion.ts`。
- **资源冗余**：`signal1~4.svg` 与 `Signal-1~4.svg` 两套信号图标并存，按主题分支 require。

#### 1.3.3 实现不一致

- **状态管理 3 套范式**：自研 `createMr`（`domain.ts` 1826 行，类 concent）/ reducer（`sessionDetail`）/ 页面级 `useState`+`useSafeState`。`useState` vs `useSafeState` 无统一策略。
- **国际化 4 套入口**：`$rum.t()` / `Lang['key']` 静态对象 / `GETLOCALE` / `useI18n`，并存在硬编码中文（如 `common.tsx` 的 `'可根据服务名称…搜索'`）。
- **目录深度极端**：最深 11 层（`retrieval/.../oldIndex/view/tabCont/record/table`），相对 import 达 16 个 `../`；probe 多为 3~4 层。
- **响应码判断不一**：`res.code == 200`（number）与 `resp.code == '200'`（string）混用。
- **主题色违规**：`components` 内约 23 个文件仍硬编码 hex 色值（`BrEcharts/theme.ts` 80+ 处），与 AGENTS 要求的 `var(--bonree-*)` 规范冲突，深色模式下「漏网」。
- **跨包反向依赖**：`retrieval/netReqDetail` import `experience/request/models/domain`，存在循环依赖与重复打包风险。
- **导入别名脱节**：AGENTS 写 `import from 'components'` 实际 0 处使用，200+ 处用 `_components/*` 深 import，barrel `components/index.ts` 仅导出 12/35+ 组件。

#### 1.3.4 过时 / 废弃 / 无用代码

- **运行时双轨长期存在**：3 处详情入口 `snapshotVersion ? New : Old`，旧实现无法自然消亡，约 50% 详情代码冗余。
- **死代码**：`hooks/useDebounce.tsx`（生产 0 引用，已全面用 ahooks）、`components/basic/Name`（仅 1 处引用，BrName 已覆盖）、`utils` 中注释的 `filtratePower`/`filtrateMergePower`、`services/common.ts` 注释的 `getAppResource`。
- **生产 console.log**：`pageDetail/index.tsx`、`domain.ts` 等 100+ 文件含 `console.log`（含 `console.log(..., 888)` 调试残留）。
- **过时 API**：`utils/operstion.ts` 用已废弃的 `unescape()`（应改 `decodeURIComponent`）。
- **模块级可变标志**：`CrashRecord/index.tsx` 的 `let isQuery = false`，热重载/多实例下状态污染，应改 `useRef`。

### 1.4 前后端协同与一致性问题（横切）

前端硬编码了大量「本应由后端下发」的协议/枚举/校验，导致后端变更需前端同步发版，极易前后端漂移：

| 项 | 前端硬编码位置 | 风险 | 建议 |
|---|---|---|---|
| **事件类型协议** | `sessionDetail/utils/eventTypeConfig.tsx`（3460+ 行，type code 如 `105001`/`100001`） | 后端新增事件类型需前端发版 | 后端提供 event-type registry + 字段 schema，前端仅做 render map（**ROI 最高**） |
| **检索筛选字段矩阵** | `models/constant.ts` 各 recordType 的 keyword/operator 全集 | 与 `/rest/rum/filter/query` 动态树漂移 | 跳转场景改 backend-driven preset id |
| **问题类型枚举** | `LinTable` `problemEnum` + 各 record 硬编码 problemType（6/7/12，且 retrieval 与 experience 取值不一致） | 新问题类型需改 enum + 路由 + 表格 | 后端 record-list 返回 problemType 字典 |
| **应用类型判断** | `isMiniProgram(appType==5/7/8/9)` 等魔法数三处定义 | 新增小程序类型改多处 | 单一 `AppType` enum 或后端下发元数据 |
| **指标展示名/单位** | `utils/constant.ts` `RESOURCE_*_INDICATOR_MAP` 前端写死 | 指标重命名需双端改 | 展示名以后端为准，前端只映射 color role |
| **数值校验规则** | 各配置 Modal 内联 validator | 前后端校验不一致 | 配置 API 返回 field constraints |

> **共性命名问题**：前后端均存在 `Es`/`old`/`new`/`V2` 等版本痕迹命名长期保留，建议建立「迁移完成 → 命名转正 → 删除旧实现」的收尾机制。

### 1.5 整体评价与量化汇总

| 维度 | 后端量化 | 前端量化 |
|---|---|---|
| 查询/请求样板重复 | 60+ Druid `assembleParam`、49 处 filterComponent 解析、70+ 处 appId 过滤 | filter/query 6+、problem/detail 3、AppSelect 6+、ConditionItem 40+ |
| 上帝类 | 5 个 >1500 行（合计约 1.7 万行）+ FilterFieldsCreator ~6000 行 | relation.tsx 1874、domain.ts 1826、eventTypeConfig 3460、utils/index 1106 |
| 实现多套并存 | 3 套缓存 / 3 套锁 / 4 套调度 / 6+ 线程池 / 3 套分页模型 | 3 套状态管理 / 4 套 i18n / ESM-CJS 混用 |
| 版本迁移残留 | QueryType.ES、RumEsToCk*、v4 迁移 833 行 | old/new 双轨 54+ 文件、snapshotVersion 运行时分支 |
| 技术债标记 | @Deprecated 仍活跃 11+、TODO 72+ 文件、注释测试 100+ | console.log 100+ 文件、死 hook/组件、注释死代码 |

**结论**：RUM 前后端功能完整、覆盖面广，但**技术债高度集中且同源**——核心矛盾是历史版本兼容（ES→CK、旧→新快照）以「保留双轨 + 复制粘贴」方式沉淀，叠加缺乏统一的查询框架（后端）/ 公共能力层（前端）。当前阶段适合**渐进式收敛**，应优先止血（建立公共抽象 + 设定旧代码下线时间表），避免在新功能中继续复制现有模式。

## 二、工程化重构与优化实施方案

### 2.1 执行摘要（领导速览）

#### 2.1.1 背景

RUM 模块前后端插件经过多年迭代，功能完整、覆盖面广，但技术债高度集中：后端 60+ 查询类重复拼装、5 个 >1500 行上帝类；前端 old/new 双轨 54+ 文件、`relation.tsx`/`domain.ts` 等巨型组件。根因是 ES→ClickHouse、旧快照→新快照等重大迁移以「保留双轨 + 复制粘贴」方式沉淀，缺乏统一公共框架。

#### 2.1.2 方案核心

采用 **「绞杀者模式 + AI 辅助 + 工程化护栏」** 渐进式重构，而非一次性大重写：

| 维度 | 策略 |
|---|---|
| 重构模式 | 绞杀者模式：新抽象旁路旧实现，埋点验证后逐步删旧 |
| AI 角色 | 影响分析（CodeGraph）、批量改造、测试补全、Review 辅助——**不替代人工验收与回归** |
| 质量保障 | 测试先行 + 埋点先行 + 小步 PR + CI 门禁 + 灰度验证 |
| 组织方式 | 2~3 人专项 + 前后端并行，分三阶段 8~12 个月 |

#### 2.1.3 预期收益

| 收益项 | 量化目标（阶段二完成后） |
|---|---|
| 新增指标/查询开发成本 | 从复制 80~200 行样板 → 调用公共 Assembler，**降 60%+** |
| 详情页双轨维护成本 | 删除 54+ 双轨文件，**维护面减半** |
| 单文件复杂度 | 上帝类/组件拆至 <1500 行（后端）/ <300 行（前端组件） |
| 前后端协议漂移 | 阶段三 metadata 化后，新增事件类型**无需前端发版** |
| 安全与稳定性 | OpenAPI 鉴权修复、统一异常/锁/缓存，降低静默失败风险 |

### 2.4 总体技术方案

#### 2.4.1 重构模式：绞杀者模式（Strangler Fig）

```
┌─────────────────────────────────────────────────────────┐
│  旧实现（oldIndex / 旧 Druid 类 / 旧工具类）              │
│  ┌─────────────────────────────────────────────────┐   │
│  │  新抽象旁路（MetricFilterAssembler / 新 hooks）   │   │
│  │  ┌─────────────────────────────────────────┐   │   │
│  │  │  新调用方逐步迁移 → 埋点验证 → 删旧实现   │   │   │
│  │  └─────────────────────────────────────────┘   │   │
│  └─────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**原则**：不一次性替换，而是新抽象旁路旧实现，调用方逐步迁移，埋点确认旧路径无流量后再删。

#### 2.4.2 AI 辅助体系（Cursor + MCP）

| AI 能力 | 工具/手段 | 用途 | 边界 |
|---|---|---|---|
| 影响分析 | CodeGraph MCP（`codegraph_impact`/`codegraph_callers`/`codegraph_trace`） | 改 Z 前评估「谁会受影响」 | 只读分析，不自动改码 |
| 批量改造 | Cursor Agent + 项目 Rules | 按模板抽取公共类、迁移调用 | **须人工 Review + 回归** |
| 测试补全 | AI 生成单测/契约测试 | 高回归风险项（SessionUtil、双轨删码） | 用例须人工审核 |
| Code Review | Bugbot / Security Review 子代理 | PR 阶段自动 Review | 不替代人工合并决策 |

**AI 使用红线**（保证正确性的核心）：

1. **禁止 AI 一次性大范围改码后直接合并**——必须小步 PR（单 PR 影响面可控）。
2. **高回归风险项必须先补测试再让 AI 改**——SessionUtil、双轨删码、上帝类拆分。
3. **删码必须有人工确认的埋点数据**——oldIndex、QueryType.ES、v4 迁移代码等。
4. **AI 改完后必须跑通**：`pnpm tsc` / `pnpm test` / `pnpm run build`（前端）、`mvn test`（后端）。

#### 2.4.3 质量保障体系（保证改动准确且不影响功能）

**（1）影响可感知：改前必做影响分析**

| 步骤 | 做法 | 工具 |
|---|---|---|
| 1 | 确定改动入口符号（类/方法/组件） | CodeGraph `codegraph_search` |
| 2 | 查调用方与被调用方 | `codegraph_callers` / `codegraph_callees` |
| 3 | 评估「改 Z 会破坏什么」 | `codegraph_impact` |
| 4 | 输出影响清单，人工确认范围 | 写入 PR 描述 |

**目标**：消除「影响范围很大且不可感知」——每次改动前有一份可审查的影响清单。

**（2）测试先行：高回归项先补安全网**

| 改动类型 | 测试要求 |
|---|---|
| SessionUtil 拆分 | 按 EventType 补 Converter 单测，覆盖新旧数据路径 |
| 双轨删码（oldIndex） | 埋点 + 快照版本分布统计，删前 E2E/关键路径回归 |
| MetricFilterAssembler 试点 | 5 类 Druid 改造前后结果对比测试（同条件同结果） |
| 上帝类拆分 | 拆前提取关键方法单测，拆后行为不变 |
| 前端横切 hook 抽取 | 接入页的表格/筛选/详情关键路径手工 + 自动化 |

**（3）小步 PR + 人工 Review**

- 单 PR 原则：**一个重构项或一个子域**，避免「一次改 50 个文件」。
- PR 必须包含：影响分析摘要、测试/回归说明、是否涉及删码及埋点依据。
- 合并前：CI 绿 + 至少 1 人 Review + 关键路径自测。

**（4）埋点先行：删码须数据支撑**

| 删码对象 | 埋点指标 | 删码阈值（建议） |
|---|---|---|
| oldIndex 详情页 | `snapshotVersion=0` 的 PV/UV | 连续 2 周 <1% 可启动删码 |

## 三、Controller 性能调优方案

> 基于 `controller/rum-controller` 源码梳理（版本 3.5.0.2）。配置来源：Nacos 动态配置（`global.private.rum.*` / `global.kafka.*` / `global.brfs.*` 等）+ JVM 启动参数。核心配置类：`BaseConfig.java`、`GlobalConfig.java`、`KafkaConfig.java`、`CKThreadConfig.java`。

### 3.1 架构概览与调优思路

RUM Controller 采用 **Netty 接入 → 本地内存队列 → 多线程消费处理 → 多存储后端写入** 的流水线架构。性能瓶颈通常出现在以下环节：

| 环节 | 典型症状 | 主要调优手段 |
|------|----------|--------------|
| Netty 接入层 | 连接拒绝、请求超时、大包 OOM | boss/worker 线程、SO_BACKLOG、max-context-length |
| HTTP 线程池 | 接口排队、拒绝策略 | thread.api/upload/config/track 池参数 |
| 本地数据队列 | 队列满、Kafka 溢出队列堆积 | data-cache.*-queue-* 参数 |
| 数据处理线程 | 消费慢、积压 | upload/crash/brfs/replay 线程数 |
| CK/Zeus 入库 | 写入延迟、批量过小 | ingest 批量/线程、表级线程 |
| 外部依赖 | Redis/BRFS/Kafka 超时 | 连接池、超时、重试 |

**关键机制**：大量参数在 `-1`（未显式配置）时会根据 **JVM 最大堆内存（maxMemoryMB）** 自动推算，详见 3.3 节。

### 3.2 模块与参数分布

```
controller/rum-controller/
├── network/          → Netty HTTP 接入、Upload/Config 接口
├── manager/          → 启动编排、线程池/队列初始化、SelfMonitor
├── data-queue/       → 本地内存队列 + Kafka 溢出队列
├── data-handler/     → 协议解析与业务处理
├── base/             → Zeus/VM/Nebula/BRFS 客户端
├── cache-server/     → 配置缓存、License、Redis 队列
├── config/           → BaseConfig / GlobalConfig 等全部 Nacos 参数
├── data-forward/     → 数据转发 Kafka
├── symbol-analysis/  → 崩溃符号化解析
├── online-track/     → 在线调试 Track
├── topk/             → TopK 统计
└── monitor/          → 自监控与线程自愈
```

### 3.3 JVM 与内存自适应机制

#### 3.3.1 JVM 启动参数（代码硬编码）

| 参数 | 说明 | 示例 |
|------|------|------|
| `-DsendLimit` | 5 位开关，控制是否发送 Brfs/Es/Ck/Nebula/Biz（0=不发送，1=发送） | `-DsendLimit=11111` |
| `-DisApmExist` | 强制指定 APM 服务是否存在 | `-DisApmExist=true` |
| `-Xmx/-Xms` | **间接影响**队列大小和处理线程数（通过 maxMemoryMB） | 建议生产 ≥4GB |

内存常量定义（`MemoryCacheConstants.java`）：

```java
public static final Long maxMemoryMB = Runtime.getRuntime().maxMemory() / 1024 / 1024;
```

#### 3.3.2 队列大小内存自适应（`BaseConfig.getSizeByMemory`）

当队列参数配置为 **-1**（默认）时，启动时按堆内存自动计算：

| JVM 堆内存 | 队列容量系数（相对 defaultVal） |
|------------|--------------------------------|
| < 1GB | defaultVal / 10 |
| 1GB ~ 2GB | defaultVal / 4 |
| 2GB ~ 3GB | defaultVal / 2 |
| ≥ 3GB | defaultVal（完整值） |

**适用队列**（defaultVal 见下表）：

| 配置项 | defaultVal（内存队列） | defaultVal（Kafka 溢出队列） |
|--------|------------------------|------------------------------|
| upload-queue | 2000 | 1000 |
| snapshot-queue | 2000 | 1000 |
| metric-queue | 2000 | 1000 |
| crash-queue | 2000 | 1000 |
| so_backlog（Netty） | 1000 | — |

**POC 模式**（`global.common.deploy.type=2`）：所有上述队列统一使用 `poc-queue-data-size`（默认 200）。

#### 3.3.3 数据处理线程内存自适应（`MainManager`）

| 线程类型 | 配置项 | 未配置时（-1 或 <1 或 >99）按内存分配 |
|----------|--------|----------------------------------------|
| Upload 主处理 | `global.private.rum.upload.thread.num` | ≤1G→1, ≤2G→2, ≤3G→3, >3G→4 |
| 会话回放 | `global.private.rum.replay.upload.thread.num` | 同 Upload |
| 崩溃转移 | `global.private.rum.crash.thread.num` | ≤1G→2, ≤2G→3, ≤3G→4, >3G→6 |
| BRFS 快照 | `global.private.rum.brfs.thread.num` | ≤2G→8, >2G→16 |

### 3.4 Netty HTTP 接入层

**配置前缀**：`global.private.rum.netty.server.*`
**实现类**：`NettyHttpServer.java`

| 参数 | 默认值 | 单位 | 热更新 | 说明 |
|------|--------|------|--------|------|
| `boss-count` | 2 | 个 | 否 | Boss 线程（接受连接） |
| `worker-count` | 6 | 个 | 否 | Worker 线程（IO 读写） |
| `max-context-length` | 5242880 | 字节 | 否 | HTTP 请求体最大长度（5MB） |
| `so_keepalive` | true | — | 否 | TCP KeepAlive |
| `so_backlog` | -1（自适应） | — | 否 | 全连接队列，POC=200，生产按内存自适应 |
| `connect_timeout_millis` | 10000 | ms | 否 | 连接超时 |
| `so_rcvbuf` | 524288 | 字节 | 否 | 接收缓冲区（512KB） |
| `so_sndbuf` | 2048 | 字节 | 否 | 发送缓冲区 |

**调优建议**：

- 高并发接入：`worker-count` 建议设为 CPU 核数 × 2，`so_backlog` 显式设为 2048~4096。
- 大包场景：适当增大 `max-context-length`，需同步评估堆内存；超过 `multipart.maxsize` 会落盘。
- 生产默认端口：8888（可通过启动参数覆盖）。

### 3.5 HTTP 业务线程池

**配置前缀**：`global.private.rum.thread.*`
**实现类**：`MainManager.initThreadPool()` → `ThreadPoolExecutor` + `ArrayBlockingQueue`

| 池名称 | min | max | 队列 size | 用途 |
|--------|-----|-----|-----------|------|
| `thread.api` | 3 | 6 | 2000 | API 接口 |
| `thread.upload` | 3 | 6 | 2000 | Upload 上报 |
| `thread.replay.upload` | 3 | 6 | 2000 | 会话回放 Upload |
| `thread.config` | 3 | 6 | 2000 | Config 配置下发 |
| `thread.track` | 3 | 6 | 1000 | Online Track |

**共同特性**：

- 核心/最大线程：`min` / `max`
- 空闲线程存活：5 秒
- 队列：`ArrayBlockingQueue(size)`，满则触发拒绝策略（默认 AbortPolicy）

**调优建议**：

- Upload 高峰：优先增大 `thread.upload.max` 和 `thread.upload.size`。
- Config 接口慢：增大 `thread.config.*`；SelfMonitor 会定期打印各池「处理任务数/活动线程/排队数」。
- Track 并发低，默认队列 1000 通常足够。

### 3.6 本地数据队列（data-queue 模块）

**配置前缀**：`global.private.rum.data-cache.*`
**实现类**：`IDataQueueBaseImpl` — 双层 `ArrayBlockingQueue`（内存队列 + Kafka 溢出队列）

#### 3.6.1 各业务队列

| 队列 | 内存队列 size | free-rate | Kafka 溢出 size | Topic（默认） |
|------|---------------|-----------|-----------------|---------------|
| Upload（协议） | `upload-queue-data-size` | `upload-queue-free-rate` | `upload-queue-kafka-size` | ETL-PROTOCOL-DATA |
| 快照/BRFS | `snapshot-queue-data-size` | `snapshot-queue-free-rate` | `snapshot-queue-kafka-size` | ETL-BRFS-DATA |
| Metric | `metric-queue-data-size` | `metric-queue-free-rate` | `metric-queue-kafka-size` | ETL-metric-DATA |
| Crash 转移 | `crash-queue-data-size` | `crash-queue-free-rate` | `crash-queue-kafka-size` | ETL-TRANSFER-DATA |
| 会话回放 | 独立 Topic/Group | — | — | ETL-PROTOCOL-REPLAY-DATA |

**默认值**：`*-queue-data-size=-1`（内存自适应）、`*-queue-free-rate=0.9`、`*-queue-kafka-size=-1`（内存自适应）。

**free-rate 机制**：当队列使用量 ≥ `size × free-rate` 时，`freeStatus=false`，上游可感知队列压力。

**溢出机制**：内存队列 `offer` 失败时，Kafka 模式下数据进入 `kafkaQueue`；本地模式则阻塞 `put`。

**Kafka 发送检查间隔**：50ms（代码硬编码 `checkSendKafkaTimer`）。

### 3.22 分场景调优方案

#### 3.22.1 低配置 POC / 演示环境（内存 ≤2GB）

```yaml

global.common.kafka.open: 2          # 关闭 Kafka，纯本地队列
```

- JVM：`-Xmx2g -Xms2g`
- 无需手动配队列/线程，系统自动降档

#### 3.22.2 标准生产（4~8GB 堆，中等流量）

```yaml

# HTTP 线程池

```

#### 3.22.4 CK 写入瓶颈

1. 增大 `zeus.ingest.threadNum` 全局默认值
2. 对热点表单独配置 `zeus.table.thread.{表名}`
3. 无 Kafka 模式：设置 `zeus.max.batch.size` 和 `zeus.max.batch.interval`
4. 检查 `sendLimit` 第 3 位是否为 1（允许写 CK）

#### 3.22.5 内存不足 / OOM

1. 减小 `snapshot.bl-max-size`（如 5000000）
2. 显式降低各 `*-queue-data-size`
3. 降低 `upload.thread.num`、`brfs.thread.num`
4. 关闭非必要功能：`vm.switch=false`、`dataForward.switch=false`、`track.open=false`
5. 开启 Upload 排重：`upload.repeat.valid.minute=60`

#### 3.22.6 队列积压排查顺序

1. 查看 SelfMonitor 日志：队列 `dataQSize/Max`、`kafkaQSize/Max`
2. 对比 Upload 处理线程数 vs `upload.thread.num`
3. 检查 Zeus/Cmdb 初始化是否成功（`DataTaskScheduling` 会等待就绪）
4. 检查 Kafka 消费/生产是否正常（`global.common.kafka.open`）
5. 必要时通过 API 动态增加 upload 线程

### 3.24 注意事项

1. **热更新**：标注 `autoRefreshed = true` 的参数支持 Nacos 热更新；Netty、线程池、队列大小、Zeus Ingest 等多数在 `@PostConstruct` 或启动时初始化，**修改后通常需重启**。
2. **配置优先级**：显式配置 > 内存自适应 > 代码默认值。
3. **监控先行**：调优前后对比 SelfMonitor 日志中的队列深度、线程池排队、SDK 消费量。
4. **联动调优**：增大 Upload 线程时需同步评估队列大小、CK 写入线程、堆内存，避免"消费快、写入慢"导致 OOM。
5. **POC 与生产**：切勿将 POC 配置（deploy.type=2, kafka.open=2）直接用于生产。

#### 3.25.3 精准线程 Dump 命令（按线程名过滤）
