## 一、产品调研报告

### 1.1 调研背景与目标

数字体验监控（DEM）/ 真实用户监控（RUM）已成为可观测性的核心支柱之一，行业一线产品持续向"性能监控 → 行为分析 → 智能体验洞察"演进。本平台 RUM 历经多版本迭代，功能体系日趋完整，但在产品设计一致性、行为分析、自服务分析、智能化等方面与业界标杆是否存在差距，需要系统性盘点与对标，以指导后续产品规划。

调研目标：

1. 自底向上梳理本平台 RUM 在工程层面的功能与能力全景，形成现状基线。
2. 调研国内外主流 RUM 产品的成熟能力，建立对标尺。
3. 进行能力对比与差距分析，识别优势项与短板项。
4. 形成可落地的产品优化、功能改进与新建能力建议及实施路线图。

### 1.2 调研范围与方法

| 类别 | 对象 |
|------|------|
| 自有产品 | 本平台 RUM（前端 `view/rum`、后端 `framework/plugins/rum`） |
| 国外竞品 | Datadog RUM、Dynatrace（New RUM Experience）、New Relic（Browser & Mobile）、Sentry、Grafana Faro（开源） |
| 国内竞品 | 阿里云 ARMS 用户体验监控、腾讯云 RUM（Aegis）、基调听云 |

调研方法：

- **自有产品**：自底向上梳理代码工程——路由/菜单（`view/rum/src/routes`）、后端 Controller（`rum-core` 各业务域）、存储与查询层（`rum-database`）、配置域（`settings`）——形成功能与技术现状全景。
- **竞品**：依据各厂商官方文档、产品页与发布说明（调研时间 2026-06），按统一能力维度归纳关键特性。
- **对标**：以"行业七大能力支柱"为对标框架，构建产品 × 能力矩阵，进行差距分级。

### 1.3 行业能力对标框架（七大支柱）

业界一线 RUM / 数字体验产品通常具备以下七大能力支柱，作为本报告的对标尺：

1. **全端采集与会话化**：Web Vitals 完整套件、会话回放、错误监控、资源/长任务监控。
2. **体验度量体系**：核心 Web 指标（LCP/CLS/INP/FCP/TTFB）、Apdex、自定义体验分、SLO/SLI。
3. **用户行为分析**：路径分析、漏斗、留存、热力图、自定义事件分析、转化分析。
4. **智能诊断与根因**：错误聚类去重、异常检测（基线/突变）、影响面量化、根因推荐、回归检测。
5. **可观测性打通**：RUM↔APM↔Log↔Trace 全链路下钻，前后端关联，端到端时延拆解。
6. **告警与协作**：原生告警规则、异常自动检测告警、与工单/IM 协作、SLO 预算告警。
7. **可定制与自服务**：自定义 Dashboard、自定义指标、灵活查询（类查询语言）、数据导出与 API。

### 1.4 自有产品现状分析

#### 1.4.1 产品功能架构

RUM 在 ONE 平台侧栏分为 4 个一级域：

```
观测洞察 /observation
  └─ 检索中心 /observation/retrieval（Tab：会话/崩溃/ANR/AppFreeze/操作/H5加载/网络/卡顿/JS错误/启动/视图/自定义异常/自定义事件）

数字体验 /experience（菜单名 "RUM"）
  ├─ 终端应用 /application（应用列表 + 详情多 Tab 下钻）
  ├─ 用户会话 /user
  ├─ 页面分析 /page/analysis [BETA]
  ├─ 代码异常 /breakdown（崩溃/ANR/AppFreeze/卡顿/JS/自定义异常聚合）
  ├─ 网络请求 /request（业务/资源/协议）
  └─ 能耗分析 /electricityanalyse（移动端电量，后端 coulometry 已标废弃）

部署配置 /deploy
  ├─ 安装部署 /center（客户端 SDK、自动嵌码向导）
  ├─ 部署状态 /manage（应用 CRUD、探针下载）
  └─ 规则配置 /config（数据采集 / 实体识别 / 健康判定 / 数据安全）

探针管理 /admin/agent（客户端嵌码向导，仅 admin）
```

#### 1.4.2 现有能力矩阵（盘点结论）

| 能力域 | 现状 | 评估 |
|--------|------|------|
| 多端采集 | Android/iOS/HarmonyOS/Web/H5/微信·抖音·mPaaS·支付宝小程序/Windows | ✅ 业界领先的端覆盖 |
| 会话回放 | Web（rrweb）+ Native 双端，采样/脱敏配置，时间轴联动、倍速、跳过无交互 | ✅ 较完整，深度待加强 |
| 崩溃 / 异常诊断 | 崩溃、ANR、AppFreeze、卡顿、JS 错误、自定义异常六类；Native 符号化（R8/dSYM/HarmonyOS）+ JS SourceMap | ✅ 强项 |
| 页面性能 | FP/白屏、FCP、LCP、TTFB、TTI、loadTime、首屏 | ⚠️ 缺 CLS/INP/FID |
| 网络请求分析 | 域名/服务/协议维度、趋势、瀑布图、TraceId 跳转、Socket 扩展 | ✅ 完整 |
| 用户/会话分析 | 会话列表、会话详情、用户跨应用视图、操作时间线（含 leftUserPath） | ⚠️ 偏明细，缺聚合行为分析 |
| 多维下钻 | 地域/运营商/设备/版本/页面类型，BrFilter 通用筛选 | ✅ 完整 |
| APM/Trace 打通 | 请求染色、TraceId 跳调用链、服务血缘、页面嵌入 APM 拓扑 | ✅ 强项 |
| 告警 | 依赖 SmartAlert/one_alert 外挂，RUM 仅代理与等级查询 | ⚠️ 无 RUM 原生告警体验 |
| 自定义 | 自定义事件、自定义异常、健康评分自定义指标、Apdex | ⚠️ 缺自定义看板/自定义指标聚合 |
| OpenAPI | 应用管理、六类问题、网络、会话、H5、Symbol/SourceMap | ✅ 较完整 |
| 健康评分 | 多实体（原生/Web/小程序/会话/视图/H5/请求/操作）评分规则 + Apdex | ✅ 特色能力 |
| AI 能力 | AiSlow/AiCaton/AiThreshold（阈值化"AI"，非智能归因/异常检测/LLM） | ⚠️ "AI"名不副实，待升级 |
| 行为分析（漏斗/留存/路径） | 未发现独立产品能力 | ❌ 空白 |

#### 1.4.3 技术架构（后端）

```
配置数据 → MySQL（应用/规则/评分/AI阈值/采集配置/脱敏/SourceMap元数据）
分析数据 → QueryService(MyBatis+XML) → ClickHouse 快照视图 + 指标
大文件   → BRFS 对象存储（会话回放文件、快照文件、Symbol/SourceMap）
符号化   → symbol-analysis 模块（Native）+ Node.js sourcemap-resolver（Web）
集成     → APM（Trace/血缘/快照共享）、SmartAlert（告警代理）
```

整体为"配置在 MySQL + 分析在 ClickHouse + 大文件在 BRFS"的清晰三层架构，业务域划分合理，`settings` 配置域能力最丰富（32 个 Controller）。

#### 1.4.4 现状小结

- **优势**：端覆盖、崩溃符号化诊断、健康评分体系、RUM↔APM 打通、OpenAPI——构成差异化资产。
- **短板**：性能度量缺 CLS/INP；行为分析空白；自服务分析与自定义看板缺失；告警依赖外挂；AI 偏阈值。

### 1.5 国内外竞品调研

> 调研时间：2026-06，依据各厂商官方文档与发布说明。

#### 1.5.1 Datadog RUM —— 体验分析标杆（行为分析 + 智能回放）

| 能力维度 | 关键特性 |
|----------|----------|
| Web Vitals | 自动采集 LCP/CLS/INP（含 INP 的 Long Task / LoAF 帧级归因，按阶段拆解 work/render/style/layout，直达代码） |
| 会话回放 | 像素级回放，**AI 生成会话摘要 + Smart Chapters 智能章节**，自动定位关键动作与摩擦点，无需手动拖拽 |
| 挫败信号 | rage click（暴力点击）、dead click（无效点击）、error click（错误前点击），列表标记 + 专用 Dashboard + Explorer 过滤 |
| 行为分析 | **Product Analytics**：漏斗（转化率 + 按设备/地域分群）、留存、从漏斗一键下钻到流失会话回放 |
| 错误诊断 | 错误聚类去重、按业务影响优先级排序、JS 错误定位到代码行、受影响用户分群 + retention filter |
| 性能剖析 | **生产环境 Profiling**：从真实会话采集，定位到具体 JS 函数，跨版本对比快照验证修复效果 |
| 全栈关联 | RUM ↔ Logs ↔ Traces 自动关联；30+ 开箱指标，**数据保留 15 个月** |
| AI/集成 | MCP 工具、AI 摘要 |

**最值得借鉴**：把"性能指标 → 行为分析 → 会话回放"打通成闭环，AI 摘要降低回放使用门槛。

#### 1.5.2 Dynatrace New RUM Experience —— 数据湖 + AI 根因

| 能力维度 | 关键特性 |
|----------|----------|
| 数据底座 | **Grail 数据湖仓**统一存储前端遥测 + 日志/指标/Trace/拓扑/安全/业务数据，**DQL 查询语言**自由分析 |
| 会话分群 | **Session Segmentation**：按位置/设备/自定义业务属性切分用户群，隔离问题会话 |
| 会话回放 | 基于 DOM-tree（非视频，体积小），错误下钻；**成本/流量控制**——仅录制 20% 会话也能诊断非偶发错误 |
| 行为分析 | 捕获 user interactions（点击/滑动/输入）与 soft navigation（SPA 软导航），理解 AI 原生/LLM 应用中的用户流转 |
| 智能 | **Davis AI + Smartscape 拓扑**自动根因；前端异常即使后端健康也能被发现 |
| 应用化 | Experience Vitals app、Users & Sessions app 模块化；内置健康告警 |
| 合规 | 录制与回放双阶段的细粒度脱敏 |

**最值得借鉴**：统一数据底座 + 查询语言带来的探索式分析自由度；按业务属性的会话分群。

#### 1.5.3 New Relic Browser & Mobile —— 全栈错误收件箱

| 能力维度 | 关键特性 |
|----------|----------|
| Web Vitals | LCP/INP/CLS，按地域/设备/页面 URL 分段；**CWV 数据表直接内嵌会话回放列**，按 LCP>INP>CLS 优先级预过滤回放 |
| 会话回放 | Browser + **Mobile（iOS/Android/RN，2026-04 GA）**，与 breadcrumbs/logs 同步；错误/崩溃可视标记、跳过无交互、倍速、全屏、**分享片段** |
| 错误诊断 | **Errors Inbox**：聚合 Browser/Mobile/APM/Lambda 全栈错误，按用户影响与回归状态排序优先级 |
| 诊断辅助 | Session traces（会话追踪）、Error profiles（错误画像）、页面资源 timing |
| 行为 | Mobile User Journeys（崩溃分析）；分布式追踪打通前后端 |
| 合规 | 开箱不采 PII，脱敏/采样服务端可配，自定义角色权限 |

**最值得借鉴**：错误收件箱（全栈错误统一收口 + 回归检测）；CWV 表内嵌回放的"指标即下钻"交互。

#### 1.5.4 Sentry —— 错误 + 性能 + 回放一体化（开发者向）

| 能力维度 | 关键特性 |
|----------|----------|
| Web Vitals | LCP/CLS/FCP/TTFB/INP（SDK v10 起 FID 弃用转 INP）；Long Task（主线程阻塞 >50ms）自动埋点 |
| 会话回放 | 基于 rrweb；**错误采样模式**——错误发生时回溯录制前 1 分钟缓冲；回放时间轴叠加 Trace 与 Logs，点击 span 跳 Trace 视图 |
| 错误诊断 | 强项；错误分组/指纹、堆栈、上下文；SourceMap |
| 全栈 | 分布式追踪、N+1 查询自动检测 |
| AI | **AI 调试（Seer）+ GitHub 集成**，自动定位与修复建议；告警捕获性能回归 |

**最值得借鉴**：错误前 1 分钟缓冲式回放（低成本高价值）；回放时间轴与 Trace/Logs 三合一调试视图。

#### 1.5.5 Grafana Faro —— 开源 + OpenTelemetry

| 能力维度 | 关键特性 |
|----------|----------|
| Web Vitals | Web Vitals v5（LCP/CLS/INP），**归因数据强制采集**；User Actions GA；SPA 软导航实验特性 |
| 标准化 | 完全基于 OpenTelemetry；与 LGTM 栈（Loki/Grafana/Tempo/Mimir）关联前后端 |
| 错误 | SourceMap 上传解析 |
| 行为 | user sessions、journeys、KPI、feature usage |

**最值得借鉴**：OpenTelemetry 标准化采集，2 行代码接入；对自建可观测栈的开放性。

#### 1.5.6 阿里云 ARMS 用户体验监控 —— 无埋点会话轨迹

| 能力维度 | 关键特性 |
|----------|----------|
| 多端 | Web/H5、App、小程序；**无埋点**，SDK 初始化即自动采集 |
| 会话轨迹 | **用户会话轨迹（Session ID 自动串联）**，还原单用户完整操作时间线；会话级采样控制 |
| 异常追踪 | 网络/页面/卡顿/崩溃/ANR 自动捕获 + 符号化定位代码行 + **会话轨迹回溯还原现场** |
| 数据探索 | **全维度 × 全指标自由组合分析**，缩短问题定位路径 |
| 集成 | 数据入 SLS 日志服务可查询、指标打通 Prometheus、与 ARMS 应用监控端到端联动 |

**最值得借鉴**：无埋点开箱采集理念；"异常 → 会话轨迹回溯还原现场"的排障动线；全维度数据探索。

#### 1.5.7 腾讯云 RUM（Aegis）与基调听云 —— 无侵入 + 业务行为

| 产品 | 关键特性 |
|------|----------|
| **腾讯云 RUM** | Web/小程序(微信/QQ)/Hippy/Weex/RN/Flutter/Cocos；页面/接口/CDN 测速、JS/Ajax 错误、CWV、瀑布图、慢页面详情；**无侵入一行代码**；错误/页面耗时/性能数据告警；与 APM 前后端一体化；数据保留：原始日志 30 天、指标 30 天、日聚合 90 天 |
| **基调听云** | 聚焦小程序；**无埋点用户行为路径分析 + 自定义漏斗分析**，偏业务转化链路优化与精细化运营 |

**最值得借鉴**：无侵入接入的极简体验；听云的业务漏斗与转化分析视角。

矩阵结论：

- **本平台优势项**：端覆盖（鸿蒙 + 4 类小程序业界最全）、崩溃符号化诊断、健康评分体系、RUM↔APM 打通、OpenAPI——这些是差异化资产，应继续巩固并对外强调。
- **本平台明显短板（红线项）**：见 1.7 节"差距总结"。

### 1.7 对标与差距分析

#### 1.7.1 能力雷达差距

#### 1.7.2 核心功能差异详解

**1.7.2.1 性能度量：核心 Web 指标不完整**
- 差异：本平台有 LCP/FCP/TTFB/TTI/白屏，但缺 **CLS、INP**（INP 自 2024 起取代 FID 成为 Google 核心指标）。Datadog 更进一步做到 INP 的帧级（LoAF）归因与阶段拆解。
- 影响：无法回答"页面是否抖动""交互是否跟手"，在 Web 体验对外宣讲与 SEO 场景处于劣势。
- 对标方向：SDK 补采 CLS/INP → 后端指标模型扩展 → 前端提供 CWV 评级（Good/NI/Poor）与 P75 分布，并关联到慢交互会话回放（参考 New Relic CWV 表内嵌回放）。

**1.7.2.2 行为分析：从"会话明细"到"业务洞察"的代差**
- 差异：本平台仅有会话内操作时间线（含 leftUserPath），**无聚合的漏斗、留存、路径/旅程分析**。Datadog Product Analytics、听云自定义漏斗、ARMS 会话轨迹、Dynatrace 会话分群都已成熟。
- 影响：RUM 停留在"技术性能监控"，无法服务产品/运营的转化与留存诉求，商业价值天花板低。
- 对标方向：建设行为分析套件（路径桑基图 + 漏斗转化 + 留存群组），并支持从漏斗流失步骤一键下钻到会话回放定位流失原因（Datadog 模式）。

**1.7.2.3 排障动线：缺少"挫败信号"与"智能回放摘要"**
- 差异：本平台会话回放需人工拖拽查看；**无 rage/dead/error click 标记**，**无 AI 会话摘要/智能章节**。
- 影响：回放使用门槛高、效率低，难以快速定位摩擦点。
- 对标方向：SDK 增加挫败信号采集并在会话列表/回放时间轴标记；引入会话关键事件自动摘要（错误/慢请求/卡顿/挫败聚合成"故事线"）。

**1.7.2.4 错误治理：缺少统一收件箱与回归闭环**
- 差异：本平台 problem 域有问题列表与影响面，但**缺指纹聚类去重、Issue 状态机、回归检测、跨端统一收口**。New Relic Errors Inbox / Sentry 是范式。
- 对标方向：建设 RUM 错误收件箱——按堆栈指纹聚类、状态流转（新/处理中/已解决/忽略/回归）、责任人分配、回归自动告警、跨 Web/移动/小程序统一视图。

**1.7.2.5 自服务分析：缺少自定义看板与探索式查询**
- 差异：本平台查询固化在各业务接口，**无自定义 Dashboard、无类 DQL/NRQL 的自由探索**。这是 Datadog/Dynatrace/New Relic/Grafana 的共性基础能力。
- 对标方向：面向 ClickHouse 建设探索式分析（任意维度过滤/分组/聚合/可视化切换 → 存为看板或告警）+ 拖拽式自定义 Dashboard。

**1.7.2.6 智能化：从"静态阈值"到"AI 根因"**
- 差异：本平台 AiSlow/AiCaton/AiThreshold 本质是静态阈值；竞品已普遍具备动态基线异常检测（Davis）、AI 调试（Seer）、AI 会话摘要。
- 对标方向：动态基线 + 突变检测替代固定阈值；多维自动归因（找异常聚集维度）；与平台 SmartAsk 打通做"自然语言问 RUM"。

**1.7.2.7 接入与合规：体验与治理可再简化**
- 差异：竞品强调"一行/两行代码、无埋点、服务端可调采样与脱敏"；本平台配置域虽强大但接入与治理较重，隐私脱敏与回放合规审计偏弱。
- 对标方向：简化默认接入（开箱自动采集）、服务端动态采样与脱敏、回放权限与审计日志。

#### 1.7.3 差距总结（红线短板）

1. **CLS / INP 缺失**——几乎所有竞品已标配，直接影响 Web RUM 竞争力与 SEO 体验话术。
2. **行为分析三件套（漏斗/留存/路径聚合）几乎空白**——Datadog/听云/ARMS 的核心卖点。
3. **自定义 Dashboard + 探索式查询缺失**——竞品普遍具备查询语言（DQL/NRQL）或拖拽看板。
4. **错误收件箱/聚类/回归检测较弱**——New Relic Errors Inbox、Sentry 是标杆。
5. **挫败信号缺失**——低成本高感知的体验洞察能力。
6. **智能根因偏阈值化**——竞品已普遍 AI 化（Davis/Seer/AI 摘要）。

## 二、产品能力分析与优化建议

### 2.1 产品设计层面的优化提升点

> 此部分聚焦"信息架构、交互一致性、分析心智"，不新增大功能，但显著提升产品观感与可用性。

#### 2.1.1 收敛"数字体验"与"检索中心"的信息架构重叠

**问题**：当前同一类对象在两处出现——数字体验（聚合分析视角）与检索中心（明细记录视角）。例如"用户会话"在 `/experience/user` 和 `/observation/retrieval/user/session` 各有入口；崩溃/JS/网络等同理。用户需在两套导航间切换，心智负担重，且 componentName 复用（如 `RetrievalAppViewPageRecordList` 三处复用）导致体验割裂。

**建议**：
- 明确"**分析（Analyze）→ 下钻（Drill）→ 检索（Search）→ 单条详情（Inspect）**"的统一漏斗式心智，检索中心定位为"分析下钻的落点"，而非独立平行入口。
- 在每个分析视角（应用/页面/会话/网络/异常）内置"查看明细记录"按钮，携带当前筛选上下文跳转检索，避免用户重新选条件。
- 评估是否将检索中心收编为数字体验的二级"记录"Tab，减少一级导航数量。

#### 2.1.2 建设 RUM 统一总览首页（Landing / Overview）

**问题**：进入"数字体验"直接落到"终端应用"列表，缺少跨应用、跨端的体验健康总览，无法一眼回答"今天体验好不好、哪里在恶化"。

**建议**：新增 RUM 总览页，包含：体验健康分大盘（按端/按应用）、Apdex 趋势、Top 恶化应用/页面、活跃错误 Top、实时在线用户与会话、核心指标同环比。作为"先总览、后下钻"的入口。

#### 2.1.3 统一筛选与时间上下文（Filter / Time Context 一致化）

**问题**：各页面使用 BrFilter，但筛选维度、时间选择器、版本选择器在不同页面（experience vs retrieval vs pageAnalysis）存在不一致与上下文丢失。

**建议**：建立全局可携带的筛选上下文（应用/版本/时间/地域/端类型），跨页面跳转时保持；统一筛选交互与可选维度，降低重复操作。

#### 2.1.4 强化"归因引导"而非"指标堆砌"

**问题**：详情页多为指标卡 + 趋势图的罗列，用户需自行判断问题根因。

**建议**：在异常/慢请求/慢页面详情中增加"归因摘要"模块（如"该问题集中在 iOS 16 / 华东 / v4.2.1 版本，影响 1.2 万会话，疑似某资源加载超时"），用结构化结论替代纯图表，提升专家级洞察的普惠性。

#### 2.1.5 BETA 能力（页面分析）的转正与体验对齐

**问题**：页面分析带 BETA 徽标，且与"终端应用→页面详情"存在功能交叉。

**建议**：明确页面分析与应用详情页能力边界，去重，制定转正标准（指标完整度、稳定性、与检索打通），避免长期 BETA。

#### 2.1.6 清理废弃与半下线能力

**问题**：能耗分析后端 `coulometry` 已标废弃但前端入口仍在；部分代码注释下线（pageAnalysis 告警列、application 视图路由）。

**建议**：决策能耗分析"下线 or 重做"；统一清理半下线代码与菜单，避免产品形态模糊。

### 2.2 可改进的功能（增强已有能力）

#### 2.2.1 补齐核心 Web Vitals（CLS / INP / FID）⭐高优先

**现状**：已有 LCP/FCP/TTFB/TTI/白屏，但代码中未发现 CLS（布局偏移）、INP（交互到下次绘制，已取代 FID 成为 Google 核心指标）、FID。

**建议**：
- SDK 采集层补齐 CLS、INP；后端指标模型（`PageMetric`/`RumMetricPageMapper`）与前端 `utils/constant.ts` 扩展对应字段。
- 页面分析与页面详情提供 Web Vitals 评级（Good/Needs Improvement/Poor）与分布直方图（P75）。
- 这是对标 Google CWV、SEO 体验评分的基础能力，缺失会直接影响 Web RUM 竞争力。

#### 2.2.2 会话回放深度增强

**现状**：已具备 Web（rrweb）+ Native 双端回放、时间轴、倍速、跳过无交互。

**建议**：
- **回放内联诊断**：回放时间轴叠加错误/慢请求/卡顿标记，点击直接定位事件。
- **隐私与合规增强**：可视化脱敏配置（元素级遮罩预览）、按角色控制回放权限、回放水印与审计日志。
- **回放检索**：支持"包含某错误/某 rage click/某 dead click 的会话"快速过滤。
- **挫败信号（Frustration Signals）**：识别 rage click（暴力点击）、dead click（无效点击）、error click，并在会话列表标记。

#### 2.2.3 错误监控的聚类、去重与影响面量化

**现状**：problem 域有问题列表、特征、版本对比、影响用户/会话（ProblemCardEnum 有 impactUser/Session）。

**建议**：
- **指纹聚类**：相同根因的错误自动聚合为 Issue（按堆栈指纹），避免同类错误刷屏。
- **状态流转**：Issue 支持"新增/处理中/已解决/忽略/回归"状态机，支持分配责任人。
- **回归检测**：已解决的 Issue 再次出现时自动标记"回归"并告警。
- **首次/末次出现、趋势、受影响版本分布**一体化展示。

#### 2.2.4 RUM 原生告警体验

**现状**：告警依赖 SmartAlert/one_alert 外挂，RUM 仅做代理（`RumSmartAlertProxyController`）与等级查询。

**建议**：
- 在 RUM 内提供"基于 RUM 指标一键创建告警"的轻量入口（如在任意指标卡右键"为该指标设阈值告警"），后端转换为 SmartAlert 规则，降低跨系统配置成本。
- 提供 RUM 告警概览面板，聚合各应用 RUM 相关告警，形成监控闭环，而非仅嵌入告警 Tab。

#### 2.2.5 把"AI"做成真智能（异常检测 / 基线 / 根因）

**现状**：AiSlow/AiCaton/AiThreshold 本质是**静态阈值配置**，并非智能检测。

**建议**：
- 引入**动态基线**（按时段/版本/端的历史分布）替代固定阈值，自动识别突变（spike/dip）。
- **智能根因推荐**：基于多维下钻自动找出异常聚集维度（版本/地域/设备/页面）。
- 与平台已有 AI 能力（如 SmartAsk/智能问答）打通，支持"自然语言问 RUM"。

#### 2.2.6 网络与资源体验治理增强

**现状**：网络请求分析完整（域名/服务/协议/瀑布图/Trace）。

**建议**：
- 增加**静态资源体积与加载治理**视角（JS/CSS/图片体积 Top、未压缩资源、慢资源、第三方资源占比），这是前端性能优化高频诉求。
- **长任务（Long Task）/主线程阻塞**监控，关联到卡顿与 INP。
- API 端到端时延拆解（DNS/TCP/TLS/TTFB/下载）可视化对照。

#### 2.2.7 移动端启动与页面体验闭环

**现状**：有应用启动、视图启动记录与详情、慢启动判定。

**建议**：补齐冷/热/温启动分类对比、启动阶段拆解（进程创建→Application→首帧）、ANR 与启动关联分析，形成移动端体验专项。

### 2.3 需要新建设的能力（补空白）

#### 2.3.1 用户行为分析套件（路径 / 漏斗 / 留存）⭐高优先

**空白**：当前仅有会话内操作时间线，无聚合行为分析。

**建议新建**：
- **路径分析（Path/Flow）**：用户在页面/操作间的流转桑基图，发现主路径与异常跳出。
- **漏斗分析（Funnel）**：自定义关键转化步骤（如 进入→加购→下单→支付），量化各步流失，并可下钻到流失会话（结合会话回放定位流失原因）。
- **留存分析（Retention）**：按用户群组的次日/7日/30日留存。
- 价值：将 RUM 从"技术性能监控"升级为"业务数字体验分析"，直接服务产品/运营，是与竞品拉开差距的关键。

#### 2.3.2 自定义 Dashboard 与自定义指标聚合 ⭐高优先

**空白**：当前仅有 `CustomCardController`/`customCard` 雏形，无完整自助看板。

**建议新建**：
- 拖拽式自定义 Dashboard，组件库化（指标卡/趋势/Top 列表/分布/地图/表格）。
- 自定义指标聚合：基于采集字段任意维度分组聚合，保存为可复用指标。
- 看板分享、订阅、导出（PDF/图片）、大屏模式。

#### 2.3.3 灵活查询与探索式分析（Explore）

**空白**：查询能力固化在各业务 Controller，用户无法自由组合维度/度量探索。

**建议新建**：面向 ClickHouse 的探索式分析界面（类似 Datadog 的 RUM Explorer / Grafana Explore），支持任意字段过滤、分组、聚合、可视化切换，并可一键存为看板或告警。

#### 2.3.4 SLO / 体验预算管理

**空白**：有健康评分与 Apdex，但无 SLO 目标管理与预算消耗。

**建议新建**：定义体验 SLO（如"95% 页面 LCP < 2.5s"），跟踪达成率与错误预算（Error Budget）消耗，预算耗尽自动告警。将健康评分体系升级为可承诺、可管理的服务等级。

#### 2.3.5 端到端会话画像与用户旅程

**空白**：用户详情已跨应用，但缺少完整用户旅程的统一画像。

**建议新建**：以"用户/设备"为主体，聚合其全部会话、错误、慢交互、转化行为，形成可追溯的用户旅程视图，支撑 VIP 用户问题排查与客诉定位。

#### 2.3.6 体验对比与发布回归门禁

**空白**：有版本对比（compareVersion），但未形成"发布前后体验回归"工作流。

**建议新建**：版本/发布维度的体验回归看板（崩溃率、关键指标、错误新增），与 CI/CD 集成做发布门禁（体验恶化阻断发布或告警）。

#### 2.3.7 合规、采样与成本治理中心

**空白**：采集/脱敏配置分散在各规则页。

**建议新建**：统一的数据治理中心——采样策略（按重要性动态采样）、数据保留分级、隐私合规（GDPR/个保法）配置与审计、数据量与成本可视化，帮助大规模落地时控成本、保合规。

### 2.4 对标驱动的体验建设清单（按主题归并）

|------|----------|------|

## 三、综合结论

### 3.1 优势资产与短板红线

本平台 RUM 已是一套**覆盖全端（Android / iOS / HarmonyOS / Web / H5 / 微信·抖音·mPaaS·支付宝 4 类小程序 / Windows）、贯通"采集 → 识别 → 分析 → 检索 → 诊断 → 配置"全链路**的成熟模块，核心诊断能力（会话回放、崩溃符号化、SourceMap、瀑布图、Trace 联动）扎实，端覆盖与可观测性打通处于行业领先水平。

- **优势资产（应巩固与对外强化）**：端覆盖最全（含鸿蒙 + 4 类小程序）、崩溃符号化诊断、健康评分体系、RUM↔APM 打通、OpenAPI 开放。
- **六条红线短板（与一线竞品的主要差距）**：
  1. CLS / INP 缺失——几乎所有竞品已标配，直接影响 Web RUM 竞争力与 SEO 体验话术。
  2. 行为分析三件套（漏斗/留存/路径聚合）几乎空白——Datadog/听云/ARMS 的核心卖点。
  3. 自定义 Dashboard + 探索式查询缺失——竞品普遍具备查询语言（DQL/NRQL）或拖拽看板。
  4. 错误收件箱/聚类/回归检测较弱——New Relic Errors Inbox、Sentry 是标杆。
  5. 挫败信号缺失——低成本高感知的体验洞察能力。
  6. 智能根因偏阈值化——竞品已普遍 AI 化（Davis/Seer/AI 摘要）。

### 3.2 演进定位

以三波路线图推进——第一波（0–3 月）补齐 CWV、统一总览与信息架构、错误聚类；第二波（3–6 月）建设行为分析套件、自定义 Dashboard、回放增强；第三波（6–12 月）走向智能根因、探索式分析与平台化。最终推动 RUM 从"技术性能监控"升级为"业务数字体验分析 + 智能根因平台"。

### 3.3 下一步建议

建议针对第一波清单（CWV 补齐、统一总览、错误聚类）启动 PRD 细化与技术方案评估，明确 SDK 采集端改造范围与 ClickHouse 数据模型扩展点。
