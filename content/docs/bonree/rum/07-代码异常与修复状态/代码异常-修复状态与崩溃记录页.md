# 一、修复状态实现逻辑

## 1. 背景与功能概述

「数字体验 > 代码异常」下的各页签（崩溃、ANR、卡顿、JS错误、自定义异常、AppFreeze）都提供了「修复状态」能力，包含三部分交互：

1. **顶部状态筛选 Tabs**：全部 / 未修复 / 复现 / 处理中 / 已修复 / 已忽略，带各状态计数。
2. **行内修复状态下拉**：列表每一行的「修复状态」列是一个 Select 下拉，可直接修改单条问题的状态。
3. **权限控制**：无代码异常操作权限时，行内下拉渲染为禁用态并提示无权限。

本节梳理「状态如何存储、如何写入、如何查询与展示、各页签差异、关键 ID 字段关系」，作为研发维护与排错的参考。

## 2. 状态枚举与数据库存储

### 2.1 状态值定义

| 值 | 含义 | 前端文案 key |
|----|------|-------------|
| 1 | 未修复 | `experience.breakdown.unrepair` |
| 2 | 已修复 | `experience.breakdown.fixed` |
| 3 | 处理中 | `experience.breakdown.pocessing` |
| 4 | 复现 | `experience.breakdown.reproduction` |
| 5 | 已忽略 | `experience.breakdown.ignored` |
| 0 | 全部（仅前端筛选用，不入库） | `experience.breakdown.all` |

> 默认值：未设置过状态的问题视为 `1 未修复`（后端在列表查询时兜底赋值）。

### 2.2 存储表 `t_rum_problem_status`

**表注释**：问题记录修复状态表

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | bigint(20) PK | 自增 ID |
| `app_id` | bigint(20) | 应用 ID |
| `user_id` | bigint(20) | 主账号 ID（状态按用户隔离） |
| `question_id` | varchar(45) | 问题 ID（值 = 前端 `problemId`） |
| `status` | int(11) | 修复状态，1/2/3/4/5 |
| `problem_type` | int(11) | 问题类型，**存前端体系值**：`6:Crash; 7:SELF_CRASH; 4:ANR; 5:LAG; 3:JS_ERROR` |
| `create_time` | datetime | 创建时间 |
| `update_time` | datetime | 更新时间 |

**唯一业务键**：`app_id + problem_type + question_id + user_id`

对应写入 SQL（`framework/plugins/rum/rum-database/src/main/resources/com/bonree/rum/mysql/common/RecordMapper.xml`）：

```xml
<!-- 插入 -->
<insert id="statusInsertAction" ...>
  INSERT INTO t_rum_problem_status
    (app_id, user_id, question_id, status, problem_type, create_time, update_time)
  VALUES
    (#{appId}, #{userId}, #{relationKey}, #{status}, #{problemType}, now(), now())
</insert>

<!-- 更新（按 app_id + problem_type + question_id 定位） -->
<update id="statusUpdateAction" ...>
  UPDATE t_rum_problem_status
  SET status = #{status}, update_time = now()
  WHERE question_id = #{relationKey}
    AND problem_type = #{problemType}
    AND app_id = #{appId}
</update>
```

### 2.3 关键澄清：`problem_type` 在两张表里的数值口径不同

仓库里存在**两套** `problem_type` 数值体系，容易踩坑：

| 体系 | 取值范围 | 用途 |
|------|---------|------|
| **前端体系**（ClickHouse 指标分类） | `3=JS_ERROR, 4=ANR, 5=LAG, 6=Crash, 7=SELF_CRASH, 9=APP_FREEZE` | `t_rum_problem_status.problem_type`、前端 Tab 枚举、列表查询入参 |
| **记录体系**（操作日志分类） | `8=崩溃, 9=ANR, 10=卡顿, 11=JS错误, 12=自定义异常, 13=AppFreeze` | `t_rum_problem_record.problem_type`（操作日志表） |

映射表 `ProblemService.problemTypeRecordMap`（`rum-core`）：

```java
// 6:Crash ; 7:SELF_CRASH; 4:ANR; 5:LAG; 3:JS_ERROR
// 8-崩溃 9-ANR 10-卡顿 11-JS错误 12-自定义异常 13-AppFreeze
public static final Map<Integer, Integer> problemTypeRecordMap = Map.of(
    6, 8, 4, 9, 5, 10, 3, 11, 7, 12, 9, 13
);
```

> **重要结论（已通过 DB 实测验证）**：`problemTypeRecordMap` 的转换**只作用于操作日志表 `t_rum_problem_record`**，**不作用于状态表 `t_rum_problem_status`**。
>
> 也就是说：崩溃问题在 `t_rum_problem_status.problem_type` 存的是 **6**（前端体系值），不是 8。
>
> 这与表字段注释 `6:Crash` 完全一致。

原因在于 `RecordService.statusAction` 的执行顺序——**先写状态表，后做数值转换，再写操作日志**：

```java
public String statusAction(RecordCondition condition) {
    String msg = updateProblemStatus(condition);           // ① 先写 status 表，problemType 仍是前端值（如 6）
    if (CommonConstant.SUCCESS_MSG.equals(msg)) {
        condition.setProblemType(
            ProblemService.problemTypeRecordMap.get(condition.getProblemType()));  // ② 之后才转成记录体系值（如 8）
        addOperationProcess(log);                          // ③ 用记录体系值写 t_rum_problem_record
    }
    return msg;
}
```

排错时务必注意：查 `t_rum_problem_status` 用前端体系值（3/4/5/6/7/9），查 `t_rum_problem_record` 用记录体系值（8/9/10/11/12/13）。

### 2.4 为什么两张表的 problem_type 用不同枚举（设计历史分析）

> 本节是对"为什么需要 `problemTypeRecordMap` 转换、而不是统一一套枚举"的设计历史分析。代码无直接注释解释此事，故分**代码可证事实**与**合理推测**两层，推测部分已标注。

#### 2.4.1 代码可证的事实

**事实 1：两套体系覆盖的业务范围不同**

前端体系 `problemTypeMap` 的注释里写了 `[1:net,2:h5,3:js_error,4:anr,5:lag,6:crash,7:selfCrash,8:launch,9:view]`——这套编号**原本是为更广的"问题类型"设计的**，涵盖网络、H5、启动、视图等。只是当前 `problemTypeMap` 这个 Map 实例只 put 了代码异常相关的 6 个值（3/4/5/6/7/9），但编号位 `8=launch`、`9=view` 在注释里已被占用。

记录体系 `problemTypeRecordMap` 是**专为代码异常重新编号**的，从 8 开始连续分配给崩溃/ANR/卡顿/JS错误/自定义异常/AppFreeze。

**事实 2：两张表的语义和复用范围不同**

- `t_rum_problem_record` 是一张**通用记录表**，用 `type` 字段区分 `1=评论 / 2=操作记录 / 3=状态变更` 等多种记录类型，承载"问题"相关的所有留痕行为，`problem_type` 需要能覆盖所有可能有记录的问题类型。
- `t_rum_problem_status` 是一张**专用状态表**，只存修复状态，且只服务于"代码异常"这一类问题（网络/H5/启动/视图这些没有"修复状态"概念）。

**事实 3：转换是单向、定点发生的**

`problemTypeRecordMap` 只在写入 `t_rum_problem_record` 之前转换（`RecordService.statusAction` 第 ② 步、`addRecord`、`addOperationProcess` 等）。`t_rum_problem_status` 的读写全程用前端体系值，不经过这个 Map。

#### 2.4.2 合理推测（代码未明说，但线索强烈）

**推测 1：`t_rum_problem_record` 先有，`t_rum_problem_status` 后加**

- `t_rum_problem_record` 表名带 record，语义是"问题记录留痕"，是一张更早期的通用表。
- `t_rum_problem_status` 只做状态，职责单一，是后来从 record 表职责中拆分出来的独立表（状态和评论/操作日志语义差异大，拆表是正常演进）。
- 两张表的 `problem_type` 字段名相同但值域不同，更像"各自设计时没对齐"，而非"一开始就计划两套"。
- 转换层 `problemTypeRecordMap` 的存在本身就是"两套已成型、不得不适配"的证据——如果是同时设计，正常做法是直接复用同一套枚举，没必要引入转换层。

**推测 2：record 表的编号避开前端体系的占用位**

前端体系里 `8=launch`、`9=view`（`problemTypeMap` 注释可证）已被非代码异常类型占用。如果 record 表也用前端体系，那 record 表里 `problem_type=8` 就有歧义：是"崩溃"还是"启动"？是"视图"还是"AppFreeze"？

为了消除歧义，record 表另起一套从 8 开始的连续编号专门给代码异常用。这也解释了为什么 record 体系的起点是 8 而不是 1 或 3——它不是"重新从 1 编号"，而是"在前端体系占用位之后另起一段"。

**推测 3：status 表对齐前端是为了查询简洁**

`t_rum_problem_status` 每次列表查询都要按 `problemType` 过滤（`selectProblemTypeList` 入参就是前端 problemType）。如果 status 表用 record 体系，每次查询都要先 `problemTypeRecordMap.get` 转一次，写起来啰嗦也容易漏转。直接用前端体系值，前端传什么就存什么、查什么，链路最短、最不容易出错。

而 record 表查询场景少（只有详情页看操作日志时才查），转换成本低，可以接受用另一套。

#### 2.4.3 不统一到一套的代价与可能原因

**当前代价**：
- 需要维护 `problemTypeRecordMap` 这张映射表，新增问题类型时要同步加两处。
- 排错时容易踩坑（例如曾因 `statusAction` 执行顺序判断错而得出"status 表存 8"的错误结论）。
- 两张表 JOIN 分析时需要先转义 `problem_type`，BI/运维查询不直观。

**没统一的可能原因**：
1. **历史包袱**：record 表已有大量历史数据用 8~13 编号，改 status 表对齐 record 体系需要数据迁移；改 record 表对齐前端体系也需要迁移。两边都不想动。
2. **风险规避**：`t_rum_problem_record` 可能还有其他模块（评论、操作日志）在写，改枚举影响面大，没人敢动。
3. **收益不高**：转换只是一个 Map 查找，性能无影响；踩坑主要靠文档和 review 规避，业务上没有强驱动力去统一。
4. **职责分离**：两张表分属不同业务语义（状态 vs 留痕），团队可能有意让它们保持独立编号空间，避免被误认为"同一张表的分身"。

#### 2.4.4 如何进一步确认

如果想确认"哪张表先有 / 演进时间线"，最可靠的证据是查 `script/one_framework_rum/INIT/` 下的建表 SQL 脚本按版本时间排序，看哪张表的 `CREATE TABLE` 先出现、哪张表是后续版本 ALTER 进来的。这能把"推测 1"从推测升级为事实。

#### 2.4.5 一句话总结

- **直接原因**：前端体系的编号位 8/9 被启动/视图等非代码异常类型占用，record 表为了无歧义地标识代码异常类型，另起了一套 8~13 的编号；status 表后加时为了查询链路简洁，直接对齐了前端体系。
- **深层原因**（推测）：两张表演进时间不同，record 表先有自成一套编号，status 表后加并对齐前端，没人回头统一，于是用 `problemTypeRecordMap` 做适配层长期共存。

### 3.2 后端写入接口

**入口**：`POST /rest/rum/common/problem/status` → `RumCommonController.statusAction`

```java
@PostMapping("/problem/status")
@AppWritePermissionCheck
@OperatePermissionCheck(value = {RUM_RESOURCE_READ_AND_WRITE, RUM_CODE_ISSUES_MANAGE_RESOURCE})
public RestResponse statusAction(@RequestBody RecordCondition condition) {
    String msg = recordService.statusAction(condition);
    ...
}
```

**权限**：
- `@AppWritePermissionCheck`：校验 `appId` 是否在可管理范围。
- `@OperatePermissionCheck`：`RUM_RESOURCE_READ_AND_WRITE` 或 `RUM_CODE_ISSUES_MANAGE_RESOURCE` 任一通过。
- 无权限 → 403，前端 Select 显示禁用态。

**核心逻辑**：`RecordService.statusAction` → `updateProblemStatus`（upsert 语义）

```java
private String updateProblemStatus(RecordCondition condition) {
    RecordEntity recordEntity = buildStatusRecordEntity(condition);
    recordEntity.setStatus(condition.getStatus());
    if (hasRecord(recordEntity)) {
        index = recordMapper.statusUpdateAction(recordEntity);  // 已存在 → update
    } else {
        index = recordMapper.statusInsertAction(recordEntity);  // 不存在 → insert
    }
    return index >= 0 ? SUCCESS_MSG : errorMsg;
}
```

**字段映射**：`RecordService.buildStatusRecordEntity`

```java
recordEntity.setRelationKey(condition.getProblemId());  // 前端 problemId → relationKey → DB question_id
recordEntity.setProblemType(condition.getProblemType()); // 前端 problemType（前端体系值，如 6）
```

**写入成功后**：同步写一条操作记录到 `t_rum_problem_record`（type=2，内容来自 `getRecordStatusContent(status)` 的中英文文案），用于详情页的操作日志展示。

### 3.3 写入流程图

```
前端 Select onChange
   │  { appId, problemId, type:3, status:v, problemType:6 }
   ▼
POST /rest/rum/common/problem/status
   │
   ▼
RumCommonController.statusAction
   │  权限校验：@AppWritePermissionCheck + @OperatePermissionCheck
   ▼
RecordService.statusAction
   │
   ├─① updateProblemStatus(condition)
   │     │  condition.problemType = 6（前端体系）

   │     └─ !hasRecord? → statusInsertAction (insert t_rum_problem_status, problem_type=6)
   │
   ├─② condition.setProblemType(problemTypeRecordMap.get(6) = 8)
```


### 4.3 后端列表查询逻辑

**入口**：`POST /rest/rum/problem/overview/listQuery` → `ProblemService.listQuery`

核心步骤（非 JS_ERROR 分支）：

```java
public RestResponse listQuery(RumBaseCondition condition, String envId) {
    Integer problemType = parseInteger(queryMap.get("problemType"));     // 前端体系值
    Integer repairedState = parseInteger(queryMap.get("repairedState"));

    // 1. 从 ClickHouse 查问题指标列表
    List<Map<String, Object>> resultList = decoratorMetricListData(...);

    // 2. 从 MySQL 查当前用户对该 problemType 的所有状态记录
    List<RecordEntity> recordList = recordService.selectProblemTypeList(
        startTime, endTime, appIds, userProvider.getAccountId(), problemType, null, null);

    // 3. 把状态回填到每条问题（没匹配的默认 1 未修复）
    for (Map<String, Object> info : resultList) {
        String infoCode = parseString(info.get("problemId"));
        if (!"JS_ERROR".equals(problemName)) {
            RecordEntity recordEntity = recordList.stream()
                .filter(r -> r.getRelationKey().equals(infoCode))
                .findFirst().orElse(null);
            if (recordEntity != null) {
                info.put("status", recordEntity.getStatus());
            }
        }
    }
    // 兜底：没 status 的设为 1
    resultList.forEach(v -> {
        if (!v.containsKey("status")) v.put("status", 1);
        else if (Convert.toInt(v.get("status"), 1) == 0) v.put("status", 1);
    });

    // 4. 按 repairedState 过滤（仅当 repairedState > 0）
    List<Map<String, Object>> filterList = resultList;
    if (repairedState > 0) {
        filterList = resultList.stream()
            .filter(v -> parseInteger(v.get("status")).equals(repairedState))
            .collect(Collectors.toList());
    }

    // 5. 统计各状态计数（基于未过滤的全量 resultList）
    long notRepairedNum  = resultList.stream().filter(v -> Convert.toInt(v.get("status"),1)==1).count();
    long repairedNum     = resultList.stream().filter(v -> Convert.toInt(v.get("status"),1)==2).count();
    long repairingNum    = resultList.stream().filter(v -> Convert.toInt(v.get("status"),1)==3).count();
    long reappearanceNum = resultList.stream().filter(v -> Convert.toInt(v.get("status"),1)==4).count();
    long ignoreNum       = resultList.stream().filter(v -> Convert.toInt(v.get("status"),1)==5).count();

    // 6. 分页 + 返回
    response.setResults(finalResultList);
    response.setTotalRecord(filterList.size());
    response.setNotRepairedNum(notRepairedNum);
    response.setRepairedNum(repairedNum);
    response.setRepairingNum(repairingNum);
    response.setReappearanceNum(reappearanceNum);
    response.setIgnoreNum(ignoreNum);
    return RestResponse.success(response);
}
```

> **注意**：状态计数基于**全量 `resultList`**（未过滤前），分页/排序用 `filterList`（过滤后）。所以切到某个状态 Tab 时，该 Tab 计数仍是全量计数，不会随筛选变化——这与 UI 上「全部 10 = 2+2+2+2+2」一致。

### 4.4 查询流程图

```
前端列表请求
   │  { problemType:6, repairedState:0/1~5, ... }
   ▼
POST /rest/rum/problem/overview/listQuery
   │
   ▼
ProblemService.listQuery
   │
   ├─① ClickHouse 查问题指标列表（按 problemType 聚合）
   │     → resultList: [{ problemId, problemCount, impactUserNum, ... }]
   │
   ├─② MySQL 查 t_rum_problem_status（按 problemType + userId）
   │     → recordList: [{ relationKey=question_id, status, ... }]
   │
   ├─③ 内存 join：resultList.problemId == recordList.relationKey → 回填 status
   │     未匹配的 status 默认为 1（未修复）
   │
   ├─④ repairedState > 0 时，按 status 过滤 resultList → filterList
   │
   ├─⑤ 基于全量 resultList 统计 5 个状态计数
   │
   └─⑥ filterList 分页 → 返回 { results, totalRecord, notRepairedNum, ... }
```

## 6. 关键 ID 字段关系

### 6.1 前端 `problemId` 与后端 `question_id`

**同一个字符串值，不同层不同名字**：

```
前端 problemId
   ↓  (request body)
RecordCondition.problemId
   ↓  (buildStatusRecordEntity)
RecordEntity.relationKey
   ↓  (MyBatis #{relationKey})
DB t_rum_problem_status.question_id
```

查询时反向：`RecordMapper.xml` 里 `relation_key as problemId` 把 DB 字段映射回前端字段名。

### 6.2 `problemId` 的来源

**非 JS_ERROR**：来自 ClickHouse 维度聚合的 `codeErrorId` 字段（见 `custom-header-cn.xml` 里 `key="problemId" metaKey="codeErrorId"`），是按崩溃特征聚合后给同一类问题分配的稳定 ID。

**JS_ERROR（problemType=3）**：按 `problemGroup` 不同，是 **Base64 编码**后的维度值：

```java
// ProblemService.java
if ("file".equals(problemGroup)) {
    String info = parseString(problemData.get("fileUrl"));
    problemData.put("problemId", DigestUtil.BASE64.base64Encode(info.getBytes()));
} else if ("page".equals(problemGroup)) {
    String info = parseString(problemData.get("page"));
    problemData.put("problemId", DigestUtil.BASE64.base64Encode(info.getBytes()));
}
```

所以 JS 错误的 problemId 在 file/page 分组下含义不同、值不同——**同一 JS 错误在 file 分组和 page 分组下的修复状态各自独立存储**，这是切 file/info/page 时状态会「重置」的根本原因。

### 6.3 三者组合关系

```
              前端请求                          后端 DB（t_rum_problem_status）
┌──────────────────────────┐        ┌─────────────────────────────────┐
│ problemId  = "#1985732725"│        │ question_id = "#1985732725"     │  ← 同一个值
│ problemType= 6            │  ───→  │ problem_type= 6                 │  ← 前端体系值，不转换
│ appId      = 371586057805740│       │ app_id      = 371586057805740   │
│ status     = 2            │        │ status      = 2                 │
└──────────────────────────┘        └─────────────────────────────────┘
```

**唯一业务键 = `app_id + problem_type + question_id + user_id`**，含义：

- **`problemId`（→ `question_id`）**：定位「哪一条代码问题」。JS 错误为 Base64 维度值，其他为原生 codeErrorId。
- **`problem_type`**：定位「哪一类代码异常」。`t_rum_problem_status` 用前端体系值（3/4/5/6/7/9）。
- **`app_id`**：定位「属于哪个应用」。
- **`user_id`**：状态按用户隔离，不同账号对同一问题的状态各自独立。

**推论**：
1. 同一个 problemId 在不同 problem_type 下是独立的（崩溃 #xxx 和自定义异常 #xxx 是两条状态记录）。
2. 同一个 problemId 在不同 app_id 下是独立的（应用 A 和应用 B 的 #xxx 互不影响）。
3. 切换页签 = 切换 `problem_type`，列表查询按当前 problemType 过滤，崩溃页设的状态不会污染 ANR 页。
4. JS 错误切 file/info/page 分组 = problemId 值变了（Base64 维度不同），状态各自独立。

## 8. 修复状态研发维护注意事项

1. **改 `t_rum_problem_status` 的 `problem_type` 取值口径时务必谨慎**：当前存的是前端体系值（3/4/5/6/7/9），与表字段注释一致。`selectProblemTypeList` 查询也用前端体系值。若要改成记录体系值（8/9/10/11/12/13），需同步改 `statusAction` 执行顺序、`selectProblemTypeList` 入参、前端传参，并做数据迁移。
2. **JS_ERROR 的状态展示是历史遗留**：行内下拉能改但列表不读回、不计数、不筛选。若要补齐，需改 `ProblemService.listQuery` 的 JS_ERROR 分支，风险较高，建议先评估影响。
3. **状态按 `user_id` 隔离**：不同账号对同一问题的修复状态各自独立。若要做「团队共享状态」，需重新设计表结构与查询。
4. **JS 错误的 problemId 是 Base64 维度值**：切 file/info/page 分组时 problemId 值会变，状态各自独立。排错时注意区分。
5. **权限双注解**：`@AppWritePermissionCheck`（appId 维度）+ `@OperatePermissionCheck`（功能权限）。新增类似接口时两个注解都要加，避免越权（历史上有越权 BUG，见 `RumCommonController` 注释）。
6. **操作日志表 `t_rum_problem_record` 的 `problem_type` 用记录体系值**：与状态表口径不同，查表时注意区分。
7. **状态计数基于全量、分页基于过滤后**：切状态 Tab 时计数不变是预期行为，勿当 BUG 处理。

## 10. 外部跳转读取的 URL 参数

### 10.1 顶层参数

`CrashRecord` 页面初始化时会执行：

- `const filter = props.urlParams?.filter`
- `const [typeFilters, setTypeFilters] = useAutoLinkFilter({ filter, sortedInfo: {} }, 'crash')`

说明这个页面外部跳转时，真正会读取的顶层 URL 参数主要是：

1. `filter`
2. `sortedInfo`

其中：

- `filter`：搜索框默认筛选值，最核心
- `sortedInfo`：表格排序信息

虽然 `useAutoLinkFilter` 这个通用 Hook 还支持：

- `requestType`
- `actionId`
- `retrievalTabKey`
- `pagination`

但 **当前崩溃记录页并没有实际消费这些参数**，所以对这个页面来说，外部跳转真正有意义的还是 `filter` 和 `sortedInfo`。

### 10.2 Hook 行为细节

`useAutoLinkFilter`（`view/rum/src/hooks/useAutoLinkFilter.ts`）的内部行为：

```ts
interface autoLinkFilterProps {
  filter: BrAny[]
  sortedInfo?: BrAny
  requestType?: BrAny
  actionId?: BrAny
  detail?: BrAny
  tab?: BrAny
  retrievalTabKey?: BrAny
  pagination?: BrAny
}

const useAutoLinkFilter = (props: autoLinkFilterProps, type: string) => {
  const { filter, sortedInfo, requestType, actionId, retrievalTabKey, pagination } = props
  const [typeFilters, setTypeFilters] = useUrlPersistState({...})
  useMount(() => {
    // filter 为空时回退到 sessionStorage，避免切换页面时丢失 filter
    setTypeFilters({ ...typeFilters, filter: filter?.length ? filter : typeFilters.filter || [] })
  })
  const linkFilter = useMemo(() => {
    const convertFilter = (filter?.length ? filter : typeFilters.filter)
      ?.map((its: BrAny) => {
        const item = cloneDeep(its)
        // 按页面类型选映射表：session 用 userModelKeyMap，其他用 modelKeyMap
        const key = (type == 'session' ? userModelKeyMap : modelKeyMap)[item.keyword] || item.keyword
        item.keyword = key
        // 命中 constant.ts 中 operator=='' 的字段时，强制改为 checkbox 原型
        const autolinkKey = groupBy(Const[type], 'keyword')?.[its.keyword]
        if (autolinkKey && autolinkKey?.[0]?.operator == '') {
          item.prototype = 'checkbox'
          delete item.operator
        }
        return item
      })
      ?.filter((i: BrAny) => i.value)
    // ...
    return omitBy(result, isNil)
  }, [JSON.stringify(filter)])
  return [linkFilter, setTypeFilters]
}
```

关键点：
- 通过 `useUrlPersistState` 把 filter/sortedInfo 等同步到 URL query 与 sessionStorage。
- `type` 参数决定使用哪张实体映射表：`'session'` 用 `userModelKeyMap`，其他（含 `'crash'`）用 `modelKeyMap`。
- 若 `filter` 数组为空，会回退读取 sessionStorage 中的 filter，避免来回切换页面时丢筛选。
- 命中 `constant.ts` 中 `operator == ''` 的字段会被强制改为 `checkbox` 原型（删除 `operator`）。

### 10.3 参数序列化方式

路由跳转最终通过 `getUrlParams()` 序列化：

- 普通字段直接追加到 query string
- 对象字段会做 `JSON.stringify`

所以外部跳转时通常是这种形式：

```text
...?filter=[...]&sortedInfo={...}
```

其中 `filter` 本质上是一个数组，数组里的每一项通常类似：

```json
{
  "keyword": "app.instanceId",
  "name": "应用名称",
  "value": ["123"],
```

# 三、关联关系

## 17. 两个页面的定位差异

| 维度 | 数字体验 > 代码异常 | 检索中心 > 崩溃记录 |
|------|--------------------|--------------------|
| 入口 | `view/rum/src/packages/experience/breakdown/Breakdown/index.tsx` | `view/rum/src/packages/retrieval/breakdown/CrashRecord/index.tsx` |
| 数据形态 | 按 problemId（崩溃特征）聚合后的「问题」列表 | 原始崩溃记录逐条展示 |
| 核心能力 | 修复状态管理（增/改/查/计数/筛选） | 多维度检索原始记录 |
| 列表接口 | `POST /rest/rum/problem/overview/listQuery` | 检索中心通用查询接口 |
| 状态写入接口 | `POST /rest/rum/common/problem/status` | 不涉及 |
| 是否读 `t_rum_problem_status` | 是 | 否 |
| 典型用法 | 看哪些崩溃问题还没修、修到什么阶段 | 按应用/版本/设备/时间等条件检索具体崩溃样本 |

> 简单理解：「代码异常」回答"有哪些问题、修了没"；「崩溃记录」回答"具体某条件下发生了哪些崩溃"。

---

## 18. 共同的字段纽带：codeErrorId / problemId

两个页面虽然定位不同，但通过 `codeErrorId` 这个字段天然耦合：

- **代码异常页**：`problemId`（前端字段）在非 JS_ERROR 场景下来自 ClickHouse 维度字段 `codeErrorId`（见 `framework/plugins/rum/rum-core/src/main/resources/custom-header-cn.xml` 中 `key="problemId" metaKey="codeErrorId"`）。修复状态以 `problemId`（即 `codeErrorId`）为唯一标识写入 `t_rum_problem_status`。
- **崩溃记录页**：后端 `FilterFieldsCreator.getCrashTable()` 注册了 `codeErrorId` 作为可搜索字段（含义：代码问题ID）。

也就是说：**`codeErrorId` 是连接"聚合问题"与"原始记录"的桥梁**。同一个 `codeErrorId` 在代码异常页对应一条修复状态记录，在崩溃记录页对应一批原始崩溃样本。

> 注意：崩溃记录页还有 `crashId`（代码问题ID 旧字段）和 `selfCrashId`（自定义问题ID）两个相关字段。`crashId` 是历史字段，当前页面表头更偏向 `codeErrorId`；`selfCrashId` 对应自定义异常（前端体系 problemType=7，SELF_CRASH）的问题 ID。从代码异常页跳转过来时，应根据页签类型选择对应字段：
> - 崩溃（problemType=6）→ `codeErrorId`
> - 自定义异常（problemType=7）→ `selfCrashId`

## 19. 典型跨页面联动场景

### 19.1 代码异常页 → 崩溃记录页（按问题下钻）

用户在「数字体验 > 代码异常 > 崩溃」页选中某条问题，希望查看其全部原始崩溃样本。典型跳转参数构造：

```text
?filter=[
  {"keyword":"app.instanceId","name":"应用名称","value":["<appId>"],"displayValue":["<应用名>"]},
  {"keyword":"codeErrorId","name":"代码问题ID","value":["<problemId>"],"displayValue":["<problemId>"]}
]
```

- `app.instanceId` 走 `modelKeyMap` 映射为 `appId`，命中应用相关列。
- `codeErrorId` 直接命中后端原生字段，把列表收敛到该问题的原始记录。

### 19.2 仪表盘 / 告警 → 崩溃记录页

仪表盘或告警卡片跳转到崩溃记录页时，推荐使用第 [15](#15-推荐的外部跳转携带方式) 节列出的"前端显式适配过"的 keyword（`app.instanceId`、`appVersion`、`clientOsName` 等），与 `useAutoLinkFilter(..., 'crash')` 完全对齐，保证筛选条件能稳定带入。

### 19.3 崩溃记录页 → 代码异常页（反向回到聚合视图）

崩溃记录页本身不直接写修复状态，但用户在记录页定位到某个 `codeErrorId` 后，可以回到代码异常页查看/修改该问题的修复状态。由于状态按 `app_id + problem_type + question_id + user_id` 唯一存储（见 [6.3](#63-三者组合关系)），只要保证 `problemType=6`（崩溃）和 `problemId=codeErrorId` 一致，状态就能匹配上。

## 20. 跨页面联动的研发维护注意事项

1. **`codeErrorId` 是跨页面联动的核心字段**：在代码异常页它叫 `problemId`，在崩溃记录页它叫 `codeErrorId`，值是同一个字符串。新增跨页面跳转时优先使用该字段作为精确锚点。
2. **自定义异常用 `selfCrashId`，不要错用 `codeErrorId`**：自定义异常（problemType=7）在状态表里用前端体系值 7 存储，问题 ID 字段对应崩溃记录页的 `selfCrashId`，而不是 `codeErrorId`。
3. **外部跳转字段优先走前端显式适配**：使用 `useAutoLinkFilter(..., 'crash')` 已映射的 keyword（如 `app.instanceId`）能确保与现有逻辑一致；如需更精确过滤再叠加后端原生字段（如 `codeErrorId`）。
4. **修复状态不会随崩溃记录页查询返回**：崩溃记录页接口不读 `t_rum_problem_status`。若需求要求在记录页也展示修复状态，需新增后端能力并评估与现有代码异常页状态口径的一致性。
5. **URL 参数按 `getUrlParams()` 序列化**：`filter` 为数组、`sortedInfo` 为对象，外部跳转构造方需按 `JSON.stringify` 序列化后追加到 query string，否则页面无法解析。
6. **JS_ERROR 的 problemId 是 Base64 维度值**：若从代码异常页 JS 错误页签跳转到对应的 JS 错误记录页，需注意 problemId 的语义随 `problemGroup`（file/info/page）变化，不能直接当作 `codeErrorId` 使用。
