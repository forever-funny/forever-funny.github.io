# RUM 页面与视图类型识别逻辑

## 1. 文档目标

本文梳理 RUM 模块中以下四类对象的识别逻辑及其在前后端之间的传递方式：

- H5 页面
- 单页面（SPA / Route）
- 原生视图
- 小程序视图

重点回答四个问题：

1. 这四类类型在 `upload` 协议里最初是通过哪些字段表达出来的。
2. 它们在后端落库、聚合、返回前端时分别使用什么字段和枚举。
3. 前端页面分析模块是如何把这些类型映射成页面展示和接口参数的。
4. 协议里的原始字段与业务代码中的 `pageType`、`pageAnalysisType`、`appType/platform` 分别是什么关系。

## 2. 结论先行

RUM 模块里并不存在一个"统一字段"从头到尾完整表达这四类对象，而是分成了四层语义：

1. **upload 原始协议层**：由 `Event.k` 和事件体 `Event.v` 中的类型字段表达最原始语义。这是"类型识别的第一现场"。
2. **采集/落库层**：后端把原始协议映射为内部模型，再落到不同 CK 结果表。这一层已经开始形成内部 `pageType`。
3. **查询/聚合层**：为了让页面分析、页面列表、指标查询能统一口径，后端把不同来源的数据继续归并成统一页面类型。统一类型范围是 `1~11`。
4. **前端页面分析层**：前端不会把 `2~9` 的原生视图再逐个展示，而是继续归并成 4 类：
   - `1 = H5 页面`
   - `2 = 原生视图`
   - `3 = 小程序视图`
   - `4 = 单页面`
   - 典型字段是前端自行计算出的 `pageAnalysisType`。

换句话说：

- **原生视图** 在采集和落库时保留 Activity、Fragment、Window、Controller、RN、Flutter、Ability、AbilitySlice 等细分值。
- **前端页面分析** 展示时不会继续细分，而是统一归并为"原生视图"。
- **单页面** 在后端统一枚举里是 `11`，但在前端页面分析接口里会再映射为 `4`。
- **小程序视图** 在采集侧通常对应 `mpview` 事件或 `10`，在前端页面分析接口里会映射为 `3`。

另外，从 `upload` 协议角度看，真正决定类型的第一层并不是 `appType`，而是：

1. `Event.k` 是什么事件类型
2. 事件体 `Event.v` 里是否还有专用类型字段
3. `AppInfo.at` 只是"应用平台类型"的辅助维度，不直接等于页面/视图类型

## 3. 关键概念与字段区分

### 3.1 `pageType` 不是一个单一概念

在 RUM 代码里，`pageType` 至少有三种不同语义，阅读代码时必须结合上下文区分：

1. **视图明细类型**：常见于接入、落库、明细过滤。枚举通常是：
   - `1=H5`
   - `2=Activity`
   - `3=Fragment`
   - `4=Window`
   - `5=Controller`
   - `6=RN`
   - `7=Flutter`
   - `8=Ability`
   - `9=AbilitySlice`
   - `10=MP`

2. **统一页面类型**：用于页面列表、页面分析等统一查询语义。比上面的体系多了 `11=单页面(Route)`。

3. **前端页面分析归并类型**：前端调用部分统计接口时，不再传 `1~11`，而是传归并后的 4 类：
   - `1=H5 页面`
   - `2=原生视图`
   - `3=小程序视图`
   - `4=单页面`

### 3.2 `appType` / `platform` 也不是页面类型

`appType` 或 `platform` 表达的是**应用平台类型**，不是 H5 / 单页 / Activity 这种页面或视图类型。

需要特别区分两套枚举：

1. **upload 原始协议中的 `AppInfo.at`**：
   - `0=iOS`
   - `1=Android`
   - `2=Windows`
   - `3=HarmonyOS`
   - `4=H5`
   - `5=微信小程序`
   - `6=抖音小程序`
   - `7=支付宝小程序`
   - `8=mPaaS 小程序`

2. **前端/后端业务代码里当前使用的 `appType/platform`**：是服务端清洗、兼容或业务归并后的值，其数值与 upload 原始协议里的 `ai.at` 不是严格同一套枚举。

在前端当前代码中的常见逻辑：

- `appType == 3` 认为是 `web`
- `appType in {5,7,8,9}` 认为是 `miniProgram`
- 其他则归为 `app`

因此：

- `ai.at` / `appType/platform` 解决的是"应用属于 web、app、小程序哪类平台"
- `pageType` 解决的是"当前被分析对象属于 H5、单页、原生视图、小程序视图中的哪一种"

这两层经常同时出现，但不能混用。

### 3.3 从 upload 协议看，四类对象是基于哪些字段判断出来的

如果只看 `upload` 协议，四类对象的第一层判断规则如下。

#### 3.3.1 H5 页面

主要依据：

1. `Event.k = "h5"`
2. 对应事件体为 `H5Event`
3. 关键字段：
   - `v.pvid`：页面 ID
   - `v.url`：页面 URL
   - `v.vt`：页面标题
   - `v.wpi`：页面性能信息

补充说明：`H5Event` 是 H5 页面专属协议，因此只要上报的是 `k=h5`，就已经能判定这是 H5 页面。在 `view` 事件里虽然也存在 `v.t=1` 表示 H5，但当前业务链路里，H5 页面分析的主识别来源仍然是 `h5` 事件链路。

#### 3.3.2 单页面（SPA / Route）

主要依据：

1. `Event.k = "routechange"`
2. 对应事件体为 `RouteChangeEvent`
3. 关键字段：
   - `v.tu`：目标路由
   - `v.fu`：来源路由
   - `v.d`：路由切换耗时
   - `v.pt`：当前路由的子路由地址
   - `v.rt`：root 路由全量地址
   - `v.pu`：主页面地址
   - `v.fw`：框架名称
   - `v.pvid`：路由页面 ID

补充说明：单页面不是靠某个通用 `pageType` 字段直接采集出来的，而是通过独立的 `routechange` 事件协议表达。后端再将这条链路统一归并成 `11 = ROUTE`。

#### 3.3.3 原生视图

主要依据：

1. `Event.k = "view"`
2. 对应事件体为 `ViewEvent`
3. 核心类型字段是 `v.t`
4. 当 `v.t` 取值为以下范围时，判定为原生视图：
   - `2=activity`
   - `3=fragment`
   - `4=window`
   - `5=controller`
   - `6=RN`
   - `7=Flutter`
   - `8=Ability`
   - `9=AbilitySlice`

补充说明：原生视图的主识别字段就是 `ViewEvent.t`。这一层保留细分类；到前端页面分析时，`2~9` 会被统一归并成"原生视图"。

#### 3.3.4 小程序视图

主要依据：

1. `Event.k = "mpview"`
2. 对应事件体为 `MPViewEvent`
3. 关键字段：
   - `v.pvid`：页面视图 ID
   - `v.n`：页面名称
   - `v.rt`：ready 阶段耗时
   - `v.lt`：用户可交互加载耗时
   - `v.std`：setData 明细

补充说明：小程序视图的第一层判断主要看事件类型就是 `mpview`。同时 `AppInfo.at` 可以辅助确认这是某类小程序应用，例如微信小程序、抖音小程序、支付宝小程序、mPaaS 小程序。后端统一归并时使用 `10 = MP 视图`。

### 3.4 upload 协议里还有哪些辅助字段会参与类型判断

除了四类对象对应的主事件链路外，协议里还有一些"辅助类型字段"会用于补充页面类型上下文。

#### 3.4.1 `JSErrorEvent.pt`

JS 错误事件中存在：

- `v.pt = 0`：未知
- `v.pt = 1`：H5 页面
- `v.pt = 2`：路由页面
- `v.pt = 3`：微信小程序页面

这说明：JS 错误链路不会自己重新识别页面类型，而是由探针在上报错误时，通过 `pt` 直接声明该错误发生在哪类页面上。

#### 3.4.2 `ActionEvent.vt`

操作事件中存在：

- `v.vn`：发生视图名称
- `v.vt`：该视图对应的类型

枚举为：`0=未知`、`1=h5`、`2=activity`、`3=fragment`、`4=window`、`5=controller`、`6=RN`、`7=Flutter`、`8=Ability`、`9=AbilitySlice`、`10=mpview`。

说明：操作事件本身不是页面类型主来源，但它会带上"该操作发生在哪类页面/视图上"的上下文。

#### 3.4.3 `LagEvent.vt`

卡顿事件中存在：

- `v.vn`：发生卡顿的视图名称
- `v.vt`：发生卡顿时的视图类型

枚举与原生视图类型基本一致：`0=未知`、`1=h5`、`2=activity`、`3=fragment`、`4=window`、`5=controller`、`6=RN`、`7=Flutter`、`8=Ability`、`9=AbilitySlice`。

说明：卡顿事件通过 `vt` 标记"这次卡顿挂在哪类视图上"，但页面分析的主类型识别仍不是由它单独决定。

### 3.5 基于 upload 协议的判断顺序建议

如果完全站在 upload 原始协议角度，推荐按下面顺序理解类型来源：

1. 先看 `Event.k`：
   - `h5` -> H5 页面
   - `routechange` -> 单页面
   - `mpview` -> 小程序视图
   - `view` -> 继续看 `v.t`
2. 若 `Event.k = "view"`，再看 `ViewEvent.t`：
   - `1` -> H5 兼容视图
   - `2~9` -> 原生视图
   - `10` -> MP 兼容值
3. 再看辅助上下文字段：
   - `ai.at`：应用平台类型
   - `JSErrorEvent.pt`：JS 错误所在页面类型
   - `ActionEvent.vt` / `LagEvent.vt`：操作/卡顿挂载的视图类型
4. 最后再进入后端统一归并与前端展示归并

这个顺序和现有代码链路是一致的：先按事件协议表达业务语义，再按服务端和前端做统一映射。

## 4. 后端识别来源

从 upload 协议进入服务端后，后端识别逻辑本质上是把协议里的事件类型和事件字段映射到内部模型、CK 结果表和统一页面类型。

### 4.1 原生视图的识别

原生视图的类型最直接，基本是 SDK 上报什么，后端就按什么落：

- `upload` 协议中 `Event.k = "view"`
- `ViewEvent` 事件体里有类型字段 `t`
- 后端将该字段转换到 `ViewEventModel.type`
- 再写入 `ViewResultZeus.pageType`

对应枚举定义中，`ViewTypeEnum` 说明如下：

- `1=H5`
- `2=Activity`
- `3=Fragment`
- `4=Window`
- `5=Controller`
- `6=RN`
- `7=Flutter`
- `8=Ability`
- `9=AbilitySlice`
- `10=MP`

因此，原生视图的识别本质上不是后端推断，而是 SDK 类型透传 + 后端校验 + 落库。

### 4.2 H5 页面的识别

H5 页面不是通过 `view.pageType=1` 这一条路单独推断出来的，而是通过 H5 事件链路进入专门的 H5 数据表或 H5 指标体系：

- `upload` 协议中 `Event.k = "h5"`
- `H5Event` 中的 `pvid/url/wpi` 作为页面标识和页面性能主体
- H5 事件进入 `h5` 转换流程
- 落 H5 相关结果表
- 查询时通过 H5 相关指标识别，例如 H5 PV

所以 H5 的识别更多是：`Event.k = h5` 决定主链路，指标命中决定统一查询口径，而不是统一依赖一个落库字段。

### 4.3 单页面（SPA / Route）的识别

单页面来自独立的 `routechange` 事件链路：

- `upload` 协议中 `Event.k = "routechange"`
- `RouteChangeEvent` 中 `tu/fu/pt/rt/pu/fw/pvid` 表达本次 SPA 路由切换
- 路由切换事件进入 `RouteChangeResultZeusConvert`
- 写入 Route 相关结果表
- 该表本身更关注：`switchNum`、`switchTime`、`framework`、`domain`

单页面在统一页面类型里被定义为 `11 = ROUTE`。

也就是说：采集层单页面是独立事件链路；统一页面类型层单页面被编码为 `11`。

### 4.4 小程序视图的识别

小程序视图来自独立的 `mpview` 事件链路：

- `upload` 协议中 `Event.k = "mpview"`
- `MPViewEvent` 中 `pvid/n/rt/lt/std` 表达小程序视图生命周期和耗时
- 小程序视图事件走 `mpview` 处理策略
- 在 CMDB / 页面归档语义中固定为 `VIEW_MP`
- 编码为 `10`

因此小程序视图也不是后端根据 URL 或平台猜出来的，而是：事件类型先天决定，后端使用固定枚举编码 `10` 归档。

### 4.5 后端统一页面类型枚举

后端统一页面类型可以概括为：

- `1 = H5`
- `2 = Activity 视图`
- `3 = Fragment 视图`
- `4 = Window 视图`
- `5 = Controller 视图`
- `6 = RN 视图`
- `7 = Flutter 视图`
- `8 = Ability 视图`
- `9 = AbilitySlice 视图`
- `10 = MP 视图`
- `11 = 单页 Route`

这里最重要的点是：`10` 表示小程序视图，`11` 表示单页面。

## 5. 后端聚合时如何统一识别页面类型

在页面列表等聚合场景里，后端并不会重新深度推断页面类型，而是基于已有指标做规则合并。

核心规则优先级为：

1. `switchNum` 命中，则认定为 `11`，即单页面
2. `sumPv` 命中，则认定为 `1`，即 H5 页面
3. `sumMpPv` 命中，则认定为 `10`，即小程序视图
4. 否则回退到 `view.pageType`

因此页面列表统一识别逻辑可以理解为：

- 单页优先于 H5
- H5 优先于小程序视图
- 小程序视图优先于原生视图明细

这说明后端"识别"更多是聚合归并，不是重新判断业务语义。

补充成一句更准确的话：

- upload 协议负责表达原始类型
- 后端负责接收、校验、落库、聚合归并
- 前端负责统一展示口径

## 6. 前端页面分析模块如何识别四类对象

前端页面分析模块有一套自己的历史枚举：

- `1 = H5`
- `2 = Activity`
- `3 = Fragment`
- `4 = Windows`
- `5 = Controller`
- `6 = Rn`
- `7 = Flutter`
- `8 = Ability`
- `9 = AbilitySlice`
- `10 = Mp`
- `11 = siglePage`

这里有两个注意点：

1. `11` 的内部名称写成了 `siglePage`，存在拼写错误，但实际语义就是单页面。
2. 前端保留了 `2~9` 的原生细分类，但很多统计场景并不会逐个区分展示。

### 6.1 前端的核心归并函数

前端通过一个核心映射把路由中的 `pageType` 归并成页面分析所需的 4 类：

- `pageType = 1` -> `pageAnalysisType = 1`，H5 页面
- `pageType = 10` -> `pageAnalysisType = 3`，小程序视图
- `pageType = 11` -> `pageAnalysisType = 4`，单页面
- `pageType = 2~9` -> `pageAnalysisType = 2`，原生视图
- 其他异常情况默认按 H5 兜底

因此，前端真正控制页面分析详情、趋势、维度、饼图逻辑的不是原始 `pageType`，而是归并后的 `pageAnalysisType`。

### 6.2 前端路由是如何传入 `pageType` 的

页面分析详情页 URL 结构中会带入一个 `pageType` 参数，这个参数来源于不同入口的映射：

- H5 tab 进入详情时传 `1`
- 单页面 tab 进入详情时传 `11`
- 原生视图 tab 进入详情时传具体视图类型 `2~9`
- 小程序视图 tab 进入详情时传 `10`

因此前端详情页实际看到的 `pageType` 已经是"统一页面类型层"的值，而不是任意自由字符串。

### 6.3 前端如何决定是 `page` 还是 `view`

前端还会根据 `pageType` 决定详情页走页面接口还是视图接口：

- `pageType = 1` 或 `11` 时，认为是 `page`
- 其他类型认为是 `view`

即：H5 页面、单页面走页面维度接口；原生视图、小程序视图走视图维度接口。

这一点会直接影响：基本信息接口选择、健康分查询参数、别名修改类型、指标卡/趋势/维度查询逻辑。

### 6.4 前端展示层如何区分四类对象

在页面分析详情里，前端会根据归并后的 `pageAnalysisType` 控制展示文案和组件：

- `1` 显示 H5 页面相关文案
- `2` 显示原生视图相关文案
- `3` 显示小程序视图相关文案和图标
- `4` 显示单页面相关文案和图标

典型展示差异包括：面包屑标题、顶部卡片标题和图标、某些饼图是否显示、某些接口是否触发、单页面额外查询框架类型。

## 7. 四类对象的完整链路梳理

### 7.1 H5 页面

完整链路：

1. SDK 在 upload 中上报 `Event.k = "h5"`
2. `H5Event` 通过 `pvid/url/wpi` 表达页面实体与页面性能
3. 后端进入 H5 转换链路
4. 查询/聚合时通过 H5 指标识别该页面
5. 前端详情路由使用 `pageType=1`
6. 前端进一步映射为 `pageAnalysisType=1`
7. 页面分析详情按 H5 页面渲染

识别关键点：

- 原始协议主字段是 `Event.k = h5`
- 页面实体关键字段是 `pvid`、`url`
- 后端主要依赖 H5 事件链路和 H5 指标
- 前端识别码是 `1`

### 7.2 单页面（SPA）

完整链路：

1. SDK 在 upload 中上报 `Event.k = "routechange"`
2. `RouteChangeEvent` 通过 `tu/fu/pt/rt/pu/fw/pvid` 表达路由切换
3. 后端写入 Route 结果表
4. 统一页面类型中使用 `11` 表示单页面
5. 页面列表聚合时，若命中 `switchNum` 优先判为单页面
6. 前端详情路由使用 `pageType=11`
7. 前端进一步映射为 `pageAnalysisType=4`
8. 页面分析详情按单页面渲染，并额外拉取框架类型

识别关键点：

- 原始协议主字段是 `Event.k = routechange`
- 单页面还会携带 `fw` 标明框架类型
- 后端聚合优先级最高
- 前端展示层不是继续使用 `11`，而是改用 `4`

### 7.3 原生视图

完整链路：

1. SDK 在 upload 中上报 `Event.k = "view"`
2. `ViewEvent.t` 上报原始视图类型
3. 当 `t=2~9` 时识别为原生视图细分
4. 后端将 `t` 直接写为 `view.pageType`
5. 前端详情路由保留具体值 `2~9`
6. 前端页面分析时统一归并为 `pageAnalysisType=2`
7. 页面分析详情统一按"原生视图"呈现

识别关键点：

- 原始协议主字段是 `Event.k = view` + `ViewEvent.t`
- 采集和落库保留细分类
- 展示和统计很多场景统一归并

### 7.4 小程序视图

完整链路：

1. SDK 在 upload 中上报 `Event.k = "mpview"`
2. `MPViewEvent` 通过 `pvid/n/rt/lt/std` 表达小程序页面生命周期与性能
3. `AppInfo.at` 可辅助说明所属小程序平台
4. 后端归入小程序视图链路
5. 统一页面类型使用 `10`
6. 页面列表聚合时，命中 MP 相关指标则识别为 `10`
7. 前端详情路由使用 `pageType=10`
8. 前端页面分析映射为 `pageAnalysisType=3`
9. 页面分析详情按小程序视图渲染

识别关键点：

- 原始协议主字段是 `Event.k = mpview`
- 应用平台辅助字段是 `AppInfo.at`
- 后端编码是 `10`
- 前端页面分析归并编码是 `3`

## 8. 代码中的主要映射关系

### 8.1 upload 协议中的原始判断字段

- `Event.k = h5` -> H5 页面
- `Event.k = routechange` -> 单页面
- `Event.k = mpview` -> 小程序视图
- `Event.k = view` 且 `ViewEvent.t = 2~9` -> 原生视图

补充辅助字段：`ViewEvent.t`、`JSErrorEvent.pt`、`ActionEvent.vt`、`LagEvent.vt`、`AppInfo.at`。

### 8.2 后端统一页面类型

- `1 = H5`
- `2~9 = 原生视图细分`
- `10 = 小程序视图`
- `11 = 单页面`

### 8.3 前端页面分析归并类型

- `1 -> H5 页面`
- `2~9 -> 原生视图`
- `10 -> 小程序视图`
- `11 -> 单页面`

再归并为：

- `1 -> H5 页面`
- `2 -> 原生视图`
- `3 -> 小程序视图`
- `4 -> 单页面`

### 8.4 应用平台类型

需要区分两层：

1. upload 原始协议 `AppInfo.at`：
   - `0 = iOS`
   - `1 = Android`
   - `2 = Windows`
   - `3 = HarmonyOS`
   - `4 = H5`
   - `5 = 微信小程序`
   - `6 = 抖音小程序`
   - `7 = 支付宝小程序`
   - `8 = mPaaS 小程序`

2. 当前前端业务代码常见识别：
   - `appType == 3` -> `web`
   - `appType in {5,7,8,9}` -> `miniProgram`
   - 其他 -> `app`

所以在查问题时必须先确认：看到的到底是 upload 原始 `at`，还是业务侧已经兼容转换过的 `appType/platform`。

## 9. 容易混淆的点

### 9.1 `10` 和 `11` 容易搞反

- `10` 是小程序视图
- `11` 是单页面

这两个值在很多排查场景里最容易写反。

### 9.2 单页面在不同层用了不同编码

单页面至少有四种表达方式：

- upload 原始事件类型：`Event.k = routechange`
- 后端统一页面类型：`11`
- 前端历史名称：`siglePage`
- 前端页面分析接口归并类型：`4`

所以如果只搜"singlePage"或只搜 `11`，很容易漏掉一部分链路。

### 9.3 H5 也不是只有一种表达方式

H5 至少有三种表达方式：

- upload 原始事件类型：`Event.k = h5`
- `ViewEvent.t = 1` 的兼容表达
- 后端统一页面类型：`1`

实际业务里，页面分析主链路更多依赖 `h5` 事件和 H5 指标，而不是只依赖 `view.t = 1`。

### 9.4 原生视图在采集层和展示层口径不同

采集层原生视图会区分：Activity、Fragment、Window、Controller、RN、Flutter、Ability、AbilitySlice。但展示层很多地方只显示"原生视图"，不再展示这些细分。

### 9.5 `appType/platform` 和 `pageType` 不能混用

常见误区是把以下两个问题混在一起：

- 这个应用是 Web、App 还是小程序？
- 这个被分析对象是 H5 页面、单页面、原生视图还是小程序视图？

前者看 `ai.at` 或业务态 `appType/platform`，后者看 `Event.k`、事件体类型字段和最终的 `pageType` 归并逻辑。

### 9.6 upload 原始协议枚举和前端业务枚举不是同一套值

例如：

- upload 协议里 `AppInfo.at = 4` 表示 H5
- 但当前前端业务代码里 `appType == 3` 才会判为 `web`

这说明中间一定存在服务端或业务兼容层的映射，排查时不能直接把两边数值一一等同。

## 10. 最终结论

RUM 模块对 H5 页面、单页面、原生视图、小程序视图的识别并不是单点完成，而是一个"原始协议类型 -> 落库类型 -> 聚合类型 -> 前端归并类型"的分层过程：

1. **upload 原始协议层**：
   - H5 页面主要由 `Event.k = h5` 表达
   - 单页面主要由 `Event.k = routechange` 表达
   - 原生视图主要由 `Event.k = view` + `ViewEvent.t = 2~9` 表达
   - 小程序视图主要由 `Event.k = mpview` 表达

2. **后端统一类型层**：用 `1~11` 的统一编码承接查询和聚合，其中 `10=小程序视图`，`11=单页面`。

3. **前端页面分析层**：再归并成 4 类（H5 页面、原生视图、小程序视图、单页面）。

4. **真正的识别逻辑本质**：大部分情况下是"事件链路透传 + 规则归并"，而不是后端基于内容做复杂推断。

如果后续要排查页面分析类型错误，建议按下面顺序检查：

1. upload 中 `Event.k` 是什么
2. 对应事件体里是否存在类型字段，如 `ViewEvent.t`、`JSErrorEvent.pt`、`ActionEvent.vt`
3. `ai.at` 表示的应用平台是什么
4. 后端落库或聚合得到的 `pageType` 是多少
5. 前端路由传入的 `pageType` 是多少
6. 前端 `getPieChartPageType` 最终归并成了哪一类
